Kick off fleet work in this project. Run the preflight first, and start work only if it comes back green. This command is what `/coder-fleet:init` points at after its restart, so assume nothing - the point of the preflight is to catch a half-finished setup.

## Preflight

Check each of these, collecting results rather than stopping at the first failure:

1. **Plugin.** The coder-fleet agents are available (`scout`, `spec-writer`, `spec-editor`, `coder`, `reviewer`, `ui-designer`, `tech-writer`, `tech-editor`, `researcher`, `fleet-steward` and `lead` appear as `coder-fleet:` agent types). An editor the project's `.claude/settings.json` denies with an `Agent(coder-fleet:<name>)` rule, as check 8 describes, is left out of the session's agent types, so its absence passes. If any other is missing, the plugin is not installed or the marketplace cache is stale.
2. **Lead.** `.claude/settings.json` exists and sets `agent` to `coder-fleet:lead`. Note, without failing, if the current session is visibly not running as the lead - that means the settings changed since the session started and a restart is needed. Then check that `TaskUpdate` is among this session's own tools. Without it no `[board:<id>]` task can be completed and no item ever reaches Done, and on current models Claude Code offers it only when `CLAUDE_CODE_ENABLE_TODO_TOOLS` is set. `TaskUpdate` missing fails this step: name that cause, offer to add `env.CLAUDE_CODE_ENABLE_TODO_TOOLS` (`"1"`) to the project's `.claude/settings.json` and add it only on the human's yes, and say a new session is needed, because env is read at startup. With `TaskUpdate` present, a project file that lacks the key is a note, not a failure: something else, such as the human's own user settings, is covering it, and `/init` adds the key to the project.
3. **Skeleton.** `AGENTS.md` exists at the project root and contains no `<FILL: ...>` markers. A marker left in place is a line the session reads literally on every turn, so surviving markers are a failure, not a note. Then check for a shadow: a `CLAUDE.md`, `.claude/CLAUDE.md` or `CLAUDE.local.md` in the project root or any directory above it, up to `/` - Glob each of the three names in each directory, or run `d=$PWD; while :; do for f in CLAUDE.md .claude/CLAUDE.md CLAUDE.local.md; do [ -e "$d/$f" ] && [ "$d/$f" != "$HOME/.claude/CLAUDE.md" ] && echo "$d/$f"; done; [ "$d" = / ] && break; d=$(dirname "$d"); done` from the root, which prints every shadow and nothing else. `~/.claude/CLAUDE.md` does not count, even though the walk passes the home directory: it is the user's global file and loads alongside `AGENTS.md`. A `CLAUDE.md` directly in the home directory does count. If a shadow exists, the check fails and names the path, with the fix: rename that file to `AGENTS.md` (at the project root, where an `AGENTS.md` already exists, merge its content into that file and delete it), or set the project-instructions setting to `claude-md-and-agents-md` so Claude Code reads both (the `instructionFiles` option of the built-in `agents-md` plugin, reachable through `/config`); until then Claude Code reads the shadow and ignores `AGENTS.md` without a message.
4. **Glossary rule.** `.claude/rules/glossary.md` exists.
5. **Fleet files.** Specs and run articles live in the board's directory, not in the project, so the project needs no directory for them. Check that the fleet's files that do live in the project - agent memory, the installed rules and `.claude/coder-fleet.json` - are out of its history: run `"${CLAUDE_PLUGIN_ROOT}/boards/boards.sh" fleet exclude status` from the project root. `state: excluded` passes. `state: not-excluded` or `state: needs-migration` is a note naming its `missing`, `tracked` and `gitignore` lines, and the fix is `/coder-fleet:init`, which writes the exclude and offers the migration. A refusal that this is not a repository is said, and the check skipped.
6. **Board.** The full check is its own step below; here just note whether the board answers at all - `${CLAUDE_PLUGIN_ROOT}/boards/boards.sh where` from the project root. No board means no board work, which is fine and is not a failure.
7. **Worktree base.** Read `worktree.baseRef` from `.claude/settings.local.json`, then `.claude/settings.json`, then `~/.claude/settings.json`; the first that sets it wins. `"head"` passes, and so does a user-scope `"head"` (set through `/config`), which covers every project on the machine. Absent or `"fresh"` is a note, not a failure: agent worktrees are cut from origin's default branch, whatever the fleet's base branch is, so a local base branch that is ahead of the remote leaves every coder behind it. Offer to set `"head"`, which cuts them from the local HEAD, and say that from a feature branch the worktrees stack on that branch. Ask with AskUserQuestion; on the human's yes, and only then, merge `{"worktree": {"baseRef": "head"}}` without touching another key, into `.claude/settings.local.json` when that is the file that set `"fresh"` (a local value would otherwise override the change) and into the project's `.claude/settings.json` otherwise, and say a restart is needed. On a no, say the setting is left on the default and do not ask again this run. Then check that `AGENTS.md` has a `Worktree setup` section with no `<FILL: ...>` marker left in it; a missing section is a note, and the fix is to add it from `${CLAUDE_PLUGIN_ROOT}/templates/AGENTS.md`. Last, say in one line where the three optional settings live, never as a failure: The base branch, push policy and release setting are `baseBranch`, `push` and `release` in `.claude/coder-fleet.json` in the main checkout, which the fleet keeps out of the project's history; `/coder-fleet:agents base`, `push` and `release` show each and set it. None of them goes in `AGENTS.md`, so a project whose `AGENTS.md` is not the human's to edit needs nothing in it for these.
8. **Earlier editor answers.** Both editors run in every project, like every other fleet agent, and `/coder-fleet:agents disable spec-editor` or `tech-editor` is the one switch for either. What an earlier `/init` wrote for them is a leftover: `Spec editor:` and `Tech editor:` lines in `AGENTS.md`, and editor deny rules in `.claude/settings.json` or `.claude/settings.local.json`. Run `"${CLAUDE_PLUGIN_ROOT}/boards/boards.sh" fleet editor-leftovers status` from the project root. `state: none` passes, with nothing said. Otherwise report each `found` line it printed, which is a note, never a failure, and offer once, with AskUserQuestion, to remove them. Question: "Remove these leftover editor settings? Both editors run in every project now; the lines are no longer read, and a deny rule keeps its editor from running." Options: **Remove them (Recommended)**, "Delete exactly these lines and rules, and nothing else"; **Keep them**, "Change nothing". On remove, run the same command with `remove` and report its `removed` lines; it touches nothing else in either file. On keep, change nothing and say that an editor deny rule keeps that editor from running, and that for `spec-editor` the challenge gate cannot see the rule and refuses every spec it never ran on, so `/coder-fleet:agents disable spec-editor` is what lets specs through without it. A `refused` line, exit 1, means a settings file is not valid JSON or is a link out of the project: pass it on, say nothing was removed, and count the check as failed until the human fixes the file. Exit 3 means a write failed: pass on the message, which names what was already written, and count the check as failed.
9. **Use mode.** Read `AGENTS.md` for an `App start:` line with no `<...>` placeholder. On a project with a client UI - a web front end, a desktop or mobile app, any screen a user drives, as the manifest, the build configuration and the directory layout show - no such line is a note, not a failure: say the reviewer's use mode will not run, so no acceptance criterion on that UI is checked in the running product and a UI change rests on a screenshot the lead compares by hand, and recommend adding the `App start:` and `App url:` lines from `${CLAUDE_PLUGIN_ROOT}/templates/AGENTS.md`. A project with no client UI and no such line passes. When `AGENTS.md` does not exist, check 3 has already failed, so say nothing here.

If anything failed: report every failure with its one-line fix (`/coder-fleet:init` for missing skeleton pieces, restart-and-trust for a plugin or agent problem, edit the marker for a surviving `<FILL: ...>`, rename the shadowing file to `AGENTS.md` for a shadow), and stop. Do not start work on a red preflight.

## Board

Run this step only when `${CLAUDE_PLUGIN_ROOT}/boards/boards.sh where` exits 0. Exit 127 means the `boards` binary will not run on this machine, and any other failure means this repo has no board; both are legitimate outcomes: say which and move on. Read the `help-boards` skill first; it is the contract this step is verifying. No board is a legitimate outcome throughout - most work is not board work, and the human declining any part of this is a note in the report, never a failure.

**Check.** `boards.sh where` prints the board's key, its prefix and its directory, `~/.config/boards/<PREFIX>/` (`$XDG_CONFIG_HOME/boards/<PREFIX>/` when that is set). A repo with no board is told so: say that the human makes one in their own terminal with `${CLAUDE_PLUGIN_ROOT}/boards/boards.sh init`, which asks for the board's id prefix, and stop the step; never make one yourself. With a board:

- The board's MCP tools answer: `card_list` with no filter returns without an error. If the tools are missing, say why as `work` does.
- The board's `config.yml` sets `test:`, the command the test gate runs on a release. Without it no release ever moves a card to Released: name the gap, say the human sets it by hand in that file, and count it a note, not a failure.
- Nothing of the board's belongs in the repository. A `.boards/`, `docs/specs/` or `docs/runs/` the old board left there is the human's to delete or keep; say so once when one exists, and never delete it yourself.

**State the conventions.** End the board section by saying, concretely, what the fleet will use - so the session and the human agree before the first card is filed:

- that the board lives outside the repository, in the directory `boards.sh where` printed, one markdown file per card under its `cards/`, with the specs in its `specs/` and the run articles in its `runs/`, on this machine only,
- the prefix, so a card is `BD-12` and a sub-issue `BD-12.1`,
- the eight columns, in order: Draft, Backlog, Next, In Progress, Done, Released, Blocked, Blocked by Human. Only the human fills and orders Next, in the web UI, and `card_next` hands out its top card, then Backlog's,
- that hooks and gates move every column but Draft to Backlog: a card goes to Done only with every acceptance criterion and Definition of Done item ticked, and to Released when a release's annotated tag names it on a `Cards: BD-12, BD-13` line and the board's test command passes on that commit,
- that a card is parked by adding an Action for Human, which moves it to Blocked by Human until the human ticks it,
- and the binding: call `card_focus` with `BD-12` (or the human runs `/work BD-12`) before spawning against a card, or put a `Board-Item: BD-12` line in the spawn prompt, and a task closes a card only when its subject carries the `[board:BD-12]` marker.

**What this step cannot do, said out loud.** It can see the shim answer, but not which binary answered. `boards.sh` runs a build beside it, then the release build for this plugin version that the session-start fetch put in place, then Bun on the plugin's own source. End with the one manual check: `grep -F 'boards-binary' ~/.local/state/coder-fleet/log/hooks.log | tail -3`, which says when the release build was installed or why it was not.

## The idea

The text after the command is the idea. If there is none, ask the human one open question - what are we building, in a sentence or a brain dump, messy is fine - and wait. Do not invent a task, and do not substitute a repo TODO for an answer.

## Start

With a green preflight and an idea in hand, read `AGENTS.md` for a line starting `Requirements source: <path>`, the same line the lead's step 2 and the `spec-to-card` workflow read, then start the fleet's intake as the lead's routing says.

Without that line, nothing changes: an unshaped idea goes to `spec-writer`, which writes in the board's `specs/` and builds the interview brief you run with the human before the spec closes the problem down - the `spec-to-card` flow. Read your memory and send `scout` ahead if the idea touches existing code, then spawn `spec-writer` with the idea verbatim, not paraphrased, asking it to build the interview brief and not to write the spec yet, and interview the human from the questions it returns. From there the normal pipeline holds: the human edits and approves the spec, its acceptance criteria go on the card, and a `coder` runs only once the human orders the item.

With the line, spec-writer never runs and no spec is written. Recall as above, send `scout` to read the path for the requirement clauses the idea answers, and file the card with the idea verbatim in its description and those clauses as its criteria, in clause order, as the `lead-procedures` skill says under Handoffs and proposals - for a directory of requirement files, its files sorted by path, then each clause's place in its file; for an item already on the board, `spec-to-card` on its card files the clauses instead. Each decision the clauses leave open is an Actions for Human question on the card, answered before the first build spawn, and a `coder` still runs only once the human orders the item. If the path does not exist, or the line names no path, stop and ask the human to fix the line or delete it, and never fall back to a spec.

Report the preflight result either way - one line per check when green, the failure list when not.
