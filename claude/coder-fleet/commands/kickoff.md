Kick off fleet work in this project. Run the preflight first, and start work only if it comes back green. This command is what `/coder-fleet:init` points at after its restart, so assume nothing - the point of the preflight is to catch a half-finished setup.

## Preflight

Check each of these, collecting results rather than stopping at the first failure:

1. **Plugin.** The coder-fleet agents are available (`scout`, `spec-writer`, `spec-editor`, `spec-editor-fable`, `coder`, `reviewer`, `refuter`, `ui-designer`, `tech-writer`, `tech-editor`, `tech-editor-fable`, `researcher`, `fleet-steward` and `lead` appear as `coder-fleet:` agent types). An editor definition the project's `.claude/settings.json` denies with an `Agent(coder-fleet:<name>)` rule, as check 8 describes, is left out of the session's agent types, so its absence passes. If any other is missing, the plugin is not installed or the marketplace cache is stale.
2. **Lead.** `.claude/settings.json` exists and sets `agent` to `coder-fleet:lead`. Note, without failing, if the current session is visibly not running as the lead - that means the settings changed since the session started and a restart is needed. Then check that `TaskUpdate` is among this session's own tools. Without it no `[issue:#N]` task can be completed and no issue is ever held to its card gate, and on current models Claude Code offers it only when `CLAUDE_CODE_ENABLE_TODO_TOOLS` is set. `TaskUpdate` missing fails this step: name that cause, offer to add `env.CLAUDE_CODE_ENABLE_TODO_TOOLS` (`"1"`) to the project's `.claude/settings.json` and add it only on the human's yes, and say a new session is needed, because env is read at startup. With `TaskUpdate` present, a project file that lacks the key is a note, not a failure: something else, such as the human's own user settings, is covering it, and `/init` adds the key to the project.
3. **Skeleton.** `AGENTS.md` exists at the project root and contains no `<FILL: ...>` markers. A marker left in place is a line the session reads literally on every turn, so surviving markers are a failure, not a note. Then check for a shadow: a `CLAUDE.md`, `.claude/CLAUDE.md` or `CLAUDE.local.md` in the project root or any directory above it, up to `/` - Glob each of the three names in each directory, or run `d=$PWD; while :; do for f in CLAUDE.md .claude/CLAUDE.md CLAUDE.local.md; do [ -e "$d/$f" ] && [ "$d/$f" != "$HOME/.claude/CLAUDE.md" ] && echo "$d/$f"; done; [ "$d" = / ] && break; d=$(dirname "$d"); done` from the root, which prints every shadow and nothing else. `~/.claude/CLAUDE.md` does not count, even though the walk passes the home directory: it is the user's global file and loads alongside `AGENTS.md`. A `CLAUDE.md` directly in the home directory does count. If a shadow exists, the check fails and names the path, with the fix: rename that file to `AGENTS.md` (at the project root, where an `AGENTS.md` already exists, merge its content into that file and delete it), or set the project-instructions setting to `claude-md-and-agents-md` so Claude Code reads both (the `instructionFiles` option of the built-in `agents-md` plugin, reachable through `/config`); until then Claude Code reads the shadow and ignores `AGENTS.md` without a message.
4. **Glossary rule.** `.claude/rules/glossary.md` exists.
5. **Work directory.** `docs/specs/` exists. Then check that run articles are ignored: `git check-ignore -v docs/runs/x.md` from the project root. Exit 0 passes, except that a source of `.git/info/exclude` or the global excludes file means the only rule is machine-local and does not travel with the repo, which is a note. Exit 1 is a note too, as is exit 128 (not a repository, so say so and skip the check): a plain `git add -A` in the main checkout would commit every run article, and the fix is `/coder-fleet:init`, which adds `docs/runs/` to `.gitignore`, or adding the line by hand.
6. **GitHub.** The full check-and-setup is its own step below; here just note whether `gh auth status` succeeds and `gh repo view --json nameWithOwner -q .nameWithOwner` names a repository. Without either there is no board, which is a note naming the fix (`gh auth login`, or a GitHub remote), not a failure.
7. **Worktree base.** Read `worktree.baseRef` from `.claude/settings.local.json`, then `.claude/settings.json`, then `~/.claude/settings.json`; the first that sets it wins. `"head"` passes, and so does a user-scope `"head"` (set through `/config`), which covers every project on the machine. Absent or `"fresh"` is a note, not a failure: agent worktrees are cut from `origin/<default-branch>`, so a local main that is ahead of the remote leaves every coder behind it. Offer to set `"head"`, which cuts them from the local HEAD, and say that from a feature branch the worktrees stack on that branch. Ask with AskUserQuestion; on the human's yes, and only then, merge `{"worktree": {"baseRef": "head"}}` without touching another key, into `.claude/settings.local.json` when that is the file that set `"fresh"` (a local value would otherwise override the change) and into the project's `.claude/settings.json` otherwise, and say a restart is needed. On a no, say the setting is left on the default and do not ask again this run. Then check that `AGENTS.md` has a `Worktree setup` section with no `<FILL: ...>` marker left in it; a missing section is a note, and the fix is to add it from `${CLAUDE_PLUGIN_ROOT}/templates/AGENTS.md`.
8. **Editors.** Run `python3 -I "${CLAUDE_PLUGIN_ROOT}/scripts/editor-models.py" status` from the project root. An editor whose answer is `opus`, `fable` or `neither` passes, and nothing is asked about it. An `unreadable (<value>)` answer fails, with the fix: edit that `AGENTS.md` line to `opus`, `fable` or `neither`, and the deny rules with it. For each editor whose answer is `none` - no line, or a `<...>` placeholder - ask and record exactly as step 2c of `${CLAUDE_PLUGIN_ROOT}/commands/init.md` says: the same AskUserQuestion question and options, and `editor-models.py set`, which writes the `AGENTS.md` line and the deny rules in `.claude/settings.json` without touching any other key. A spawn of a denied definition by its `coder-fleet:` name fails with "has been denied by permission rule"; one by the bare name reads "not found" whether or not a rule exists, which is expected and not a sign the rule failed. Its exit codes are init's: on 1 or 3, pass the message on, record nothing by hand, and count the check as failed. When `AGENTS.md` does not exist, check 3 has already failed, so ask nothing here. When this check records an answer, end the run once the preflight report is given, with no board step, no idea taken and no work started: say the answer is recorded and a new session is needed before `/coder-fleet:kickoff` carries on, because this session's lead holds `AGENTS.md` as it was when the session started while the challenge gate reads it from disk, so the two would disagree about whether the project has a spec editor.

If anything failed: report every failure with its one-line fix (`/coder-fleet:init` for missing skeleton pieces, restart-and-trust for a plugin or agent problem, edit the marker for a surviving `<FILL: ...>`, rename the shadowing file to `AGENTS.md` for a shadow), and stop. Do not start work on a red preflight.

## Board

Run this step only when check 6 found `gh` signed in and a GitHub remote. Otherwise say why and move on: no board is a legitimate outcome throughout - most work is not board work, and the human declining any part of this is a note in the report, never a failure. Read the `help-boards` skill first; it is the contract this step is verifying.

**Check.** The board is this repository's GitHub issues, so everything here is a `gh` read:

- The labels exist: `gh label list --limit 200 --json name -q '.[].name'` lists `status:next`, `status:in-progress`, `status:blocked` and `status:blocked-by-human`, `priority:high`, and `outcome/shipped`, `outcome/abandoned` and `outcome/superseded`. A missing one is a note, not a failure: the first hook that needs a status label creates it.
- `AGENTS.md` has a `## Definition of Done` section. A missing one is a note: issues get filed with no Definition of Done, and the fix is `/coder-fleet:init` or the section from `${CLAUDE_PLUGIN_ROOT}/templates/AGENTS.md`.
- No open issue carries two status labels: `gh issue list --state open --limit 500 --json number,labels`. Each one that does is a note naming it, since the hooks read the one nearer the human and a person left the other.

**Setup.** Say what is missing and ask the human before changing anything. On a yes, create the missing labels exactly as step 2b of `${CLAUDE_PLUGIN_ROOT}/commands/init.md` does. Never add or remove a status label on an issue here; the doubled ones are the human's to settle.

**State the conventions.** End the board section by saying, concretely, what the fleet will use - so the session and the human agree before the first issue is filed:

- that the board is this repository's GitHub issues, `<owner>/<repo>` as `gh repo view` named it, an issue written `#12` and a sub-issue a GitHub sub-issue of its parent,
- the columns: To do is an open issue with no status label, then `status:next`, `status:in-progress`, `status:blocked` and `status:blocked-by-human`, and Done is closed by a merged pull request whose body says `Closes #12`,
- that only the human labels an issue `status:next`, the hooks write the other status labels, and no agent closes an issue,
- labels: `priority:high` for an issue the human asked for twice, and `outcome/shipped`, `outcome/abandoned` or `outcome/superseded` once the answer is known,
- a branch named `12-short-title` and every commit subject ending `(#12)`,
- and the binding: run `"${CLAUDE_PLUGIN_ROOT}/scripts/focus.sh" 12` (or the human runs `/work 12`) before spawning against an issue, and only a task subject carrying `[issue:#12]` is held to its card gate.

**What this step cannot do, said out loud.** `gh auth status` says the token is signed in, not that it can write this repository's issues and labels: a fine-grained token needs Issues read and write here. A `gh ... failed (exit N)` or `gh is not installed` line in `~/.local/state/coder-fleet/log/hooks.log` after the first real spawn is the symptom of a board the hooks cannot reach.

## The idea

The text after the command is the idea. If there is none, ask the human one open question - what are we building, in a sentence or a brain dump, messy is fine - and wait. Do not invent a task, and do not substitute a repo TODO for an answer.

## Start

With a green preflight and an idea in hand, read `AGENTS.md` for a line starting `Requirements source: <path>`, the same line the lead's step 2 and the `spec-to-card` workflow read, then start the fleet's intake as the lead's routing says.

Without that line, nothing changes: an unshaped idea goes to `spec-writer`, whose interview opens the problem out before the spec closes it down - the `spec-to-card` flow. Read your memory and send `scout` ahead if the idea touches existing code, then spawn `spec-writer` with the idea verbatim, not paraphrased. From there the normal pipeline holds: the human edits and approves the spec, its acceptance criteria go on the card, and a `coder` runs only once the human orders the item.

With the line, spec-writer never runs and no spec is written. Recall as above, send `scout` to read the path for the requirement clauses the idea answers, and file the card with the idea verbatim in its description and those clauses as its criteria, in clause order, as the lead's step 5 says - for a directory of requirement files, its files sorted by path, then each clause's place in its file; for an item already on the board, `spec-to-card` on its card files the clauses instead. Each decision the clauses leave open is an Actions for Human question on the card, answered before the first build spawn, and a `coder` still runs only once the human orders the item. If the path does not exist, or the line names no path, stop and ask the human to fix the line or delete it, and never fall back to a spec.

Report the preflight result either way - one line per check when green, the failure list when not.
