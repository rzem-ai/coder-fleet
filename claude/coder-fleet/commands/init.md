Initialise this project for the fleet. Work through the five steps in order, report at the end, and never overwrite anything the project already has.

Templates live in this plugin at `${CLAUDE_PLUGIN_ROOT}/templates/`. Read each one from there; never reconstruct its content from memory.

## 0. Repository

Run `git rev-parse --is-inside-work-tree` at the project root before anything else.

If it prints `true`, compare `git rev-parse --show-toplevel` with the current directory. When they match, say nothing and continue. When they differ, this directory sits inside a repository rooted elsewhere; the fleet initialises a repository root, not a subdirectory. Say where the root is and ask, with AskUserQuestion, whether to run the remaining steps at that root or stop.

If it is not a repository, the fleet cannot work here: coder worktrees, review-round diffs, run articles and the `[board:...]` task markers all assume git. Ask, with AskUserQuestion, whether to initialise one - `git init -b main` - or stop. On yes, run exactly that and continue; the first commit stays the human's, made after this command has created the skeleton, which the report already reminds them to do. On no, stop here and say that every later step assumes a repository.

## 1. Settings

Merge the four keys from `${CLAUDE_PLUGIN_ROOT}/templates/project-settings.json` into the project's `.claude/settings.json`:

- `agent` (`coder-fleet:lead`)
- `worktree.baseRef` (`"head"`), added inside an existing `worktree` object when there is one. Claude Code's default, `"fresh"`, cuts every agent worktree from `origin/<default-branch>`, so a local main that is ahead of the remote leaves each coder behind it. `"head"` cuts from the local HEAD.
- `env.CLAUDE_CODE_ENABLE_TODO_TOOLS` (`"1"`), added inside an existing `env` object when there is one. Claude Code turns `TaskCreate` and `TaskUpdate` off for current models without it, and a `[board:<id>]` task completed with `TaskUpdate` is the only route to Done.
- `extraKnownMarketplaces.rzem`

If `.claude/settings.json` does not exist, copy the template as-is. If it exists, add only the keys that are missing and leave every existing key exactly as it is - including an existing `agent`, an existing `rzem` marketplace entry, and any other plugins. A key that is present but differs from the template is a conflict: report it and leave it alone rather than changing it.

Do not add `enabledPlugins`. The plugin is enabled at user scope on each machine, and a project-scope enable mints a separate install record for every path that carries it, including every agent worktree, each pinned to whatever version was current. If the project already enables `coder-fleet@rzem` in `.claude/settings.json` or `.claude/settings.local.json`, say so in the report and explain that cost; removing it is the human's call, because a project that runs on Claude Code on the web needs the committed enable to get the fleet there at all.

## 2a. The fleet's files out of history

This step runs before step 2b, because step 2b makes the state worktree, whose first commit takes the board onto the `coder-fleet/state` branch, and the board must already be out of the default branch's history then.

The fleet keeps its own files out of the project's history, always, with no question about it: the board (`.boards/`), the fleet's agent memory (`.claude/agent-memory/coder-fleet-*/`), each rule file this plugin installs under `.claude/rules/`, `.claude/coder-fleet.json`, `docs/specs/` and `docs/runs/`. They are listed in the common git dir's `info/exclude`, which every linked worktree shares, the state worktree included, and which is never committed. The board and the memory are committed on `coder-fleet/state` instead, specs stay in the main checkout and are committed on that branch too, and that branch is pushed to the remote the default branch comes from after each commit, so a fresh clone gets them back on its first board use. `.claude/settings.json` and `AGENTS.md` are not listed and stay committed. Never write a `.gitignore` line for any of them, and never edit `info/exclude` by hand: one script does it.

Run `python3 -I "${CLAUDE_PLUGIN_ROOT}/scripts/fleet-exclude.py" status` from the project root. Its last line is the state:

- `state: excluded`: nothing to do. Say so.
- `state: not-excluded`: run `python3 -I "${CLAUDE_PLUGIN_ROOT}/scripts/fleet-exclude.py" write`, which adds each missing entry once, and keep its `added` lines for the report.
- `state: needs-migration`: an earlier `/init` left some of these files tracked, or left its old `.gitignore` lines (`docs/runs/`, `.boards/`, `.claude/agent-memory/`). The `tracked` and `gitignore` lines name them. Say what will be untracked and which lines removed, then ask once, with AskUserQuestion. Question: "Untrack the fleet's files in one commit on the current branch? They stay on disk here and the board and memory stay on coder-fleet/state, but another clone that pulls the commit has them removed from its working tree: the board and memory come back there from coder-fleet/state, and the rules and config by re-running /init." Options: **Migrate (Recommended)**, "`git rm --cached` every path listed, remove the old `.gitignore` lines, write the exclude, and commit the removals and the `.gitignore` change as one commit"; **Not now**, "Change nothing; the project stays half set up". On migrate, run `python3 -I "${CLAUDE_PLUGIN_ROOT}/scripts/fleet-exclude.py" migrate` and keep its lines for the report. It never touches `coder-fleet/state`. Exit 1 is a refusal that changed nothing: something else is staged, or this is a linked worktree; pass its reason on and ask the human to deal with it, then re-run `/init`. Exit 3 means a git step failed and what it changed was put back; pass the message on. On not now, change nothing and say plainly in the report that the project is half set up: the fleet's files are still tracked on the default branch, `board flush` says so, and re-running `/init` asks again.

When the board's config says `auto_commit: false`, which an earlier `/init` set on an answer to keep the board out of git, say in the report that board commits on `coder-fleet/state` stay off until the human sets it back to `true`, which is safe now that the board is out of the default branch's history. Change nothing. What the exclude means for commits, the push and other clones is in `docs/board-config.md`.

## 2b. Board

The board starts as this repository's `.boards/`, which step 2a keeps out of its history. The live board is the state worktree's copy, `.claude/worktrees/coder-fleet-state` on the `coder-fleet/state` branch, made from it; the fleet's hooks and the board MCP server find it from any checkout through git, and every board write commits there. Create both here so the first `/kickoff` has a board to check.

- If `.boards/config.yml` exists, say so, make the state worktree as the last bullet says, and skip the rest of this step. If its `statuses` list `Doing`, first offer the rename by following the Rename paragraph of `${CLAUDE_PLUGIN_ROOT}/commands/kickoff.md`, with AskUserQuestion and `--by init` in place of `--by kickoff` (and `Board-Writer: init` on the config commit), taking the path `board.sh state` printed as the board's checkout, or the main checkout when it failed. If its `statuses` lack `Next`, then offer to add it by following the Next paragraph of `${CLAUDE_PLUGIN_ROOT}/commands/kickoff.md`, with AskUserQuestion and `Board-Writer: init` on the config commit. A new board gets `In Progress` and `Next` from the template.
- Otherwise copy `${CLAUDE_PLUGIN_ROOT}/templates/board.config.yml` to `.boards/config.yml` and `${CLAUDE_PLUGIN_ROOT}/templates/board.gitignore` to `.boards/.gitignore`, and create `.boards/tasks/`, `.boards/docs/` and `.boards/milestones/`, each holding a `.gitkeep` so an empty directory survives on the state branch.
- Set `project_name` in the copied config to the repository's directory name. Then offer the prefix with AskUserQuestion: `BD` (recommended) or a short upper-case one derived from the repository name, two to four letters. Write the answer as `task_prefix`.
- Say that the config carries a default Definition of Done under `definition_of_done:` - the reviewer approved, with a break round where the lead's step 4 calls for one; the gates declared in `AGENTS.md` green; the spec linked where there is one - which every new item starts with, unticked, that step 3a offers to name the project's gates in it, and that the human changes it by editing that list in `.boards/config.yml`, which reaches items created afterwards.
- Say that the config switches on `require_acceptance_criteria: true`, so the board refuses to create an item with no acceptance criteria from the CLI, MCP `task_create` or the web UI, Drafts included, and that the human turns it off by setting `require_acceptance_criteria: false` in `.boards/config.yml`.
- Say that every write the binary makes will be committed on `coder-fleet/state` in the state worktree, never on the default branch or a feature branch, and pushed to the remote as that branch, and that `auto_commit: false` in the config or `CODER_FLEET_BOARD_NO_COMMIT=1` in a shell turns the commits off, and `CODER_FLEET_STATE_PUSH=off` the push. Read the config's `auto_commit` value and key the report on it: with `false`, say board writes are not committed.
- Say that in a repository with no commit yet the board stays in the main checkout until there is one, and its writes there are not committed, since the exclude keeps the board off the default branch; the move takes them across after the first commit.
- Last, make the state worktree: run `${CLAUDE_PLUGIN_ROOT}/board/board.sh state` from the project root. Exit 0 prints its path; say it. In a fresh clone of a project whose state branch was pushed, it re-attaches that branch from the remote the default branch is fetched from, never another, and logs which. In a repository with no commit yet it fails saying so: say that the board moves into the state worktree on its first use after the first commit, with nothing for the human to do. Any other failure leaves the board in the main checkout, readable and writable as before: report the reason it printed and say that `board.sh state` tries again once the cause is fixed.

Renumber nothing: step 3 below stays step 3. Never remind the human to commit `.boards/`: it is excluded, and it reaches other clones on `coder-fleet/state`.

## 2c. Editors

The fleet has two editors, `spec-editor` and `tech-editor`, both on Opus. A project runs each editor, or not. Run `python3 -I "${CLAUDE_PLUGIN_ROOT}/scripts/editor-models.py" status` from the project root. It prints `spec editor: <answer>` and `tech editor: <answer>`, where the answer is `opus`, `neither`, `none`, `retired (fable)` or `unreadable (<value>)`. Ask only about an editor whose answer is `none` or `retired (fable)`, so a re-run asks nothing already answered. Before asking about a retired one, tell the human the fleet no longer ships a Fable editor, so the project's earlier `fable` answer needs answering again. Report an `unreadable` one as a line to fix by hand, and ask nothing about it.

Ask the two as separate AskUserQuestion questions, the spec editor first, each with these two options in this order:

- Spec editor. Question: "Should this project run a spec editor? It runs on Opus and challenges each spec draft once, after the interview and before you edit it, and building waits until its must-resolve challenges are resolved or struck." Options: **Opus (Recommended)**, "`spec-editor` on Opus, the default"; **Neither**, "No spec editor and no challenge gate. Specs go from spec-writer straight to you".
- Tech editor. Question: "Should this project run a tech editor? It runs on Opus and edits every tech-writer document once, in place, before it ships." Options: **Opus (Recommended)**, "`tech-editor` on Opus, the default"; **Neither**, "No tech editor. External-audience documents get the lead's own Opus pass, and internal ones get none".

Record each answer with `python3 -I "${CLAUDE_PLUGIN_ROOT}/scripts/editor-models.py" set <spec|tech> <opus|neither>`, never by hand. It writes the `Spec editor: <answer>` or `Tech editor: <answer>` line in `AGENTS.md`, replacing the template's placeholder or a retired `fable` answer, and it is the one line this command adds to an `AGENTS.md` it otherwise leaves alone. For neither it also adds `Agent(coder-fleet:<name>)` to `permissions.deny` in `.claude/settings.json`, inserting it into the file's text so every other byte stays as it was, and refusing a file with a duplicate key; opus adds no rule. Over a retired `fable` answer, opus removes the `Agent(coder-fleet:<name>)` rule the Fable answer wrote, and leaves any rule naming a removed Fable definition, which denies nothing that exists. A denied spawn by the `coder-fleet:` name fails with "has been denied by permission rule". A spawn by the bare name, such as `spec-editor`, reads "not found" whether or not a rule exists, because a plugin agent never resolves by its bare name; that is expected and not a sign the rule failed. Exit 0 means it recorded the answer. Exit 1 is a refusal and changed nothing. Exit 3 means a file could not be read or written, and its message says which and whether the deny rules were already written, in which case running it again once the file is fixed adds no rule twice. On 1 or 3, pass the message to the human and record nothing by hand. To change an answer later, edit the line and the deny rule together.

Add the answers and the rules written to the report.

## 3. Guided fill

Skip this step entirely if step 2 skipped `AGENTS.md`.

Read the project before asking anything: manifest and lockfiles (`package.json`, `pyproject.toml`, `Cargo.toml`, `go.mod` or equivalent), build and test configuration, the directory layout, and the last dozen commit subjects (none, in a repository step 0 just created). Draft an answer for every `<FILL: ...>` marker in the copied `AGENTS.md` from that evidence.

Then walk the markers with the human using the AskUserQuestion tool, one topic per question, offering the inferred value as the recommended option. Markers you could not infer get an open question, not a guess. The `Worktree setup` section is always asked, never inferred silently: a fresh agent worktree holds only tracked files, so ask how it gets its dependencies (an install command, symlinks to the main checkout's `node_modules`, a script) or whether none are needed, and offer what the lockfiles suggest as the recommended option. `none needed` is a complete answer. The `Requirements source` line in `Where work lives` is also always asked, never inferred, because the line alone skips `spec-writer` for every item: ask whether the project has approved requirements and where they are, write the path on a yes, and on a no delete the line and the paragraph after it. The `App start` and `App url` lines are inferred from a `start` or `dev` script or the README's run instructions and confirmed like any other marker; on a project with nothing a user drives, such as a library, delete both lines and the paragraph after them, and the reviewer never runs in use mode. On a project with a client UI - a web front end, a desktop or mobile app, any screen a user drives - an `App start` line the human declines or leaves unfilled means the reviewer's use mode will not run, so no acceptance criterion on that UI is checked in the running product and a UI change rests on a screenshot the lead compares by hand: say so, recommend the line, and put that in the report. Write each confirmed value into `AGENTS.md` as you go, and delete the marker-explainer paragraph near the top once no markers remain.

If the human declines the interview, fill the markers you inferred with confidence, leave the rest as `<FILL: ...>`, and say which remain. Always leave the `Worktree setup` marker: it is never inferred, and an unfilled one is what tells kickoff and coders the setup is unknown. Leave the `Requirements source` marker too, for the same reason: kickoff fails on it until the human fills the line or deletes it.

## 3a. Definition of Done

This step runs whether or not step 3 did, after it, so it reads the gates block as the walk left it. The board's live config is `.claude/worktrees/coder-fleet-state/.boards/config.yml` when that file exists and `.boards/config.yml` otherwise; with neither, skip the step. Read its `definition_of_done` list.

When the list carries the coder-fleet repo's own release steps, first follow the Definition of Done paragraph of `${CLAUDE_PLUGIN_ROOT}/commands/kickoff.md`, with `Board-Writer: init` on the config commit.

Then offer the gates. Ask only when the list still holds the template's gates item, `The gates declared in AGENTS.md are green on the branch`, exactly, and `AGENTS.md` has a `gates` block with at least one `name: command` line that is not a `<FILL: ...>` marker. Ask with AskUserQuestion. Question: "Name this project's gates in the Definition of Done?" Options: **Name them (Recommended)**, "`The gates declared in AGENTS.md (<names>) are green on the branch`", with every gate's name in block order, the last two joined by `and`; **Keep the general item**, "Leave the item as the template wrote it". On name, replace that one entry in place and change nothing else in the file, in the live config and in the main checkout's `.boards/config.yml` when it holds the same entry. When the live config is the state worktree's, `auto_commit` is `true` in it and `CODER_FLEET_BOARD_NO_COMMIT` is unset, commit that file alone there: `git -C .claude/worktrees/coder-fleet-state commit -m "Name the gates in the Definition of Done" -m "Board-Writer: init" -- .boards/config.yml`. Otherwise commit nothing; the main checkout's copy is the human's to commit with the rest. With no gates block, or only markers in it, ask nothing, and say in the report that the gates item has nothing to check until the block is filled, so the lead ticks it not applicable until then. Either way, say in the report what this step changed in the list, or that it changed nothing.

## 4. Report

End with a short report: whether step 0 created a repository, what was created, what was merged and which keys, what was skipped and why, any settings conflicts, and any markers still unfilled. Say what step 2a did - the entries it added to `info/exclude`, the migration commit and what it untracked, or that the project is half set up - and any `auto_commit: false` it found. Remind the human to commit `.claude/settings.json` and `AGENTS.md`, so every clone and every Claude Code on the web session gets the same fleet; the board and memory reach them on `coder-fleet/state`.

Then say what comes next, exactly: restart Claude Code and trust the folder - the new settings, `AGENTS.md` and (if it was not already installed) the plugin all load at session start, so nothing done here is live until then - and in the new session run `/coder-fleet:kickoff` to verify the install and start the first piece of work. That holds for the editor answers too: this session's lead holds `AGENTS.md` as it was when the session started, while the challenge gate reads it from disk, so in this session the two would disagree about whether the project has a spec editor.

Re-running this command is safe: every step skips what already exists, step 0 is silent in a repository, step 3 only offers markers still present, and step 3a asks only while the general gates item or a release step is on the list.
