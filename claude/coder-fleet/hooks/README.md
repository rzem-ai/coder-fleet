# Hooks

The machinery that writes the board and enforces per-agent tool scoping. Every hook runs the `boards` binary, either as `boards hook <event>` for the board or through a shim onto `boards fleet <tool>` for the fleet's own rules; no agent is ever asked to remember anything.

| File | Event | What it does |
|---|---|---|
| `boards-binary.sh` | `SessionStart` | Fetches the release build of the `boards` binary for this plugin version and platform, as "The board's hooks" below says |
| `main-fast-forward.sh` | `SessionStart` | In the main checkout only, fetches the base branch (`baseBranch` in `.claude/coder-fleet.json` when set, else what the remote's HEAD names, else `main`) with a 5-second bound and brings the local branch level by fast-forward alone: `git merge --ff-only` when it is out, a checked `update-ref` when nothing has it out, nothing when a linked worktree has it out. One line of context says how many commits it moved, which branch is out, or a fixed reason it changed nothing; silent when level, in a linked worktree, outside a repository or with no remote. With `baseBranch` set it also says when that branch is ahead of its remote copy or has none, and which branch is out when the checkout is on another; a `baseBranch` the resolver cannot use moves nothing and says so. Fetches only https, ssh and git remotes, fetches nothing when the repository's own config (which any agent session can write) holds a key off its allowlist of keys that run nothing, or the repository borrows objects through alternates, and puts git's own words only in the hook log, with URL credentials cut; never fails a session |
| `enforce-agent-scope.sh` | `PreToolUse` | Denies tool calls that violate an agent's own Invariants, and, in every session and agent, the lead's own included, any Bash call the project's `push` and `release` settings refuse |
| `agent-clock.sh` | `SubagentStart`, `PreToolUse` (every tool) | Starts a reviewer's clock once per agent id; for a reviewer whose brief names break mode, or cannot be read, denies every tool call past the 25-minute hard cap, and under it trims a Bash `timeout` to the time left |
| `enforce-disabled-agents.sh` | `PreToolUse` (`Agent`) | Denies a spawn of any agent the project lists under `disabledAgents` in `.claude/coder-fleet.json`, naming the file; reports the file invalid when it lists `lead`, `coder` or `reviewer` |
| `lib/reviewer-modes.sh` | - | Reads the modes a reviewer's brief names on its `Modes:` line, for `agent-clock.sh` and `enforce-agent-scope.sh`, and records the first clean read; see "The reviewer's modes" |
| `lib/fleet-config.sh` | - | Finds the main checkout and reads and validates its `.claude/coder-fleet.json` - `disabledAgents`, `phase`, `baseBranch`, `push` and `release` - and resolves the base branch in `fleet_trunk`, for the hooks and scripts that read any of them |
| `lib/push-policy.sh` | - | Reads the `push` and `release` settings and the base branch, lexes the command as the shell does and judges it, for `enforce-agent-scope.sh`; see "The push and release settings" |
| `lib/remote-guard.sh` | - | The repository-config keys known to run no command, the remote URLs reached, and the log redaction, for the fast-forward hook |
| `hooks.json` | - | Registers the hooks with Claude Code |

Board writes are design section 7. `permissions.deny` is session-scoped, so `enforce-agent-scope.sh` is the per-agent half that settings cannot express. `agent-clock.sh` is the one hook that watches time rather than text.

`enforce-agent-scope.sh`, `agent-clock.sh`, `enforce-disabled-agents.sh`, `main-fast-forward.sh` and every file under `lib/` are shims onto `boards fleet`, whose code is in `../boards/src/fleet/` ("The fleet's tools" in `../boards/README.md`): the push policy is `push-policy.ts` and the write checker `write-scope.ts` there, and `lib/push-policy.py` and `lib/check-write-scope.py` only pass their arguments on. The scope hook, the disabled-agents hook, the push policy and the write checker refuse when the binary cannot run; the clock and the fast-forward let the session go on.

## The board's hooks

`hooks.json` runs every board hook on the `boards` binary, as `"${CLAUDE_PLUGIN_ROOT}/boards/boards.sh" hook <event>`, whose code is in `../boards/src/hooks/`. The board lives under `~/.config/boards/<PREFIX>/`, outside the repository, so no hook commits anything; with no board for the repository the hooks do nothing and say so once per session.

| Command | Event | What it does |
|---|---|---|
| `boards hook session-start` | `SessionStart` | Clears the checkout's focus on every start but a compaction, reminds the session to check the board first and to reconcile it before stopping, and on every start but a compaction restarts a vanished release run and catches up on release tags pushed outside a session |
| `boards-binary.sh` | `SessionStart` | Fetches `boards-<platform>.gz` for this plugin version (darwin-arm64, darwin-x64, linux-x64 or linux-arm64) from the release, checked against `boards-SHA256SUMS`, into `${CLAUDE_PLUGIN_DATA}/bin/boards-<version>`, where `boards.sh` looks after a binary built in the plugin. The one hook that is not the binary, since it fetches it. Once per version; never fails a session |
| `boards hook pre-agent` | `PreToolUse` (`Agent`) | Binds the spawn to its card when it is sent: the card its `Board-Item:` line names, which also focuses the checkout on it, else the checkout's focus at that moment. Records the binding under the call's `tool_use_id` and starts work on the card. Never blocks the spawn |
| `boards hook subagent-start` | `SubagentStart` | Notes the agent's start with the checkout's focus, the binding a workflow lane falls back to; a resumed agent starts work on its card again |
| `boards hook subagent-stop` | `SubagentStop` | The handoff-format check, with exit 2 and the reasons to re-emit, then binds the agent to the card its spawn was sent for, turns each `Blocker:` line into an Action for Human, which moves the card to Blocked by Human, and on a coder's or scripter's stop runs the card gate. Matched to the fleet agents but the lead |
| `boards hook task-completed` | `TaskCompleted` | Runs the card gate on the card a `[board:<id>]` task subject names. It fires only when a task is completed with `TaskUpdate`, which Claude Code offers to current models only when `CLAUDE_CODE_ENABLE_TODO_TOOLS` is set, so the project settings `/init` writes set it |
| `boards hook post-push` | `PostToolUse` (`Bash`) | The tag watch: after a successful `git push` of a release tag that origin now holds and whose message carries a `Cards:` line, starts the test gate in the background, which moves the cards it names from Done to Released when the suite passes |
| `boards hook stop` | `Stop` | Sends the lead back once, as "The Stop hook" below says |

### Binding a spawn when it is sent

`SubagentStart` carries no `tool_use_id` and fires before the agent's transcript exists, so it cannot tell which Agent call it is. The binding is therefore made when the spawn is sent and found again at the agent's first stop, through the `toolUseId` in the `.meta.json` Claude Code writes beside the agent's transcript (`agent_transcript_path`), and kept for the rest of its run. A focus that changes later in the same batch never reaches an earlier spawn. A workflow lane is sent by no Agent call and its meta names none, so it binds to the focus as it was when it started. A card in Done or Released binds nothing, and the event trail says so. The records live in the board's private state directory, `$XDG_STATE_HOME/coder-fleet-boards` or `~/.local/state/coder-fleet-boards`, under `spawns/`, `starts/` and `agents/`.

### The Stop hook

`boards hook stop` runs when the main session stops, in any project with a board. When the checkout's focused card still has an unticked acceptance criterion, it sends the lead back once, naming the card and the criteria still open, with the same instruction as the session-start reminder: finish them, or reconcile the board before stopping. It lets the stop through, adding nothing, when Claude Code is already continuing for a stop hook (`stop_hook_active`), so one stop costs at most one extra turn; when there is no focus or no board; when the card is fully ticked, has an unticked Action for Human, or is Blocked or Blocked by Human; when the lead's last message asked a question; and when a background task is still running. It writes nothing and moves no column, and an error reading the focus or the card lets the stop through and is logged on stderr. `sendBackAtStop: false` in the board's `config.yml`, under `~/.config/boards/<PREFIX>/` (or `$XDG_CONFIG_HOME/boards/<PREFIX>/`), turns it off for that board.

## The handoff-format check

### Who it applies to

`SubagentStop` takes a matcher and the matcher is the agent type, so `hooks.json` registers this hook against the fleet agents but the lead, and nothing else:

```
^(coder-fleet:)?(scout|spec-writer|spec-editor|coder|scripter|reviewer|ui-designer|tech-writer|tech-editor|researcher|fleet-steward)$
```

The optional prefix is there because a plugin agent arrives as `scout` or as `coder-fleet:scout` depending on how it was named.

The lead is left out on purpose (item 27). It is the session agent and never spawned, and the runtime types its own side calls, the prompt suggestion after every turn among them, as the session's agent, so a `coder-fleet:lead` stop is always one of those and never owes a handoff. The hook stands one down too, in case a runtime lets it past the matcher, and stands down any other fleet type's side call by its shape: no start record and no transcript on disk.

Without the matcher the gate would fire on every subagent, including the built-in `general-purpose` lanes the workflows spawn. Those lanes never preload the `handoff` skill and are asked for structured JSON, so every one of them would fail the check, hit exit 2 and be told to re-emit a handoff it was never asked for. Scoping the registration is the right fix rather than a special case inside the validator, because a lane that returns JSON is not a malformed handoff - it is not a handoff at all.

The cost is that a non-fleet subagent's handoff is never read: no `Blocker:` reaches the human queue and no comment lands. That only matters for a spawn bound to an item, and the lead only binds those to fleet agents.

A second cost, worth stating plainly because two things depend on it: an `agentType`-less lane is outside *both* hooks. The `SubagentStop` matcher skips it, and no branch of `enforce-agent-scope.sh` claims it either, since every branch there keys on an agent name. So when `review-round.js` tells its git and mechanical lanes "read-only git only", that sentence is an instruction to a model and not a boundary anything enforces. The two mechanical lanes and `review-round`'s two git lanes are all in that position. The trade is deliberate: those lanes need `git worktree list`, `merge-base` and `rev-parse`, and widening `scout`'s or `reviewer`'s allowlist to cover them would weaken a role boundary for every run rather than for the one workflow that needs it.

The rule that falls out of all this, worth keeping whenever a workflow is written: **give a fleet agent a schema only where its handoff is worth nothing.** A spawn's `schema` decides whether the gate, the `## Done` card comment and the `Blocker:` route to the human queue exist for that run at all.

### What it checks

`boards hook subagent-stop` (`../boards/src/handoff.ts`) validates `last_assistant_message` against `skills/handoff/SKILL.md` and exits 2 if it does not parse, which stops the subagent stopping and hands it the list of problems. The anchors come from the skill, quoted rather than reinvented. Every line is right-trimmed before any anchor sees it - trailing whitespace is invisible in rendered markdown and models emit it habitually (two trailing spaces is the hard-line-break idiom), so it never changes what a line means; leading whitespace still does:

| Rule | Regex | Line in `skills/handoff/SKILL.md` |
|---|---|---|
| Section headings | `^## (Done\|Not done\|Unverified\|Decisions needed)$` | "Anchor: `^## (Done\|Not done\|Unverified\|Decisions needed)$`" |
| Any level-2 heading | `^## ` | "Use no other level-2 heading anywhere in the final message." |
| An item | `^- ` | "Every item is one markdown list item starting `- ` at column 0." |
| A typed line | `^- (Blocker\|Propose item): ` | "Anchor: `^- (Blocker\|Propose item): `" |
| An empty section | `^- None$` | "An empty section contains exactly one line: `- None`." |
| Where a typed line may appear | `^- (Blocker\|Propose item): ` under `## Decisions needed` only | "A typed line belongs under `## Decisions needed` and nowhere else." |
| A blank line inside a section | a blank line with another item after it, before the next heading | "No blank line inside a section." |

What it rejects: a missing, duplicated or out-of-order heading; any other H2; an empty section; a line under a section that does not start with `- ` at column 0, which is also how "the handoff is the last thing in the message" is enforced; an untyped line under Decisions needed; a typed line under any heading other than Decisions needed; a blank line between two items in the same section; and `- None` mixed with real items.

What it tolerates on purpose:

- **Prose before `## Done`.** The skill says the handoff is the last thing in the message, not the only thing. Nothing above the first heading is parsed at all, which is why an agent may name a prefix in prose while explaining what it did with someone else's handoff.
- **A blank line before the next heading.** That one is ordinary markdown and is what the skill's own example does. A blank line with another item after it is not, and is rejected.
- **No exception for a failed or cancelled run.** Nothing tells the hook a run failed or was cancelled (item 15), so every typed stop that carries a message is checked.

Blockers are extracted from the Decisions needed section only, not from the whole message, and the validator rejects a typed line found under any other heading, so a stray one under Done is caught by the validator instead of quietly parking a false alarm in the human queue. Rescuing it silently would be worse than refusing it: a misplaced blocker means the agent has the format wrong, and the human only learns that if the run is sent back.

### One rule set, two implementations

`claude/evals/lib/handoff-check.sh` is the CI gate and applies the same rules to the final assistant message of an eval run. The two are held identical by `claude/evals/lib/handoff-parity.sh`, which runs both over every case in `claude/evals/fixtures/handoff-cases/` and fails if a verdict ever differs:

```sh
claude/evals/lib/handoff-parity.sh        # verdicts only
claude/evals/lib/handoff-parity.sh -v     # and each side's reasons
```

Change one side and run it. They differ only in wording and in how many complaints each lists for the same message; the verdict is the contract.

## Per-agent tool scoping

`enforce-agent-scope.sh` switches on `agent_type` and denies with `permissionDecision: "deny"`, quoting the invariant that was violated. Every agent without a rule here, and the main session, is untouched by the role rules; the push and release settings below hold for all of them.

**Every agent's own memory** comes first. Each fleet agent sets `memory: project`, so Claude Code gives it `.claude/agent-memory/<agent type>/` in the project, with every character outside `[a-zA-Z0-9_-]` replaced by `-` (`coder-fleet:reviewer` keeps `coder-fleet-reviewer/`). A write tool whose path resolves inside that directory is allowed before any role's rule runs, through `lib/check-write-scope.py --memory`, which takes the project from `CLAUDE_PROJECT_DIR` or `cwd`, and also the worktree holding `cwd` when the project's own `git worktree list` names it under `.claude/worktrees/`, because Claude Code puts a subagent's memory under its spawn cwd while a hook's `CLAUDE_PROJECT_DIR` stays the main checkout. What git says about `cwd` itself is not believed, since a planted `.git` file leads any directory to the repository. It refuses a memory directory that is itself a symlink. Another agent's directory, a lookalike prefix and a `..` out of it are not inside. For the roles whose body forbids the tool everywhere else - `Write` and `Edit` for `scout`, `reviewer` and `researcher`; `Edit` for `spec-writer`, `tech-writer` and `ui-designer`; `Write` for both editors and `fleet-steward` - `memory_only_tools` then denies the tool anywhere outside memory, and with no `python3` the memory cannot be established, so the deny holds. The frontmatter grants those tools because `memory` adds `Read`, `Write` and `Edit` to an allowlist but `disallowedTools` wins over it: a role that disallowed `Write` could not write its memory at all.

**`spec-writer`** - "Never write anywhere except under `docs/specs/`". Any `Write`, `Edit`, `MultiEdit` or `NotebookEdit` whose path does not resolve inside a `docs/specs/` directory is denied. Paths are made absolute against `cwd` and normalised lexically first, so `docs/specs/../../etc/passwd` does not slip through.

**`spec-editor`** - "Never edit anything but the spec named in the brief, under `docs/specs/`" and "never run a command". Write tools get `spec-writer`'s `docs/specs/` check, and every `Bash` call is denied outright: an editor reads with `Read`, `Grep` and `Glob`, so a shell is never part of its job, and `Bash` is not in its tools either.

**`tech-editor`** - "Never edit anything but the `tech-writer` documents named in the brief" and "never run a command". Write tools get `tech-writer`'s scope exactly, through the checker below, a write tool with no path is denied, and every `Bash` call is denied outright, for the same reason as the spec editor.

**`scout`** - "Never edit, write or create a file" and the Bash allowlist from its Invariants. Write tools are denied outright. A Bash command is denied unless every segment of it starts with `ls`, `cat`, `head`, `tail`, `sed`, `wc`, `file`, `rg`, `grep`, `find`, `git`, `gh`, `cd`, `pwd`, `echo`, `true` or `read`, with:

- `sed` requiring `-n` and rejecting `-i`, because the invariant says `sed -n`
- `find` rejecting `-exec`, `-execdir`, `-ok`, `-okdir`, `-delete` and the `-f*` actions, which run or write things
- `git` limited to `log`, `show`, `blame`, `diff` and `ls-files`
- `gh` limited by group and subcommand pair to `issue list`/`view`/`status`, `pr list`/`view`/`diff`/`checks`/`status`, `run list`/`view`, `repo view`, `release list`/`view`, `label list`, `search issues`/`prs`/`repos`/`code`/`commits`, and `api`. Every other pair is denied, `gh auth` included, because `gh auth token` prints the credential. Only `-R`/`--repo` may stand before the pair, since gh can read the word after any other option as its value and so change which subcommand runs. `gh api` is an allowlist: one plain endpoint, which may end in a query string, and only `--paginate`, `--slurp`, `-i`/`--include`, `-q`/`--jq`, `-t`/`--template` and `-H`/`--header`, with unquoted values that do not start with `-`, plus `-X`/`--method` `GET` in either case (`-X GET`, `-XGET`, `-X=GET`, `--method GET`, `--method=GET`). A header must be an `Accept:` header, since another header can change what the request does. `--cache` is denied because it writes cache files. Any other word is denied, and so is any quote in a `gh api` word. In every `gh` segment a word may not hold `$`, `{`, `*`, `[` or a backtick, nor `?` outside the api endpoint's query string, because the shell builds flags from those (`$'-f'`, `${IFS}-XPOST`, `-{X,}POST`); an option may not be quoted; and `--web` and `-w` are denied, since a browser runs whatever config or the environment names. The quoted-option shape - a quote opening a word that starts with `-` - is checked over the whole command, not only the `gh` segment, so a command that runs `gh` and quotes such a word anywhere is denied. A command that runs `gh` may assign no variable in any segment, whether in front of a command or behind `env` or another wrapper (its options and duration skipped), and may not run `read` or hold a `for NAME in` header, both of which assign: `GH_CONFIG_DIR` alone points gh at a config whose browser it then runs. `export`, `declare` and the like are already off scout's allowlist. `gh` reached through `xargs` is denied whatever the pair, because xargs appends words from standard input that no check sees
- redirection (`>`, `>>`), command substitution (`$(`, backticks) and process substitution denied anywhere in the command

`cd`, `pwd`, `echo`, `true` and `read` are on the allowlist and are **not** in scout's Invariants. They are there because none of them can change state and all of them turn up inside otherwise legal commands - `read` as the head of `while read f; do ...; done`. That is the only addition; if you would rather it were exactly the invariant, delete them from `SCOUT_ALLOWED_CMDS`. `reviewer` carries `read` for the same reason.

A `for NAME in WORDS` loop header runs nothing, so every role reads it as shell syntax rather than a command and checks only the body behind `do`. A loop that only reads is allowed wherever the reads are. C-style `for ((...))` is not recognised and stays denied for the allowlist roles.

Two deliberate softenings so the hook is not merely annoying: quoted spans are stripped before the redirection scan, so `grep -rn '=>' src/` is allowed, and `2>/dev/null` is removed before that scan, because discarding output is not a state change.

**`fleet-steward`** - "Never touch anything outside the `coder-fleet` working copy" and "never run a git command that rewrites shared history". Write tools are denied outside the coder-fleet repo root, and `git merge`, `rebase`, `reset`, `filter-branch`, any force-push, `push --delete`, `push --mirror` and any push naming `main`, `master` or the base branch are denied. Pushing a feature branch and opening a pull request are allowed, because that is the whole job.

The coder-fleet repo root is `CODER_FLEET_REPO` if set. Otherwise it is derived from the plugin's own location: if the plugin sits at `<root>/claude/coder-fleet` and `<root>/.claude-plugin/marketplace.json` exists, `<root>` is it. From the plugin cache, where the plugin directory is named for its version, this finds nothing. If neither works, the check degrades to "the path contains a `coder-fleet` directory" and the deny message says to set `CODER_FLEET_REPO`.

**`reviewer`** - its rule depends on its modes (below, "The reviewer's modes"). In review mode alone, "Never edit, write or create a file", "Never run a git command that writes ... Read-only git only" and "Run the project's declared gates read-only, from the top of the review worktree, and nothing else that executes code". Write tools are denied outright, which is the one that matters: design section 4 singles the reviewer out because a review agent that edits makes the diff the human approves a different diff from the one they read. `git` is an allowlist - `log`, `show`, `blame`, `diff`, `ls-files`, `status`, `shortlog`, `describe`, `rev-parse`, `rev-list`, `cat-file`, `grep`, `whatchanged` - because "read-only git only" is wider than the seven verbs the invariant names and a denylist would miss the eighth. Every other command is a read from `REVIEWER_ALLOWED_CMDS` or a declared gate. The gates are a fenced block with the info string `gates` in the project's `AGENTS.md`, one `name: command` per line (the template carries the section), read from the main checkout through the worktree's git common dir so that a diff cannot widen what its own reviewer executes. A gate segment must match a declared gate word for word, or be the gate named `test` followed by one relative path without `..` that does not start with `@` or `+` and, resolved physically, stays inside the worktree (so a symlink out is refused), one test-name filter (`-t`, `--testNamePattern`, `--test-name-pattern`, `-g`, `--grep`) or one of each. It must run from the top of a linked worktree, reached only by the tool call's `cwd` or a leading `cd <path> && ... &&` (the same `cd_shape_ok` rule coder's guard uses, below). A `--separate-git-dir` or bare layout, where the main checkout is not the common git dir's parent, fails closed. Refused whatever the list says, each with its own contract case: package managers (`npm`, `npx`, `pnpm`, `yarn`, `bun` and the rest, since `pnpm --filter x typecheck` may install first), installs (`install_verb`, so `playwright install` too), snapshot updates (`-u`, any short cluster holding `u` with or without `=value` such as `-u=false` or `-tu=x`, `--u`, `--u=<value>`, `--update`, every `--update=<value>`, cac's dotted `--update.<key>`, `--update-snapshots` and kin; `--update=none` included, because vitest 3.x takes no value and reads `none` as a file filter while updating every snapshot), `--fix`, `--write` and `--apply`, watch mode (`--watch`, `-w`, a `watch` or `dev` subcommand), build output inside the repository (`tsc` without `--noEmit`, a `build` subcommand, or an output flag whose path is not under `TMPDIR` or a Claude Code scratchpad and outside both checkouts, compared lexically and physically), network tools, and the main checkout or a subdirectory as the working directory. The word rules are scout's gh rule, shared rather than copied: `word_expansion_denial` refuses `$`, `{`, `*`, `?`, `[`, backticks and quoted options, `GH_QUOTED_FLAG_RE` is checked over the whole command, `gh_command_assigns` refuses any variable assignment, `for` header or `read` - except a literal `CI=true` as the first word of a segment whose command is a gate, where the declared gate carries it too, since in CI mode vitest 3 and 4 and jest write no snapshot; a bare `CI=true ;` or `CI=true &&`, or `CI=true` in front of a read, is an ordinary assignment and is refused - and no `COMMAND_WRAPPERS` word may stand in front of the gate. The reviewer still reads the tree with `rg`, `cat` and `find`.

In every mode one write is allowed: its progress log (CF-192), matched whole on the command as sent, `date [-u] '+<format>' >> <main checkout>/docs/runs/<YYYY-MM-DD>-reviewer-<issue>-progress.log` and `mkdir -p <main checkout>/docs/runs`. The step's words ride in date's single-quoted format, so no substitution is needed and none is allowed. The main checkout is the one `CLAUDE_PROJECT_DIR` belongs to, never the call's `cwd`, which must be in that same repository, so a reviewer that cds into a repository made for the purpose cannot use its `docs/runs`; the path must be plain and absolute, its directory must resolve physically to that `docs/runs`, and an existing log must be a regular file.

In break mode (`reviewer-break` in the hook) the rule is the old refuter's: write tools only outside the project, failing closed when the checker cannot run, and Bash open but for read-only `git`, because mutation testing is copy, change, run. In use mode alone (`reviewer-use`) write tools are held the same way, and Bash has `ui-designer`'s rule through `enforce_readonly_git_no_install`: read-only `git` and no install verb, so it can start the product, `curl` it and run a browser driver fetched with `npx -p playwright@<version>` into npx's own cache. A brief naming both is `reviewer-break`, the wider. In every mode the reviewer is refused any write tool aimed under the fleet's state directory or Claude Code's transcripts directory, and any Bash command naming either, case-insensitively since APFS folds case, because those directories hold the record of its own modes and clock; the deny names the path it matched. A path the command does not show gets past it (`docs/limits.md`). `check-write-scope.py --outside` refuses the same two directories as a second lock.

**`ui-designer`** - "Never run a git command that writes, and never install anything into the product repo". The same read-only `git` allowlist. Installs are matched on the verb rather than the command, because "use Bash only to build, serve or screenshot a prototype" is the job: `npx serve` and `npm run build` are allowed, `npm install`, `pnpm add`, `pip install`, `cargo add`, `go get` and `brew install` are not.

**`coder`** has its own branch: its writing git verbs are confined to a linked worktree (item 18 below).

Write destinations go through `lib/check-write-scope.py`, which runs before the role dispatch for the roles that hold `Write`. A glob on a lexically normalised path answers the wrong question three ways - `*/docs/specs/*` matches *any* project's specs directory, `..` collapsed without asking the filesystem lets a symlinked `docs/specs` resolve to itself, and `Write` replaces a source file as completely as `Edit` does - so the checker resolves symlinks on the deepest existing ancestor and anchors to this project:

| Role | May write |
|---|---|
| `spec-writer` | `<project>/docs/specs/**` |
| `spec-editor` | `<project>/docs/specs/**` |
| `tech-writer` | `<project>/docs/**` (`.md`, `.mdx`, `.txt`) and a Markdown file at the project root |
| `tech-editor` | `tech-writer`'s scope, read from `tech-writer`'s entry in `CODER_FLEET_OUTPUT_FILES` when that is set |
| `ui-designer` | `<project>/prototypes/**` and `<project>/docs/runs/**` |
| `fleet-steward` | anywhere inside `$CODER_FLEET_REPO` |

`docs/runs/**` is open to `ui-designer` on purpose: a commissioned run article is an authorised deliverable. Set `CODER_FLEET_OUTPUT_FILES` in the launching environment - never in agent-authored content - to narrow `tech-writer` or `ui-designer` to an exact list of commissioned files:

```json
{"tech-writer": ["README.md", "docs/adr/001-session-refresh.md"]}
```

It only narrows. Listing a path outside the role's default scope does not grant it, and two agents needing different lists need a binding keyed by agent identity rather than one shared, widened list.

**The push and release settings** (CF-209.3) hold for every Bash call in every session, before any role rule. The hook's `PreToolUse` matcher has no agent filter, so it sees the main session's calls as well as each subagent's. The lead is the call with no `agent_id` whose `agent_type` is empty or `lead`: Claude Code sets `agent_id` only inside a subagent and sets `agent_type` for the main session when it runs as a named agent, so a subagent typed `lead` is not the lead. The settings are read live from the main checkout through `lib/fleet-config.sh`, and with `push` unset or `all` and `release` unset nothing is checked. Otherwise:

| Setting | Refused |
|---|---|
| `push: base-only` | every `git push`, `send-pack` and `http-push` but the lead's plain push of the base branch, and of one version tag when `release` allows it; `gh pr create` from anyone. The lead's push takes `-u`, `-q`, `-v`, `-n`, `--porcelain`, `--atomic`, `--no-verify` and `--no-follow-tags` at most, names the base branch or nothing (a bare push from the base branch), and is refused when the repository's config would make it send more: a remote's `mirror` or `push` key, `push.followTags`, submodule recursion, or a `push.default` other than `simple` or `current` for a bare push |
| `release: off`, or unset under `push: base-only` | creating a tag (`git tag`, `update-ref` or `symbolic-ref` on a tag ref, `fast-import`), any push that sends a tag, and `gh release create`, from anyone, whatever `push` is. Unset says to set `release` |
| `release: tag` | `gh release create`. Under `push: base-only` the lead may push one annotated `vMAJOR.MINOR.PATCH` tag that points at a commit on the base branch, pushed alone |
| `release: github` | as `tag`, except the lead may run `gh release create` with `--verify-tag` and no `--target`, so gh stops rather than create a tag that is not already on the remote |

An invalid or unreadable value is the strict one: `push` base-only, `release` off. `lib/push-policy.py` reads the command as the shell does - quotes, `$'...'`, substitutions, heredocs, subshells, operators - and judges each command in it, a string handed to `sh -c`, `eval`, `env -S`, `su -c`, `script -c` or `watch` included, and git or gh named later in another command's words. Under a restrictive setting it refuses what it cannot read rather than guess: a word the shell builds at run time, an alias or a shell function standing in for git or gh, a variable assigned anywhere in the command, a git option that changes its config or repository, xargs in front of git or gh, a shell reading a pipe, a `cd` it cannot follow, and a command such as `python3 -c`, `node -e`, `perl -e` or `awk` whose own words name git or gh with a push, tag or release word. Unlike the role rules it fails closed: no `python3`, or a crash, refuses. What can be decided from the words - a push by anyone but the lead under base-only, more than two refspecs, more than 16 words after a push's options - is decided before any git runs, and the whole check holds itself to a 5-second budget and refuses past it, because the hook's own 10-second timeout renders no decision, which lets the call through. `gh release create` must carry `--verify-tag` once, bare, with no `--` before it. `state-push.sh` pushes nothing under `push: base-only`.

`scripts/prune-worktrees.sh` is not a hook but reads the same settings: a worktree counts as merged when its HEAD is an ancestor of the base branch, local or origin's, and under `push: base-only` also when its whole diff landed there as one squashed commit. With the settings absent the base branch is what the remote's HEAD names, else `main`, and only the ancestor test applies.

**The settings guard** (the human's decision on CF-209.3) is small and fails closed. Under any setting, for every agent but the lead, it refuses a write tool aimed at the main checkout's `.claude/coder-fleet.json`, through a symlink, a hard link or another case of the name included; any Bash command whose text, with line continuations joined, backslashes and quotes removed and case folded, names `coder-fleet.json` at all, readers included, since no agent but the lead has a reason to touch it; and `scripts/fleet-agents.sh base`, `push` or `release` with a value. What it cannot see is in `docs/limits.md`.

This hook **fails open**. Bad input, a missing `jq`, an unexpected error: it logs and allows. Be clear about what that costs. For the per-agent half there is no second lock, because that is precisely the half `permissions.deny` cannot express: a deny rule strong enough to stop `scout` writing stops `coder` writing too. The session-wide half - credentials, `curl`, `sudo`, destructive git verbs - is denied in `claude/home/settings.json` and by the sandbox whatever this hook does. A shell-command allowlist parsed with `sed` and `awk` is a speed bump for an agent that has misread its brief, not a sandbox for one that is trying to get out. `/sandbox` is the sandbox.

## Per-agent time caps

`agent-clock.sh` holds a table of agents with a wall-clock cap. It has one row, because the human's rule names one agent in one mode:

| Agent | Told to finish by | Hard cap |
|---|---|---|
| `reviewer`, break mode | 20 minutes (1200 s) | 25 minutes (1500 s) |

The 20 lives in the reviewer's body and the `looping` skill; the hook enforces only the 25. A reviewer in review or use mode alone is never denied or trimmed: its clock file is written at its start like any reviewer's, because the brief may not be on disk yet, and is never acted on. A `coder` legitimately runs long inside a worktree and a round budget of its own, so no other agent is capped.

**The clock** starts at `SubagentStart`: the hook writes `clocks/<agent_id>` in the state directory with `date +%s`. Elapsed time is `date +%s` minus that, on the same machine, so it includes machine sleep - the rule is wall-clock - and a clock stepped backwards counts as zero.

**Past the hard cap every tool call is denied**, MCP tools included, because the hook is registered with no matcher. The one exception is `StructuredOutput`, which is how a schema-spawned run returns its result: denying it would leave such a run no way to end. The reason quotes the reviewer's invariant verbatim, `"Never let a break-mode run go past 20 minutes of wall-clock from your spawn."`, says how long the run has gone and tells it to stop calling tools and write its four-heading handoff from what it has, with unfinished mutations under Not done. The agent still gets a turn after each deny and needs no tool to write text, so `SubagentStop` still checks what it writes.

**Under the cap a Bash call's timeout is trimmed** to the time left, so a command started at 24:50 cannot hold the run to 35:00. The requested timeout is `tool_input.timeout`, else `BASH_DEFAULT_TIMEOUT_MS`, else the runtime's 120000 ms. If the time left is shorter, the hook returns `updatedInput` with `timeout` set to the time left, floored at 5000 ms, and every other field of the input unchanged; otherwise it returns nothing. The true ceiling is 25:05 plus the time the runtime takes to kill the command. It never sends a `permissionDecision` with the rewrite - see item 20.

**A resume keeps the first start.** A SendMessage resume fires `SubagentStart` again for the same agent id; the file is created with noclobber (O_EXCL), so the second start finds it and leaves it alone. The lead spawns a fresh break-mode reviewer on the Not done list rather than resuming a capped one.

**Missing state fails open and starts the clock.** A capped agent with no clock file at `PreToolUse` - a lost `SubagentStart`, a hook that timed out - has the call allowed and its clock started then, so the worst case is a late start. A file that will not parse, an unwritable directory and a missing `jq` allow the call and log why.

**Nothing is removed at `SubagentStop`**, because it fires before every resume too, and a deleted file would restart the clock. Clock files are about 60 bytes each and are never pruned, like `sessions/`.

**A brief that cannot be read is capped.** A reviewer whose brief cannot be found, has no user message on disk yet or carries a malformed `Modes:` line is treated as break mode on that call, and the log says so once per agent id (`clocks/<id>.nobrief`). Nothing is recorded for it, so the first call that reads the brief cleanly decides the run's mode from then on.

**The board does not govern it.** The hook does not source `lib/board.sh`, and it ignores `CODER_FLEET_BOARD=off` and the `disabled` file: the clock runs whether or not the board does.

## The reviewer's modes

The reviewer has three modes, and the lead's brief names them on one line: review, on every spawn; break, mutation testing, only on an authentication or credential path or in the harden phase; use, driving the running product against the card's acceptance criteria, only where `AGENTS.md` has an `App start:` line. Two hooks need to know which: the clock caps break mode and nothing else, and the scope hook gives break and use mode the outside-the-project write rule they need. A hook cannot ask the model, so `lib/reviewer-modes.sh` reads the brief.

**Where the brief comes from.** No hook event carries the spawn prompt. `SubagentStart` sends `agent_id` and `agent_type`, and every event's `transcript_path` is the session's own transcript, never the subagent's (read from the 2.1.322 bundle: the hook base input sets `transcript_path` from the session id). The runtime writes the subagent's transcript beside it, at `<session transcript without .jsonl>/subagents/agent-<agent_id>.jsonl`, or deeper for a workflow lane (`subagents/workflows/wf_<run>/agent-<agent_id>.jsonl`), and its first user message is the spawn prompt, which a live transcript confirmed. The lib finds that file from the two fields every event has.

**Why not the Agent call.** A `PreToolUse` hook on the Agent tool sees the prompt as structured input, which is cleaner to parse, but it fires before the spawn and carries no agent id the spawn will get, so there is nothing to key a record by; two spawns in one turn would race for it. And whether a workflow's `agent()` spawn passes through that hook at all was never shown (see Disabled agents). The brief on disk has neither problem.

**The signal.** Only the spawn prompt counts, and only its first five lines. A header line is one of those that looks like a mode line in any case or spacing; its format is closed: exactly `Modes: ` at column 0, then one or more of `review`, `break` and `use`, comma-separated with at most one space, nothing else but trailing whitespace. A brief with no header line is review only, the body's default. A malformed header, two header lines, no brief on disk, no user message yet, an agent id that is not plain `[A-Za-z0-9_-]` or no `jq` is unread, and each hook fails closed its own way: the clock caps the run, the scope hook gives review mode's narrow rule. A `Modes:` line lower in the prompt - quoted from a file, a diff, a handoff - is never read, and neither is a later user message, such as a SendMessage resume's.

**Sticky.** The first clean read is recorded in `modes/<agent_id>` under the state directory, created exclusively (noclobber) with mode 0600 in a 0700 directory, and both hooks answer from the record for the rest of the run, so a run cannot gain or lose break mode part way. A record in any other form than the lib writes is no answer: the clock caps. A record that is missing is not an answer either way; the brief is read again, so deleting the record gains the reviewer nothing while the brief is intact. An unread brief records nothing, because `SubagentStart` can fire before the prompt is on disk, and a recorded "unread" would cap a review run for good. The reviewer is refused writes to the state and transcript directories (Per-agent tool scoping, above); what a same-user agent can still do is in `docs/limits.md`.

Contract cases are in `claude/evals/lib/scope-hook-contract.sh`: the `clock-` cases for the cap, header position, closed format, stickiness, an unreadable brief and a workflow lane's transcript, and the reviewer cases for scope in each mode.

## Disabled agents

A project switches a fleet agent off by listing it in its main checkout's `.claude/coder-fleet.json`, by hand or with `/coder-fleet:agents`:

```json
{ "disabledAgents": ["researcher"] }
```

`enforce-disabled-agents.sh` runs at `PreToolUse` on the Agent tool. It finds the repository's main checkout starting from `CLAUDE_PROJECT_DIR` when that is a directory, and from the call's `cwd` otherwise - the first worktree `git worktree list --porcelain` names, asked with every git variable that could redirect it unset, and believed only when that checkout's own list names the starting worktree - and reads that checkout's file live through `lib/fleet-config.sh`. When no main checkout can be found that way (no git, no repository, a bare main, a `.git` file pointing at a repository that does not list the worktree) it reads no file at all and every agent is enabled; the starting directory's own copy is never a fallback. What the listing check does not catch is a forged worktree: a repository made for the purpose that registers the worktree itself passes, because the check asks that repository. Starting from `CLAUDE_PROJECT_DIR` is the defence, since a `cd` into such a worktree cannot move it; a session with the variable unset, where the `cwd` decides, is not defended. It denies a spawn whose `subagent_type` is listed, bare or `coder-fleet:`-prefixed; another plugin's agent of the same name is left alone. The reason names the agent and the file, tells the caller not to retry or run the agent's work in its place, and says how to re-enable it.

**The rules** are stated once, in `lib/fleet-config.sh`. No file or no `disabledAgents` key disables nothing. The file is one strict JSON value, as `JSON.parse` reads it, with no byte order mark and brackets nested no deeper than 64 levels; the shell parses it with python3's `json` module (`lib/fleet-config.py`), with NaN and Infinity refused and numbers never converted, because jq 1.6 accepted number forms such as `01` and `.5` that `JSON.parse` refuses. Without python3, or with a python3 on `PATH` that cannot run (the macOS developer-tools stub), the file is invalid and honours nothing, and the warning says python3 is missing or could not run rather than blaming the file. A name must be printable ASCII, is trimmed, lower-cased and loses any `coder-fleet:` prefix, in that order, then must look like an agent name. `lead`, `coder` and `reviewer` cannot be disabled. A file that breaks a rule - a core agent listed, broken JSON, a list that is not a list of strings - is invalid and honours nothing: every spawn is allowed and carries a `systemMessage` and `additionalContext` saying the file is invalid and why. `review-round` reads the same main-checkout file through its pin lane with the same rules, and `workflow-logic.mjs` runs both readings over one set of fixtures, comparing state, names and reason. A `refuter` or `evaluator` entry, left from before CF-192 folded both into the reviewer, keeps the file valid and disables nothing: `--check` warns about it like any name that matches no fleet agent, and `review-round` logs it and goes on.

**Read on every call.** Nothing is cached in the state directory or at session start, so an edit takes effect on the next spawn with no restart.

**Fails open.** No `jq`, input that is not JSON, or any other error allows the call and logs why.

**`--check [dir]`** validates the file in the main checkout of `dir`'s repository and exits 1 when it is invalid. `check-all.sh` runs it on the coder-fleet repo, which carries no copy, so in CI it can only pass; locally it checks the human's live copy. The contract test is what proves `--check` fails on an invalid file. A listed name that matches no fleet agent - a hand-edited `"researchr"`, or a `refuter` left from before CF-192 - gets a `warning:` line naming it and the fleet agents, and `--check` still exits 0: the file is valid, known entries are honoured, and the spawn hook's decisions do not change. The roster is `fleet_roster` in `lib/fleet-config.sh`, one agent per body under `agents/`, and `scripts/fleet-agents.sh` calls the same function.

Whether the hook sees a workflow's `agent()` spawn is untested, which is why `review-round` reads the list itself rather than relying on the deny. Contract: `claude/evals/lib/disabled-agents-contract.sh`.

## Security

- **There is no secret here.** The board is files under `~/.config/boards` reached by a local binary, so no hook reads a token and the installer renders none. The only network calls are the session-start binary fetch, the fast-forward's fetch and the test gate's `git ls-remote --tags origin`. **No hook ever calls `op`.** Design section 12 is explicit about why: it adds latency to every subagent start and stop, and a locked `op` silently stops the board updating.
- The board is the one the repository containing the hook's `cwd` reaches, by its origin URL or its git directory's path, so a hook fired inside a coder's worktree or the main checkout writes to the same board. Its private state - each checkout's focus and each spawn's binding - is under `$XDG_STATE_HOME/coder-fleet-boards` or `~/.local/state/coder-fleet-boards`, made 0700 and refused when it is a symlink or another user's.

## Failure behaviour

Every board write fails soft: logged, and the session goes on. A binary that will not run, a repository with no board, a card the gate holds - none of it stops a session.

Exactly one board hook exits 2: `SubagentStop`, when a typed stop's handoff does not parse, which sends the agent back to re-emit it. The card gate never blocks a stop or a task, and the test gate never holds a turn. The scope, disabled-agents and push-policy rules fail closed instead, because a rule that cannot be judged is not satisfied.

`../boards/README.md`, "Tests", says how the board's hooks are driven by hand and in tests.

## What breaks them

- **No board for the repository.** The hooks do nothing and SessionStart says so once per session; the human makes one with `boards init`.
- **No focus and no `Board-Item:` line.** The spawn binds to nothing and nothing moves, which is right for a scout and a silent gap for real work.
- **A `boards` binary that will not run.** `boards.sh` exits 127; the board hooks do nothing and the rule shims refuse.
- **Renaming or moving a script** without updating `hooks.json`. The paths there are literal.
- **Dropping the execute bit.** `git update-index --chmod=+x` if it happens.
- **Editing an agent's Invariants without editing `enforce-agent-scope.sh`.** The deny messages quote those invariants verbatim. If they drift apart, an agent gets told off for breaking a rule its body no longer states. The `migration-checklist` run is the place to catch that. `agent-clock.sh` quotes the reviewer's break-mode time invariant the same way.
- **A CLI that stops honouring `updatedInput` sent without a decision.** The Bash trim silently stops and the in-flight gap reopens; the deny still holds. Item 20 says how to re-check.

## Decisions this layer makes

Items 1 to 7, 11 and 14 describe the old board CF-1.5 removed - its focus file, column names, test command, card comments and comment cap - and are kept, numbered, because other documents cite items by number. The board's own decisions are in `../boards/README.md`.

The design specifies the board writes and the gates; the mechanics below are this layer's own decisions, recorded here so they are found rather than rediscovered.

1. **How a hook knows the item.** The `.boards/.focus` file per checkout, the `[board:<id>]` task-subject marker for completion, `CODER_FLEET_BOARD_PAGE_ID` for a scripted launch, and the state-file layout under `~/.local/state/coder-fleet/`. The design says the hook knows the item from the spawn context; this is what that means.
2. **The column names.** The status names and how the column labels are spelled in the board's config are this layer's choice, matched to the templates `/init` writes, and fixed: there is no override. The in-progress column alone is resolved per board: `SubagentStart` writes `In Progress` when the config lists it, including when it lists both, `Doing` when only that is listed, and nothing, with a log line saying so, when neither is. A move the board refuses is reported on the card rather than worked around.
3. **How "tests pass" is decided.** The command, then the marker file with its staleness window, then the lenient default. The design asserts the gate and never says what it reads.
4. **A comment on the card at every transition**, and where each one's text comes from. The design specifies a comment only for the `Blocker:` path. A card that says nothing but which column it is in is a status light, not a board.
5. **Where the overflow of a cut comment goes.** One file per cut comment under the state directory, at `archives/<session_id>/<stamp>-<agent>.md`, and the state directory rather than the working directory because a worktree agent's cwd does not survive its own session. See "What the card says" above; the handoff format is untouched.
6. **The `## Done` comment is posted from `SubagentStop` rather than `TaskCompleted`.** The design gives Done to `TaskCompleted`, which never receives a handoff, so the text is read where it exists and the column move stays where the design put it.
7. **A valid handoff with no blockers changes no column.** The design gives Done to `TaskCompleted`, so `SubagentStop` leaves the item in In Progress. It comments there; it does not move it.
8. **The handoff check** tolerates preamble prose, which is unparsed. Everything else in the skill is enforced strictly, including the blank-line rule and where a typed line may appear. See above for why.
9. **`cd`, `pwd`, `echo`, `true` and `read`** on scout's Bash allowlist, the `for` header read as syntax, and the quote-stripping and `2>/dev/null` softenings.
10. **`fleet-steward`'s repo-root resolution** by walking up from the plugin directory, and the git verb list, which is read off its Invariants prose.
11. **Which CLI calls a column move and a comment are made of**, and the ten-second timeout around each. The design names the board and not the commands; `board task view --json`, `board task edit -s`, `board task edit --comment --comment-author`, `board task edit --action=<ask>` for each Blocker's ask, and the `board task list --status <name> --limit 1` probe `SubagentStart` uses to ask whether the config lists a column, are this layer's choice, as is using the hook's own name (`@SubagentStop` and so on) as the comment author.
12. **The `SubagentStop` matcher.** The design gives the hook to every subagent. Scoping it to the fleet agents but the lead is this layer's decision, because the workflows spawn `general-purpose` lanes that return JSON.
13. **`reviewer` and `ui-designer` scoping rules**, including the read-only git allowlist both share and the install-verb matching that keeps `ui-designer` able to build and serve a prototype.
14. **The comment length cap.** `BOARD_COMMENT_MAX_CHARS`, its default of 8000 and the `BOARD_COMMENT_HARD_MAX` clamp. A task file imposes no limit a card comment would meet, so where to cut is this layer's choice, made for the reader; see "Comment length" above.
15. **The event field names come from the shipped CLI, not the docs.** The docs pages truncate before the event sections, so the hooks read the fields the zod schemas in the binary define:

    | Event | Fields |
    |---|---|
    | `TaskCompleted` | `task_id`, `task_subject`, `task_description?`, `teammate_name?`, `team_name?` |
    | `SubagentStart` | the common fields, `agent_id`, `agent_type` |
    | `SubagentStop` | `stop_hook_active`, `agent_id`, `agent_transcript_path`, `agent_type`, `last_assistant_message?`, `background_tasks?` |

    `task_title`, `task_name` and `completion_reason` appear nowhere in the binary. Three consequences:

    - `board-task-completed.sh` reads `task_subject` for the `[board:<id>]` marker, and nothing else.
    - `board-subagent-start.sh` has no spawn prompt to read, so the `Board-Item:` route never fires; the focus file is the binding.
    - `board-subagent-stop.sh` reads no status. See `docs/limits.md`. A `Blocker:` line in the handoff routes to Blocked by human, and `TaskCompleted` is the only writer of Blocked.

    To re-derive this after a CLI upgrade:

    ```sh
    strings -a "$(readlink -f "$(command -v claude)")" \
      | grep -o 'hook_event_name:"TaskCompleted".\{0,200\}'
    ```

    `claude/evals/lib/board-hook-contract.sh` pins all of it.

16. **Structured output carries no handoff, and the hook tells that apart from an empty one.** A subagent spawned from a workflow with `agent(prompt, {agentType, schema})` is forced through StructuredOutput, and its `SubagentStop` payload **omits `last_assistant_message` entirely**. Not the JSON in that field, not an empty string: the key is absent.

    | Spawn | `last_assistant_message` |
    |---|---|
    | with `schema` | key absent |
    | without `schema` | the Markdown handoff |

    Reading `.last_assistant_message // ""` would erase the difference between *absent* and *empty* and fail `validate_handoff` on every schema spawn. Since the `SubagentStop` matcher covers every fleet name but the lead, and every workflow spawns fleet agents with schemas - `scout` and `reviewer` in `review-round.js`, `researcher` at five sites in `deep-research.js`, `scout` and `spec-writer` in `spec-to-card.js` - the gate would refuse to let those runs stop. Item 12 scopes the matcher away from the built-in lanes; it cannot reach a schema-carrying agent which is itself a fleet agent, so the hook separates the two cases once, at the read:

    ```sh
    has_message="$(printf '%s' "$input" \
      | jq -r 'if has("last_assistant_message") and .last_assistant_message != null
               then "yes" else "no" end')"
    ```

    Absent, or JSON `null`, means there is no handoff to check, so the gate does not fire and the column is left alone - `TaskCompleted` owns Done, and a card that invents a comment out of structured output nobody parsed is worse than a card that says nothing. Present-but-empty still fails, because that is an agent which was asked and said nothing, and it is the thing the gate exists to catch. `claude/evals/lib/board-hook-contract.sh` pins all three cases - `stop-structured-run-passes`, `stop-empty-message-blocks`, `stop-prose-blocks` - so a softening of the gate has to walk past two tests that say no.

    Fields item 15's table does not list, all present on a real event:

    | Event | Additional fields observed |
    |---|---|
    | `SubagentStart` | `cwd`, `prompt_id`, `session_id`, `transcript_path` |
    | `SubagentStop` | `cwd`, `effort`, `permission_mode`, `prompt_id`, `session_crons`, `transcript_path` |

    `agent_type` is bare on the probe agent's event (`probe-worker`) and arrives with the `coder-fleet:` prefix for a fleet agent (item 20), so `agent-clock.sh` and the scope hook strip everything up to the last colon. `cwd` is a supported route to the directory a subagent actually worked in.

    **Absent does not prove why, so the hook asks the transcript.** The runtime builds the field as

    ```js
    let p = findLast(m => m.type === "assistant"),
        f = p ? textOf(p.message.content).trim() || void 0 : void 0
    ```

    `.trim() || void 0` turns an empty *or whitespace-only* final message into `undefined`, and undefined properties drop out of the payload. So `last_assistant_message: ""` is **unreachable** - a fleet agent that was asked for a handoff and produced nothing sends a byte-identical payload to a schema spawn. Passing every absent field would retire the gate for exactly the case it exists to catch, so `agent_transcript_path` is read to tell them apart:

    | Last assistant content block | Means | Hook does |
    |---|---|---|
    | `tool_use` named `StructuredOutput` | a schema run, never asked for a handoff | passes, column untouched |
    | `text` | the runtime dropped a message the transcript still holds | recovers it and validates it like any other |
    | `tool_use` with any other name, or `thinking` | the agent stopped mid-turn, with no closing text to validate | passes unchecked, as intended, and says the transcript could not be read (`stop-transcript-trailing-tool-passes`) |
    | unreadable, oversized, absent, or no assistant content | cannot tell | passes, and says so |

    Read `agent_transcript_path`, never `transcript_path`: the event sends both and only the first is scoped to the subagent. The last two rows are the residual gap and it is deliberate - a transcript this hook cannot classify is not a reason to refuse to let a subagent stop, because deadlocking a run is worse than a rare silent pass. `CODER_FLEET_TRANSCRIPT_MAX_BYTES` caps the read at 20 MB. The reader, `transcript_final_block`, takes the last assistant block first and classifies it after, so anything but a StructuredOutput call or text falls to the same pass as an unreadable file; reaching back past a trailing tool call to an earlier text block would validate prose that was never a handoff. No contract case feeds a trailing `thinking` block; it takes the same `else empty` branch as the tool call.

    This table is the whole account of which typed stops are checked. A stop with an event message is validated as it stands, and the transcript is never read: the StructuredOutput exemption applies only when the event carries no message, so a schema run that also sent text is held to the handoff. Two passes come before any of it. Without `jq` the hook logs that it cannot run and exits 0; no contract case covers that, because the suite itself needs `jq`. A stop with no `agent_type` is not a fleet agent and exits 0 unchecked (`stop-untyped-stands-down`, item 19).

    To re-derive after a CLI upgrade, spawn one agent twice from a workflow - once with a `schema`, once without - behind a `SubagentStop` hook that dumps its stdin, and diff the two payloads. The control spawn is the point: an empty dump alone cannot distinguish "StructuredOutput ate the message" from "the hook never fired".

17. **The git verb is found past the global options.** Reading the subcommand as the second whitespace-separated token would resolve `git -C /path log` to a verb of `-C`, and the parser and the shell would disagree about where the verb is. That breaks in both directions at once depending on how each role's check is written:

    | Role | Check shape | Unrecognised verb | Result |
    |---|---|---|---|
    | `scout`, `reviewer`, `ui-designer` | allowlist | denies | **false deny** - `git -C <worktree> diff` refused |
    | `fleet-steward` | denylist | allows | **false allow** - `git -C /path push --force` passes |

    `git_verb()` finds the real verb. Every git global option is dashed and a verb never is, so it skips dashed tokens and skips the value of the eight that take a separate argument (`-C`, `-c`, `--git-dir`, `--work-tree`, `--namespace`, `--exec-path`, `--super-prefix`, `--config-env`). A segment with no undashed token yields the empty string, which matches no allowlist and no denylist entry, so `git -C /path` on its own is not a read.

    It also collapses backslash-escaped pairs before splitting. Quoted paths never arrive unsplit - the quote stripper runs first - but escapes do, and `git -C /tmp/a\ b reset --hard` would otherwise resolve its verb to `b`. Nothing downstream reads the path, only the verb, so replacing each escaped pair with one ordinary character keeps the path a single token without pretending to know what it says.

    `claude/evals/lib/scope-hook-contract.sh` pins both directions: the reads that must work, and every forbidden verb that must stay forbidden when a `-C`, a `-c`, a `--no-pager` or an escaped space is put in front of it.

    This does not make the scope hook a containment boundary. A program run through Bash writes wherever the process can, and no shell-level check sees inside it.

18. **coder writes in its own worktree, or it does not write.** The one preventive check in the fleet, and the backstop behind the worktree `review-round` cuts for its fix lane.

    `coder` carries `isolation: worktree`, and the harness honours it for an Agent-tool spawn. Workflow-spawned agents get no harness isolation: a workflow `agent()` call with `agentType: 'coder-fleet:coder'` starts in the main checkout (observed in a live `review-round` run, `docs/decisions/claude-code-behaviours.md`, "Agent worktrees"), with this guard the only thing between the fix-lane coder and main. `review-round` compensates: a git lane cuts a linked worktree on a new branch at the pinned head before the coder exists, the run stops with no coder spawned if the lane cannot vouch for it, the coder's prompt tells it to work only there through `git -C` and absolute paths, and the fix gate refuses a commit git does not find on that worktree's branch. That is still the workflow asking and then checking: the prompt is an instruction, and the verification can only *detect* a fix that landed elsewhere after the coder has committed. But `coder` has an `agentType`, so this hook governs its Bash calls, and git answers the question directly: a linked worktree's git dir sits under `.git/worktrees/`, a main checkout's does not.

    ```
    $ git -C <linked worktree> rev-parse --absolute-git-dir
    /repo/.git/worktrees/fix-r1
    $ git -C <main checkout> rev-parse --absolute-git-dir
    /repo/.git
    ```

    So a git command that **writes** - the verbs in `CODER_WRITING_GIT` - is refused unless its target directory can be shown to be a linked worktree. The target is the command's own `-C` where it has one, otherwise the directory the segment runs in: the tool call's `cwd`, or the directory of a leading `cd`, so `cd <repo> && git commit` is judged against `<repo>` exactly as the `-C` form is. The guard does not model the shell beyond that one shape (`cd_shape_ok`): a writing git command in a command that also holds a `cd`, `pushd` or `popd` is allowed only as `cd <path> && ... && git <verb>`, with one cd, no option, a path starting with `/`, `./` or `../`, and only `&&` between. `cd -P <main> && git commit` would bypass a looser model, because the option is skipped while the shell still moves, and `true || cd <wt>; git commit`, `( cd <wt> ); git commit`, `cd -` and zsh's `cd old new` all leave the model and the shell in different places. The one writing verb allowed from a main checkout is `git worktree add`, because it creates the isolation this check requires rather than breaking it, and it is how a coder gets a worktree in a repository the harness did not cut one in; `worktree remove`, `prune` and `move` stay governed. Reads are untouched, and so is everything that is not git: `git log`, `git diff`, `npm test` and `pytest` all run in a main checkout. This enforces `coder.md`'s own second step, which says to confirm the worktree before touching anything.

    **Not being able to tell is not permission.** A directory that is not a repository at all is refused too, on the grounds that a git write there would fail anyway and that the case this exists for - isolation silently not happening - is precisely the case where nothing announces itself.

    **Know what this costs.** A `coder` with no linked worktree is **blocked from every writing git command** rather than quietly committing to the checkout it happens to be in. That is the intended failure and the right one, but it is a stop rather than a slow leak: when coder raises blockers about worktrees, this hook is why, and the answer is to fix isolation rather than to remove the check. `worktree.baseRef` defaults to `fresh`, which branches from `origin/<default-branch>` and leaves a worktree behind an unpushed local main; the project settings template sets `"head"` so worktrees are cut from the local HEAD, and `/init` writes it and `/kickoff` offers it to a project still on the default. A type-isolated coder spawn is cut at the local HEAD even with local main ahead of `origin` (`docs/decisions/claude-code-behaviours.md`, "Agent worktrees"), and `review-round`'s fix lane cuts its own worktree at the pinned head; that cut is unobserved in a live run, and `docs/limits.md` carries it.

20. **A break-mode reviewer is stopped at 25 minutes, from a hook of its own.** The human's rule was first that a refuter must not run past 20 minutes and a hook stops it at 25; since CF-192 folded the refuter into the reviewer it is a break-mode reviewer, and the mode comes from the brief ("The reviewer's modes"). "Per-agent time caps" above describes the behaviour; this item records why it is built the way it is.

    **Not in the scope hook.** `enforce-agent-scope.sh` is matched on `Write|Edit|MultiEdit|NotebookEdit|Bash`, so Read, Grep, Glob and every MCP call never reach it. Widening its matcher to every tool would put its JSON validation, five `jq` calls and quote recovery on every call of every agent and the main session, and would tie the cap to its 10-second timeout; `docs/limits.md` lists command shapes that blow that timeout, and a hook that times out gives no decision, so the cap would vanish on exactly those calls. `agent-clock.sh` has no matcher, exits before `jq` when the input carries no `agent_id` (the main session), makes one `jq` call otherwise, and has a 5-second timeout. When parallel `PreToolUse` hooks disagree, deny wins: Claude Code folds decisions as `case"deny":vo="deny"` ahead of ask and allow (read from the 2.1.283 bundle).

    **The trim relies on behaviour the documentation contradicts.** code.claude.com/docs/en/hooks says "Without a decision, `updatedInput` is ignored". Claude Code does this instead (read from the 2.1.283 bundle):

    ```js
    if(Ee.updatedInput&&Ee.permissionBehavior===void 0)yield{type:"hookUpdatedInput",...}
    // consumed as
    case"hookUpdatedInput":ze=vo.updatedInput
    ```

    before the normal permission decision runs on the rewritten input, which is schema-checked with `n.inputSchema.safeParse`; a failure is a deny. So the trim sends `updatedInput` and no `permissionDecision`, and the rest of the permission flow still applies. The bundle also sets the Bash default at 120000 ms (or `BASH_DEFAULT_TIMEOUT_MS`), clamps a requested timeout to `max(600000, BASH_MAX_TIMEOUT_MS)` rather than rejecting it, has no minimum, and auto-backgrounds a timed-out command only when `isMainAgent`, so a subagent's command is ended rather than backgrounded. That last point is a reading of the bundle, not observed live.

    **Never `"allow"` with the rewrite.** The docs say `"allow"` "bypasses both deny and ask rules in settings", which would wave a break-mode reviewer's Bash calls past the `curl`, `sudo` and destructive-git denials in `claude/home/settings.json`. Contract case `clock-bash-trimmed` asserts the rewrite carries no `permissionDecision` key.

    **Resume evidence.** A SendMessage resume re-fires `SubagentStart` for the same agent id, and a fleet agent's `agent_type` arrives with the `coder-fleet:` prefix (observed in `hooks.log`: one `coder-fleet:spec-writer` id started six times and one `coder-fleet:coder` id three times). So the hook strips everything up to the last colon, as the scope hook does. Keying the clock by agent id alone, written once, is what keeps a resume from resetting it; `bound_at` in `sessions/` cannot serve: it is ISO text that macOS `date` cannot parse portably, and it is keyed by session.

    **`SubagentStop` still lets a capped reviewer end.** After a deny the model gets the tool result and another turn, and needs no tool to write text. A valid handoff exits 0; a malformed one exits 2 with the reasons and the fix is text-only again; a run that stops on a trailing denied `tool_use` passes unchecked, per item 16's table. A capped reviewer that keeps writing malformed handoffs is sent back at most `CODER_FLEET_HANDOFF_REEMIT_CAP` times (item 27), or once by `stop_hook_active` when it has no agent id or its count cannot be written, and each re-emit is text-only. A capped reviewer spawned with a `schema` ends by calling `StructuredOutput`, not by writing text, so the hook never denies that tool.

    **Timeouts are floored in `jq`.** jq 1.7 prints an unmodified number the way it was written, so a timeout of `600000.0` or `6e5` would reach the shell as `600000.0` or `6E+5`, the integer comparison would error, and the call would escape the trim. `floor` makes a new number, which every jq prints canonically, and the shell treats anything but plain digits as no timeout.

    **Contract cases**, in `claude/evals/lib/scope-hook-contract.sh`, driven through `/bin/bash` so macOS exercises bash 3.2: `clock-start-records`, `clock-start-prefixed`, `clock-start-board-off`, `clock-start-others`, `clock-resume-keeps-first`, `clock-under-cap-<tool>`, `clock-edge-allows`, `clock-over-cap-<tool>` (MCP included), `clock-over-cap-prefixed`, `clock-reason`, `clock-others-unaffected-<agent>`, `clock-main-session`, `clock-missing-starts-late`, `clock-corrupt-allows`, `clock-bash-far-untouched`, `clock-bash-trimmed`, `clock-bash-default-trimmed`, `clock-bash-env-default`, `clock-bash-short-untouched`, `clock-bash-floor`, `clock-bash-other-agent`, `clock-over-cap-structured-output-allowed`, `clock-invariant-in-body`, `clock-typed-no-agent-id`, `clock-no-jq-allows`, `clock-main-session-skips-jq`, `clock-unwritable-state-allows`, `clock-bash-timeout-<literal> (<jq version>)` for every jq on the machine, `clock-registered` and `clock-executable`. It needs both, because each one alone also describes a real agent. The start hook writes no record when it cannot read the focus (the board is off, or there is no board here), and a real run's transcript exists while it runs, so neither signal alone is safe. What the shape check gives up: a real agent whose start left no record and whose transcript is missing at its stop is let go unchecked. A real transcript is on disk mid-run (observed); whether it is there at the moment of the stop is unmeasured. A stop with no agent id is always gated. A malformed handoff earns exit 2 at most `CODER_FLEET_HANDOFF_REEMIT_CAP` times per agent, 3 unless set. The count is kept in `agents/<agent_id>.reemits` and is cleared by a valid handoff and by the stop the cap lets go, so a SendMessage resume starts fresh. With no agent id, or a count that cannot be written, `stop_hook_active` allows one re-emit. A stop let go either way is logged, and when the agent is bound to a card it gets a comment there, through the ordinary comment path. The comment names the agent type, says the handoff was still malformed and quotes any `Blocker:` line in the final message wherever it sits; nothing moves, because a Blocker read out of a malformed handoff is a guess. Every line the stop hook logs carries `session=<id> cwd=<path>` inside its bracketed tag, the library's lines included, by wrapping `board_log` in the hook rather than changing the library; control characters are stripped from both values so a crafted one cannot forge a log line. `CODER_FLEET_HOOK_DUMP=<dir>` copies each raw event into that directory, made 700 with each file 600, and writes nothing when unset; it is off by default and kept for the next stop the log cannot explain.
