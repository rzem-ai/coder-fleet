## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Sub-issue 1 of 3 of CF-183. Read CF-183's description and decision comment first.

The board binary's root resolution (hooks/lib/board.sh:417 says it finds "the main checkout's .boards/ of the repository containing its working directory") and its one commit routine, commitBoard in claude/coder-fleet/board/src/git/operations.ts, move to a dedicated state worktree on its own branch. Default on for every project (Alex's decision), so the migration on first use is the risky part.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 Every board write the binary makes - CLI, MCP, hooks, web UI - reads and writes the state worktree's .boards and auto-commits on the state branch, never on the default branch or a feature branch, whichever checkout or linked agent worktree it is run from; a test with a real linked worktree pins it
- [ ] #2 Every reader (hooks, MCP server, web UI, board.sh) resolves the same live board from the main checkout, the state worktree and an agent worktree
- [ ] #3 In a project without a state worktree, the first board write creates it and moves the live board into it, losing no uncommitted or unpushed .boards change from the main checkout; a test pins a migration with uncommitted and unpushed board changes present
- [ ] #4 A migration that fails leaves the board readable and writable where it was and logs the reason to hooks.log; a test pins one failure path
- [ ] #5 /coder-fleet:init and /coder-fleet:kickoff create the state worktree up front, and prune-worktrees never removes it
- [ ] #6 docs/board-config.md and help-boards say where board writes go and that they reach the default branch only through CF-183.3's flush; docs/limits.md drops the entries about local main carrying unpushed board commits
<!-- AC:END -->
