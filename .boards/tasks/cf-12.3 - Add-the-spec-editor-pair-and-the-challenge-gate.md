## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Part of CF-12 (spec docs/specs/CF-12.md, approved 2026-09-29 after the CF-59 revision: Decisions Q2, Q5, Q14, Q15, Q18 to Q21; "The four agents", "The challenge notation", "Which workflow runs the gate", "The Fable rule"). This item adds spec-editor and spec-editor-fable, generated from claude/agent-pairs/spec-editor.md (CF-12.2's generator). The editor reads spec-writer's revised draft adversarially, before the human edits it. It writes challenges into a "## Challenges (spec-editor)" section with inline markers and never rewrites prose. One shared gate script runs from lead.md step 3 before the first build spawn on an item, and from spec-to-card's card stage before it files criteria. A project with no editor record gets no gate and a /kickoff suggestion. The item carries its own roster rows and the design's bounded Fable exception.

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 `bash claude/evals/lib/check-all.sh` passes on the branch, and `roster-contract.sh` checks all thirteen bodies with no existing check weakened.
- [ ] #2 `spec-editor` and `spec-editor-fable` have `effort: medium`, `maxTurns: 15`, models `opus` and `fable`, a single-line tools allowlist with no `Bash`, `WebSearch` or `WebFetch`, and memory write tools under `disallowedTools`. The PR carries the `migration-checklist` findings for both.
- [ ] #3 Both spec-editor bodies tell the agent to make its next turn the four-heading handoff, with the unfinished work under Not done, when its turn budget is nearly spent. The instruction is checked at review by reading both bodies; no eval or contract greps for it (the human's decision of 2026-10-07, per the CF-145 rule in AGENTS.md).
- [ ] #4 The scope hook denies either spec editor a write or edit outside `docs/specs/`, and any Bash command. Each is proven by a scope-hook contract case that failed before the change.
- [ ] #5 After a `spec-editor` run the draft carries a `## Challenges (spec-editor)` section in the spec's notation, every challenge line `[open]`, and every other line byte-identical to the input apart from appended inline markers, checked in the spec-editor eval's `checks.sh` by diffing the draft with the section and markers stripped.
- [ ] #6 Every inline marker in the draft names a challenge that exists in the section, and every challenge line has an id, one of the three severities and a state.
- [ ] #7 `spec-editor`'s handoff lists its challenges grouped by severity, and never contains a `Blocker:` line for a challenge.
- [ ] #8 The spec-editor eval has three to five prompts, each a draft with planted flaws, that across the set must catch an acceptance criterion that cannot fail, an unmarked guess, a contradiction between non-goals and criteria, and a claim about the codebase the draft does not cite; one prompt is a sound draft that should draw no must-resolve challenge.
- [ ] #9 One shared gate script is covered by deterministic fixtures in a contract under `claude/evals/lib/`, none reading git history, that pass on: every must-resolve line `[resolved]`; a `[struck: <reason>]` with a non-empty reason; only `[should resolve]` and `[note]` lines open; the closed-marker line; no section where the project answered "neither".
- [ ] #10 The gate contract has a fixture for a project whose `AGENTS.md` records no editor answer and whose spec has no section and no closed marker: the gate passes, does not refuse, and its output suggests `/kickoff`.
- [ ] #11 The gate contract has fixtures that refuse, each naming every blocking challenge id where there is one: a `[struck: ]` with an empty reason; a must-resolve line still `[open]`; a must-resolve line whose state tag was deleted; no section and no closed marker where the project records Opus or Fable for the spec editor; a section deleted by hand.
- [ ] #12 The gate contract has a close fixture: after the gate passes on an intact section, the closed spec has the closed-marker line, no other Challenges content and no `[challenge Cn]` marker, and every other line is byte-identical to the gated spec.
- [ ] #13 When the gate passes on an intact section, the close lands as a commit touching only the spec file, subject "Close the challenges on <issue>", and the `<sha>` in its closed marker names a commit whose copy of the spec holds the intact, gate-passing section.
- [ ] #14 `lead.md` step 3 runs the shared gate script before the first build spawn on an item: on an intact passing section it closes and commits, then spawns; on a closed marker, a "neither" answer or no recorded answer it spawns with no new commit; otherwise it refuses to spawn and names the blocking challenge ids.
- [ ] #15 A `workflow-logic.mjs` test shows `spec-to-card`'s card stage, given a spec with an open must-resolve challenge, files nothing onto the card and names the blocking challenge ids.
- [ ] #16 A `workflow-logic.mjs` test shows `spec-to-card`'s card stage, given an intact spec that passes the gate, runs the close and commits it before it files any criterion.
- [ ] #17 A `workflow-logic.mjs` test shows `spec-to-card`'s card stage never files a criterion carrying a `[challenge Cn]` marker, and `spec-to-card` runs the same shared gate script as `lead.md` step 3, with no copy of the gate logic of its own.
- [ ] #18 `lead.md` step 2 spawns the project's chosen spec editor once per spec, after `spec-writer`'s interview revision and before the human edits; when `AGENTS.md` records no editor answer it spawns none and suggests `/kickoff`. The lead's model invariant is unchanged.
- [ ] #19 `docs/fleet-design.md` states the Fable exception with the four bounds, limited to `spec-editor-fable` and `tech-editor-fable`, and has the two spec-editor roster rows; no sentence in it or in `lead.md` step 4 still says Fable is never a subagent model without the exception.
- [ ] #20 `spec-editor` and `spec-editor-fable` are generated from `claude/agent-pairs/spec-editor.md` by `gen-agent-pairs.sh`, and `gen-agent-pairs.sh --check` passes.
