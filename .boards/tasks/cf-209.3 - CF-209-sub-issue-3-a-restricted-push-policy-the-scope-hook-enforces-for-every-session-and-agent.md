## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Make "only my branch is ever pushed" and "this project does not release" things the plugin refuses to break, not things an agent is asked to remember. With `push` unset or `all` and `release` unset, nothing changes.

What the hook does today (`claude/coder-fleet/hooks/enforce-agent-scope.sh`): a coder or scripter may run any writing git verb, `push` included, from a linked worktree, with no check on the remote, the branch or force (`:2407`, `:2481-2502`). fleet-steward may push anything but a force-push or a push naming `main`/`master` (`:1437-1445`). The reviewer and scout cannot push at all (`:2364`, `:2547`, `:693-712`). The scout found no rule governing the lead's own pushes, and nothing executable opens a pull request or creates a tag: the lead runs `git` and `gh` itself from `lead-procedures` Shipping. So the lead's own session has to be covered too, which is new ground for this hook, and this sub-issue's builder confirms first whether the hook can see the lead's Bash calls at all. Contract: `claude/evals/lib/scope-hook-contract.sh`.

What `push: base-only` refuses (the human's answer, CF-209 comment 2): `git push` in any form (`git -C <path> push`, a refspec, `--all`, `--mirror`, `--tags`) that would send anything but the base branch or an allowed version tag; `gh pr create`; and any push of the base branch with force or delete. What it allows: the lead's plain push of the base branch. Builders - coder, scripter, fleet-steward - never push under it, the base branch included.

How `release` crosses it (CF-209 comment 5). The two settings are independent, so there are two rules:
- `release: off` refuses creating a tag, pushing a tag and `gh release create`, whatever `push` is.
- `release: tag` or `github` under `push: base-only` lets one more thing through for the lead: a push of a single annotated tag named `vMAJOR.MINOR.PATCH` that points at a commit on the base branch. `gh release create` is allowed only under `github`, and only for a tag that already exists.
- `release` unset leaves tags as they are today under `push: all`, and under `push: base-only` is treated as `off`, since a tag is a push the human did not grant.

This is a permission rule on a path that writes to a remote the human does not control, so its review is the deeper one and names break mode.

The state branch. Until CF-207 group G ships, `hooks/state-push.sh` still pushes `coder-fleet/state` on its own, outside the scope hook. This sub-issue closes that gap with the smallest change that holds: under `push: base-only` `state-push.sh` pushes nothing and logs why. That one guard is deleted with the file when CF-207 removes it; if group G lands first, criterion 6 is void.

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 With `push: base-only`, a `git push` that names or implies any ref other than the base branch or an allowed version tag - an item branch, `--tags`, `--all`, `--mirror`, a bare `git push` from a branch that is not the base branch, and the `git -C <path> push` form of each - is refused, with a message naming the `push` setting and the base branch.
- [ ] #2 With `push: base-only`, `gh pr create` is refused with the same message, in the lead's session and in every agent.
- [ ] #3 The refusals hold for the lead's own session as well as for coder, scripter and fleet-steward, and `scope-hook-contract.sh` has a deny case for each of the four.
- [ ] #4 With `push: base-only`, the lead's plain push of the base branch is allowed, a force-push, `--force-with-lease` or `--delete` of it is refused, and a push of the base branch by coder, scripter or fleet-steward is refused.
- [ ] #5 An invalid or unreadable `push` value is enforced as `base-only` and an invalid or unreadable `release` value as `off`, and a contract case pins each.
- [ ] #6 With `push: base-only`, `hooks/state-push.sh` pushes nothing and logs the reason, covered by a case in `state-push-contract.sh`; with `push` unset it pushes as today.
- [ ] #7 With `push` unset or `all` and `release` unset, every existing case in `scope-hook-contract.sh` and `state-push-contract.sh` passes with no expectation changed.
- [ ] #8 With `release: off`, `git tag` creating a tag, any push of a tag and `gh release create` are each refused in every session and agent whatever `push` is, with a message naming the `release` setting.
- [ ] #9 With `push: base-only` and `release` at `tag` or `github`, the lead's push of one annotated tag named `vMAJOR.MINOR.PATCH` pointing at a commit on the base branch is allowed, and refused when the tag is lightweight, is named otherwise, points at a commit not on the base branch, or is pushed by any agent but the lead.
- [ ] #10 `gh release create` is allowed only with `release: github`, only in the lead's session and only for a tag that already exists; with `release: tag` it is refused naming the setting.
- [ ] #11 With `push: base-only` and `release` unset, tag creation and tag pushes are refused as under `off`, and the message says to set `release`.
<!-- AC:END -->
