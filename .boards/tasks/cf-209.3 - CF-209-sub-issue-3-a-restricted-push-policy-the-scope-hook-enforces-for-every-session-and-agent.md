## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Make "only my branch is ever pushed" something the plugin refuses to break, not something an agent is asked to remember. With `push` unset or `all`, nothing changes.

What the hook does today (`claude/coder-fleet/hooks/enforce-agent-scope.sh`): a coder or scripter may run any writing git verb, `push` included, from a linked worktree, with no check on the remote, the branch or force (`:2407`, `:2481-2502`). fleet-steward may push anything but a force-push or a push naming `main`/`master` (`:1437-1445`). The reviewer and scout cannot push at all (`:2364`, `:2547`, `:693-712`). The scout found no rule governing the lead's own pushes, and nothing executable opens a pull request: the lead runs `gh` itself from `lead-procedures` Shipping. So under a restricted policy the lead's own session has to be covered too, which is new ground for this hook. Contract: `claude/evals/lib/scope-hook-contract.sh`.

What a restricted policy refuses: `git push` in any form (`git -C <path> push`, a refspec, `--all`, `--mirror`, `--tags`, a tag name) that would send anything but the base branch; `gh pr create`; and any push of the base branch with force or delete. Whether a plain push of the base branch itself is allowed is the human's answer to the parent card's Actions for Human, and decides whether there is one restricted value or two.

This is a permission rule on a path that writes to a remote the human does not control, so its review is the deeper one and names break mode.

The state branch. Until CF-207 group G ships, `hooks/state-push.sh` still pushes `coder-fleet/state` on its own, outside the scope hook. This sub-issue closes that gap with the smallest change that holds: under a restricted policy `state-push.sh` pushes nothing and logs why. That one guard is deleted with the file when CF-207 removes it.

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 With `push` restricted, a `git push` that names or implies any ref other than the base branch - an item branch, a tag, `--tags`, `--all`, `--mirror`, a bare `git push` from a branch that is not the base branch, and the `git -C <path> push` form of each - is refused, with a message naming the `push` setting and the base branch.
- [ ] #2 With `push` restricted, `gh pr create` is refused with the same message, in the lead's session and in every agent.
- [ ] #3 The refusals hold for the lead's own session as well as for coder, scripter and fleet-steward, and `scope-hook-contract.sh` has a deny case for each of the four.
- [ ] #4 A push of the base branch itself is allowed or refused exactly as the human's recorded answer on CF-209 says, and where it is allowed a force-push, `--force-with-lease` or `--delete` of it is still refused.
- [ ] #5 An invalid or unreadable `push` value is enforced as the restricted policy, and a contract case pins it.
- [ ] #6 With `push` restricted, `hooks/state-push.sh` pushes nothing and logs the reason, covered by a case in `state-push-contract.sh`; with `push` unset it pushes as today.
- [ ] #7 With `push` unset or `all`, every existing case in `scope-hook-contract.sh` and `state-push-contract.sh` passes with no expectation changed.
