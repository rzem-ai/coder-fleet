# Reviewing CF-41's prune-worktrees script

2026-09-27, reviewer, CF-41: read the scripted `/coder-fleet:prune-worktrees` for ways to delete the wrong thing, and found the biggest risk outside the parts the brief pointed at.

## What the run was

A first-round review of `cf-41-prune-script`. The branch turns the prune command's prose into `claude/coder-fleet/scripts/prune-worktrees.sh` plus an 84-assertion contract. The brief pointed at the scratch sweep, because a hand-rolled `grep -qx "$n"` had once deleted live worktrees' scratch.

## What was tried and abandoned

- **Linux `tr`:** the review started by suspecting that GNU `tr` on ubuntu CI would treat the `'--'` in `tr '/.' '--'` as end-of-options, since GNU getopt permutes arguments. Dropped: coreutils `tr` parses in POSIX order, and even if it did not, `enc()` would return empty, every entry would read as live, and nothing would be deleted. The failure would show up as a red CI run, not as data loss. It stays unverified until CI runs on the branch.
- **Mid-delete refusal:** time went on what happens when `git worktree remove` fails partway through. It matters for the command's prose, but the harm is limited: by then the worktree had passed the clean and merged checks.
- **Blocked commands:** the scope hook stopped `git ls-tree`, `git worktree list`, `ps` and `gh`. Reading `.git/worktrees/*/locked` directly with `grep` answered the question those would have answered.

## What the constraint turned out to be

The worktree lock, not the sweep. The sweep's comparisons are clean. The plan's premise, "the harness locks what it cuts", came from an earlier observation. The repository on the day showed the harness locks a worktree only while its agent runs, with the pid in the reason (`claude agent <id> (pid N start <date>)`); every finished worktree was unlocked. So the one signal that says "in use" is exactly what the script threw away before removing, and any freshly cut coder worktree passes every other check: it is clean and its HEAD is an ancestor of main.

## What to do differently

Read the harness's on-disk state before trusting a plan finding about it. One `grep -r . --include=locked .git/worktrees` would have changed the plan's decision 6. The next reviewer of a destructive script should ask which of its inputs a concurrent process writes, not only whether its comparisons are quoted.
