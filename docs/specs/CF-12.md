## Problem

Two passes in the fleet have no dedicated agent:

- **A spec gets no adversarial read.** It goes from `spec-writer`'s revised draft straight to the human, and nothing between them tries to break it before the human edits and approves it. `refuter` does that for code - "a green review is a claim, not evidence" (design section 4). A spec has no equivalent, so an untestable acceptance criterion, a guess left unmarked or a non-goal that lets scope back in reaches the human unflagged, and after approval its criteria reach the card a coder builds from. **[revised 2026-09-29]** The 2026-09-27 text ended "it reaches the Plan agents"; without plans, the approved spec's criteria go onto the card (`spec-to-card`'s card stage) and the coder builds from the card.
- **Most documents get no second pass.** `tech-writer` runs on `sonnet` (design section 4). Only external-audience output gets a second pass today: "`tech-writer` output with an external audience gets an opus pass, which is you, before it ships" (`claude/coder-fleet/agents/lead.md:32`, step 4). That pass spends the lead's context, and the lead's body gives it no procedure, tools or eval. Internal documents get no second pass at all.

The fix is two short-lived agents:
- `spec-editor` challenges a spec draft before the human edits it, and building waits until every serious challenge is dealt with. **[revised 2026-09-29]** Was "planning waits".
- `tech-editor` edits every `tech-writer` document in place.

Both run on Opus by default. A project can upgrade either to Fable or switch it off, one choice per editor, asked once at `/init` and enforced in the project's settings.

## The challenge notation

The gate in Q14 is a grep and the close in Q18 and Q19 is mechanical, so the notation has to be exact. The closed-marker line is the human's (Q19); the rest is **[supplied]**.

- **The section.** The section heading is a line that is exactly `## Challenges (spec-editor)`, with nothing after it. It runs to the next line starting `## `, or to the end of the file.
- **One line per challenge.** Each challenge is a single list line in that section:

  ```
  - C3 [must resolve] [open] Acceptance criterion 4 cannot fail: it passes whether or not the hook fires.
  ```

  - **Id**: `C` and a number.
  - **Severity**: one of `[must resolve]` (a coder could not build from the card as it stands), `[should resolve]` (a coder could build from it, but the build will carry the flaw), or `[note]`. **[revised 2026-09-29]** The 2026-09-27 definitions read "the plan cannot be written from the draft" and "the plan can be written but will carry the flaw".
  - **State**: always written by `spec-editor` as `[open]`.
- **Closing a challenge.** The human closes one by replacing `[open]` with one of two tags:
  - `[resolved]`: the human's edit fixed it;
  - `[struck: <reason>]`: the human rejects the challenge, with a one-line reason that must not be empty.
- **Inline markers.** A marker is a single space followed by `[challenge C3]`, appended to the end of the line it points at. The markers help the human while editing but play no part in the gate. **[supplied]** A marker appended to an acceptance-criterion line is part of that line's text until the close strips it, which is why the close runs before `spec-to-card` files any criterion (Q20).
- **The closed marker.** It is a line that is exactly `## Challenges (spec-editor): closed in <sha>`. **[supplied]** `<sha>` is a hexadecimal commit id of 7 to 40 characters, and nothing follows it on the line.

The gate, run by one shared script before the first build spawn on an item and before `spec-to-card` files criteria (Q14, Q19, Q20; **[revised 2026-09-29]** was "before any planning"):
- **The project's `AGENTS.md` records no editor answer.** The gate passes and suggests `/kickoff`, and the lead spawns no spec editor (Q21). A spec with no section and no closed marker builds.
- **The project's answer is "neither".** There is no section and no gate.
- **The closed-marker line is present.** The gate passes, and the caller goes on with no strip and no commit.
- **The intact section is present.** Refuse if any line in it carries `[must resolve]` and does not carry `[resolved]` or a `[struck: ...]` with a non-empty reason.
  - A line that still says `[open]` fails the gate. So does a line whose state tag was deleted.
  - `[should resolve]` and `[note]` challenges never block.
  - When the gate refuses, it names every blocking challenge id.
- **Neither the section nor the closed marker is present, and the project records a spec editor** (its recorded answer is Opus or Fable). The gate refuses and says so. A section deleted by hand is not a passed gate.
- **A closed marker typed by hand passes.** That is by design (Q19): the gate guards against accidental skipping, not deliberate override.

The close, only after the gate passes on an intact section (Q18, Q19):
1. **[supplied]** Make sure the intact, gate-passing spec is committed. If the working copy of the spec differs from its last commit, commit the spec file alone first, so that `<sha>` names a commit that really holds the section the gate passed.
2. Replace the whole `## Challenges (spec-editor)` section, from its heading up to, but not including, the next `## ` line or the end of the file, with the single closed-marker line naming that commit.
3. Remove every appended ` [challenge C<n>]` marker from every other line, and change nothing else.
4. Commit the spec file alone, with the subject "Close the challenges on <issue>".
5. Build from, or file the criteria of, the closed spec. **[revised 2026-09-29]** Was "Plan from the closed spec".

The closed spec carries the closed-marker line, no other Challenges content and no `[challenge C<n>]` marker. The section, every challenge and the human's resolutions stay readable at the commit the marker names.

### Which workflow runs the gate

Of the three workflows (checked 2026-09-29), only `spec-to-card` runs the gate (Q20):
- `spec-to-card.js`'s card stage reads the spec's numbered acceptance criteria and files each onto the card with `task edit <issue> --ac=...` (`spec-to-card.js:31-33`, `:444`). It is where a spec becomes something a coder builds from, so it takes the place `spec-to-plan`'s plan stage had in Q14 and Q18. It runs the shared gate script before reading the criteria. When the gate refuses, it files nothing and names the blocking ids. When the gate passes on an intact section, it runs the close first and files from the closed spec, so no `[challenge Cn]` marker reaches a card. On a closed marker, or a project with no record or "neither", it files as today.
- `review-round.js` reviews a diff that already exists, so it runs after the first build spawn and is too late to gate one. It does not run the gate.
- `deep-research.js` spawns no builder and does not run the gate.
- `spec-to-card`'s spec stage needs no new spawn: it drafts before the interview, and the interview and revision happen in the session, so the `spec-editor` spawn belongs to the lead after the revision. **[supplied]**

## The Fable rule, and why the Fable upgrade sits outside it

With Opus as the default, the default case raises no Fable question: both editors are ordinary Opus subagents like `coder` and `reviewer`. The exception below applies only to a project that chooses `spec-editor-fable` or `tech-editor-fable`.

The design says Fable is never a subagent model:

- Section 2, principle 4: "Fable 5.1 is an escalation, not a default".
- Section 4: "Fable 5.1 is not in the table on purpose. It is the model you switch the lead to, not a subagent model, for the reasons in section 5." (`docs/fleet-design.md:55`)
- `lead.md` step 4 ends the same way: Fable "is never a subagent model" (`lead.md:32`).
- Section 5 gives the reasons:
  - Pro does not include Fable at all.
  - Max 5x and 20x include Fable up to 50% of weekly usage, under one shared weekly cap.
  - Fable draws roughly twice what an Opus session does. That figure is from a secondary source.
  - "Put it in an agent that fires twenty times an hour and you hit the wall on Wednesday."
  - On API, Fable 5.1 costs $10 input and $50 output per million tokens, against Opus 5.5's $4 and $20: 2.5x on both.

The stated reason is frequency and volume, not capability. A Fable editor sits outside that argument only while all four of these bounds hold:

1. **A fixed number of passes.** `spec-editor` runs once per spec. `tech-editor` runs once on each `tech-writer` output. Neither ever runs inside a loop, a review round or a workflow fan-out.
2. **One document of input**, plus the sources its brief names, not a codebase.
3. **No tools that grow the run**: no `Bash`, no web, no spawning.
4. **A hard cap**: `maxTurns: 15` and `effort: medium`, both static frontmatter.

The two editors do not make the case equally well:
- **`spec-editor-fable` makes the strongest case.** It runs once per spec, which is once per issue that gets a spec, far below "twenty times an hour". Its job - finding what is wrong with a document before anyone builds on it - is also the adversarial reasoning where a stronger model is most plausibly worth paying for.
- **`tech-editor-fable` makes the weaker case.** It runs on every `tech-writer` output (Q4), so it runs as often as `tech-writer` does. `tech-writer` is a late-stage agent commissioned per document, not a loop worker, so the rate is still per document and far below the design's example. **[supplied]** But the rate rises with how much documentation a project commissions, and that is the cost a project accepts by upgrading.

What this argument does not cover, stated plainly:
- **[revised 2026-09-29]** Pro. The 2026-09-27 text said "A Pro account has no Fable" and left the behaviour to CF-12.1. CF-12.1 found: on a non-Pro account a `model: fable` subagent runs on Fable 5.1, and any fallback to another model shows in the transcript's `message.model`, so it is not silent. On Pro, Fable is outside the plan's usage limits and billed to usage credits, and under `-p` Claude Code bills it without asking (Claude Code docs and Anthropic support article 15424964, both cited in the findings). No Pro account was available, so the Pro behaviour is inferred, not observed (findings, question 1; CF-12 comment #9).
- The Fable editors' early-handoff instruction is untested on Fable (Q5 revision).
- Nothing in the design shows Fable challenges or edits better than Opus. Its benchmarks are agentic and reasoning ones. The upgrade is offered on the human's judgement, not on evidence, and the spec says so rather than implying otherwise.

When `/init` or `/kickoff` asks, the wording must say plainly:
- Fable on `tech-editor` runs on every `tech-writer` document, not only external ones.
- Fable draws against the same weekly cap as everything else.
- Pro plans do not include Fable. **[revised 2026-09-29]** Per the CF-12.1 finding, this line says that on Pro a Fable editor is billed to usage credits and may be billed without asking, and that this is inferred from the docs rather than observed.

**[revised 2026-09-29] [supplied]** The exact wording of the question is the builder's, within those required points; the 2026-09-27 text left it to the plan.
