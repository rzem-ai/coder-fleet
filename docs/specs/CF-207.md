# CF-207: a new board for coder-fleet

Status: revised after the interview on 13 Nov 2026, the human's ruling in comment #5 and the human's answers to the spec-editor's must-resolve challenges in comment #8. Not approved: the human edits it and changes the status to approved. Nothing downstream runs until then.

How to read it: a line marked (card) is the human's own answer or a feature the human picked, from the CF-207 card's description and comments #1 to #8, which win over anything here. A line marked [lead's default] is a default the lead proposed for the human to confirm; the human asked for few questions, so these are written as decided and only the one question the human must answer stays open. A line marked [supplied] is something the spec-writer wrote without hearing it - edit those first.

## Problem

coder-fleet's current board doesn't have the combination of features the human picked in the Board Feature Picker (https://claude.ai/artifact/FQBiYaFTqvQVQRFcP7qvVG). The human's ruling is "just replace the old board system": this board, built in the coder-fleet repo, replaces the current one - its board binary, MCP server and CLI, its hooks, `.boards/`, and the whole `coder-fleet/state` branch, with agent memory and specs moving under `~/.claude` beside the board. (card, comments #5 and #8)

It works with coder-fleet's agents as they are, reading their existing handoff, including `Blocker:` lines as the `handoff` skill defines them. (card, comment #5)

The combination it delivers (card):

- One markdown file per card, with frontmatter, kept under the home directory in `~/.claude`, one board per repo, with a repo's git worktrees sharing its board. The board never goes into git.
- Eight columns: Draft, Backlog, Next, In Progress, Done, Released, Blocked, Blocked by Human. Next is the human's ordered queue, filled only by the human, and taken top first.
- Hooks own the column moves; no agent writes a status. A `Blocker:` line in an agent's handoff sends its card to Blocked by Human.
- Two gates: ticks in, tests out. A card reaches Done when every checklist item is ticked, and reaches Released when the project's suite passes on a release that names it, without ever holding a session's turn.
- Acceptance criteria and Definition of Done checklists with live project-wide defaults, Actions for Human, sub-issues, dependencies.
- One Bun binary serving the MCP tools and a CLI, and a loopback web UI with full editing in the human's chosen design.
- Per-card locks, a board-wide lock for card numbers, atomic writes, and an append-only event trail kept forever.
- Context hooks that remind an agent to check the board first and reconcile before stopping, across compaction.

Cost the human accepted: the board, the agents' memory and the specs exist on one machine only. Other clones and web sessions can't see them, and they aren't backed up. (card) This reverses `docs/fleet-design.md` principle 1 ("Nothing that matters lives only in `~/.claude`"), so the design is rewritten to match (criterion 49). [challenge C1]

## Non-goals

Left out on purpose (card):

- A git branch for the board, the memory or the specs, or any git history of them.
- Milestones and documents. The glossary's Milestone row and the substitutions that point at it go too (criterion 51). [challenge C2]
- A database.
- A claim/submit/oracle lifecycle.
- Fenced status edits.
- Two-way links and stories.
- Rich work-scope fields.
- Attachments.
- An always-on dashboard.
- Importing or exporting boards.
- Backup.
- Keeping the old text of a card. The event trail records moves and their sources, not past content.

## Acceptance criteria

CF-207 delivers this spec and the whole working board; the lead splits the build into sub-issues under this card, and each one carries the card's coder-fleet Definition of Done as it stands. (card) The criteria are grouped so each group can become one sub-issue and be tested on its own; groups B to J build on the storage in group A. The grouping and the wording of every criterion are [supplied]; the behaviour each one checks is (card) unless marked otherwise.

While the build runs, its sub-issues are tracked on the old board and close through its hooks. Group G's sub-issue, which removes the old board, is cut last, is filed on the new board, and closes there. [lead's default] [challenge C3]

### A. Storage, board keying and card ids

1. Every card is one markdown file with YAML frontmatter. A repo's board lives in one directory under `~/.claude`, `~/.claude/boards/<key>/`, holding its cards, config, event log, locks, test-run logs, specs and agent memory. [supplied: the path and layout]
2. After any operation through the MCP tools, the CLI or the web UI, `git status` in the repo and in each of its worktrees shows no file written by the board.
3. A repo's main checkout and every linked worktree of it read and write the same board.
4. A board is keyed by the repo's origin remote URL, so moving or re-cloning the repo on the same machine reaches the same board. Two spellings of the same remote (SSH and HTTPS) reach the same board. [supplied: the URL normalisation]
5. A repo with no origin remote gets a board keyed by the absolute path of its shared git directory, and that board is used from the main checkout and every worktree. When such a repo later gains an origin remote, its board moves to the URL key once, the first time the board sees the remote. [lead's default for the first sentence] [supplied: the second]
6. A fork, whose origin is the fork's own URL, gets its own board, separate from the upstream repo's. [lead's default]
7. A board is created only through the CLI or the web UI, which ask the human for the board's id prefix. (card: the prefix question) An agent in a repo with no board gets a message telling it to ask the human to create one. [supplied]
8. Card ids are the prefix, a dash and a number (for example `XY-12`). Sub-issues carry dotted ids under their parent (`XY-12.1`, `XY-12.2`). A number is never reused, including after a card is deleted.
9. Anyone may delete a card through any interface; its file goes and the event log keeps a line for the deletion. [supplied]
10. When no board can be found for the session (for example a Claude Code web session, whose `~/.claude` has none), the board's hooks do nothing and say so once per session. [lead's default] [challenge C1]

### B. Concurrency and integrity

11. Many processes creating cards on the same board at once never receive the same number; numbers come from a board-wide lock.
12. Two writers on the same card are serialised by a per-card lock file.
13. A writer that finds a card's lock held waits 5 seconds and then fails with an error that names the card and the lock's holder (process and, where known, session or agent). (card: "waits a few seconds") [supplied: 5 seconds]
14. A lock whose holder's process no longer runs, or which is older than 30 seconds, is broken, and the next writer proceeds. (card: broken after a timeout) [supplied: the numbers]
15. A reader never sees a partly written card: a test that reads a card in a tight loop while another process rewrites it always parses a complete file, old or new.
16. The card file is the source of truth. A move writes the card first and appends its event log line after; after a crash between the two, the card stands and the log lacks that line. [lead's default] [challenge C16]

### C. Columns and hook-owned moves

17. A board has exactly eight columns, shown in this order: Draft, Backlog, Next, In Progress, Done, Released, Blocked, Blocked by Human.
18. Anyone (the human, an agent, the CLI, MCP or the web UI) can file a card into Draft and move a card out of Draft, and a card leaving Draft goes to Backlog only. Draft is never a route into any other column: a move from Draft to anywhere else is refused through every interface, the web UI included. (card, comment #8) [challenge C4]
19. A card can be filled into Next only through the web UI. The same move attempted through an MCP tool or the CLI is refused, says why, and leaves the card where it was. A hook returning a card to Next (criterion 25) is a return, not a fill, and is allowed. [lead's default for the last sentence] [challenge C9]
20. The web UI's address carries a token made fresh for each session, printed only to the human. A request without the token, such as one from an agent's Bash, is refused and changes nothing; the test drives a move into Next with and without the token. [lead's default] [challenge C5]
21. The human orders Next in the web UI, and an agent asking for work is given the top card of Next first.
22. No MCP tool or CLI command sets a card's column directly except a move out of Draft into Backlog. Every other column change is made by the board's hooks, its gates or the human in the web UI. Ticking a checklist item never moves a column. [lead's default for the last sentence]
23. The human's moves in the web UI override the gates: the human can move any card to any column except out of Draft other than into Backlog (criterion 18). Every move that bypassed a gate writes an event log line naming which gate it bypassed (card gate or test gate). (card, comment #8) [challenge C6]
24. Focus binding, as coder-fleet does today: each checkout has its own focus file naming one card; a worktree spawned from a focused checkout inherits its focus; a `Board-Item:` line in a spawn prompt also binds; a new, cleared or resumed session clears its checkout's focus and a compaction keeps it. Agents bound to a card move only that card, and a second checkout bound to a different card moves only its own. [lead's default] [challenge C7]
25. An agent starting work on its bound card moves it to In Progress only from Backlog or Next. A start on a card in any other column moves nothing and the event log says why. [lead's default] [challenge C8]
26. A `Blocker:` line in an agent's handoff, as the `handoff` skill defines it, adds an unticked Action for Human to its card carrying the blocker text, and adding any Action for Human moves the card to Blocked by Human (criterion 39). A `Propose item:` line never moves a column. [lead's default for the action] [challenge C15]
27. A card leaving Blocked or Blocked by Human returns to the column it was blocked from, read from the event trail. It leaves Blocked by Human once every Action for Human on it is ticked. It leaves Blocked when the human moves it in the web UI, or when a later release run that names it passes. [lead's default for the first two sentences] [supplied: the third] [challenge C9]
28. The table of which hook event moves a card from which column to which is written in the board's documentation, and a test drives each event and checks the resulting column.

### D. Gates and release

29. Card gate: when a `coder` or `scripter` subagent bound to a card stops, or a task whose subject carries the `[board:<id>]` marker completes, and every acceptance criterion and Definition of Done item on that card is ticked, a hook moves the card to Done. A stop of any other agent never moves a card to Done. Apart from the human's web UI override (criterion 23), no route moves a card with an unticked item into Done, and a refused attempt names the unticked items. [lead's default] [challenge C10]
30. The project's test command is set in the board's config under `~/.claude`, not in the repo.
31. A release names its cards in its annotated tag's message, on one line of the form `Cards: CF-1, CF-2`. A tag with no such line moves nothing. [lead's default] [challenge C11]
32. A successful `git push` of a release tag made in a Claude Code session starts the test gate for the named cards, caught by a hook in that session. A tag push made outside any session is caught at the next session start in that repo, which asks the remote with `git ls-remote --tags` for tags it has not yet processed. A test pushes a tag from a shell, starts a session, and sees the gate start. [lead's default] [challenge C12]
33. Every run of the test command the board makes is recorded in the board's event trail with the commit it tested and its result. Test gate: if a green run is recorded for the tagged commit, the named cards in Done move to Released at once. Otherwise the suite runs in the background against the tagged commit, checked out in a temporary worktree, and the cards move when it passes. [lead's default] [challenge C13]
34. A background run's log is kept beside the board and survives the session that started it; it can be read through the CLI and the web UI while the run is in flight and after. A run whose process has gone without a result is started again at the next session start in that repo. [lead's default for the log] [supplied: the restart] [challenge C13]
35. A failed run moves the named cards to Blocked, with the run's output added as a comment.
36. The push and the session's turn never wait for the suite: the turn that pushes the tag returns before the run finishes, measured against a test command that sleeps for longer than the turn takes.
37. A card named by a release but not in Done stays where it is, and the release's result says so. [supplied]
38. Released is the final column: only the human, in the web UI, can move a card out of it. [supplied]

### E. Checklists, Actions for Human, sub-issues and dependencies

39. Actions for Human are numbered items on a card. Adding one moves the card to Blocked by Human, and while any is unticked the card stays there and no move other than the human's web UI override takes it out. [lead's default for adding] [challenge C15]
40. A card carries an acceptance criteria checklist and a Definition of Done checklist, each item tickable on its own.
41. The project-wide default criteria and Definition of Done live in the board config and are read live: changing a default changes what every open card shows, with no edit to the card files. (card) A tick on a default item is stored on the card by the item's text, so editing a default item's text shows it unticked on every card, and an added default item shows unticked. A card already in Done or Released is not moved by a change to the defaults. [lead's default for the tick storage] [supplied: the last sentence] [challenge C14]
42. A card can be a sub-issue of another, with a dotted id, and can list cards it depends on.
43. A filter, available through MCP, the CLI and the web UI, returns exactly the cards whose dependencies are all in Done or Released. [supplied: Done counts]

### F. Event trail

44. Every column move, from any source, appends one line to the board's append-only event log, recording the time, the card, the from column, the to column, the source (hook, MCP, CLI or web UI), the session or agent where known, and the gate bypassed, if any.
45. Each card's frontmatter carries its last event and that event's source, and they match the log's last line for that card except after the crash criterion 16 describes.
46. Lines are never removed or rewritten; the log is kept forever.
47. The web UI shows each card's move history in its card detail, and no board-wide feed. [supplied]

### G. Binary, MCP tools, CLI and replacing the old board

48. The board builds with Bun into one compiled binary for each of darwin-arm64, darwin-x64, linux-x64 and linux-arm64, and that one binary serves both the MCP tools and the CLI. An installed plugin gets the binary for its machine through a session-start hook, as today. [lead's default for the architectures and the fetch] [challenge C17]
49. Agents use the MCP tools only, served by the MCP server, which runs outside the Bash sandbox, for every card operation a session needs (file, read, list, filter, edit, tick, comment, add and tick Actions for Human, bind focus). The CLI offers the same operations for the human's own terminal. The fleet's sandbox keeps `~/.claude` under `denyWrite`, so a CLI write from an agent's sandboxed Bash is refused. [lead's default] [supplied: the list of operations] [challenge C18]
50. Once this board ships, the coder-fleet plugin carries none of the old board system: no old board binary, MCP server, CLI or board hooks, no `.boards/` directory, no `coder-fleet/state` branch, no state push, and no branch commits from the memory hook. (card, comments #5 and #8) [challenge C19]
51. Each agent's memory for a repo lives under that repo's board directory in `~/.claude`, and an agent reads and writes the same memory from the main checkout and every worktree. (card, comment #8) [supplied: the per-repo location inside the board directory] [challenge C19]
52. Each spec lives under its repo's board directory in `~/.claude` as `specs/<issue>.md`, `spec-writer` writes specs there and nowhere else, and `enforce-agent-scope.sh` confines its writes to that directory. (card, comment #8) [supplied: the file name and the scope hook] [challenge C19]
53. Nothing in the repo still says the board, memory or specs live on the state branch or under `.boards/`: `docs/fleet-design.md` principle 1 and its "where the board lives" section are rewritten to the home-directory board and its accepted cost, the glossary's Board, Memory and Spec rows describe the new locations and eight columns, and AGENTS.md's sections on where work lives, releasing and the closing gate describe the new board. (card, comment #8) [challenge C1] [challenge C19]
54. The glossary's Milestone row goes, and the "epic" and "sprint" substitutions no longer point at a milestone. [lead's default] [challenge C2]
55. The procedures that depend on the old board's behaviour are rewritten to the new columns and markers, not just renamed: `/drain`, `/triage`, `/work`, `/kickoff`, `lead-procedures` and AGENTS.md. Each says how it finds work (top of Next, then Backlog), how it parks a card (adding an Action for Human), how it binds a task to a card (the `[board:<id>]` subject marker), and how a release closes cards (the `Cards:` tag line). `check-all.sh` passes. [lead's default] [challenge C20]
56. The OpenCode port gets a divergence-register row saying its board wiring still follows the old board; replacing it there is its own later card. [supplied]

### H. Web UI

57. The web UI listens only on a loopback address and is unreachable from another machine.
58. It starts on request through the CLI or an MCP tool, which prints its tokened address (criterion 20) to the human. A second session's request while one runs reuses the running server and its port rather than starting another. The server stops when the last session using it ends. [lead's default for the reuse] [supplied: start on request, the port reuse and the stop] [challenge C21]
59. It does full editing: titles, descriptions, criteria and Definition of Done items, Actions for Human, comments and moves, under the column rules in group C.
60. Its look is the human's chosen design, the Ledger canvas "Kanban Board Refresh - Ledger" (https://claude.ai/artifact/V6YMifMqcQcg1ahzNFFCx5), built on shadcn/ui, with its laptop, desktop and ultrawide boards, card detail, dark mode, and empty, dragging and loading states.
61. The design is drawn with six columns. The built UI uses the same design extended to the board's eight columns, adding no structure the design lacks. [lead's default]
62. For each of the design's views and states, a screenshot of the running UI sits beside the design's own, and the human judges they match.

### I. Context hooks

63. At session start in a repo with a board, the agent's context carries a reminder to check the board first, and the reminder is there again after compaction.
64. Before a session stops, the agent is reminded to reconcile the board, and this reminder also survives compaction. The reminder only adds context and never blocks a stop, so an unattended `/drain` under `/goal` stops normally. [lead's default for not blocking] [challenge C22]
65. The default wording, which the human gave none for, is [lead's default]: at start, "This repo has a board. Before starting work, check it: take the top card in Next, or the card this checkout is bound to." Before stopping, "Before you stop, reconcile the board: tick what you finished, comment on what you didn't, and raise a `Blocker:` line for anything only the human can decide."

### J. Scope guard

66. None of the non-goals above is built. Checked by a test that lists the MCP tools, the CLI commands and the card frontmatter fields and fails on any that carries a non-goal (milestones, documents, attachments, links, claim, submit or oracle states, import, export, backup), and by reading. [lead's default] [challenge C23]
67. Nothing in the board's code, docs or this spec describes it as a migration path, and it has no import or export path. Checked by reading.
