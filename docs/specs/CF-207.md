# CF-207: a new board for coder-fleet

Status: revised after the interview on 13 Nov 2026 and the human's ruling in comment #5. Not approved: the human edits it and changes the status to approved. Nothing downstream runs until then.

How to read it: a line marked (card) is the human's own answer or a feature the human picked, from the CF-207 card's description and comments #1 to #5, which win over anything here. A line marked [lead's default] is a default the lead proposed for the human to confirm. A line marked [supplied] is something the spec-writer wrote without hearing it - edit those first. Every [lead's default] and every load-bearing [supplied] line also stands under Open questions.

## Problem

coder-fleet's current board doesn't have the combination of features the human picked in the Board Feature Picker (https://claude.ai/artifact/FQBiYaFTqvQVQRFcP7qvVG). The human's ruling is "just replace the old board system": this board, built in the coder-fleet repo, replaces the current one - its board binary, MCP server and CLI, its hooks, the state branch and `.boards/`. (card, comment #5)

It works with coder-fleet's agents as they are, reading their existing handoff, including `Blocker:` lines as the `handoff` skill defines them. (card, comment #5)

The combination it delivers (card):

- One markdown file per card, with frontmatter, kept under the home directory in `~/.claude`, one board per repo, with a repo's git worktrees sharing its board. The board never goes into git.
- Eight columns: Draft, Backlog, Next, In Progress, Done, Released, Blocked, Blocked by Human. Next is the human's ordered queue, filled only by the human, and taken top first.
- Hooks own the column moves; no agent writes a status. A `Blocker:` line in an agent's handoff sends its card to Blocked by Human.
- Two gates: ticks in, tests out. A card reaches Done when every checklist item is ticked, and reaches Released when the project's suite passes on a release that names it, without ever holding a session's turn.
- Acceptance criteria and Definition of Done checklists with live project-wide defaults, Actions for Human, sub-issues, dependencies.
- One Bun binary for macOS and Linux serving the MCP tools and a CLI, and a loopback web UI with full editing in the human's chosen design.
- Per-card locks, a board-wide lock for card numbers, atomic writes, and an append-only event trail kept forever.
- Context hooks that remind an agent to check the board first and reconcile before stopping, across compaction.

Cost the human accepted: the board exists on one machine only. Other clones and web sessions can't see it, and it isn't backed up. (card) [challenge C1]

## Non-goals

Left out on purpose (card):

- A git branch for the board, or any git history of the board.
- Milestones and documents. [challenge C2]
- A database.
- A claim/submit/oracle lifecycle.
- Fenced status edits.
- Two-way links and stories.
- Rich work-scope fields.
- Attachments.
- An always-on dashboard.
- Importing or exporting boards.
- Backup.
- Keeping the old text of a card. The event trail records moves and their sources, not past content.

## Acceptance criteria

CF-207 delivers this spec and the whole working board; the lead splits the build into sub-issues under this card, and each one carries the card's coder-fleet Definition of Done as it stands. (card) The criteria are grouped so each group can become one sub-issue and be tested on its own; groups B to J build on the storage in group A. The grouping and the wording of every criterion are [supplied]; the behaviour each one checks is (card) unless marked otherwise. [challenge C3]

### A. Storage, board keying and card ids

1. Every card is one markdown file with YAML frontmatter, under a board directory in `~/.claude`. The exact path under `~/.claude` is [supplied] (open question 3).
2. After any operation through the MCP tools, the CLI or the web UI, `git status` in the repo and in each of its worktrees shows no file written by the board.
3. A repo's main checkout and every linked worktree of it read and write the same board.
4. A board is keyed by the repo's origin remote URL, so moving or re-cloning the repo on the same machine reaches the same board. Two spellings of the same remote (SSH and HTTPS) reach the same board. [supplied: the URL normalisation]
5. A repo with no origin remote gets a board keyed by the absolute path of its shared git directory, and that board is used from the main checkout and every worktree. [lead's default] (open question 2)
6. A fork, whose origin is the fork's own URL, gets its own board, separate from the upstream repo's. [lead's default] (open question 2)
7. Creating a repo's board asks the human for the board's id prefix. (card) How the question reaches the human when an agent is first to need the board is open question 4.
8. Card ids are the prefix, a dash and a number (for example `XY-12`). Sub-issues carry dotted ids under their parent (`XY-12.1`, `XY-12.2`). A number is never reused, including after a card is deleted.

### B. Concurrency and integrity

9. Many processes creating cards on the same board at once never receive the same number; numbers come from a board-wide lock.
10. Two writers on the same card are serialised by a per-card lock file.
11. A writer that finds a card's lock held waits a few seconds and then fails with an error that names the card and the lock's holder (process and, where known, session or agent). The exact wait is [supplied] (open question 5).
12. A lock left by a process that no longer runs is broken after a timeout, and the next writer proceeds. The timeout is [supplied] (open question 5).
13. A reader never sees a partly written card: a test that reads a card in a tight loop while another process rewrites it always parses a complete file, old or new.

### C. Columns and hook-owned moves

14. A board has exactly eight columns, shown in this order: Draft, Backlog, Next, In Progress, Done, Released, Blocked, Blocked by Human.
15. Anyone (the human, an agent, the CLI, MCP or the web UI) can file a card into Draft and move a card out of Draft. [challenge C4]
16. A card can be moved into Next only through the web UI. The same move attempted through an MCP tool or the CLI is refused, says why, and leaves the card where it was. [challenge C5]
17. The human orders Next in the web UI, and an agent asking for work is given the top card of Next first.
18. No MCP tool or CLI command sets a card's column directly except the moves this spec allows (out of Draft, and the human's moves in the web UI). Every other column change is made by the board's hooks or its gates. Ticking a checklist item never moves a column. [lead's default for the last sentence] [challenge C6]
19. Focus binding: once a checkout is bound to a card, the agents spawned from that checkout move that card and no other, and a second checkout bound to a different card moves only its own.
20. An agent starting work on its bound card moves the card to In Progress.
21. A `Blocker:` line in an agent's handoff, as the `handoff` skill defines it, moves its card to Blocked by Human and adds the blocker text to the card as a comment. A `Propose item:` line never moves a column.
22. A card leaving Blocked or Blocked by Human returns to the column it was blocked from, as recorded in the event trail. [lead's default] Who or what moves a card out of Blocked is open question 6.
23. The table of which hook event moves a card from which column to which is written in the board's documentation, and a test drives each event and checks the resulting column.

### D. Gates and release

24. Card gate: when an agent stops or a task completes on a card whose every acceptance criterion and Definition of Done item is ticked, a hook moves the card to Done. [lead's default] No route moves a card with an unticked item into Done, and a refused attempt names the unticked items.
25. The project's test command is set in the board's config under `~/.claude`, not in the repo.
26. A release names the cards it carries in its annotated tag's message, and pushing that tag starts the test gate for those cards.
27. A release tag pushed from a Claude Code session is caught by a hook in that session. A release tag pushed outside any session is caught at the next session start in that repo. [lead's default]
28. Test gate: if a green run of the test command is recorded for the tagged commit, the named cards in Done move to Released at once. Otherwise the suite runs in the background and they move when it passes.
29. A failed run moves the named cards to Blocked, with the run's output added as a comment.
30. The push and the session's turn never wait for the suite: the turn that pushes the tag returns before the run finishes, measured against a test command that sleeps for longer than the turn takes.
31. A card named by a release but not in Done stays where it is, and the release's result says so. [supplied]
32. Released is the final column. [supplied: whether a card can ever leave it is open question 8]

### E. Checklists, Actions for Human, sub-issues and dependencies

33. A card carries an acceptance criteria checklist and a Definition of Done checklist, each item tickable on its own.
34. The project-wide default criteria and Definition of Done live in the board config and are read live: changing a default changes what every open card shows, with no edit to the card files.
35. Actions for Human are numbered items on a card. While any is unticked the card stays in Blocked by Human; once every one is ticked, it leaves Blocked by Human for the column it was blocked from (criterion 22). [lead's default for leaving]
36. A card can be a sub-issue of another, with a dotted id, and can list cards it depends on.
37. A filter, available through MCP, the CLI and the web UI, returns exactly the cards whose dependencies are all in Done or Released. [supplied: whether Done counts or only Released is open question 9]

### F. Event trail

38. Every column move, from any source, appends one line to the board's append-only event log, recording the time, the card, the from column, the to column, the source (hook, MCP, CLI or web UI) and the session or agent where known.
39. Each card's frontmatter carries its last event and that event's source, and they match the log's last line for that card.
40. Lines are never removed or rewritten; the log is kept forever.
41. How much of the trail the web UI shows is open question 10.

### G. Binary, MCP tools, CLI and the old board's removal

42. The board builds with Bun into one compiled binary for each of macOS and Linux, and that one binary serves both the MCP tools and the CLI.
43. Every card operation a session needs (file, read, list, filter, edit, tick, comment, bind focus) is available as an MCP tool and as a CLI command, under the column rules in group C. [supplied: the list of operations]
44. Once this board ships, the coder-fleet plugin carries none of the old board system: no old board binary, MCP server, CLI or board hooks, no `.boards/` directory, and no board commits on the state branch. (card, comment #5) What else the state branch carries today is open question 1.
45. Every place in the coder-fleet repo that names the board's columns, paths or tools (the glossary, agent bodies, skills, commands, docs, evals) describes this board, and `check-all.sh` passes. [supplied]

### H. Web UI

46. The web UI listens only on a loopback address and is unreachable from another machine.
47. It lives only as long as the session that started it: when that session ends, the server stops. When it starts is open question 11.
48. It does full editing: titles, descriptions, criteria and Definition of Done items, comments and moves, under the column rules in group C.
49. Its look is the human's chosen design, the Ledger canvas "Kanban Board Refresh - Ledger" (https://claude.ai/artifact/V6YMifMqcQcg1ahzNFFCx5), built on shadcn/ui, with its laptop, desktop and ultrawide boards, card detail, dark mode, and empty, dragging and loading states.
50. The design is drawn with six columns. The built UI uses the same design extended to the board's eight columns, adding no structure the design lacks. [lead's default] (open question 12)
51. For each of the design's views and states, a screenshot of the running UI sits beside the design's own, and the human judges they match.

### I. Context hooks

52. At session start in a repo with a board, the agent's context carries a reminder to check the board first, and the reminder is there again after compaction.
53. Before a session stops, the agent is reminded to reconcile the board, and this reminder also survives compaction.
54. The default wording, which the human gave none for, is [lead's default] (open question 13): at start, "This repo has a board. Before starting work, check it: take the top card in Next, or the card this checkout is bound to." Before stopping, "Before you stop, reconcile the board: tick what you finished, comment on what you didn't, and raise a `Blocker:` line for anything only the human can decide."

### J. Scope guard

55. None of the non-goals above is built.
56. Nothing in the board's code, docs or this spec describes it as a migration path, and it has no import or export path. Checked by reading.

## Open questions

Ordered by how much they hold up building. Where the lead gave a default, it is stated; everything else is the spec-writer's suggestion.

1. The state branch carries more than the board today: the memory hook commits each agent's memory and each spec on `coder-fleet/state` and pushes it. The ruling replaces "the state branch" along with the board. Does the state branch go entirely, taking memory and spec persistence with it (and if so, where do they live), or does it stay for memory and specs and lose only the board? No suggestion: this reaches past the board, so it's the human's call. [supplied: the question]
2. No remote and forks. [lead's default] A repo with no origin remote is keyed by the absolute path of its shared git directory; a fork is keyed by its own origin URL and gets its own board. Unsettled: when a repo with no remote later gains one, does its path-keyed board follow it to the URL key, or does the repo start a fresh board? Suggestion: it follows, once, when the board first sees the remote. [supplied]
3. The exact path under `~/.claude` and the board directory's name. Suggestion: `~/.claude/boards/<key>/`, with the board config and event log beside the cards. [supplied]
4. How the prefix question reaches the human when an agent is first to need a repo's board. Suggestion: the board is created only through the CLI or web UI, so the human answers there, and an agent in a repo with no board is told to ask the human. [supplied]
5. The lock wait and the stale-lock timeout. "A few seconds" and "a timeout" are the human's words; no numbers were given. Suggestion: wait 5 seconds; treat a lock as stale when its holder's process is gone, or after 30 seconds. [supplied]
6. Who or what moves a card out of Blocked after a failed release run or other failure: the human in the web UI, a later green run, or the next agent stop on the card. [lead's default] covers only where it goes (back to the column it was blocked from). Suggestion: the human in the web UI, or the next green run of a release naming it. [supplied]
7. What becomes of the cards already on coder-fleet's own board when this board replaces it? The human has ruled out migration paths. No default.
8. Whether a card can ever leave Released (a reopened bug, say), and by whom. Suggestion: only the human, in the web UI, back to Backlog. [supplied]
9. For the dependency filter, does a dependency count as met once it is in Done, or only once Released? Suggestion: Done, since Done means the work is finished and only tests are pending. [supplied]
10. How much of the event trail the web UI shows. Suggestion: each card's move history in its detail view, and no board-wide feed. [supplied]
11. When the web UI starts: with every session, or on request. Since Next can only be filled in the web UI, it has to be easy to reach. Suggestion: on request through a CLI command or MCP tool, which prints the loopback address. [supplied]
12. [lead's default] The Ledger design, drawn with six columns, extended to eight, with nothing added that the design lacks. Confirm, or say how the two extra columns should sit (Released and the Blocked pair may need to scroll or collapse on a laptop width).
13. [lead's default] The context hooks' wording in criterion 54. Confirm or rewrite.
14. Deleting cards: numbers are never reused, which implies cards can be deleted. Who may delete one, and does deletion leave anything behind beyond the event log line? Suggestion: anyone, through any interface; the file goes and the log keeps the line. [supplied]
15. The OpenCode port has its own board wiring. Does this board replace it there too, under this card, or does the port get a divergence-register row and its own later card? Suggestion: a divergence row now, its own card later. [supplied]
