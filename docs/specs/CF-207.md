# CF-207: a new board mod for Claude Code

Status: draft. This is a strawman written before the interview, not after one. Change the status to approved once you've edited it; nothing downstream runs until then.

How to read it: a line ending (card) is your own words or a feature you picked, taken from the CF-207 card filed on 13 Nov 2026. A line ending [supplied] is something the spec-writer wrote without hearing it from you - edit those first. Recommendations live only in Open questions; nothing below takes one as decided.

## Problem

Not yet stated. The card lists the features you picked in the Board Feature Picker but never says what goes wrong today, or what you can't do, with the boards you already have. This section needs your words (open question 2). [supplied]

What the card does say: this is a brand-new Claude Code mod, designed from scratch. It is not a change to coder-fleet's board or to sidequest, and the spec must not frame it as a move from either. (card)

Costs you accepted (card):

- The board exists only on this machine, so other clones and web sessions can't see it and it isn't backed up with the repo.
- Every close runs the test suite, including a close on release from inside a hook, which holds the session's turn. The spec has to answer that (open question 9).

## Non-goals

Left out on purpose (card):

- A git branch for the board, or any git history of the board.
- Milestones and documents.
- A database.
- The claim/submit/oracle lifecycle.
- Fenced status edits.
- Two-way links and stories.
- Rich work-scope fields.
- Attachments.
- An always-on dashboard.
- Keeping the old text of a card. The event trail replaces a local git repo, so history is moves, not content. (card)

Proposed, not yet agreed [supplied]:

- Importing an existing board, whether this repo's `.boards/` or a sidequest board (open question 16). [supplied]
- Export or backup of a board (open question 16). [supplied]

## Acceptance criteria

Open question 1 is blocking and decides what these are. If CF-207 delivers the spec only, the card's criteria become "this spec is approved and its sub-issues are filed", and the list below becomes the criteria those sub-issues are built against. If CF-207 delivers the working mod, the list below goes on the card as written. [supplied]

Each criterion restates a feature from the card as a check a test can run. The wording of every one is [supplied]; the feature behind it is (card). Where a criterion depends on an unanswered question, it names the question and stays incomplete until that is answered. [supplied]

Storage and format

1. Every card is one markdown file with YAML frontmatter, and creating, editing or moving a card through any interface changes only that card's file and the board's event trail. (card) [supplied wording]
2. A board is stored under `~/.claude`, and after any board operation `git status` in the repo and in each of its worktrees shows no file written by the mod. (card) [supplied wording; exact path depends on open question 5]
3. Running the mod from the repo's main checkout and from any linked worktree of that repo reads and writes the same board. (card) [supplied wording; keying depends on open question 5]
4. Card ids follow the scheme agreed in open question 6, and sub-issues carry dotted ids under their parent (for example `X-12.1`). (card: dotted ids) [supplied wording]

Columns and hooks

5. A board has exactly seven columns: Draft, To Do, Next, In Progress, Blocked, Blocked by human, Done. (card)
6. An attempt from an agent session to move a card into Next is refused, and the card's column is unchanged; the same move made by the human succeeds. (card) [supplied wording; how the mod tells the two apart is open question 8]
7. Agents taking work from Next take the top card first. (card) [supplied wording: how a test observes "take" depends on the hook design]
8. No MCP tool available to an agent sets a card's status directly; every column change an agent's work causes comes from a hook on agent start, agent stop or task completion. (card) [supplied wording]
9. The mapping from each hook event to the column move it makes is written down in this spec, and a test drives each event and checks the resulting column. (card: "hooks own the columns") [supplied; the mapping itself is not yet written - see open question 7 for Draft]
10. With focus bound to a card in a checkout, an agent spawned from that checkout moves that card and no other. (card) [supplied wording]
11. An agent report containing a line starting `Blocker:` moves its card to Blocked by human, and the line's text is added to the card as a comment. (card) [supplied wording; whose report format is open question 3]

Gates

12. A card with any unticked acceptance criterion or Definition of Done item cannot be moved to Done by any route, and the attempt says which items are unticked. (card: card gate) [supplied wording]
13. A card cannot close while the project's test suite fails; a close attempted on a red suite leaves the card short of Done. (card: test gate) [supplied wording; where the suite is found is open question 9]
14. A release tag that names a card closes it through both gates: a fully ticked card on a green suite reaches Done, and any other named card stays where it was. (card) [supplied wording; tag format and trigger are open question 10]
15. A close on release does not hold the session's turn for the length of a suite run. (card: the cost the spec has to answer) [supplied wording; mechanism is open question 9]

Checklists, questions and dependencies

16. A newly created card carries the board's project-wide default acceptance criteria and Definition of Done. (card) [supplied wording; copy-at-creation versus live is open question 14]
17. Actions for Human are numbered questions on a card, and while any is open the card stays in Blocked by human. (card) [supplied wording]
18. A card can list other cards it depends on, and a filter returns exactly the cards whose dependencies are all Done. (card) [supplied wording]

Binary and interfaces

19. One binary serves both the MCP tools and the CLI. (card)
20. The web UI listens only on a loopback address and stops when the session that started it ends. (card) [supplied wording; what it can do is open question 13]

Concurrency

21. Two processes creating cards on the same board at the same moment never receive the same card number, and no number is ever handed out twice. (card) [supplied wording; reuse after deletion is part of open question 6]
22. A reader never sees a partly written card file: every write goes to a temporary file and is renamed into place. (card)
23. Two writers on the same card are serialised by a per-card lock; what the second writer sees is open question 12. (card) [supplied wording]

Event trail

24. Every column move, whatever its source, appends one entry to the board's event trail recording at least the card, the old column, the new column and the source. (card) [supplied wording; format is open question 11]
25. Each card shows its last event and that event's source. (card)

Context hooks

26. A session start in a repo with a board gives the agent a reminder to check the board first, and that reminder is present again after compaction. (card) [supplied wording; reminder text is open question 15]
27. Before a session stops, the agent is reminded to reconcile the board, and this survives compaction too. (card) [supplied wording]

Scope guard

28. Nothing in the spec, the mod's docs or its code describes the mod as a move from coder-fleet's board or from sidequest, and none of the non-goals above is built. (card, provisional criterion 6) [supplied wording; "describes as a move" is checked by reading, not by a test]

## Open questions

Ordered as they'd best be asked. Each carries the spec-writer's recommendation, which is a guess until you accept it. [supplied]

1. Blocking. What does CF-207 itself deliver: (a) the spec only, with building split into sub-issues once you sign it off, (b) the spec and the whole working mod under this one card, or (c) the spec plus a first slice, with the rest as sub-issues? Recommended: (a). The card's six provisional criteria all say "the spec defines...", which reads as spec-only, but its Definition of Done includes a version bump and a tagged release, which only fits if something ships.
2. Blocking. In your own words, what problem does this mod solve that the boards you already have don't? What goes wrong today, or what can't you do? And what would make it not worth building? No recommendation: the Problem section has to come from you. If the answer is "coder-fleet's board, but kept in the home directory", that's a different spec from a fresh product.
3. Blocking. Who drives the mod? (a) Standalone: it works with any Claude Code setup and defines its own report format, including how it spots a `Blocker:` line. (b) Built for coder-fleet's agents, assuming their handoff format and roles. (c) Standalone, but coder-fleet moves onto it later. Recommended: (a). The `Blocker:` rule, focus binding and gates are coder-fleet concepts, so the spec has to say whose agents it reads, and whether this repo's `.boards/` goes away eventually.
4. Blocking. Where does the code live? (a) Its own new repo, as its own plugin. (b) Inside the coder-fleet repo, as a second plugin in the rzem marketplace. (c) In eigenwise-toolshed, next to sidequest. Recommended: (a) if question 3 is standalone, (b) if built for coder-fleet. This also decides whether the card's Definition of Done (coder-fleet's `check-all.sh`, a coder-fleet version bump) is the right one.
5. How is a board tied to a repo, and what happens when the repo moves? (a) By the canonical path of the repo's shared `.git` directory: worktrees fold in for free, but the board is lost when the repo moves. (b) By the origin remote URL: survives a move, breaks for repos without a remote and for forks. (c) By an id file the mod writes once inside the repo's `.git` directory: survives a move and folds worktrees in. Recommended: (c), plus a CLI command to reattach an orphaned board. sidequest already finds worktrees through `git rev-parse --git-common-dir`.
6. What's the card id scheme? Recommended: a short per-board prefix (defaulting to letters from the repo name), a dash, a number the board-wide lock hands out, dotted numbers for sub-issues, and numbers never reused even after deletion. Is the prefix yours to set, and can it change after cards exist?
7. What is Draft for, and who moves cards in and out of it? Recommended: a card filed before its spec is approved starts in Draft, agents can file into it, and only you promote it to To Do. Without a rule, "hooks own the columns" has a hole.
8. How does the mod tell you apart from an agent for Next and for leaving Draft? (a) The MCP tools refuse those moves and only the CLI and web UI allow them. (b) A hook blocks agent sessions from those moves and the CLI is trusted. (c) Both. Recommended: (c), since an agent with a shell can call the CLI.
9. Where does the test gate find each project's suite, and how does a release close avoid holding the turn? Suite: (a) a command in the board's own config in the home directory, or (b) read from the repo, the way coder-fleet reads the `gates` block in `AGENTS.md`. Recommended: (a). Release close: (a) run the gate in the background and move the card when it passes, (b) reuse a green run recorded for the same commit and run the suite only without one, (c) both, (b) first. Recommended: (c). If a background run fails, where does the card go - Blocked, with the failure as a comment?
10. How does a release tag name the cards it closes? (a) Ids in the annotated tag's message. (b) Ids in brackets at the end of the release commit's subject, as coder-fleet does now. (c) Either. Recommended: (b). And does pushing the tag trigger the close, or making it locally?
11. What's in the event trail and how much do you see? Recommended: one append-only line-per-event log per board, recording time, card, from-column, to-column, source (hook name, MCP, CLI or web) and session or agent where known; each card's last event and source in its frontmatter; the web UI shows each card's last event and its move history, with no board-wide feed. Kept forever, or trimmed?
12. What does a writer see when it hits a lock? Recommended: it waits a short bounded time, then fails with an error naming the card and the lock's holder, and a lock left by a dead process is broken after a timeout. Waiting or failing straight away, and is there a timeout you already have in mind?
13. What can the web UI do: (a) read-only, (b) read plus your moves (ordering Next, promoting Draft, answering Actions for Human), or (c) full editing? Recommended: (b). Does it start with every session or only on request?
14. Where do the project-wide default criteria and Definition of Done live, and what's in them by default? Recommended: in the board's config file in the home directory, empty unless you set them, and copied onto a card at creation so later edits don't rewrite existing cards.
15. Is anything already fixed about runtime and platform: Bun, Node or something else for the one binary, and macOS only or Linux too? And what exactly should the two context hooks tell the agent? No recommendation on runtime: that's your call or the builder's.
16. Are importing an existing board (this repo's `.boards/` or a sidequest board) and export or backup out of scope? Recommended: both out, listed as non-goals, so a builder doesn't add them "helpfully".
