## What the human said

Verbatim, 2026-09-27: "when a card is moved into 'Blocked by human', there needs to be a sections called 'Actions for Human' or something to that effect which tells the human, near the top of the card, what exactly is need the human's attention or action"

Issue #3, from the Fathom card FTH-001.12, in the lead's summary: a reviewer's "request changes" wrote its two code findings as `Blocker:` lines. `SubagentStop` then moved the card to Blocked by human with nothing waiting on the human (fathom commit 7475a38). When the human opened the card, there was no question on it.

## Problem

The human queue is "the one thing the human monitors" (glossary). A card in it does not say what the human is being asked without scrolling, and it can sit in the queue when nothing is being asked at all.

- **Where the ask lands today.** On a `Blocker:` line, `SubagentStop` moves the item to Blocked by human and passes the blocker lines as a comment in the same `board_write` call (`hooks/board-subagent-stop.sh:359-367`). The comment renders after the description, the criteria and the Definition of Done in every view: the file, the CLI, the MCP `task_view` and the web modal.
- **False blockers.** Three were seen on 2026-09-27:
  - FTH-001.12's two review findings;
  - CF-8 comment #4, a refuter's surviving mutants;
  - CF-8 comment #8, a `spec-writer` blocker bound to the wrong card.
  The first two come from `reviewer.md:42` and `refuter.md:48`, which tell those agents to raise findings as `Blocker:` lines. CF-31 fixes that rule. This spec adds the other half: a card that makes a probable false blocker visible at once, and lets the lead void one.

## What the carried board fork offers today

Checked 2026-09-27 under `claude/coder-fleet/board/`.

- **The task file.** The file is YAML frontmatter followed by H2 sections from a fixed set: Description, Acceptance Criteria, Definition of Done, Implementation Plan, Implementation Notes, Comments and Final Summary (`src/markdown/section-titles.ts:1-9`). Each section is delimited by markers such as `<!-- SECTION:DESCRIPTION:BEGIN -->`, or `<!-- AC:BEGIN -->` for the criteria checklist.
- **A checklist shape to reuse.** Acceptance criteria are stored as `- [ ] #1 <text>` lines, ticked with `--check-ac n` on the CLI and `acceptanceCriteriaCheck` on MCP `task_edit`, and ticked by clicking in the web modal. Definition of Done items use the same shape (`src/markdown/structured-sections.ts`, `AcceptanceCriteriaManager` and the Definition of Done manager beside it). Removing an item renumbers the rest (`structured-sections.ts:1364-1370`).
- **The views.**
  - `formatTaskPlainText` (`src/formatters/task-plain-text.ts:114-267`) prints the metadata, then Description first. The MCP `task_view` output has the same layout.
  - The web modal opens with Title, then Description (`src/web/components/TaskDetailsModal.tsx:1268-1647`).
  - The kanban card shows the title, criteria progress, priority and up to three labels (`src/web/components/TaskCard.tsx:83-287`).
- **The fork is already fleet-modified,** for example in `task-plain-text.ts:157, 194, 240`. AGENTS.md says the fork is trimmed by deletion and ported by hand, and that `LICENSE` and `NOTICE.md` stay.
- **CI does not run the fork's tests yet.** `check-all.sh:80-81` skips them without bun, and CI has none. CF-29 adds bun to CI.
- **`SubagentStart` can fail to move a card at all.** Issue #3 point 2: SubagentStart fired on a resumed run but failed on an "In Progress" override, which CF-9 fixes. This is part of why the clear lives in the binary rather than in a hook (Q3).

## Decisions

The human's answers, 2026-09-27:

- **Q11. It is worth doing.** A dedicated section is worth the fork change. Reordering comments newest-first is not enough.
- **Q1. A new field in the fork.** It is stored as its own marked section in the task file and rendered first in the CLI, MCP and web views.
- **Q2. The name is "Actions for Human",** the human's own words.
- **Q3. The binary clears it.** Any status change out of Blocked by human clears the section, whoever makes it: a hook, the CLI, MCP or the human's drag in the web UI. The binary archives what it clears as a comment.
- **Q3b and Q4. Append, and clear one by one.** This went against the drafter's lean.
  - A second `Blocker:` handoff against an item already in Blocked by human adds its actions to the section.
  - Each action has an identifier and can be ticked off on its own.
  - Leaving the column archives every action, ticked or not (Q3).
- **Q5. Just the ask.** This went against the drafter's lean. An action line holds only the ask. The agent and the time are not on the line; they stay in the `SubagentStop` comment and the archive comment.
- **Q7. Flag.** The hook moves the item as it does today, and marks an action whose ask is not phrased as a question, so the human sees a likely false blocker at once.
- **Q8. The kanban card shows the first action's text,** truncated. This went against the drafter's lean of a count.
- **Q9. The lead may clear the section** with a comment giving the reason. The column stays for a hook or the human to move.
- **Q6 moved to CF-31.** The `Blocker:` rule moved there, with the reviewer and refuter body changes and the handoff skill's worked example.
- **Q10 is answered by CF-29,** which runs the fork's tests in CI.
- **Q12. The lead may tick an action on the human's behalf** when the human answers it in the session, and says so in a comment on the item.
- **Q13. Ticked actions stay visible,** shown ticked, until the card leaves Blocked by human. Then the whole section clears and archives (Q3).
- **Q14. Two writers add actions.** This went against the drafter's lean of `SubagentStop` only.
  - `SubagentStop`, one action per `Blocker:` line, as before.
  - The lead, when it needs the human's decision outside a subagent handoff.
  - A lead-added action carries the same not-a-question flag as a hook-added one (Q15).
- **Q15. The flag is the fixed prefix `[not a question] `** on any action whose text does not end in `?`.

## The Actions for Human section

Everything in this section is **[supplied]** unless it restates a decision. Where the fork makes a choice non-obvious, the requirement stands and the mechanism is the plan's.

- **Storage.** A marked section of its own in the task file, a sibling of the acceptance criteria checklist. It holds checklist lines in the same shape: `- [ ] #1 <ask>` open and `- [x] #1 <ask>` ticked. Reusing the criteria shape and its manager is the drafter's lean for how; the requirement is only a numbered, tickable list that survives a parse and serialise round trip.
- **Numbering.** Actions are numbered from 1 each time an empty section is filled, and appending continues the numbering. Nothing removes a single action, so numbers never move while the section is filled. The only removals are the whole-section clears below.
- **Adding (Q14).** One add operation in the binary, reached two ways:
  - the CLI, a new repeatable flag on `task edit` (for example `--action <text>`), which `SubagentStop` calls with each `Blocker:` line's text, prefix stripped;
  - MCP `task_edit` (for example `actionsAdd`), which is how the lead adds one.
  Adding appends to whatever is there (Q3b), from either writer.
- **The flag (Q7, Q15).** An ask is "phrased as a question" when it ends in `?` once right-trimmed. One that does not is stored with the prefix `[not a question] `. **[supplied]** The binary's add operation applies the prefix, not the hook, so both writers get it from one place and neither can skip it. The prefix goes at the front because the kanban card truncates the text (Q8) and a suffix would be cut off. The column moves either way, and the `SubagentStop` comment is unchanged.
- **Adding never moves a column.** **[supplied]** This is the drafter's recommendation for how a lead-added action meets "the lead never writes a column":
  - An add, from any writer, is a field write and never changes status. `SubagentStop` still moves the item on a `Blocker:` line exactly as today; that move is the hook's, not the add's.
  - A lead-added action on a card already in Blocked by human appends, as a second `Blocker:` handoff would.
  - A lead-added action on a card outside Blocked by human is stored and shown (the modal, the views and the kanban card) but moves nothing. The card enters the human queue only as today: a `Blocker:` line through `SubagentStop`, or the human's own move.
  - The reason: having the binary move a card into Blocked by human when the lead adds an action would be the lead writing a column by proxy. The consequence, accepted by this recommendation: a lead-added action on a card outside the queue is not in the one place the human monitors. The lead is in the session with the human when it adds one, so it asks there as well.
  - The alternative the human may prefer instead: the lead routes its ask through a subagent whose handoff carries the `Blocker:` line. The drafter did not recommend it, because it spends a spawn to move a card.
- **Ticking (Q3b, Q12).** One action is ticked, or unticked, by number from three places: the CLI (for example `--check-action n` and `--uncheck-action n`), MCP `task_edit` (for example `actionsCheck`), and a checkbox in the web modal. Ticking changes only that action and never the status. The lead ticks through MCP only when the human answered that action in the session, and posts a comment saying so in the same session. **[supplied]** The comment quotes or summarises the human's answer and names the action's number.
- **Ticked actions stay (Q13).** A ticked action stays in the section, shown ticked, until the section is cleared.
- **Clearing on leaving (Q3).** On any status change out of Blocked by human, the binary empties the section in the same write. It also posts one comment archiving every action with its number, its text and whether it was ticked. A status write that leaves the item in Blocked by human clears nothing.
- **Clearing a card that never entered the column.** **[supplied]** Q3's clear only fires on leaving Blocked by human, so a lead-added action on a card outside the column would otherwise ride through to Done and into `.boards/completed/`. The drafter's recommendation: a move into Done from any column also empties and archives a non-empty section, in the same shape. Other status changes outside Blocked by human leave it alone.
- **The lead's clear (Q9).** A separate operation, for example `--clear-actions --comment <reason>`, that empties the section without a status change. It archives the actions in the same shape as the automatic clear, with the lead's reason. `lead.md` says the lead uses it only for an action it knows is void, such as a mis-bound or mislabelled blocker, and that the column stays.
- **Rendering.** The CLI view, MCP `task_view` and the web modal show the section before the Description, with each action's number and ticked state. The section appears only when it holds actions.
- **The kanban card (Q8).** The card shows the text of the first unticked action, truncated to a fixed length the plan picks, so a `[not a question] ` prefix is always visible. Nothing extra shows when no action is open.

## Non-goals

All **[supplied]** unless marked:

- No change to who writes columns. The section is a field, and adding an action, ticking one or clearing the section never moves the item (Decisions, Q9 and Q14).
- Ticking the last open action moves nothing. The human or a hook moves the item.
- No agent name or time on an action line (Decisions, Q5).
- No rewrite of a description, and no deleted comment. Every clear archives.
- The `SubagentStop` blocker comment stays as it is.
- The `Blocker:` rule and the reviewer and refuter bodies belong to CF-31 (Decisions, Q6).
- Not in this spec: CI coverage (CF-29), `task edit` on a completed card (CF-26), and the MCP `task_edit` status default (CF-27).
- No subagent gains a way to add actions directly. Subagents reach the section only through a `Blocker:` line.
- No notification outside the board.
- No fix for the focus re-binding behind CF-8's #8.
- No port implementation. The OpenCode board is deferred, and the Codex port is a spec.

## Acceptance criteria

The requirements are the human's (Decisions). The test shapes and exact wording are **[supplied]**, as are criteria 5, 11 and 12 wherever they rest on the drafter's recommendations above.

1. When `SubagentStop` moves an item to Blocked by human, the section holds one unticked action per `Blocker:` line. Each action's text is the ask alone, with no agent name or time. This is proven by a `board-hook-contract.sh` dry-run case that fails before the change.
2. An action whose text does not end in `?` once right-trimmed is stored with the prefix `[not a question] `, and one that does is stored without it, whichever writer added it. For `SubagentStop`, the item moves to Blocked by human in both cases, proven by dry-run contract cases. For the add operation itself, both cases are proven by a fork test.
3. A second `Blocker:` handoff against an item already in Blocked by human appends its actions, numbered after the existing ones. The existing actions and their ticks are unchanged. This is proven by a contract case and a fork test.
4. The lead can add an action through MCP `task_edit`. It appends after any existing actions, and the item's status is unchanged whatever column it is in. This is proven by a fork test that asserts the status before and after, run once on an item in Blocked by human and once on an item outside it.
5. **[supplied]** A move into Done from a column other than Blocked by human empties a non-empty section and posts the archive comment, in the same write. Any other status change outside Blocked by human leaves the section untouched. This is proven by fork tests.
6. The CLI view, MCP `task_view` and the web modal render the section before the Description, with each action's number and ticked state, and render nothing for it when it is empty. This is proven by fork tests.
7. The kanban card shows the text of the first unticked action, truncated with the flag prefix intact, and shows no action text when none is open. This is proven by a fork test.
8. One action can be ticked, and unticked, by number through the CLI, MCP `task_edit` and the web modal. Ticking changes no other action and no status, and a ticked action stays in the section, shown ticked. This is proven by one fork test per path.
9. Any status change out of Blocked by human empties the section in the same write and posts one archive comment listing every action with its number, text and ticked state. This holds whether the change comes through the CLI, MCP `task_edit` or the web server's update path, and it is proven by one fork test per path. A status write that stays in Blocked by human leaves the section untouched.
10. The lead's clear empties the section without a status change and posts the archive comment with the lead's reason. This is proven by a fork test that asserts the status is unchanged.
11. `lead.md` says when the lead may add an action (it needs the human's decision outside a subagent handoff), that adding one moves no column and so the lead also asks in the session, when it may tick one (the human answered it in the session) and that it comments when it does, and when it may clear the section (an action it knows is void), with the column staying in every case.
12. A task file with the section survives a parse and serialise round trip byte for byte. A task file without the section is written back without one. This is proven by fork tests.
13. The `SubagentStop` blocker comment is posted unchanged, so CF-19's assertions still hold.
14. board-conventions (including its CLI table), `docs/fleet-design.md` section 7, `docs/agent-contract.md` and `hooks/README.md` describe how the section is written by both writers, flagged, ticked and cleared.
15. `bash claude/evals/lib/check-all.sh` passes, and each new fork test file is listed in `BOARD_TESTS`. Until CF-29 lands, the PR records a local `bun test` run. The version is bumped in both manifests, and `claude/coder-fleet/board/LICENSE` and `NOTICE.md` are unchanged. `migration-checklist` findings are in the PR, since `lead.md` changes.
16. The OpenCode divergence register has a row marked Deferred with the board, and the Codex docs carry a note.
