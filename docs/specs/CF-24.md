## What the human said

Verbatim, 2026-09-27: "Acceptance Criteria and Definition of Done never appear to be filled in by the agents."

Issue #3, from the Fathom card FTH-001.12, in the lead's summary:
- The card's criteria read 0/5, its Definition of Done was empty, and its Implementation Notes were three days stale. The human reasonably moved it to Done in the web UI.
- The lead then called it not done because plan phase 10 was unmerged, even though all five criteria were proven on main by named tests. Nothing on the card showed that the card and the plan had diverged.

The issue sets three requirements for the lead:
- **(a) At plan approval:** copy the plan's "Done when" into the Definition of Done, and turn plan phases outside the card's criteria into criteria or a sub-issue.
- **(b) At each phase start and each merge:** post one progress comment.
- **(c) When a criterion is proven on main:** tick it and name the test.

## Problem

- **Criteria are written but never ticked.** CF-8's and CF-6's were ticked by hand after merge on 2026-09-27, and those are the only ticks on this board. Open items filed ahead of a spec carry no criteria at all: CF-1, CF-2, CF-3, CF-7, CF-24 and CF-25.
- **Definition of Done is never written.** The fork supports project defaults through `definition_of_done:` in `.boards/config.yml` (`board/src/file-system/operations.ts:2135`), but applies them only when an item is created (`board/src/core/backlog.ts:1337`). Neither this repository's config nor `templates/board.config.yml` sets the key.
- **Plans have no "Done when".** No plan under `docs/plans/` has one, and neither `lead.md` nor `spec-to-plan` asks for one.
- **The card and the plan can diverge silently.** This is FTH-001.12's failure.
- **No rule says who ticks.** The design and board-conventions assign columns and say nothing about fields. `docs/agent-contract.md:80` forbids every board write by an agent, although the lead already files items and comments (see "The agent-contract line" below).

## Decisions

The human's answers, 2026-09-27:

- **Q1. Only the lead ticks,** and only once a criterion is proven on main, naming the test that proves it (issue #3 (c)). No subagent, hook or handoff line ticks.
- **Q2. Every plan ends with a required "Done when" section.** The lead writes it, and `spec-to-plan`'s plan stage refuses a plan without it.
- **Q3 and Q12. Enforcement is by machinery.** `TaskCompleted` refuses Done while anything on the card is unticked (Q13 widens this to the Definition of Done), and moves the item to Blocked with a comment listing what is unticked. It has two stated limits:
  - It depends on CF-20. Until the lead can complete a `[board:<id>]` task, nothing reaches this path.
  - It cannot see the human dragging a card to Done in the web UI. The human's own move is not gated.
- **Q4. Never.** No item may be created without acceptance criteria. This went against the drafter's lean.
  - **[lead's reading]** An item filed ahead of its spec carries provisional criteria that say what the spec must settle, for example `- [ ] #1 Provisional: the spec settles who ticks criteria and on what evidence`. The spec's criteria replace them when the spec is approved (Q4b).
  - This covers every item the lead files and every item `fleet-steward` files.
- **Q4b. One card criterion per spec criterion.** Each is a one-line summary with the same number as the spec's, and the spec is authoritative on the wording. The cost, accepted knowingly: board-conventions says to link specs rather than paste their contents, because "a copy on the issue goes stale silently". This is a paste of the criteria list. board-conventions has to name it as the one exception, and the spec wins wherever the two disagree.
- **Q5. The default Definition of Done** for this repository has six items:
  1. `bash claude/evals/lib/check-all.sh` passes on the branch.
  2. The reviewer approved, and a refuter round ran where the plan calls for one.
  3. `migration-checklist` findings are in the PR when an agent body or skill frontmatter changed.
  4. The version is bumped in `plugin.json` and `.claude-plugin/marketplace.json`, and the release is tagged and pushed. This is the human's rule of 2026-09-27, tracked as CF-28.
  5. The port divergence register has a row where a ported artefact changed.
  6. The spec and plan are linked as references.

  The mechanism is option (i): the defaults are applied when the item is filed, and the plan's "Done when" is appended at approval, with duplicates dropped.
- **Q6. The phase comment's first line** is as drafted: `Phase <n> of <m>: <started | merged to main at <sha>>. Done still needs: <criteria numbers or phases>.`
- **Q7. The plan wins** when the card and the plan disagree. This went against the drafter's lean.
  - **[lead's reading]** The plan is authoritative. Before judging an item done or not done, the lead brings the card into line with the plan, by adding criteria or splitting a sub-issue, so the card never silently diverges.
  - That still closes issue #3's failure, which was a card that did not show the divergence.
  - It means the lead never calls an item not done on a ground the card does not show.
- **Q8. `/init` gives new projects a default.** The `/init` template carries a generic default Definition of Done, and `/init` says so.
- **Q9. Backfill once.** The defaults are added once to every open item, and closed items are left alone. Implementation Notes stays the human's field; the lead's phase comments are the progress record.
- **Q10. Two specs.** Whether one plan covers both CF-24 and CF-25 is the lead's call at planning.
- **Q11. The OpenCode port** gets register rows only.
- **Q13. The lead ticks Definition of Done items too,** by the same rule as criteria: with evidence, named in a comment. The `TaskCompleted` gate refuses Done while any acceptance criterion or any Definition of Done item is unticked.
- **Q14. No criteria means refused.** An older item with no acceptance criteria at all is refused by the gate, not waved through. The one-time backfill (Q9) gives each open item without criteria provisional ones first, so no open item meets the gate empty-handed.
- **Q15. An unreadable card follows `CODER_FLEET_TEST_GATE`.** If the gate cannot read an item's criteria or Definition of Done (board missing, file unparseable), strict refuses and lenient passes with a log line, as the test gate treats an unknown result.
- **Q16. The requirement is on by default for new projects.** The `/init` template switches "never file an item without criteria" on, and a project can turn it off in its board config.
- **Q17. Numbering.** **[lead's default]** Taken on the drafter's lean without a question; the human may edit it. The card's criteria mirror the spec's, numbered 1 to n. Criteria the plan adds beyond the spec follow after n. If the spec is revised, the lead rewrites the list to match.

## What "never without criteria" needs

The requirement is Q4 and Q16; the mechanism is the plan's. **[supplied]** What each place would need:

- **The board fork.**
  - A config key, for example `require_acceptance_criteria: true`, which makes the core create path refuse an item with no criteria.
  - The refusal has to hold on every path: the CLI (`task create`), MCP `task_create` and the web UI's create form. The check belongs in the core rather than in one front end.
  - The refusal message says why and names the key, so a project that wants it off knows what to change (Q16).
  - Fork tests show the refusal on each path, and show that the key being absent or `false` keeps today's behaviour. A project installed before this change has no key and is unaffected until it opts in; a project initialised after it gets the key from the template.
- **MCP `task_create`.** The refusal must come back as a tool error the lead sees, not a silent success. CF-26's "fail loudly" rule for `task edit` applies here too.
- **`fleet-steward`.** Its body's filing step (`fleet-steward.md:28`) says to write criteria for every item it files. For a sweep finding, the criteria state what closing it means, for example "the new model is in the roster or recorded as not adopted". The steward smoke eval gains a check that the items it files carry criteria.
- **The lead.** `lead.md` step 5 says every filed item carries criteria, and that an item filed ahead of its spec carries provisional ones.
- **This repository and the template.** Both configs set the key to on (Q16). The template says in a comment how to turn it off.

## Acceptance criteria

The requirements are the human's (Decisions). The test shapes and exact wording are **[supplied]**.

1. Four documents say that only the lead ticks an acceptance criterion or a Definition of Done item, only with evidence (for a criterion, proven on main), naming the test or evidence in a comment, and that a tick is a field edit and never a column write: `docs/fleet-design.md` section 7, board-conventions, `lead.md` and `docs/agent-contract.md`. `docs/agent-contract.md:80` names the board writes listed under "The agent-contract line", building on CF-9's wording.
2. Every plan ends with a "Done when" section. `lead.md` step 3 says to write one, and `spec-to-plan`'s plan stage refuses a plan without it, proven by `workflow-logic.mjs` tests that fail first. **[supplied]** The heading is exactly `## Done when`.
3. `lead.md` says what the lead does at plan approval:
   - append the plan's "Done when" items to the card's Definition of Done after the defaults, dropping duplicates;
   - bring the card into line with the plan, making each plan phase not covered by a criterion either a criterion or a sub-issue;
   - post one comment saying which it did.
4. `lead.md` says the lead posts exactly one comment at each phase start and each merge, whose first line is the agreed shape (Decisions, Q6).
5. `lead.md` says the plan is authoritative (Decisions, Q7), and that the lead never judges an item done or not done on a ground the card does not show.
6. On a passing test gate for a `[board:<id>]` task, `TaskCompleted` moves the item to Done only when it has at least one acceptance criterion and every acceptance criterion and every Definition of Done item is ticked. Otherwise it moves the item to Blocked with a comment listing each unticked item by section, number and text, or saying the item has no criteria. Proven by `board-hook-contract.sh` dry-run cases that fail first, one each for an unticked criterion, an unticked Definition of Done item and an item with no criteria. **[supplied]** It exits 2, as the failing-test path does, so the task cannot complete. Two further cases prove the edges: an item with everything ticked reaches Done, and a failing test gate still wins over the checklist check.
7. When the gate cannot read the item's criteria or Definition of Done, it follows `CODER_FLEET_TEST_GATE`: under `strict` it refuses as in criterion 6 with a comment saying the card could not be read, and under `lenient` it lets the item through and writes a line to the hook log. Proven by one dry-run contract case per mode.
8. `hooks/README.md` and `docs/limits.md` state both limits of criterion 6: it depends on CF-20, and it cannot see a human's drag to Done in the web UI. `hooks/README.md` also states criterion 7's behaviour beside the existing `CODER_FLEET_TEST_GATE` description.
9. Creating an item with no acceptance criteria is refused on the CLI, MCP `task_create` and web UI paths when the config requires criteria, as set out in "What never without criteria needs", and allowed when the key is absent or off. Proven by fork tests that fail first.
10. This repository's `.boards/config.yml` and `templates/board.config.yml` both switch the requirement on. The template says how a project turns it off, and `/init` step 2b says the requirement is on and where to change it.
11. `fleet-steward.md` requires criteria on every item it files, and the steward smoke eval checks for them. `migration-checklist` findings are in the PR.
12. `lead.md` describes provisional criteria and their replacement by the spec's criteria at approval, one card criterion per spec criterion with the same number (Q4b). **[lead's default]** Criteria the plan adds beyond the spec's are numbered after them, and a revised spec means the lead rewrites the list (Q17). board-conventions names this as the exception to "link, do not paste" and says the spec wins on wording.
13. This repository's `.boards/config.yml` carries the six-item default Definition of Done from Q5, and a newly created item carries it. Proven by a fork test or a recorded run.
14. `templates/board.config.yml` carries a generic default Definition of Done, and `/init` step 2b says it is there and how to change it.
15. After the backfill, every item not in Done or `.boards/completed/` carries the default Definition of Done items, and every open item that had no acceptance criteria carries provisional ones (Q14). Every closed item's file is byte-identical to before.
16. board-conventions and `lead.md` say Implementation Notes is the human's field and the phase comments are the progress record.
17. **[supplied]** The first item planned after this merges is cited in the PR or a follow-up comment. Its card shows the plan's "Done when" in its Definition of Done, a phase comment per phase start and merge, and each tick naming its test or evidence.
