# CF-43: Add a board_stop tool and /board stop

Status: approved by the human on 2026-09-27 with the recommended answer to every open question.

Board item: CF-43 (feature, Low, To Do). Source: GitHub issue rzem-ai/coder-fleet#15, read as data. Route: coder. It touches the board fork, and it shares `NOTICE.md` and `board/package.json` with the unmerged CF-26/27 branch.

## Findings, with evidence

1. **Two tools, no stop.** `board/src/mcp/tools/serve/index.ts:15-49` registers `board_serve` (`:18-31`) and `board_url` (`:33-45`) only. `board_serve`'s description ends "The UI stops when this session's MCP server stops." (`:22`).

2. **The stop already exists, but only at shutdown.** `McpServer.stopWebUi` (`board/src/mcp/server.ts:141-145`, "Safe to call when it is not") is called only from `McpServer.stop` (`:193`).

3. **A stop during a start is lost.** `startWebUi` sets `this.webUi` only when `ui.start` resolves (`:128-132`). `stopWebUi` reads `this.webUi` (`:142`), so a stop that arrives while `webUiStarting` is pending does nothing, and the start then sets `webUi` and the UI is left running.

4. **Stopping writes to the MCP transport.** `BacklogServer.stop` ends with `console.log("Server stopped")` (`board/src/server/index.ts:638`). In the MCP process, stdout is the JSON-RPC stream. `startWebUi` passes `quiet: true` for exactly that reason (`server.ts:122`, `:129`), but `stop` has no quiet path. Today this happens only as the session ends. A `board_stop` would write the line mid-session. Nothing in `cli.ts:252-259` redirects console output.

5. **How the stop behaves.**
   - `BacklogServer.stop` closes tracked WebSockets (`index.ts:618-623`).
   - It then calls `serverRef.stop()` without `closeActiveConnections`, raced against 1.5 s (`:627-637`), and sets `this.server = null` either way, so `url` becomes null even if a connection lingers.
   - There is a guard against re-entry (`_stopping`, `:599-601`, reset `:640` and at start `:403`).

6. **A fresh start gets a fresh port.** `startWebUi` builds a new `BacklogServer` each time (`server.ts:127`) and passes port 0 (`:129`), so a serve after a stop binds a new random port with a fresh `Core` and watchers.

7. **A pre-existing hazard, out of scope.** `BacklogServer.start` calls `process.exit(1)` on a bind failure (`index.ts:576-586`), which would end the MCP process. Port 0 makes that unlikely.

8. **Tests and suite.** `board/src/test/mcp-serve.test.ts:1-78` has four cases and is already in `BOARD_TESTS` (`claude/evals/lib/check-all.sh:92`), so new cases there need no wiring. `afterEach` calls `server.stop()` (`:34`).

9. **Nobody else lists the serve tools.**
   - Every agent except `lead` has an explicit `tools:` allowlist, and none names `board_serve` or `board_url`. `lead` has no `tools:` field and so has every tool.
   - `fleet-steward` and `spec-writer` list board write tools in `disallowedTools`, but their allowlists already exclude `board_stop`.
   - `enforce-agent-scope.sh` has no board-tool rule, and the PreToolUse matcher is `Write|Edit|MultiEdit|NotebookEdit|Bash` (`hooks/hooks.json:52`), so MCP calls never reach it.
   - No file under `opencode/` or `codex/` names `board_serve`.
   - So no hook or agent list needs the new name.

10. **Docs that describe the UI's lifetime:**
    - `commands/board.md:2`, `:5` and `:9-11`
    - `skills/board-conventions/SKILL.md:139` ("It stops when the session's MCP server stops.")
    - `README.md:43` ("`board` opens the board's web UI for this session")
    - `serve/index.ts:5-14`

11. **NOTICE and version on main differ from the CF-26/27 branch.** `NOTICE.md` on main has no behaviour-divergence section. The CF-26/27 branch adds `### Behaviour changed after import`. `board/package.json` is 0.1.4 on main and 0.1.5 on that branch.

## Design decisions

1. **`board_stop`, beside the other two in `serve/index.ts`.**
   - Empty schema.
   - Annotations `{ title: "Stop the board", readOnlyHint: false, destructiveHint: false, idempotentHint: true }`. A viewer stopping destroys no data.
   - It returns `WebUiStatus` plus `stopped: string | null`, the URL it stopped, or null when nothing was running. For example `{running:false,url:null,host:null,port:null,stopped:"http://127.0.0.1:53121"}`.
   - Its description says it is idempotent and that a later `board_serve` starts a fresh UI on a new random port, so the old URL stops working.

2. **Serialise start and stop in `McpServer`.**
   - `stopWebUi()` first awaits a pending `webUiStarting` (errors swallowed), then stops. It returns the stopped URL and records its promise in `webUiStopping`.
   - `startWebUi()` awaits a pending `webUiStopping` before starting.
   - A stop issued during a start therefore wins, and a start issued during a stop gets a fresh UI.
   - `board_stop` calls `stopWebUi` and returns `{...webUiStatus(), stopped}`.

3. **Make `BacklogServer.stop` safe inside the MCP process, with no signature change.**
   - `start` remembers `options.quiet`, and `stop` skips `console.log("Server stopped")` when it was set.
   - `stop` calls `serverRef.stop(true)`, so HTTP connections that are still active are closed rather than left to finish.
   - The only callers are `McpServer.stop`, `board_stop` and tests. `board serve` in `cli.ts:261-270` never calls `stop`, so the CLI's behaviour does not change.
   - The 1.5 s race stays.

4. **`/board stop`.**
   - `board.md` gains `argument-hint: [stop]`.
   - With no argument it does what it does today.
   - With `stop`, it calls `board_stop` (`mcp__plugin_coder-fleet_board__board_stop`), then prints either "stopped <url>" or "the board UI was not running".
   - With anything else, it names the two forms and stops.
   - The description line becomes "Start this session's board web UI, or stop it with `stop`".

5. **No hook or agent change** (finding 9). The PR says so, so a reviewer does not go looking.

### Phase 1: failing tests

Extend `board/src/test/mcp-serve.test.ts` and keep the existing four cases.
- **(a) Nothing running:** `board_stop` is not `isError`, returns `running:false` and `stopped:null`, and `board_url` still reports not running.
- **(b) Serve then stop:** `stopped` equals the served URL, `board_url` reports `running:false`, and `fetch(url + "/api/tasks")` is refused.
- **(c) Stop twice:** the second call returns `stopped:null`, with no error.
- **(d) Serve after stop:** `board_serve` returns `running:true`, and the new URL answers 200 on `/api/tasks`. The ports are not asserted to differ, because the kernel may reuse one.
- **(e) Open WebSocket:** a WebSocket opened to the UI (`url.replace("http","ws")`, awaited `open`) receives `close` within 2 s of `board_stop`.
- **(f) Stop during a start:** `board_serve` is fired without awaiting, `board_stop` is awaited, then the serve promise. `board_url` reports `running:false`, and the served URL is refused.
- **(f') The same race at the server level:** calling `server.startWebUi()` and `server.stopWebUi()` directly, so the case is red on the race alone and not on the missing tool.
- **(g) Nothing on stdout:** with `spyOn(console, "log")` and `spyOn(process.stdout, "write")` installed after `board_serve`, `board_stop` makes zero calls to either.
- **(g') The same at the server level,** calling `server.stopWebUi()` directly.
- **(h) Listed:** `listTools` includes `board_stop` with `idempotentHint: true`.

## Risks

- **Bun's `server.stop(true)` is unconfirmed.** That it closes idle keep-alive and in-flight connections is from the Bun API, not something this repo has tested. Case (b) proves the listener is gone and (e) proves the socket closes. An in-flight long request is not covered.
- **Conflicts with CF-26/27.** Expect textual conflicts in `NOTICE.md` and `board/package.json` if that branch lands first. Both resolve trivially.
- **The stdout spy may not catch Bun's console.** If Bun's `console.log` bypasses `process.stdout.write`, (g) relies on the `console.log` spy alone. That is enough for the known write at `:638`.

## Open questions, each with a recommended answer

1. Should `board_stop` report the URL it stopped? **Yes, as `stopped`.** The command can then say "stopped <url>" or "was not running" without calling `board_url` first.
2. Should `serverRef.stop(true)` apply to every caller, or only behind an option? **Every caller.** The only callers are the MCP server and tests, and a stopped viewer should not keep serving.
3. Should `destructiveHint` be true? **No.** Stopping a viewer loses no data, and `board_serve` brings it back.
4. Should the `process.exit(1)` on a bind failure be fixed here? **No.** The lead files it as a separate item. It predates this change and is not reachable with port 0 in practice.
