# CF-20: Give the lead a way to close an item when native task tools are absent

Status: approved by the human on 2026-09-28, with open question 1 answered "both scopes" rather than the recommended project scope, and the recommended answers to open questions 2 and 3.

Board item: CF-20 (bug, High, To Do). Tracked as point 7 of GitHub issue rzem-ai/coder-fleet#3. Blocks CF-24, whose TaskCompleted checklist gate cannot fire until this lands. Route: scripter, one worktree. Small.

## Findings, with evidence

1. **Nothing on this board has ever reached Done.** Fourteen items are merged and still outside Done: CF-6, CF-8 and CF-9 in To Do; CF-23, CF-25, CF-26, CF-27, CF-30, CF-31, CF-41, CF-42, CF-43, CF-44 and CF-45 in In Progress. The only route to Done is a native task whose subject carries `[board:<id>]`, completed with `TaskUpdate`, which fires `TaskCompleted` (`hooks/board-task-completed.sh`, board-conventions, `lead.md` step 6).
2. **Claude Code turns the task tools off for every current model.** In Claude Code 2.1.283 the task tools (`TodoWrite`, `TaskCreate`, `TaskGet`, `TaskUpdate`, `TaskList`) are gated by `$8() = uE() && uU()`:
   - `uE()` is true unless `CLAUDE_CODE_ENABLE_TASKS` is false.
   - `uU()` is true when the session is a background job or daemon, when the launch tool list names one of the task tools, when the model is unknown or an inference profile, or when the model is in a fixed legacy set: Claude 3.x, Opus 4.0 to 4.7, Sonnet 4.0 to 4.6, and Haiku 4.5. Otherwise it is true only when `CLAUDE_CODE_ENABLE_TODO_TOOLS` is true.
   - The lead's frontmatter says `model: opus`, which now resolves to Opus 5.5. That model is not in the set, so the lead has no `TaskCreate` or `TaskUpdate`, and `TaskCompleted` never fires.
3. **Measured, not inferred.** The tool list in each session's `init` event (`claude -p 'Say ok.' --output-format stream-json --verbose`), 2026-09-28:

   | Model | Variable unset | `CLAUDE_CODE_ENABLE_TODO_TOOLS=1` |
   |---|---|---|
   | claude-opus-5-5 | Task, TaskStop | Task, TaskCreate, TaskGet, TaskList, TaskStop, TaskUpdate |
   | claude-sonnet-5 | Task, TaskStop | Task, TaskCreate, TaskGet, TaskList, TaskStop, TaskUpdate |
   | claude-haiku-4-5 | Task, TaskCreate, TaskGet, TaskList, TaskStop, TaskUpdate | not run |

   With the variable set only in a project's `.claude/settings.json` `env` block and unset in the shell, Opus 5.5 got the same full set. `"1"` and `"true"` both work. Asking the model to list its own tools is not evidence: one such run named tools the session did not have.
4. **Where the lead is configured.** `templates/project-settings.json` sets `agent: coder-fleet:lead`. `/init` merges its keys into the project's `.claude/settings.json` (`commands/init.md:19-26`), and `/kickoff` step 2 checks `agent` (`commands/kickoff.md:13`). This repository's own `.claude/settings.json` is the template's content and has no `env`.
5. **The rejected workaround stays rejected.** The board MCP `task_complete` would move the card, but that is the lead writing a column, which `lead.md`'s Invariants forbid. It would also skip the test gate, and CF-24's checklist gate after it.

## Design decisions

1. **Turn the task tools on where the lead is configured.** `templates/project-settings.json` gains `"env": { "CLAUDE_CODE_ENABLE_TODO_TOOLS": "1" }`. Any project that runs the lead then has the tools the Done route needs, whatever the model. Nothing new decides a column: `TaskCompleted` stays the only writer of Done.
2. **User scope as well, by the human's decision.** `claude/home/settings.json` gains the same `env` key, so every session on a fleet machine has the task tools, including one in a project that has not run `/init`. `install-home.sh` merges settings additively (`claude/scripts/merge-settings.py`): objects are merged key by key, so the key lands without touching any other `env` entry a machine already has. For this one key the repository's value wins, as it does for every scalar the repository supplies. The project key stays too, so a project carries its own requirement to a machine that has not re-run the installer. Open question 1.
3. **`/init` merges the one key; `/kickoff` checks it and offers it.**
   - `/init` adds `env.CLAUDE_CODE_ENABLE_TODO_TOOLS` when absent, inside an existing `env` object if there is one, and never overwrites a value the project already sets.
   - `/kickoff` step 2 checks that the key is set, and that `TaskUpdate` is among the session's own tools. Either one missing fails the Lead step with the cause (the model gate) and the fix: the key, then a new session, because env is read at startup. The fix is offered and changes nothing without the human's yes, as the Doing to In Progress rename does.
4. **The fallback, when the tools are still absent.** board-conventions and `lead.md` say the lead never moves a card to Done itself. It names the item to the human, who moves it in the web UI. That is criterion 2's second arm, for a CLI that changes the gate again.
5. **Docs.** The hooks README's `TaskCompleted` section and design section 7 say the route needs the task tools and why they can be off. `docs/limits.md` records that the fleet depends on a CLI gate it does not own, and the kickoff check is the tripwire.
6. **A deterministic test.** A contract case, in the roster contract or a new small check wired into `check-all.sh`, asserts that the template sets the key to a truthy value, and that `kickoff.md` and `init.md` name it. The model-gated behaviour itself is proven once, live, in the release step. It is not in CI, because it needs a paid model call.

## Risks

- **The gate is Claude Code's, and it can change.** A later CLI could rename the variable or change the default. The kickoff check turns that into a named failure instead of a silent one, and `limits.md` records the dependency.
- **Other projects need a new session after `/kickoff` adds the key,** because env is read at startup. Kickoff says so.
- **A CLI older than the variable** simply ignores it. The kickoff tool check still reports the tools as missing.
- **Merge overlap with CF-52,** which adds `worktree.baseRef` to the same template. Both are one-key additions, so whichever lands second rebases trivially.

## Open questions, each with a recommended answer

1. **Project scope or user scope?** Recommended: project scope. **Decided by the human: both.** See design decision 2.
2. **Also set `CLAUDE_CODE_ENABLE_TASKS`?** **No.** It defaults to on. Setting it would pin a value the fleet has no reason to own.
3. **Close the fourteen stranded items through the gate, or by hand?** **Through the gate,** one `[board:<id>]` task each, in the release session. It proves the route at scale, and every Done card then has a `TaskCompleted` commit behind it.
