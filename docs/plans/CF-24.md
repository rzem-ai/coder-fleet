## Design decisions

1. **One plan, one board item and one PR, built in phases. No sub-issues.**
   - The card mirrors the spec's 19 criteria (Q4b). Sub-issues would each need their own criteria mapped back to one spec, which is the drift this item exists to stop.
   - Each coder phase gets its own review round.
   - Fallback: if #18 has not merged when Phase 2 is green, Phases 1-2 (fork) and 4 (workflow) may ship as a first PR, with the rest following. The Done when list below stays the single record either way.

2. **CF-24 before CF-25.**
   - CF-25's plan then follows the numbered Done when rule, and its card meets CF-24's gate.
   - CF-24's fork change is small and CF-25's is large, so CF-25 rebases over less.
   - CF-25 waits on CF-27 and CF-19 anyway.
   - The agent-contract sentence names the writes that exist on main. CF-25 adds its Actions for Human clause, which is its criterion 14. See open question 2.

3. **The checklist gate sits in TaskCompleted, on every path that would write Done.**
   - It runs on `pass`, and on the lenient no-result path, which is this repo's normal path.
   - It runs only when `page_id` is set, so an unmarked execution task never reads a card.
   - The test verdict is decided first. On `fail`, or on a strict gate with no result, the existing path runs unchanged and no card is read, so a failing test gate always wins.

4. **A new `board_item_checklist HOOK REF` in `lib/board.sh`.** One `task view --json`, one jq pass. Return codes:
   - **0:** at least one criterion, and everything ticked. An empty Definition of Done counts as all ticked.
   - **1:** unfinished. Prints one line per problem, in this order: `- This item has no acceptance criteria.` when there are none, then `- Acceptance criteria #<n>: <text>` for each unticked criterion, then `- Definition of Done #<n>: <text>` for each unticked item, each text cut to 200 characters.
   - **2:** unreadable. The call failed (no board, a timeout, shim exit 127), the output is not JSON, or either key is missing or not an array. Prints the reason.
   - **3:** the board is disabled. Nothing was read.
   - It is gated on `board_disabled`, not `board_would_send`: a dry run still reads, like `board_focus_id`, so the verdict and exit code are the same in a dry run as in a live one.

5. **What the hook does with each code.**
   - **1:** `board_write` to Blocked, headline `Blocked. The card is not finished, so "<title>" could not be marked complete.` (the untitled form drops the quote). Then a blank line, `Unticked:` and the lines. The same list goes to stderr with "The lead ticks each with its evidence, then completes the task again." Then `exit 2`.
   - **2 under strict:** Blocked, headline `Blocked. The card could not be read, so "<title>" could not be marked complete.`, plus the reason. Then `exit 2`.
   - **2 under lenient:** log `could not read the card for <id> (<reason>); the gate is lenient, so moving to Done`, then continue.
   - **3:** log `the board is off, so the card was not read and the checklist gate did not run`, then continue.
   - The existing log line `tests pass; moving to "<Done>"` stays byte-identical and moves after the check, because R03's `fresh-pass-honoured` greps it.

6. **The create refusal lives in the core, behind `require_acceptance_criteria`.**
   - It is a boolean key, parsed, serialised and listed in `BOOLEAN_CONFIG_KEYS`.
   - The check comes after the title check at `backlog.ts:1286` and before any id is allocated or file written. It counts criteria after trimming.
   - It applies to every status, Draft included.
   - Message: `Refused: this board requires at least one acceptance criterion on every new item (require_acceptance_criteria: true in .boards/config.yml). Add one with --ac on the CLI, acceptanceCriteria on task_create, or the form's criteria; set the key to false to turn this off.`
   - With the key absent or false, behaviour is exactly as today.
   - Because the serialiser keeps the key, `definition_of_done_defaults_upsert` and the web config update cannot turn the requirement off by accident.

7. **CLI additions, the smallest set the backfill and the "tools are missing" fallback need.**
   - `task edit`: repeatable `--dod <text>`, `--check-dod <n>`, `--uncheck-dod <n>`, `--remove-dod <n>`, mapped to the builder's existing fields.
   - `task create`: `--dod <text>`.
   - A new `board config show --json`, printing `{schemaVersion:1, kind:"config", config:{statuses, definitionOfDone, requireAcceptanceCriteria}}` from `loadConfig`, so scripts reuse the fork's parser rather than parse YAML themselves.

8. **The spec-to-plan refusal is a read lane plus a pure function.**
   - The writer prompt changes: a status line at the top reading "awaiting the human's approval" replaces the closing approval line. The file ends with `## Done when`: one numbered line per spec acceptance criterion with the spec's number, then plan extras numbered after.
   - A new phase, `Check plan`, runs an agentType-less lane. It runs `grep -nE '^(#{1,6} |```|~~~|[0-9]+\. )'` on the plan and on the spec and returns both outputs verbatim.
   - `doneWhenGate(planLines, specLines)` toggles fence state on the fence lines. It requires:
     - the last H2 outside a fence to be exactly `## Done when`;
     - at least one numbered line after it, numbered 1..k with no gap;
     - k to be at least n, the spec's numbered criteria under `## Acceptance criteria`, when n > 0.
   - A null lane result, or any failed check, returns `stage: 'blocked'` with the reason. The `nextStep` says the draft is at `docs/plans/<issue>.md` for the lead to finish by hand.
   - This shares its shape (lane, pure function, blocked return) with CF-12.3's planned challenge gate, which runs before `Plan angles` rather than after the writer. Whichever lands second rebases.

9. **The backfill is a shipped script: `claude/coder-fleet/scripts/board-backfill.sh [--dry-run]`.** It sits beside CF-41's `prune-worktrees.sh`. Steps:
   1. Read the defaults from `config show --json`. It exits 2 if `definitionOfDone` is empty.
   2. List items with `task list --json`. That never includes `.boards/completed/`. It then skips any item whose status matches Done, ignoring case and spaces.
   3. For each open item, one `task view --json`, then one `task edit` adding only the defaults whose trimmed text is not already on the card. If the item has no criteria, the same edit adds `--ac "Provisional: the spec settles what done means here, and its criteria replace this one"`.
   - It exports `CODER_FLEET_BOARD_NO_COMMIT=1` and ends by printing the one commit command, so the backfill is one commit rather than about seventy.
   - Output is one tab-separated line per item: `added <id> <n>`, `provisional <id>`, `unchanged <id>`, `skipped <id> done`, with `would-` prefixes under `--dry-run`.
   - Exit 0 when it ran, 1 if any edit failed, 2 on a usage error.
   - It is idempotent. It is shipped because the gate refuses criterion-less items in every project that installs this version, not only this one.

10. **Where the rules live.**
    - `lead.md` gets short sentences:
      - step 3: every plan ends with `## Done when`;
      - step 5: every filed item carries criteria;
      - steps 3 and 5, which carry the upkeep rule since v0.27.9 (#30), extended to cover criteria 1, 3, 4, 5, 12 and 16.
    - board-conventions gets a new section, "The card's fields and who writes them", carrying the detail:
      - ticks and their evidence;
      - defaults;
      - provisional criteria and their replacement with `acceptanceCriteriaSet`;
      - the "link, do not paste" exception;
      - Implementation Notes as the human's field;
      - phase comments as the progress record;
      - the gate;
      - the not-applicable rule;
      - change defaults by editing `config.yml`, not the upsert tool.
    - The lead ticks through one `task_edit` that carries both the check and the comment, so a tick and its evidence land in one commit.

11. **A Definition of Done item that does not apply** (a port row when no ported artefact changed, a `migration-checklist` finding when no body changed) is ticked with a comment reading `not applicable: <reason>`. Otherwise every item would be held open forever, and the gate would teach the lead to tick without evidence.

12. **The defaults, as block-style YAML with a comment above.**
    - This repo, Q5's six items:
      1. "`bash claude/evals/lib/check-all.sh` passes on the branch"
      2. "The reviewer approved, and a refuter round ran where the plan calls for one"
      3. "`migration-checklist` findings are in the PR when an agent body or skill frontmatter changed"
      4. "The version is bumped in plugin.json and .claude-plugin/marketplace.json, and the release is tagged and pushed"
      5. "The port divergence register has a row where a ported artefact changed"
      6. "The spec and plan are linked as references"
    - The template, a generic four:
      1. "The project's checks pass on the branch"
      2. "A reviewer approved the change"
      3. "Docs that describe the changed behaviour are updated"
      4. "The spec and plan are linked as references"

## Risks

- **Every project gets the gate on upgrade.** A Fathom item with no criteria is refused at TaskCompleted. That is Q14 as decided, and only after CF-20 does anything reach it. The release note says so.
- **The card roughly doubles.** A card carries its criteria plus the six defaults plus the plan's Done when lines, and each Done when line mirrors a criterion. The lead ticks both in one `task_edit` with one comment, and it is still more to tick.
- **Config rewrites drop comments.** `definition_of_done_defaults_upsert` and the web settings page rewrite `config.yml` and drop its comments. The key survives (extra 21). board-conventions says to edit the file by hand.
- **The plan gate trusts a lane to return grep output verbatim.** That is the same trust level as CF-12.3's Lane A. A lane that paraphrases fails closed, because a missing or garbled heading blocks.
- **In-session plans are not gated.** A plan the lead writes without `spec-to-plan` is held only by `lead.md` step 3.
- **Board noise.** About 70 backfill edits leave one commit, because the script runs with `NO_COMMIT`. A lead that runs it without committing leaves `.boards` dirty until the next board write sweeps it into an unrelated commit.
- **Conflicts** with #18, CF-42, CF-44/45 and CF-12.3 in `lib/board.sh`, the contract stub, `lead.md` and `workflow-logic.mjs`. All are textual, and the sequencing above names who rebases.
- **Delivery is two-step.** A stale `~/.local/bin/board` ignores `require_acceptance_criteria` silently until the rebuild in Release step 2.
