# CF-12.1: spike the three Claude Code behaviours the editors depend on

Status: approved by the human on 2026-09-27. Step 2 variation: the scripter attempts the paid batch in-session first and hands it to the human only if the sandbox or a nested-launch refusal stops it. No Pro account is available, so E1p is not run and question (1) on Pro rests on the ranked substitutes. AC #1 amended to three behaviours; the harness is committed. Board item: CF-12.1, parent CF-12. Spec: `docs/specs/CF-12.md`, section "Precondition: CF-12.1". Output: a findings file plus a re-runnable harness. No plugin code changes.

## What the spike must answer

1. What a subagent with `model: fable` does on a Pro account: runs on Fable, fails the spawn, silently runs on another model, or - a fourth outcome the docs reveal - runs on Fable billed to usage credits.
2. Whether a run stopped at `maxTurns` still ends with the four-heading handoff, and what `claude/coder-fleet/hooks/board-subagent-stop.sh` does with that stop.
3. Whether `permissions.deny` with `Agent(coder-fleet:<name>)` in a project's `.claude/settings.json` blocks a plugin-namespaced agent, and does not block the other half of a pair whose name shares a prefix.

The board item's AC #1 still says "five behaviours"; the lead's comment of 2026-09-27 cut it to three, and AC #1 is amended to match.

## Findings that shape the plan

- **The docs answer part of (1), not for Pro.** `code.claude.com/docs/en/sub-agents` says a subagent whose model is blocked by the organisation's `availableModels` allowlist falls back: a blocked family alias to the newest permitted version of that family, anything else to the inherited model, with the warning naming both models shown only in interactive sessions. `code.claude.com/docs/en/model-config` says, for a subagent or teammate override, "Claude Code runs the subagent or teammate on a fallback model rather than failing the request". That is the allowlist path, not plan entitlement.
- **Pro is not "no Fable" but "Fable on usage credits".** `support.claude.com/en/articles/15424964` says Fable 5 and 5.1 "aren't included in your plan's usage limits" on Pro and are used "with usage credits". The model-config page says that in `-p` mode, "When a Fable request there would bill to usage credits, Claude Code bills it without asking." A Pro project that chose Fable with extra usage switched on may run Fable and pay per token silently. Design section 5's "Pro does not include Fable at all" needs that nuance, and CF-12.5's `/init` wording must cover it whatever the spike observes.
- **The CLI knows model availability up front.** Strings in the 2.1.283 binary show the init event carries `models`, `unavailable_models` and `account.subscriptionType`, and a 404 on a model produces "The model X is not available on your ... deployment" with `model_not_found`. Both are observable without a Pro account: one tells whether the client knows about unavailable models before it spawns, the other is the server-refusal path.
- **What partial output means at `maxTurns`.** The sub-agents docs say a subagent reaching the limit has its output "marked as partial" (v2.1.246 or later; installed is 2.1.283). Binary strings show a `max_turns_reached` transcript attachment, and a stop hook blocking past the cap logs `tengu_stop_hook_block_count` with `hit_max_turns:true`, which suggests an exit 2 at the cap buys no extra turns. A hypothesis to confirm live.
- **Prediction for (2), from the v0.25.1 hook.** If the capped run's last assistant block is a tool call, the runtime drops `last_assistant_message` (the field comes from text only; hooks README item 16), the hook reads `agent_transcript_path`, finds a non-StructuredOutput last block and exits 0 "cannot tell" (`board-subagent-stop.sh:324-340`): a **silent pass**. If the last block is prose without the four headings, the hook exits 2 (line 356). The spike records which happens and whether the runtime honours the exit 2 at the cap.
- **The documented deny rule, and its gap.** `code.claude.com/docs/en/permissions` documents `Agent(AgentName)` deny rules with the plugin form `my-plugin:agent`, and says parameter rules compare "the literal input Claude sends, before any normalization". Plugin agents can also be spawned by bare name, so a scoped deny may not catch a bare-name spawn; and the unsuffixed name is a prefix of the `-fable` name, so each rule must be shown to match only its own definition. `Agent(subagent_type:*spec-editor-fable)` is a documented parameter-rule fallback worth recording if the plain form leaks.
- **The scope hook does not stand in the way; the sandbox does.** `enforce-agent-scope.sh:1295` sends `scripter` to `enforce_coder`, which refuses only the writing git verbs in `CODER_WRITING_GIT` (line 1027) outside a linked worktree; `scripter` is not in the write-scope case above the dispatch. `claude -p`, `Write` outside the worktree and redirects into a scratch directory are unrefused. What stands in the way is the session environment: user settings turn on the Bash sandbox with `denyWrite` on `~/.claude` (where `claude -p` keeps sessions and subagent transcripts) and a network allowlist; the harness's worktree guard refuses heredocs, compound git commands, `${VAR:-default}` and relative script paths; and the CLI may refuse a nested launch inside a Claude Code session. None of that differs for `coder`.
- **The worktree comes from `origin/main`**, so the spec and this plan (untracked in the main checkout) are not in it; the spawn prompt names their absolute main-checkout paths.
- **Precedent**: `codex/scripts/spike/codex-hooks/` and `codex/docs/findings/GPTA-1.1-codex-hooks.md` - a committed harness that runs outside the repo, guarded scratch setup and teardown, and a findings file with one section per question, each with a verdict and the payload behind it.

## Agent routing

`scripter`: a small harness plus a findings document, one agent phase, no production code, no credential path (the harness never reads or copies credentials; `claude -p` authenticates itself). `coder` buys nothing, because the obstacle is the sandbox and `coder` has the same one.

Three steps, and step 2 is the human's:

1. `scripter` builds the harness, gathers the free evidence, dry-runs everything and commits.
2. The human runs the paid batch from a plain terminal, not inside Claude Code: no sandbox or nested-session problems, production-faithful, and the spend in the human's hands.
3. The same `scripter` is resumed with SendMessage (after the lead focuses CF-12.1 first; a resume re-binds to the current focus), reads the logs, replays the captured payloads and writes the findings. If resuming is not possible, a fresh `scripter` checks out the pushed branch.

Before the spawn the lead calls `task_focus CF-12.1`. The spawn prompt carries `Board-Item: CF-12.1` and the absolute main-checkout paths of `docs/specs/CF-12.md` and this plan; the first commit copies the plan in byte for byte. After step 3, a review round over the branch.

## Risks

- **Project hooks may not run under `-p` in an untrusted directory.** Detected by E2a (the control); if its capture log is empty, move the hooks into a `--settings <file>` flag for the `turns` project and say so.
- **Field names in stream-json and init may differ from the binary strings.** `summarise.sh` reads defensively; the raw `.jsonl` is ground truth.
- **A denial may show as the agent missing from the list rather than a refused call.** Both count as blocked; the findings say which, because it matters to the lead's error handling.
- **A scoped deny may leak to a bare-name spawn.** A real finding, not a harness fault; CF-12.3's spawn convention must account for it.
- **Answers are pinned to CLI 2.1.283.** The README says to re-run on upgrade.
- **Privacy**: the init event carries the account email and organisation; the summary drops them, and nothing from `<scratch>` is committed except redacted excerpts.
- **The scripter may be refused reads of `<scratch>` in step 3.** The lead adds the directory with `/add-dir`, or the human places it where the scripter can read.
- **The instruction-file contract** fails on any mention of the other instruction-file name in the harness or findings.
