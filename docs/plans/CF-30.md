# CF-30: Keep a resumed subagent bound to the item it started on

Status: approved by the human on 2026-09-27 with the recommended answer to every open question.

Board item: CF-30 (bug, Medium, To Do). Folds in GitHub issue rzem-ai/coder-fleet#10, read as data. Route: coder. `<wt>` below is the worktree's absolute path. Touches the same files as CF-42 (`hooks/lib/board.sh`, the contract's stub, the hooks README); whichever lands second rebases.

## Findings, with evidence

1. **A resume re-reads the focus and rewrites the binding.**
   - `board-subagent-start.sh:50-52` reads the focus first on every start: "if page_id=\"$(board_focus_id \"$HOOK\")\"; then source_of_id=\"focus file\"".
   - `:71` calls `state_bind_agent`, and `lib/board.sh:113-117` writes the record with a plain `>`, so a second start for the same agent id overwrites it. `:120` also rewrites `last-item`.
   - `board-subagent-stop.sh:287` finds the item only through that record (`state_agent_page_id`), so a Blocker after a resume lands on whatever the focus said at the resume (`:367`).

2. **A resume does re-fire SubagentStart.**
   - `hooks/README.md:530`: "`SubagentStart` for `coder-fleet:spec-writer a12acd8657b8ff71c` six times ... a resume re-fires the start for the same id".
   - `agent-clock.sh:22-28` builds its rule on that.

3. **The keep-the-first pattern already exists.** `agent-clock.sh:164-166` creates its file in a subshell with `set -C` (O_EXCL). `:173-174` logs "started again (a resume); its first start in $clock_file stands".

4. **On main, a resume already moves a card out of Blocked by human.**
   - `board-subagent-start.sh:76` writes the in-progress column on every start, with no status check: `if col="$(board_in_progress_column "$HOOK")"; then board_write ...`.
   - So #10's "never moves the card out of Blocked by human" is not explained by the hook, provided the event fires and the write succeeds. The lead's hypothesis is CF-42: a `BOARD_COL_DOING` override the config did not list made every write fail.

5. **The focus-before-resume workaround is not in the repo.** A search for "resum" finds only the refuter clock rule in `agents/lead.md:32` and the clock notes in the hooks README. The card says "Today only a lead practice in memory covers it". So criterion 3 means stating the new rule in `skills/board-conventions/SKILL.md:59` and `agents/lead.md:34`, where no workaround exists to delete.

6. **The docs describe binding as purely per checkout.**
   - `docs/limits.md:9`: "Binding is one item per checkout, not per agent".
   - `docs/fleet-design.md:129`: "`SubagentStart` reads it ahead of everything else".
   - `hooks/README.md:29` and `:41-47` say the same.
   - All four need a clause once a resume reads its own record first.

7. **The contract stub cannot express this case yet.**
   - `board-hook-contract.sh:523` hard-codes `"focus --show") printf 'BD-1\n'`.
   - `:531-533` passes argument 5 of every `task edit` to `canon`, so a `--comment` edit fails.
   - `:548` gives every `run_start_stub` call a fresh session id.
   - The live pass (`:669-713`) already takes one item through start and a Blocker stop, which the live resume case below extends.

## Design decisions

1. **The agent's own record comes first.** At SubagentStart, if `sessions/<sid>/agents/<aid>` exists, this is a resume. Keep the record's item, do not rewrite the record or `last-item`, and still read the focus, but only to log. The log line is "`<type> <id> resumed; keeping BD-1, the item it started on`", with "` (the focus is now BD-2)`" appended when the focus is set and differs.
2. **The record is written create-if-absent.** Use `set -C` in a subshell, as `agent-clock.sh:164-166` does, so even a racing second start cannot overwrite it. `state_bind_agent` returns 0 when it wrote the record, 3 when the agent was already bound and 1 on failure, so "already bound" is never logged as "could not write the state file".
3. **A first start with no item writes an unbound record** (`page_id=` empty, no `last-item`). A resume of that agent then stays unbound too, whatever the focus says. The rule stays one sentence: a resume never takes its item from the focus.
4. **A resume moves its item back to In Progress, except from Done.** On the resume path only, one `task view --json` reads `.task.status`, compared ignoring case and spaces as the binary does. If it matches `BOARD_COL_DONE`, log "`resumed on BD-1, which is Done; leaving it there`" and write nothing. Blocked, Blocked by human and To Do all move to In Progress, which is what #10 asks for. A first start keeps today's behaviour.
5. **SubagentStop and TaskCompleted do not change.** Stop already reads the record, so keeping the record correct is the whole fix.

## Risks

- **The record is keyed by session id.** If a lead restarted with `claude --resume` sends SendMessage under a new session id, the record is not found and the resume binds to the focus as today. This is not verified.
- **A deliberate rebind is gone.** A lead that refocused to move a resumed agent onto new work now has to spawn a fresh agent. `lead.md` says so.
- **One extra `task view` per resume**, for the Done check.
- **Merge conflicts with CF-42** in `lib/board.sh`, the stub and the README.

## Open questions, each with a recommended answer

1. Should an unfocused first start write an unbound record, so a resume stays unbound? **Yes.** Otherwise a resumed scout still lands on whatever the lead focused since, which is the same bug.
2. Should a resume against a card now in Done move it? **No.** TaskCompleted writes Done on a passing gate, and a resume after that is usually a question. Moving the card would silently reopen finished work. After CF-26 a completed card refuses a status change anyway, so the guard also makes both kinds of Done card behave the same. Real reopened work is a new item or the human's move.
3. Should the Done guard also cover a fresh spawn on a focused Done card? **Not here.** That case is the "clear the focus" rule. File a follow-up item if the human wants it.
4. Should a Blocker from a resumed agent still move a Done card to Blocked by human? **Yes, unchanged.** The human queue outranks Done.
