## Findings, with evidence

1. **Two bodies tell agents to raise findings as blockers.**
   - `claude/coder-fleet/agents/reviewer.md:42`: "A defect that must be fixed before merge is a `Blocker:` line."
   - `claude/coder-fleet/agents/refuter.md:48`: "A surviving mutation that changes behaviour is a `Blocker:` line".
   - On a `Blocker:` line, the SubagentStop hook moves the card to Blocked by human and posts the blocker comment (`claude/coder-fleet/hooks/board-subagent-stop.sh:359-367`).
   - The handoff skill already defines Blocker as "the work is stopped until the human answers" (`claude/coder-fleet/skills/handoff/SKILL.md:43`), so both bodies contradict the skill they preload.

2. **The workflow never read reviewer defects from Blocker lines.**
   - `review-round.js` spawns the reviewer with `schema: VERDICT_SCHEMA` (`:762-767`). Each finding carries a `blocking` boolean (`:521-543`).
   - The fix round is driven by `(review.findings || []).filter(isBlocking)` (`:818`), which goes to `fixRequest` (`:866-877`) or to `commissionFixes` (`:921`).
   - A schema spawn sends SubagentStop no `last_assistant_message` (header `:54-59`), so a reviewer inside the workflow cannot have produced a false blocker.
   - So the false blockers came from reviewers the lead spawned directly: Fathom FTH-001.12, commit 7475a38, and CF-8.
   - For the reviewer, the fix is the body and the skill. The workflow only needs a guard test.

3. **The workflow does read refuter survivors from Blocker lines.**
   - The refuter prompt asks for them that way (`:836`).
   - `readHandoff` extracts `blockers` from Decisions needed (`:233`).
   - `:853-859` sets `stopped = 'refuted'` when `broke.blockers.length`, otherwise `clean` (`:861`).
   - The refuter is spawned without a schema (`:842-844`), so its handoff reaches the hook, and every survivor moves the card to Blocked by human. CF-8 comment #4 is an example.

4. **Survivors never started a fix round.**
   - `refuted` breaks the loop with `fixRequest` still null. NEXT_STEP (`:1125-1126`) hands the fix back to the lead: "Fix the tests, then run this again."
   - Only reviewer findings reach `commissionFixes`.
   - So AC3's "still starts a fix round on them" is true for reviewer findings and not true for survivors. This plan keeps both behaviours exactly (open question 2).

5. **A refuter Blocker line currently reads as survivors.** If the workflow simply stopped reading refuter Blocker lines, a refuter that asked the human a real question would read as `clean` with `approved: true`. That fails open, so the plan gives that case its own stop reason.

6. **The worktree-mismatch Blockers at `:1063` and `:1066` are genuine and stay.**

7. **A keyed Done bullet changes no format.**

## Design decisions

1. **The reviewer's must-fix defects** stay in its ranked findings above the handoff. Each also gets one Done bullet: `- must fix: <file>:<line> - <what breaks>`. The verdict stays the first Done bullet. Nothing parses these today. They exist for the card and the lead.
2. **The refuter's survivors** are ranked in its report and each gets one Done bullet: `- survived: <the exact edit> - <the behaviour no test noticed>`. There is no bullet when none survived. The workflow reads survivors from these bullets only. Survivors mentioned under Unverified or Not done are not read, because a survivor must be confirmed (`refuter.md:42`).
3. **Lowercase keys, like `worktree:`.** This keeps them visibly different from the three typed prefixes. It is not a fourth prefix, and the parsers and the parity tests are untouched.
4. **Parser tolerance.** The reader is case-insensitive and tolerates markdown around the key (`**survived:**`, `` `survived:` ``). It ignores a `survived:` bullet whose text is only `none`, `nothing` or `0`, because a model may write one when nothing survived.
5. **A refuter Blocker gets its own stop, `refuter raised a blocker`.** This parallels `coder raised a blocker` (`:1008`), has its own NEXT_STEP entry, and sets `approved: false`. It takes precedence over survivors, which are still carried in `refutation.survivors`, because the human's answer may change what gets fixed.
6. **One pure decision function**, `refutationStop(said, survivors)`, returns `refuter raised a blocker`, `refuted` or `clean` in that order. CF-32 adds its incomplete branch before `clean` as one line, and CF-31 does none of CF-32's work.
7. **The fix-round trigger for reviewer findings is unchanged**: the schema `blocking` field, then the fix round.
8. **Keep the two fix-prompt Blockers (`:1063`, `:1066`)**, rephrased so the coder asks the human, as a question ending in `?`, how the fix run should be set up.
9. **No hook change.** Flagging a non-question Blocker stays in CF-25, where Q7 is decided. It is not needed here because every false blocker observed traces to a body instruction this item removes.
10. **The lead learns where findings now live** in one clause at `lead.md:48`, not `:33`. CF-23 edits `:32`, and adjacent hunks would conflict.
