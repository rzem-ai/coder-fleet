# CF-42: Make kickoff check board.env against the board config

Status: approved by the human on 2026-09-27 with the recommended answer to every open question.

Board item: CF-42 (bug, Medium, To Do). Source: GitHub issue rzem-ai/coder-fleet#14, read as data. Route: coder. `<wt>` below is the worktree's absolute path. Touches the same files as CF-30 (`hooks/lib/board.sh`, the contract's stub, the hooks README); whichever lands second rebases.

## Findings, with evidence

1. **No agent can read board.env, by design.**
   - `claude/home/settings.json:20-21` denies `Read(~/.config/coder-fleet/**)`. `:52` puts the directory in the sandbox `denyRead`, which covers the lead's Bash and any script it runs. `:73` lists it under credentials.
   - `docs/fleet-design.md:248`: "Hooks run outside the agent's permission model, so a hook may read that directory where the agent cannot."
   - So "kickoff reads both" cannot be prose or a script kickoff runs. Only a hook can read the file. The directory may also hold rendered secrets (`:248`), so anything that reports on it must print the `BOARD_COL_*` values and nothing else.

2. **What kickoff checks today.**
   - `commands/kickoff.md:28` compares `statuses` with `To Do`, `In Progress`, `Blocked`, `Blocked by human`, `Done`, and names a `BOARD_COL_*` override only as the wrong fix.
   - `:58` tells the human to look in `hooks.log` for failure lines after the first spawn.
   - Nothing reaches the override. The issue's "Doing" predates v0.26.0: kickoff and the hooks now say In Progress.

3. **The hooks' defaults.**
   - `lib/board.sh:28-32`: `BOARD_COL_DOING` defaults to empty, so the column is resolved per board (`:417-436`). The other four default to the fleet's spelling.
   - `:53-56` sources `board.env` after those defaults, so an override is any value that differs from its default, or any non-empty `BOARD_COL_DOING`.
   - `:419-421` logs "BOARD_COL_DOING is set to ..." on every start and uses the value unprobed.

4. **The failure branch.**
   - `board_cli` (`:337-339`) sets `BOARD_CLI_INVALID_STATUS=1` when stderr starts with "invalid status", and `:348` logs `board task edit failed (exit 1): invalid status "In Progress". Configured statuses: ...`.
   - `board_set_status` (`:389-394`) returns 1, and `board_write` swallows it at `:526` (`|| true`).
   - The log line is all that happens, which is how Fathom went a week with nothing reported.
   - `:527` still posts any comment the caller passed, so a Blocker comment survives a failed move. SubagentStart passes none.

5. **A comment-only write still succeeds.**
   - `board/src/cli.ts:150-158`: the edit validates the status through `statusOrFail` (`:43-48`, which exits with "invalid status ...") only when `-s` is given, and before any update. A failed status edit writes nothing.
   - A separate `task edit <id> --comment ...` never touches the status, so it goes through, as `board_comment_raw` (`lib/board.sh:442-450`) already does.

6. **SubagentStart does not set `BOARD_RUN_SESSION`.** `board-subagent-stop.sh:282-284` and `board-task-completed.sh:179` do. A per-session guard written from `board_write` needs it set on start too.

7. **The contract already covers the log line.** `board-hook-contract.sh:603-608` (`start-col-override-unlisted-logged`). No case checks that anything reaches the card, and the stub (`:531-533`) cannot record a comment.

8. **A stale sentence about the installer.** `skills/board-conventions/SKILL.md:35` says "the installer writes the fleet's spelling", but `claude/scripts/install-home.sh` only warns about an old `board.env` and never writes one.

## Design decisions

1. **The check is a hook, `hooks/board-env-check.sh`, registered on SessionStart,** because nothing else fires before kickoff and only a hook can read the file.
   - It sources `lib/board.sh` and exits 0 with no output when the board is disabled or no `BOARD_COL_*` is overridden. That is the common case, and it never starts the binary.
   - Otherwise it runs `board_status_listed` once per overridden column. A probe failing for any other reason (`no board here`) logs once and exits 0.
   - For each column the config does not list, it prints one line to stdout, which reaches the session's context, and logs the same line with the repository path:
     `board.env check: BOARD_COL_DOING is "In Progress", which .boards/config.yml in <repo> does not list, so every SubagentStart move will fail. Remove the line from board.env (the in-progress column needs no override since v0.26.0) or add the status to the config.`
   - It prints variable names and values for `BOARD_COL_*` only.
2. **Kickoff reads the verdict and does not look for the file.** A new bullet after `kickoff.md:28` makes a mismatch a failure of the Board step, not of the preflight (the board is optional, `:23`). It tells the lead that board.env is unreadable to it and not to try. The verdict is in the session context, or in `grep -F '[BoardEnvCheck]' ~/.local/state/coder-fleet/log/hooks.log | tail -5`, matched against this repository's path. The lead reports each named variable with the fix and asks the human to fix it before the first `task_focus`.
3. **A failed move reaches the card as a comment, once per session per item and column.**
   - When `board_set_status` fails with `BOARD_CLI_INVALID_STATUS=1`, `board_write` calls `board_note_failed_move`.
   - That creates `sessions/<sid>/move-failed/<ID>-<column>` with `set -C`, and only when it creates the file does it post a comment-only write: "`Not moved. SubagentStart could not move BD-12 to "In Progress": the board's statuses do not list it. BOARD_COL_DOING is set to that value in board.env or the environment. Fix the config or the override; see hooks/README.md, What breaks them. Said once per session.`" The override sentence appears only when a `BOARD_COL_*` override equals the column.
   - Every later failure logs "already noted on BD-12 this session". No column is written.
   - Other failures (timeout, no board, a completed card) stay log-only.
4. **SubagentStart sets `BOARD_RUN_SESSION`, `BOARD_RUN_AGENT` and `BOARD_RUN_AGENT_ID`** as the stop hook does.
5. **The default columns are not probed at session start.** Kickoff's config check already covers them (`kickoff.md:28`), and a failed default still gets the card comment from decision 3.

## Risks

- **The SessionStart hook runs in every project with the plugin enabled.** It is free when nothing is overridden. With an override set, it makes up to five probes and at most one failed call where there is no board.
- **Plain SessionStart stdout reaching the lead's context is not verified** for a plugin hook on this CLI version. `hooks.log` is the fallback kickoff names.
- **The note is a board commit on the main checkout's branch**, bounded to one per session per item and column.
- **Merge conflicts with CF-30.**

## Open questions, each with a recommended answer

1. Should kickoff warn or refuse? **Fail the Board step and ask the human to fix it before the first focus,** but do not fail the whole preflight: no board is a legitimate outcome.
2. SessionStart hook, or a check inside SubagentStart once per session? **SessionStart.** Kickoff runs before any spawn, so a start-time check would leave kickoff nothing to report.
3. Rate limit: once per session, or once per session per item and column? **Per item and column.** The human looks at the card that did not move.
4. Should other failures (timeout, no board, a completed card) also comment? **No.** This comment is for the one failure where the card exists and takes a comment.
5. Should the session-start check probe the default columns too? **No.** Kickoff's config check covers them, and the card comment catches a failed default anyway.
6. Fix the stale installer sentence in board-conventions here (finding 8)? **Yes,** in Phase 3: it is one sentence in a file this change already makes true in a new way.
