## Findings, with evidence

1. **Reading a completed card and editing one resolve differently.**
   - `Core.getTask` resolves through `resolveTaskForRead` (`src/core/backlog.ts:822-842`). That calls `TaskIdentityIndex.resolveForRead`, which searches `getTasks(true)`, completed cards included (`src/core/task-identity-index.ts:261-270`).
   - `updateTaskFromInput` loads through `loadTaskForMutation` (`backlog.ts:909-918`). That calls `resolveForMutation`, which keeps only working-copy records of `type === "task"` (`task-identity-index.ts:272-285`, filter at `:281`).
   - So a card in `.boards/completed/` can be viewed but not edited. `updateTaskFromInput` throws `Task not found: <id>` at `backlog.ts:2114`.

2. **The Fathom message shows which path failed.**
   - The CLI's `task edit` calls `c.getTask(taskId)` first (`src/cli.ts:152`). A truly missing id fails there with `no task <id>` (`:153`).
   - Fathom saw `Task not found: FTH-001.12`. That text only comes from the core throw, so `getTask` found the completed card and the mutation lookup then refused it.

3. **The real exit code was already 1. The pipe hid it.**
   - The throw leaves the async action. `program.parseAsync(...)` rejects, and its `.catch` calls `fail` (`cli.ts:302`), which runs `console.error` and then `process.exit(1)` (`cli.ts:21-24`).
   - The missing-id path also exits 1 through `fail` (`:153`).
   - The exit 0 the lead saw was `tail`'s status at the end of the pipe. No code path exits 0 on either failure. The fix still pins both codes with tests, because nothing does today.

4. **MCP `task_edit` already returns an error.**
   - `TaskHandlers.editTask` catches every `Error` and rethrows it as `BacklogToolError(..., "VALIDATION_ERROR")` (`src/mcp/tools/tasks/handlers.ts:591-599`).
   - The wrapper turns that into `isError: true` (`src/mcp/validation/tool-wrapper.ts:53-64`, `src/mcp/errors/mcp-errors.ts:58-75`).
   - The problem is the wrong answer ("not found" for a card that exists), not a missing error.

5. **Upstream is split on whether completed cards are editable.**
   - Against editing: an upstream test pins read-only: "reads a completed-only task while keeping it unavailable to mutations" (`src/test/core.test.ts:148-159`).
   - For editing:
     - `isLocalEditableTask` counts `source === "completed"` as locally editable (`src/types/index.ts:111-113`).
     - The core already rewrites completed records in place during vacated-id cleanup (`backlog.ts:704-712`), and keeps them in the store with `ContentStore.refreshCompletedTask` (`src/core/content-store.ts:670-693`).
     - `saveTask` keeps an existing `filePath`, so a write lands back in `completed/` (`src/file-system/operations.ts:775-786`, `:796`, `:825-840`).

6. **The fleet's own rules need completed cards to take edits.**
   - `board-conventions` records whether work was any good "once the answer is known - usually later and often by the human - as an outcome label" (`claude/coder-fleet/skills/board-conventions/SKILL.md:97`). A card already in `completed/` could never get its `outcome/shipped` label.
   - The hooks comment on cards through `task edit --comment` (`claude/coder-fleet/hooks/lib/board.sh:390`).
   - The lead edited CF-8 and CF-6 after merge (item text).

7. **A naive fix through `updateTask` would fire a false status change.**
   - `updateTask` finds the original through `resolveTaskForMutation`, or failing that `fs.loadTask` (`backlog.ts:1487-1490`).
   - `fs.loadTask` returns null for a completed-only id (`operations.ts:855-857`, which `mcp-task-complete.test.ts` relies on). So `oldStatus` becomes `""`, `statusChanged` is true, `updatedDate` is always rewritten, and any `onStatusChange` callback fires (`backlog.ts:1491-1512`, `:222-231`, `:2398-2420`).
   - The core already warns about this: "a completed record must not go through updateTask" (`backlog.ts:685-689`).

8. **The web UI's edit path fails the same way.**
   - The detail view resolves through `getTask` (`src/server/index.ts:1022-1046`), so a completed card opens.
   - The modal gates editing only on `task.branch` (`src/web/components/TaskDetailsModal.tsx:202`), so every field looks editable.
   - Saving sends a PUT to `handleUpdateTask`, which calls `updateTaskFromInput` for non-drafts (`server/index.ts:1182-1184`) and answers 400 "Task not found: <id>" (`:1199-1200`).
   - The modal also shows "Complete" and the `c` shortcut on any Done card (`TaskDetailsModal.tsx:512-515`, `:1113`, `:1139-1141`), including one already completed. That POST returns 404 "Task not found", because `completeTask` uses the mutation lookup (`backlog.ts:2970-2972`, `server/index.ts:1229-1234`).
   - Completed cards are left off the kanban and can only be reached through their detail view (`src/web/utils/kanban-tasks.ts:3-5`).

9. **In this fork, "Done" does not move a card to `.boards/completed/`.**
   - Done is a status written by the `TaskCompleted` hook (`board-conventions/SKILL.md:33`, `hooks/lib/board.sh:376`), and the card stays in `.boards/tasks/`.
   - A card reaches `completed/` only through an explicit completion:
     - MCP `task_complete`, which requires the terminal status (`handlers.ts:522-549`). It is open to the lead and to every agent except `fleet-steward` and `spec-writer`, which disallow it.
     - The web modal's Complete button or `c` key.
     - `POST /api/tasks/:id/complete` (`server/index.ts:1229`).
   - The CLI has no `complete` command (`cli.ts`), no hook calls one, and upstream's age-based cleanup endpoints were removed (`NOTICE.md`).
   - This repo's `.boards/completed/` is empty today.

10. **Existing tests that change.** `core.test.ts:148-159` asserts the old refusal and is rewritten. `core.test.ts:161-195` (an active card and a completed card with the same id stay ambiguous) and `:197-226` (the mutation lookup still says `not-found` for completed cards) must keep passing unchanged.

## Design decisions

1. **Edits reach completed cards.** Findings 5 to 8 support it: upstream already marks completed cards as local and editable, the core can write them in place, and the fleet's outcome-label and after-merge habits need it. Refusing would also leave outcome labels impossible on any card someone completed.

2. **Only a status change is refused.** The file's folder says the card is finished. Letting `status` leave Done while the file stays in `completed/` would give a card the kanban hides with a live status. `board-conventions/SKILL.md:99` also says wrong work gets a label, not a trip back to To Do.
   - A requested status equal to the card's current status, compared case-insensitively after canonicalising, is a no-op and allowed. A hook re-sending Done stays harmless.
   - Any other status, including `Draft` (a demotion), is refused.
   - The message names the card and the folder and says what still works. For example: `CF-26 is completed (its file is in .boards/completed/), so its status cannot change. Criteria, comments, notes, labels and other fields can still be edited.` The folder comes from the filesystem, not a literal.

3. **A separate path, not `updateTask`.** Finding 7 rules `updateTask` out. The completed path:
   - takes the per-task lock on the completed file (`operations.ts:663-673`) and re-reads the card inside the lock;
   - applies the input with a status resolver that enforces decision 2;
   - on a mutation, sets `updatedDate` with `hasUpdatedDateRelevantChanges(original, next)`, writes with `fs.saveTask` (path kept), refreshes the store with `refreshCompletedTask`, and commits with `git.addAndCommitTaskFile(id, path, "update")` when auto-commit is on;
   - never calls `executeStatusChangeCallback`.

4. **The mutation lookup stays as it is.** `resolveForMutation` also serves complete, archive, demote, reorder and move-to-status (`backlog.ts:1488`, `:2500`, `:2715`), and upstream tests pin its `not-found` for completed cards (`core.test.ts:220-225`). A new lookup is added beside it and used only by edits, and only after the existing one returns `not-found`. Ambiguity still throws first.

5. **No CLI or MCP handler change is needed for the behaviour.** Both already reach `updateTaskFromInput` or `editTaskOrDraft`, and both already exit 1 or return `isError`. The tests pin that. The MCP error code for a truly missing id stays `VALIDATION_ERROR` (open question 5).

6. **The web UI edit comes for free** through the same core call. A server test pins it. The misleading Complete button on an already-completed card is filed as a Propose item, not fixed here (open question 4).

7. **`NOTICE.md` records the divergence** under a new "Behaviour changed after import" heading in "Adjusted after import", so a future port knows `core.test.ts:148-159` was changed on purpose.

## Risks

- **Hooks moving a completed card now fail with the read-only message instead of "not found".** For example, `SubagentStart` moving a focused completed card to In Progress, or a failed gate moving it to Blocked. Both already fail soft and log to `hooks.log` (`hooks/lib/board.sh:376`). Hook comments on completed cards now succeed, which is the intent.
- **CI does not run the board package's tests (CF-29).** `checks.yml` installs no bun, and `check-all.sh:80-81` skips the board step when bun is missing. All proof is local, and the handoff must quote the local runs.
- **Merge conflicts.** CF-31's branch and `cf-12.2-fix-3` both edit `check-all.sh`. Expect a trivial conflict in the array and keep both sides.
- **The full suite can exceed a 2-minute shell call.** Run it in the background.

## Open questions, each with a recommended answer

1. Should completed cards be editable or read-only? **Editable** (findings 5 to 8).
2. Should a status change on a completed card reopen it (move the file back to `tasks/`) or be refused? **Refuse.** Reopening is new behaviour and belongs to its own item. The message says what still works.
3. Is a same-status request (Done on a Done card) allowed? **Yes, as a no-op.**
4. Should the web modal hide Complete and `c` on an already-completed card in this PR? **No.** File a Propose item. It is cosmetic, has its own test surface (jsdom), and fails safely today.
5. Should MCP use `TASK_NOT_FOUND` rather than `VALIDATION_ERROR` for a truly missing id? **Leave it.** The criterion needs an error, and it already is one.
6. Should `NOTICE.md` record the change? **Yes**, a behaviour-divergence bullet.
7. Should the lead's docs warn against piping board writes? **No.** The CLI already exits 1. Mention it in the handoff only.
