Status: approved by the human on 2026-09-28 with the recommended answer to every open question, and with the amendments below.

## Amendments at approval, 2026-09-28

Where a section below disagrees with this one, this one wins.

1. **An open ask holds the card in Blocked by human.** The Risks section accepted that any spawn in a focused checkout clears the section: `SubagentStart` moves the focused item to In Progress on every start, so a scout sent while the human is still reading archives the questions off the top of the card, which is the failure GitHub #3 describes. Instead, `board-subagent-start.sh` leaves a card in Blocked by human while its Actions for Human section has any unticked action, moves nothing, and logs `waiting on the human: <n> open action(s) on <id>`. The lead ticks each action through `task_edit` as the human answers it in the session. Once none is open, the next start moves the card and the settle archives the section as designed. A move the human makes (a web drag, a demote) still moves and clears at once, and so does a lead clear with a reason. The first start and a resume follow the same rule. This needs: the open-action count in the JSON `task view` the hook already reads (`actionsForHuman`), a Phase 3 contract case for each of held (open actions), moved (all ticked), and moved (no section), a `lead.md` clause in step 5 that the lead ticks an action when the human answers it, and the matching lines in board-conventions and the hooks README. The Risks bullet "Any spawn in a focused checkout clears the section" no longer applies.

## Design decisions

1. **Where the section lives.** It is a marked section at the very top of the task body, before Description:

   ```
   ## Actions for Human
   <!-- ACTIONS:BEGIN -->
   - [ ] #1 Which key should the refresh use?
   - [x] #2 [not a question] Pick the session lifetime
   <!-- ACTIONS:END -->
   ```

   The human sees it first in every view, including a raw `.md` on GitHub.
   - A new `ACTIONS_FOR_HUMAN_DEFINITION` gets `placement: "start"` and `legacy: false`. Only the marked form is read, so a stray `## Actions for Human` heading in prose is never parsed as actions. `ActionsForHumanManager` follows the DoD manager, minus remove.
   - "Actions for Human" is added to `section-titles.ts`, and `ACTIONS` to the tokeniser at `:319`.
   - Placement moves onto the definition. The `=== ACCEPTANCE_CRITERIA_DEFINITION` branches become data. AC and DoD keep today's placement exactly.
   - `updateStructuredSections` inserts Description after the actions block when one exists, and so does the plan fallback. `findSectionEndIndex` and `findSectionStartIndex` gain the actions title. A description edit then never reorders the file.
   - An empty list writes no heading and no markers, so clearing removes the section whole.
2. **The field.** `Task.actionsForHumanItems?: AcceptanceCriterion[]`, parsed in `parseTask` and serialised like DoD: the section is rewritten only when the items changed. It goes into `buildUpdatedDateComparableTask`.
3. **One module owns the rules: new `board/src/core/actions-for-human.ts`.**
   - `HUMAN_QUEUE_STATUS = "Blocked by human"`, matched ignoring case and spaces as the hooks match it (Open question 2).
   - `NOT_A_QUESTION_PREFIX = "[not a question] "`.
   - `normaliseActionText` collapses every whitespace run, newlines included, to one space and trims. It rewrites `<!--` to `&lt;!--` so no action can form a board marker or break the archive comment's marker check. It refuses empty text.
   - `flagAction` leaves text alone when it ends in `?` once right-trimmed, or already starts with the prefix. Otherwise it adds the prefix. The binary applies the flag for both writers (Q7, Q15). The hook never does.
   - `settleActionsOnStatusChange(task, from, to, statuses)` clears and archives when the section is non-empty and either the card leaves the human queue (Q3) or it enters the terminal status from any other status (the spec's recommendation, criterion 5). A write that stays in Blocked by human, or any other move, does nothing. Moving from Blocked by human to Done gives one archive comment, not two.
   - `archiveComment(items, headline)` builds the one archive shape (design decision 7).
4. **Where the settle is called.** It is called on every status write, before the single save, so the clear and its archive comment are one write and one commit (criterion 9's "same write"):
   - in `applyTaskUpdateInput`, straight after the status block (`:1564-1570`) and before any action operation in the same input;
   - in `reorderTask` and `moveTasksToStatus`, where the moved task's status is set;
   - in both demote paths (plan extra 19).

   A status change is never passed an action added in the same call.
5. **The operations**, all in `applyTaskUpdateInput`, after the DoD block, in this order: add, tick, untick, clear.
   - `addActionsForHuman: string[]` appends after the highest number. Numbering starts at 1 on an empty section (spec "Numbering").
   - `checkActionsForHuman` / `uncheckActionsForHuman: number[]` touch only the named numbers. A missing number is an error listing the ones that exist, as AC does (`:2016-2023`).
   - `clearActionsForHuman: { reason, author? }` requires a non-empty reason. It is refused alongside add, check or uncheck in one call.
   - None of them touches `status`. `mutated` is set so `updatedDate` moves.
6. **Surfaces.**
   - **CLI `task edit`:** `--action <text>` (repeatable), `--check-action <n>` and `--uncheck-action <n>` (repeatable), `--clear-actions <reason>`. The commit note, in order of precedence: status, "Clear the Actions for Human on X", "Add N action(s) for the human to X", "Tick action n on X", comment.
   - **MCP `task_edit`:** `actionsAdd` (strings, maxLength 500, maxItems 20), `actionsCheck`, `actionsUncheck` (numbers, minimum 1), `actionsClear` (string, 1 to 1000, the reason). Each description says it moves no column.
   - **Web PUT:** accepts `actionsCheck` and `actionsUncheck` only. The human clears by moving the card.
   - `TaskEditArgs` and `buildTaskUpdateInput` map the CLI and MCP names. `commentAuthor` becomes the author of a lead's clear.
7. **The archive comment.**
   - Author `@board`. The commit's `Board-Writer:` trailer already names who made the write.
   - Headline, then a blank line, then one line per action as `- #1 (ticked) <text>` or `- #2 (open) <text>`. These are deliberately not checkbox lines, so no checklist parser can ever read a comment as a checklist.
   - Headlines:
     - `Actions for Human cleared: <id> moved from Blocked by human to In Progress.`
     - `Actions for Human cleared: <id> moved from In Progress to Done.`
     - `Actions for Human cleared by @lead, moving no column: <reason>`
8. **Rendering.**
   - **Plain text (and so MCP `task_view`):** straight under the title rule and before `Status:`, as `Actions for Human:`, a rule, then `- [ ] #1 text` lines with numbers, then a blank line. Nothing when empty.
   - **JSON detail:** gains `actionsForHuman: ChecklistItemJson[]`.
   - **Modal:** a new `ActionsForHumanSection.tsx` sits first in the main column, above Description, in preview and edit mode. It has an amber border, a "n of m answered" count, and a checkbox per action that sends one index, following the DoD pattern. It is disabled for cross-branch cards and absent when empty.
   - **Kanban card:** under the title, the first unticked action's text through `truncateAction(text, 80)` in a new `web/utils/actions-for-human.ts`, with the full text in `title` and a `data-first-action` attribute for tests. 80 characters keeps the 17-character prefix and about 60 characters of the ask. Nothing shows when no action is open.
9. **The hook writes actions in a call of its own, after the move and before the comment.**
   - `board_write HOOK ITEM COL [COMMENT [ACTION...]]`.
   - A new `board_add_actions HOOK ID TEXT...` runs `task edit <id> --action=<text>... --by <hook>`. The `=` form keeps an ask starting with `-` from being read as a flag.
   - An old binary then still moves the card and posts the comment, and the failed actions call is logged (finding 7).
   - The existing dry-run move line is kept byte for byte. A dry run adds one line per action: `dry run: would add an action for the human to BD-1: <text>`.
   - `board-subagent-stop.sh` passes the extracted blocker texts. Its log line and comment are unchanged (criterion 13).
10. **The scope hook's two deny tails ask for a question.**
    - `:1117` ends: `...or stop and raise a "Blocker: " line asking, as a question ending in "?", which worktree you were meant to use.`
    - `:1119` ends: `...if you have not got one, change nothing and raise a "Blocker: " line asking, as a question ending in "?", where your worktree is.`
11. **One item, one branch, five phases, two coder runs. No sub-issues.** The 16 criteria are one outcome with hard internal dependencies: the hook needs the CLI flag, `lead.md` needs the MCP schema, and the docs describe both. A fork-only sub-issue would ship a field no writer uses.
    - Run A is Phases 1-2 (the fork) and gets a review round. The settle is a data write that clears content, so under CF-45's trigger it also gets a refuter round.
    - Run B is Phases 3-5 (hooks, docs, version) and gets a review round.

    **Order against in-flight work:**
    - **After PR #16 (CF-26/27).** It edits `applyTaskUpdateInput`'s callers, adds the completed-card path this item must handle (Open question 3), drops the `task_edit` status default criteria 4 and 8 rely on, adds the NOTICE section this item appends to, and takes board 0.1.5.
    - **After PR #18 (CF-30).** Run B builds on its stub (`run_stub`, `stub_reset`, `STUB_STATUS`, `$STUB_CALLS.body`) and its live resume case.
    - **PR #17 (CF-43):** no shared code. NOTICE.md is a trivial rebase.

## Open questions, each with a recommended answer

1. **Criterion 15 says NOTICE.md is "unchanged", but a new task-file section and a status side effect are divergences.** Which reading holds? **"Intact" means the licence notice and the attribution stay: `LICENSE` is byte-identical, and NOTICE.md's attribution, pin and removal record are untouched.** Append one line under PR #16/#17's "Behaviour changed after import", which is what AGENTS.md's fork rule and NOTICE's own "Adjusted after import" practice call for. The spec wins on requirements, so the human confirms this reading, and the PR says so. The Done-when line for 15 is written to that reading.
2. **Should the binary learn the human-queue status name from config?** **No, a constant for now:** "Blocked by human", matched ignoring case and spaces, with a `docs/limits.md` line. Every template and this repo use that name, and a config key is a second place to keep in step with `board.env`. File an item if an override is ever used.
3. **Should an add be allowed on a card in the completed folder, or on a draft?** **Refuse both, loudly.**
   - Tick, untick and clear stay allowed on a completed card.
   - Nothing would ever clear an action on a completed card, and a draft is on no column.
   - An active Done card still accepts an add, as criterion 4's "whatever column" requires. `completeTask` archives any such action before it moves the file.
4. **Does demoting a card out of Blocked by human clear it?** **Yes.** Q3 says any status change, and demote is a button in the web modal. It costs one test.
5. **Should the actions ride on the status call or have their own call?** **Their own call** (design decision 9, finding 7). One extra commit per Blocker stop buys an out-of-date machine that still reaches the human queue.
6. **CF-24 or CF-25 first, or one branch?** **CF-25 first, separate branches.**
   - CF-25 is self-contained. CF-24's gate waits on CF-20 and its backfill is a separate operation.
   - CF-24's own agent-contract line already names CF-25's add, tick and clear, so it reads true only once CF-25 has landed.
   - They share little fork code: CF-24's create refusal and config key against CF-25's edit path and views.
   - CF-24's plan rebases `agent-contract.md:80`, `lead.md` and board-conventions onto this.
7. **Split into sub-issues?** **No** (design decision 11). If Run A's review finds the diff too large to review in one round, split the web modal and card (criteria 6-web, 7, 8-web) into CF-25.1, and the rest still ships.
8. **Wait for CF-19?** **No.** It is not built, criterion 13 is met by not touching the comment, and `stop-blocker-comment-unchanged` pins the text for it.
9. **The card truncation length.** **80 characters,** with the full text in the tooltip.
10. **The lead's clear takes its reason as the flag's value** (`--clear-actions <reason>`, `actionsClear: "<reason>"`), not the spec's example `--clear-actions --comment <reason>`. **Yes.** The reason sits in the one archive comment, and a clear without a reason cannot be typed.
