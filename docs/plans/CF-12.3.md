## Design decisions

### 1. The two definitions, from one source

Source: `claude/agent-pairs/spec-editor.md`. The generator renders `claude/coder-fleet/agents/spec-editor.md` (`model: opus`) and `spec-editor-fable.md` (`model: fable`).

Header lines:
- `description.opus: Challenges a revised spec draft adversarially before the human edits it, writing each challenge into a Challenges section with inline markers and never rewriting the draft. The lead spawns it once per spec.`
- `description.fable:` the same text, plus `Fable model, for a project that chose the Fable spec editor.`

Neither may contain `: `.

Template frontmatter, in this order:
- `name: {{name}}`
- `description: {{description}}`
- `model: {{model}}`
- `effort: medium` and `maxTurns: 15` (Q5)
- One comment line: memory and isolation are omitted on purpose, and `maxTurns` is a backstop rather than a budget (CF-12.1 finding 2).
- `tools: Read, Grep, Glob, Edit` plus the five memory read tools named individually, as `CF-12.md:118` proposes and as `agent-contract.md:121` expects for every agent.
- `disallowedTools: Write, NotebookEdit, Bash, WebSearch, WebFetch` and the four memory write tools.
- `color: purple`, the same as `spec-writer`. All eight colours are taken.
- `skills: glossary, handoff`. `board-conventions` is not included, because the editor never reads the board item.

**Edit only, no Write.** The editor appends; it never creates or replaces a file. A whole-file Write is exactly the rewrite Q2 forbids. This tightens the drafter's `[supplied]` tools line (`CF-12.md:118`) and still satisfies AC 2.

Body, under 60 lines including the 18 lines of frontmatter and marker, with four H2 sections:

- **Opening.** You attack `spec-writer`'s revised draft after the interview and before the human edits it. The human resolves what you raise, and the lead refuses to plan while any must-resolve challenge is open.
- **Scope.** In scope: the seven Q2 targets (`CF-12.md:37-44`), with codebase claims checked by Read, Grep and Glob. Out of scope: rewriting prose, resolving challenges, any file but the spec the brief names, and the plan.
- **How you work**, six steps:
  1. Read the spec whole, then the sources it names, and check every codebase claim.
  2. Attack the seven targets.
  3. Grade each challenge `[must resolve]`, `[should resolve]` or `[note]`, with the notation's definitions (`CF-12.md:138`).
  4. Append the whole section in one Edit at the end of the file: the heading line exactly, then one line per challenge `- C<n> [<severity>] [open] <one sentence>`, numbered from C1.
  5. Only then append ` [challenge C<n>]` to the end of each line a challenge points at, several Edits per turn, never inside a code fence. A challenge about the draft as a whole gets no marker.
  6. If the run is running long, stop placing markers and write the handoff, with unplaced markers under Not done. This is the best-effort early handoff.

  The ordering matters more than the instruction. The section, which is the only thing the gate needs, is on disk before any marker work starts, so a capped run leaves a lintable file.
- **Invariants:**
  - Never change a character of the draft beyond appending the section and the markers.
  - Never write any state but `[open]`.
  - Never write any file but the one spec the brief names. The scope hook denies Bash, Write, and an Edit to a second file.
  - Never quote the section heading in your handoff.
  - Never raise a challenge as a `Blocker:` line.
- **Handoff.**
  - The first Done bullet is `- Challenged docs/specs/<issue>.md: <n> must resolve, <n> should resolve, <n> note.`
  - Then one keyed bullet per challenge, grouped by severity: `- must resolve: C1 - <gist>`, then `- should resolve: ...`, then `- note: ...`, following CF-31's lowercase-key pattern.
  - Not done: unplaced markers and sources left unread.
  - Unverified: claims the editor could not check.
  - `Blocker:` is reserved for a question only the human can answer before any challenge can be written, phrased as that question. A brief that names no spec or two specs is a routing error for the lead and goes under Not done.

**maxTurns stays at 15**, the human's Q5 answer and the design's fourth Fable bound. Evidence that it never binds comes from the eval: `checks.sh` fails any prompt with `num_turns` over 10, and one prompt is a draft of CF-12.md's size (348 lines). If any run exceeds 10 turns, the coder stops and the human decides whether to change Q5. Nobody raises the number silently.

**Generator hardening** (card comment). `validate_source` refuses a description that:
- ends in `:`;
- starts with any of ``" ' [ ] { } & * ! | > % @ ` # ,``;
- starts with `- `, `? ` or `: `;
- contains a tab followed by `#`.

Each class gets a fixture and a contract case in `agent-pairs-contract.sh`.

**Fable guard** (CF-12.2 open question 4). `roster-contract.sh` gains one check: any body with `model: fable` must carry the generated marker on line 2, and its name must end in `-fable`. This enforces the bounded exception mechanically.

### 2. The challenge gate: one script, in a skill

Decision: one script. The spec's lean (`CF-12.md:344`) is right because the close is a byte-exact transform. Two copies would disagree the first time one is edited, and a model retyping a file is not byte-exact.

**Where it lives:** `claude/coder-fleet/skills/challenge-gate/`, holding `SKILL.md` and `gate.py`.
- It is a skill so that both callers reach it by path through the documented `${CLAUDE_PLUGIN_ROOT}` substitution in skill content: the lead through the Skill tool, and a workflow lane by loading the skill (finding 5).
- `SKILL.md` carries the three commands and the close sequence once. `lead.md` step 3 points at it rather than restating it.
- It uses Python 3 standard library only. If `python3` is missing, the gate refuses: a gate that cannot run has not passed.
- It stays model-invocable (no `disable-model-invocation`), because the workflow lane has to load it.

**`gate.py check <spec> [--no-editor] [--json]`.** Exit 0 passes, 1 refuses, 2 means a usage error or an unreadable file. Lines inside ``` or ~~~ fences are ignored throughout. Outcomes, in order:
1. **Closed.** Exactly one line matches `^## Challenges \(spec-editor\): closed in [0-9a-fA-F]{7,40}$` and no heading: pass, state `closed`.
2. **Intact.** Exactly one line equals `## Challenges (spec-editor)` and no closed marker. The section runs to the next `## ` line outside a fence, or to the end of the file. Any line in it carrying `[must resolve]` blocks unless it carries `[resolved]`, or a `[struck: <reason>]` whose reason is not blank. A line carrying `[open]` alongside a closing tag also blocks. `[should resolve]` and `[note]` never block. It passes with state `intact`, or refuses naming every blocking id (the `C<n>` after `- `, or the line number when there is none).
3. **Duplicates.** Two headings, two markers, or a heading plus a marker: refuse as ambiguous.
4. **Absent.** Neither present: refuse, unless `--no-editor` is given, when it passes with state `none`. `--no-editor` with a section present still gates the section.

`--json` prints `{"outcome","state","blocking":[...],"reason"}` for the workflow.

**`gate.py lint <spec> [--against <original>]`.** The post-editor check (AC 4, AC 5):
- exactly one intact section;
- every non-blank line in it matches `^- C[0-9]+ \[(must resolve|should resolve|note)\] \[open\] \S.*$`;
- ids are unique;
- every inline marker names an existing id;
- with `--against`: removing the section and the markers from the spec reproduces the original byte for byte.

**`gate.py close <spec> --sha <hex7-40>`.**
- Refuses unless `check` passes with state `intact`.
- Replaces the section's heading and content lines with exactly `## Challenges (spec-editor): closed in <sha>`. Content lines run through the last non-blank line before the next heading. Blank separator lines before the next heading are kept, so every line outside the section stays byte-identical.
- Removes every trailing run of ` [challenge C<n>]` outside fences.
- Preserves CRLF endings and a missing final newline.
- Writes atomically.

**Git stays with the caller**, so no fixture reads git history.

The close sequence (Q18, Q19; `CF-12.md:156-163`), identical for the lead and the workflow:
1. If the spec is untracked or differs from HEAD, commit it alone with the subject "Record the edited spec for <issue>".
2. Run `gate.py close --sha <that commit>`.
3. Commit the spec alone with the subject "Close the challenges on <issue>".
4. Plan.

**Contract:** `claude/evals/lib/challenge-gate-contract.sh` over `claude/evals/fixtures/challenge-gate/`. It covers every AC 8 row, plus these extras:
- fenced heading or marker ignored;
- two sections;
- section plus marker;
- `[open]` plus `[resolved]`;
- `[struck:   ]` with a whitespace-only reason;
- a 6-character sha and an uppercase sha;
- the section in the middle of the file versus at the end;
- CRLF, and no final newline;
- lint rejecting a non-`[open]` state, an unknown severity, a duplicate id, a dangling marker and an `--against` mismatch;
- close idempotence refused on a closed spec.

It is wired into `check-all.sh` after `scope-hook-contract` (`:71`).

**`spec-to-plan.js` plan stage.** A new phase, `Challenge gate`, sits between the approval stop (`:116`) and `Plan angles` (`:275`), with a matching `meta.phases` entry.
- **Lane A** (agentType-less, schema) loads `coder-fleet:challenge-gate` and runs `check --json` on the spec, adding `--no-editor` when `input.specEditor === 'none'`. It reports the exit code and stdout verbatim.
- The pure function `challengeGate(report)` decides:
  - null or unparseable: blocked, "the challenge gate returned nothing";
  - `refuse`: return `stage: 'blocked'`, name every blocking id, and spawn no Plan agent;
  - `closed` or `none`: plan with no commit;
  - `intact`: go to Lane B.
- **Lane B** runs the close sequence and reports `intactCommit`, `closeCommit`, the close commit's subject and `filesChanged`, and a re-run of `check`.
- The pure function `verifyClose(report, issue, specPath)` requires all of the following, or the stage is blocked:
  - both shas are hex;
  - `filesChanged` equals `[specPath]`;
  - the subject is exact;
  - the post-close state is `closed`;
  - the marker's sha matches `intactCommit` under `sameCommit` semantics.
- The spec stage's `nextStep` gains one clause: after the interview revision, the lead spawns the spec editor before the human edits.

**Tests in `workflow-logic.mjs`**, after `:179`:
- refuse names C2 and C4, and no Plan agent is spawned;
- closed plans with no Lane B call;
- intact runs Lane B with the exact subject, then plans;
- Lane B touching an extra file blocks;
- a sha mismatch blocks;
- Lane A returning null blocks;
- `specEditor: 'none'` with no section plans;
- the `nextStep` mentions the spec editor;
- the `FLEET` list at `:1057` gains both names.

**Fallback if the Phase 0 probe shows a workflow lane cannot load a plugin skill.** The plan stage takes `args.gate` (the absolute script path, which the lead copies from its skill's substituted text) and refuses when it is absent. Both paths fail closed.
