## Findings, with evidence

1. **Nothing caps the count.**
   - `refuter.md:34`: "list the behaviours the change claims, most damaging first, and give each one mutation". The count is however many claims there are.
   - `looping/SKILL.md:19` says the same thing ("one mutation per claim").
   - `lead.md:32` caps only the time ("never brief one with a longer budget").
   - The refuter prompt in `review-round.js` (`:875-887`) mentions neither the time nor a count.

2. **Recent rounds all ran more than eight.**
   - CF-23:
     - baseline 72 s, from one contract suite, not `check-all`;
     - 10 mutants plus 7 probes in about 6 minutes, run in parallel copies;
     - survivors were m4 and m10 (CF-23 card, `:150`, `:154`, `:160`, `:162`).
   - CF-31 rounds ran 12 to 14 mutations.
   - CF-9 ran 10 mutants the lead named and got 3 survivors (CF-9 card `:95`, `:104`).
   - In CF-23's order, a cap of eight would have cut m10, the survivor that became CF-36.

3. **Does eight fit in 20 minutes?**
   - Run one after another, reading, copying and the handoff take roughly 5 minutes. With a suite that takes b seconds, 5 minutes + 9b must stay under 20 minutes, so b can be at most about 100 s.
   - CF-23's 72 s contract suite fits, at about 16 minutes.
   - The whole `check-all` does not. `check-all.sh:84` says it "has to stay under two" minutes, so nine runs of it are close to 18 minutes before any overhead.
   - Parallel copies, as CF-23 used, remove the problem.
   - So time stays the binding cap, and eight is a ceiling.

4. **Today's trigger fires on nearly every review, by construction.**
   - `lead.md:32` spawns a refuter when a reviewer lists the gates under Unverified.
   - `reviewer.md:37` requires the reviewer to list every gate it could not run, and the scope hook means it can never run one.
   - So every review the lead spawns directly triggers a refuter.
   - Separately, `review-round.js:169` makes the refuter mandatory under `fix: true`.

5. **The narrower triggers that already exist.**
   - Deeper review: `lead.md:32` (authentication, authorisation, secrets, credentials).
   - The workflow's `SENSITIVE` pattern (`review-round.js:93-94`).
   - Neither covers data writes or item priority.

6. **Who else already runs the gates independently.**
   - `review-round`'s "types and build" and "tests" lanes (`:525-537`) run in the checkout under review (`:760`) and settle a previous fix's test claims (`:782-795`). They use Sonnet at low effort, and the tests lane may run a subset (`:536`).
   - The TaskCompleted hook runs `CODER_FLEET_TEST_COMMAND` only when it is set. It is lenient by default (hooks README `:215`) and tests the hook's `cwd` (`board-task-completed.sh:58-66`), which is the session checkout, not the coder's worktree. It is not set in this repo's `.claude/settings.json`.
   - CI runs the suite on push, which is after the fact and not per phase.
   - `scout` is refused anything that writes (`enforce-agent-scope.sh:698`).

7. **Body constraints.**
   - `refuter.md` has five invariants (`:40-44`), the contract's ceiling (`agent-contract.md:60`).
   - `:44` is pinned by `clock-invariant-in-body` (`scope-hook-contract.sh:1338`).
   - So the cap cannot be a sixth invariant, and `:44` must not change.
   - Bodies must stay under 60 lines (`agent-contract.md:66`): `lead.md` and `refuter.md` are 48 each.

8. **The design doc names today's trigger** at `fleet-design.md:45` ("`refuter` when a review's gates sit under Unverified"), and the round length at `:49`.

## Design decisions

1. **One phrase in four places, pinned equal by a test.** "At most eight mutants" goes in `refuter.md:34`, `looping/SKILL.md:19`, the brief rule at `lead.md:32`, and the refuter prompt in `review-round.js`.

2. **Eight is a ceiling, not a quota.** Mutants are ranked by what a wrong answer would cost:
   - authorisation and secrets first;
   - then data written or deleted;
   - then error paths;
   - then boundaries and input types (CF-23's m10 was a type boundary);
   - then messages last.
   - Claims past the eighth become a Not done bullet naming the mutation. That is the existing hand-over to the next round.

3. **Probes.** A probe that confirms or explains a mutant's result counts as part of that mutant. A probe with no mutant costs time only.

4. **Baseline against mutants.**
   - The baseline is the phase's full gates, run once. That is what makes the refuter the independent gate run.
   - Each mutant runs the narrowest suite that covers its claim, with that suite's own baseline recorded.
   - Parallel copies are allowed when the suite keeps its state in its own temporary directory.
   - This is what makes eight fit in 20 minutes on this repo.

5. **No hook counts mutants.** `docs/limits.md` records that the cap is an instruction.

6. **The workflow follows the lead's tier.**
   - Passing `refute: false` explicitly turns the refuter off even under `fix: true`. The default does not change.
   - This only applies if the human takes tiering (Open question 1).

## Risks

- **The cap loses findings.** CF-23's m10 would have been cut. The ranking guidance and the Not done hand-over are the mitigation. The reported mutant count per round will drop by about a third.
- **Tiering misses a regression on an untiered phase.** Mitigated two ways:
  - the gates are still run independently;
  - a reviewer who suspects a test would pass with the fix reverted (`reviewer.md:29`) still triggers a refuter.
- **"Data writes" is a judgement call.** The body gives examples: a database, a migration, board or state files, a user's files.
- **The tests lane may run a subset** (`:536`), so as a gate run it is weaker than a full refuter baseline.
- **A lead that runs the gates itself spends main-session context.** It captures the output to a file and reads the summary, as `AGENTS.md` prescribes for `check-all`.

## Open questions, each with a recommended answer

1. **The trigger (the human's call).** Options:
   - (a) the issue's list: authentication, authorisation, secrets, data writes, or a High item;
   - (b) today's gates-Unverified rule, applied only within that list;
   - (c) the status quo.
   **Recommended: (a) plus one trigger.** Also spawn a refuter when a reviewer says a test looks like it would pass with the fix reverted, since `reviewer.md:29` already makes the refuter the authority on that question. No refuter on any other phase.

2. **Who runs the gates on the other phases?** Options:
   - (i) `review-round`'s tests and types-and-build lanes;
   - (ii) the lead itself, once, in the coder's worktree, with the output captured to a file;
   - (iii) a refuter that only runs the baseline;
   - (iv) TaskCompleted or CI.
   **Recommended: (i) when the review goes through `review-round`, otherwise (ii).**
   - Not (iii): an Opus spawn to run one command is the cost that tiering removes.
   - Not (iv): TaskCompleted tests the session checkout and is unconfigured here, and CI is neither per phase nor present in every project.

3. **Is eight the number?** **Yes, as a ceiling.** Time binds first on any suite slower than about 100 s run one after another.

4. **Do probes count towards the eight?** **No.** A probe that confirms a mutant belongs to that mutant, and any other probe costs time only.

5. **Should `refute: false` switch the refuter off under `fix: true`?** **Yes, if (1) takes tiering.** Otherwise drop that case and the `:169` edit.

6. **Patch or minor?** **Patch**, per the lead's release rule. The human may prefer minor, following CF-23's precedent for an escalation change.
