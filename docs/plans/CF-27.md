# CF-27: Drop the status default from the MCP task_edit schema

Status: approved by the human on 2026-09-27 with the recommended answer to every open question (create's default left alone; the edit description gains "Omit to leave the status unchanged"; the default-filling helper is the failing-first proof). Board item: CF-27 (bug, Medium, To Do). Source: GitHub issue rzem-ai/coder-fleet#3, point 6, read as data. Route: coder. It depends on CF-26 for its completed-card case.

## Findings, with evidence

1. **Where the default comes from.** `generateStatusFieldSchema` sets `default: defaultStatus` (`src/mcp/utils/schema-generators.ts:22-38`, the default at `:35`). `defaultStatus` is the first configured status (`:27`), not the config's `default_status`. On this board that is "To Do" (`.boards/config.yml`).

2. **Both tools share it.**
   - `task_create` uses it at `schema-generators.ts:175`, and `task_edit` at `:296`.
   - Both are built in `registerTaskTools` (`src/mcp/tools/tasks/index.ts:18-19`) and published unchanged by `listTools` (`src/mcp/server.ts:208-221`). That is how clients such as Claude Code see `"default": "To Do"` on `task_edit.status`.

3. **The server never applies it.**
   - `validateInput` loops only over the keys the caller sent (`src/mcp/validation/validators.ts:56-72`), and `validateField` passes `undefined` straight through (`:92-94`). The `default` field is declared (`:20`) and never read.
   - The wrapper passes only the sanitised keys on to the handler (`tool-wrapper.ts:40-50`), and `callTool` hands the arguments over as they are (`server.ts:222-233`).
   - `buildTaskUpdateInput` sets `status` only when it is a string (`src/utils/task-edit-builder.ts:50-52`), and the core applies a status only when one is defined (`backlog.ts:1564`).
   - This matches the CF-8 evidence: six edits without a status, and the card stayed in Blocked by human.

4. **So the risk is on the client side.** A client that fills schema defaults, such as an ajv-style `useDefaults`, or a model that reads `"default": "To Do"` as the value to send, would move every edited card to To Do. `board-conventions` forbids that kind of move.

5. **An upstream test pins the edit default.** `src/test/mcp-tasks.test.ts:751-776` asserts `editStatusSchema?.default` is the first status (`:773`) and `createStatusSchema?.default` the same (`:768`). No other test or source file reads the status schema's default.

## Design decisions

1. **Remove the default from the edit schema only.** `generateStatusFieldSchema(config, { includeDefault = true } = {})`, with `generateTaskEditSchema` passing `{ includeDefault: false }`. `task_create` keeps its default, per criterion 3.

2. **Say it in the edit schema's description.** The edit's status description gains "Omit to leave the status unchanged." so a model reading the schema has the rule in words.

3. **A test that would fail if the default were applied.** The server does not apply it, so a plain edit-without-status test passes both before and after the fix and proves nothing about the schema. The test therefore has three parts:
   - (i) assert the listed `task_edit` schema has no `default`;
   - (ii) a helper, `fillSchemaDefaults(inputSchema, args)`, that acts like a client filling defaults from the listed schema before calling `task_edit`, so any default that comes back moves cards and fails the test;
   - (iii) the plain edit through the real server as a regression guard.

## Risks

- **A client that has cached the old tool list keeps showing the default until it restarts.** Not a code risk. Note it in the PR.
- **The `fillSchemaDefaults` helper is a model of a client, not a real one.** It only has to copy `default` into absent keys, and it lives in the test file.
- **CI does not run these tests (CF-29).** The proof is local only.

3. Does the default-filling helper satisfy "failing first if the default were applied"? **Yes.** Part (c) fails on four columns and the completed card while the default exists, and passes once it is gone.
