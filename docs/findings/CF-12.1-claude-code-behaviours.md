## A harness bug the live batch itself caught

The first attempt at the paid batch (all ten core runs, exit 0 on every one) captured **zero** `SubagentStop` payloads across every run, in every project, including `model` and `deny-none` where the hook should fire unconditionally. The cause: `setup.sh` built each project's `.claude/settings.json` by splicing the hook command's own shell-quoted string directly into the file's JSON text (`content.replace(PLACEHOLDER, cmd)`), and that command text contains literal double quotes around each absolute path. Those quotes were never JSON-escaped, so every project's `settings.json` was invalid JSON - Claude Code could not parse the `hooks` key out of it, and no hook ever ran, on a **live paid run**, silently. `run.sh` itself did not notice, because nothing about a missing hook call changes a `claude -p` process's own exit code.

Fixed by routing the substitution through `json.load` / a value replacement on the parsed structure / `json.dump`, so Python does the escaping rather than this script's text (`setup.sh`, the `for settings in ... do python3 ...` block). A regression check was added to `selftest.sh` (built a scratch area, then `json.load`s every project's `settings.json`) so this class of bug fails loudly before any future paid run rather than after one. The whole batch was then re-run from a fresh scratch directory with the fix in place, and every capture below comes from that second, corrected run.

This is reported here because it is exactly the shape of finding this spike exists to catch: a harness that reports "exit 0" on every run while quietly gathering none of the evidence it was built for.

## Question (1): `model: fable` on a Pro account

**On this (non-Pro) account: confirmed by direct observation.** `E1a`'s first spawn (`cf12spike:fablecheck`, `model: fable`) produced a `SubagentStop` payload whose `last_assistant_message` reads "I am running on Fable 5.1 (model ID: claude-fable-5-1)", and the captured transcript's `message.model` field is literally `"claude-fable-5-1"` for every assistant turn - not an inference, the field itself. `E1b` (the `allowlist` project, with a project-scope `availableModels` excluding `fable`) produced the identical outcome: `fablecheck` ran on Fable 5.1 again, confirming the free evidence's prediction that a project-scope `availableModels` setting is silently ignored (the docs say managed-settings-only, and this account's project-scope setting had no effect whatsoever - not even a warning line in the log).

`E1a`'s second spawn (`cf12spike:badmodel`, `model: claude-fable-0-0`, a model ID that does not exist) **failed the spawn outright**, with an `is_error` tool_result: "Agent terminated early due to an API error: There's an issue with the selected model (claude-fable-0-0). It may not exist or you may not have access to it. Run --model to pick a different model. (error type model_not_found, HTTP 404, request id ..., model sent to the API: claude-fable-0-0)". This is the plan's predicted "fails the spawn" outcome for a genuinely nonexistent model, distinct from a Pro-tier restriction on a real model.

**No Pro account is available** (plan status line), so E1p was not run and Pro behaviour rests on the ranked substitutes below, from highest to lowest confidence:

1. Docs and support article (high confidence): Pro plans bill Fable "with usage credits" and, under `-p`, bill silently without a consent prompt. So the most likely behaviour on Pro is: a Fable subagent runs, and is billed to usage credits without asking - not a spawn failure and not a silent fallback to another model, absent an `availableModels` allowlist (which is managed-only anyway, so a Pro *project* cannot itself impose that fallback).
2. `E1b` as a Pro proxy (low, now that it has run): it shows a project-scope allowlist has no effect on this account, which tells us nothing new about Pro specifically - it only confirms the allowlist mechanism itself is managed-only, consistent with the docs.
3. `E1a`'s `badmodel` run (medium): shows the clean "model does not exist" failure path (`model_not_found`, HTTP 404, `is_error` tool_result) on this account. Whether a Pro-tier *restriction* on a real, existing model (`fable`) produces the same explicit failure, a silent fallback, or the credits-billing path is not the same code path and is not settled by this run.
4. The init event on this account (low): carries no `subscriptionType` or `unavailable_models` field at all (see below) - so even the free "read it off the init event" plan does not work on this account's CLI/session shape, which is itself worth recording rather than assuming the field simply wasn't looked at hard enough.
5. Binary strings (low, interpretive): as above.

**Recommendation, regardless of what a future E1p run would show:** `/init`'s Fable wording for `spec-editor-fable` and `tech-editor-fable` should say plainly that on Pro, a Fable editor either bills usage credits without asking or runs on another model, and nothing in a run reports which happened - the fact that even a live, working init event on this account exposes no subscription or model-availability field to read reinforces that a runtime probe is not a reliable way to find out, and the wording has to cover the ambiguity rather than promise a runtime check will resolve it.

### What the init event actually carries

Contrary to the plan's binary-string-derived expectation, the live `system`/`init` event on this account and CLI carries no `subscriptionType`, no `unavailable_models`, and no `account` key at all. Its actual top-level keys: `agents`, `analytics_disabled`, `apiKeySource`, `capabilities`, `claude_code_version`, `cwd`, `fast_mode_disabled_reason`, `fast_mode_state`, `mcp_servers`, `memory_paths`, `messaging_socket_path`, `model`, `output_style`, `per_turn_effort_active`, `permissionMode`, `plugins`, `product_feedback_disabled`, `session_id`, `skills`, `slash_commands`, `subtype`, `terminal_slash_commands`, `tools`, `type`, `uuid`, `view_mode`. `apiKeySource` was `"none"` on this run (this account authenticates some other way). Whatever code path the binary strings for `unavailable_models` belong to, it did not populate this account's init event under `--setting-sources project,local` with `--plugin-dir`.

Useful side effect for CF-12.2: `agents` in this same init event lists `cf12spike:sub:nested` - confirming the plugin loader **does scan `agents/` recursively**, namespacing a subdirectory agent as `plugin:subdir:name` - and does **not** list `decoy` from `pairs-src/`, confirming that directory is never loaded as agents. Both are read directly off a live event, not inferred.

## Question (2): `maxTurns` and the handoff

**No, not reliably - and the hook was not observed to fire at all in the failing case.**

- **`E2a`** (control: `turncap`, asked to read only `f1.txt`, well under the 3-turn cap): finished normally with a valid four-heading handoff. `SubagentStop` fired, was captured, and `board-subagent-stop.sh` logged "cf12spike:turncap succeeded with no blockers; commenting 1 \"## Done\" item(s)" - hook exit 0, as expected for a clean run.
- **`E2b`** (`turncap`, asked to read all eight files one per turn, so the 3-turn cap bites mid-task): the subagent's own transcript shows it read `f1.txt`, `f2.txt`, `f3.txt` (three tool uses) and its final tool_result carries this exact prefix, verbatim: "NOTE: this agent stopped at its 3-turn limit before finishing. The text below is PARTIAL output; treat it as incomplete. Send the agent a message (SendMessage) to let it continue from where it stopped." - confirming the docs' "marked as partial" behaviour, live. The `last_assistant_message` itself is **"Now reading the third file."** - plain prose, not a handoff, because the third turn was spent on a tool call (reading `f3.txt`) rather than on writing the handoff the body asks for. **No `stop-*.json` was ever captured for this agent's id**, and no `hook-exit-*` or `hook-stderr-*` file exists for it either, in contrast to every other run in the batch. The `SubagentStop` hook was not observed to fire for this run at all - not "fired and returned exit 0 on a message it could not parse", but genuinely absent from the logs, with an empty `.stderr` for the whole batch run. This is a stronger failure mode than the plan's "cannot tell" hypothesis: the hook's own jq-based "cannot tell" branch never gets a chance to run, because the event that would trigger it did not arrive.
- **`E2c`** (`turncap-early`, the same eight-file task, told explicitly "make your third turn your handoff", subagent on `opus`): finished with a **valid** four-heading handoff - it read `f1.txt` and `f2.txt`, then spent its third turn entirely on the handoff, correctly listing `f3.txt`-`f8.txt` under "## Not done". `SubagentStop` fired, was captured, and the hook logged "cf12spike:turncap-early succeeded with no blockers; commenting 2 \"## Done\" item(s)" - hook exit 0.

So the cap-mid-tool-call failure mode (`E2b`) is real and is not caught by the current hook - not because the hook mishandles it, but because the hook is never invoked for it in the first place. The early-handoff instruction (`E2c`) reliably avoids the failure mode by leaving the model one full text-only turn to spend on the handoff, at the cost of one turn's worth of task progress.

**Consequence for CF-12.3-CF-12.5:** `maxTurns: 15` on `spec-editor`/`tech-editor` needs the same early-handoff instruction as a body invariant ("you have at most N turns; make your last turn your handoff"), not just the frontmatter number - `turncap`'s bare `maxTurns: 3` with no such instruction produced a silently un-gated, non-handoff stop on live evidence, and there is no hook safety net behind it in that exact circumstance. A `Propose item:` for CF-12's plan: whether `board-subagent-stop.sh` should be changed to also treat "no `SubagentStop` event arrived within the run's own lifetime" as a detectable condition is out of this spike's scope (it needs a different signal than the hook itself, since the hook is what is missing) - noting it here rather than proposing a fix.

## Question (3): `permissions.deny` and plugin-namespaced agents

**Yes, confirmed by direct observation, on both the throwaway plugin and the real `coder-fleet` plugin.**

- **`E3b`** (`deny-fable` project, `permissions.deny: ["Agent(cf12spike:probe-fable)"]`): spawning `cf12spike:probe-fable` returned an `is_error` tool_result: `"Agent type 'cf12spike:probe-fable' has been denied by permission rule 'Agent(cf12spike:probe-fable)' from projectSettings."` - blocked outright, with the exact rule named back. Spawning the **bare** name `probe-fable` (no prefix) returned a *different* `is_error`: `"Agent type 'probe-fable' not found. Available agents: cf12spike:badmodel, cf12spike:fablecheck, cf12spike:probe, cf12spike:sub:nested, cf12spike:turncap, cf12spike:turncap-early, claude, Explore, gene[ral-purpose, ...]"` - not a leak around the deny rule, but simple non-resolution: a plugin-loaded agent is not addressable by its bare name at all in this session shape, so there is nothing for the deny rule to fail to catch. Spawning `cf12spike:probe` (the prefix-sharing sibling, not denied) succeeded normally (dispatched as a background agent, no error).
- **`E3c`** (`deny-plain` project, `permissions.deny: ["Agent(cf12spike:probe)"]`, the mirror case): `cf12spike:probe` denied outright with the same message shape; bare `probe` "not found", listing `cf12spike:probe-fable` among the available agents; `cf12spike:probe-fable` (not denied) succeeded normally. Confirms the unsuffixed rule does not catch the `-fable` sibling, in either direction.
- **`E3d`** (`deny-real` project, `--plugin-dir` pointed at this checkout's real `claude/coder-fleet`, `permissions.deny: ["Agent(coder-fleet:scout)"]`): `coder-fleet:scout` denied outright: `"Agent type 'coder-fleet:scout' has been denied by permission rule 'Agent(coder-fleet:scout)' from projectSettings."` Bare `scout` "not found", with the available-agents list showing the real roster under its `coder-fleet:` prefix (`coder-fleet:coder`, `coder-fleet:fleet-steward`, `coder-fleet:lead`, `coder-fleet:refuter`, `coder-fleet:researcher`, `coder-fleet:reviewer`, `coder-fleet:scripter`, `coder-fleet:spec-writer`, `coder-fleet:tech-writer`, `coder-fleet:ui-designer`, and `claude`/`Explore`/`general-purpose`/`Plan`/`statusline-setup`). Same shape, same outcome, on the production plugin rather than the throwaway one.
- **`E3a`** (`deny-none`, control): both `cf12spike:probe` and `cf12spike:probe-fable` ran without any denial, confirming the deny rules in `E3b`-`E3d` are doing the blocking, not some other constraint (e.g. a missing agent definition).

**Consequence for CF-12.3-CF-12.5:** spec AC 17's hard stop exists as designed - `Agent(coder-fleet:<name>)` in `permissions.deny` does block the plugin-namespaced spawn, and the unsuffixed/`-fable` pair does not collide either direction. On this evidence, a `subagent_type` parameter-rule fallback (`Agent(subagent_type:*spec-editor-fable)`) is not needed: there is no leaking bare-name path to guard against, because a bare name does not resolve to a plugin agent in the first place in this session shape. That "not found" result is itself worth a one-line note in CF-12's error-handling text, since a project author denying a definition should read a "not found" result for the bare name as expected, not as a sign the deny rule failed.
