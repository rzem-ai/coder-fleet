## A harness bug the live batch itself caught

The first attempt at the paid batch (all ten core runs, exit 0 on every one) captured **zero** `SubagentStop` payloads across every run, in every project, including `model` and `deny-none` where the hook should fire unconditionally. The cause: `setup.sh` built each project's `.claude/settings.json` by splicing the hook command's own shell-quoted string directly into the file's JSON text (`content.replace(PLACEHOLDER, cmd)`), and that command text contains literal double quotes around each absolute path. Those quotes were never JSON-escaped, so every project's `settings.json` was invalid JSON - Claude Code could not parse the `hooks` key out of it, and no hook ever ran, on a **live paid run**, silently. `run.sh` itself did not notice, because nothing about a missing hook call changes a `claude -p` process's own exit code.

Fixed by routing the substitution through `json.load` / a value replacement on the parsed structure / `json.dump`, so Python does the escaping rather than this script's text (`setup.sh`, the `for settings in ... do python3 ...` block). A regression check was added to `selftest.sh` (built a scratch area, then `json.load`s every project's `settings.json`) so this class of bug fails loudly before any future paid run rather than after one. The whole batch was then re-run from a fresh scratch directory with the fix in place, and every capture below comes from that second, corrected run.

This is reported here because it is exactly the shape of finding this spike exists to catch: a harness that reports "exit 0" on every run while quietly gathering none of the evidence it was built for.

### Review round 1: two more harness bugs, and confirming the hook replay against `origin/main`

Review round 1 found two further bugs in the harness itself, both now fixed with failing-test-first `selftest.sh` cases: `resolve_scratch_dir` ran `mkdir -p` on its argument before any of its refusal checks, so a path that was going to be refused anyway (for example one under this repository's own main checkout root) got created on disk regardless - confirmed live during the fix, which created and then had to clean up a real directory under the main checkout; and `replay.sh` never called `require_scratch_shape` before writing into `<scratch>/replay-state`, so it would act on any resolvable path, not only one this harness's own `setup.sh` had built. Neither bug affected any evidence already gathered - both are about what the harness would do to an *unrelated* directory, not about what it reported from a real scratch area - but both are fixed and covered by `selftest.sh` checks 9 and 10.

Per the plan's step 3, `replay.sh` was re-run against the hook at `origin/main` over the newly captured `E2a`/`E2c` payloads from review round 1 (confirmed `diff`-identical to this branch's copy of `board-subagent-stop.sh` beforehand): both replayed to exit 0, matching their live results exactly - the hook's behaviour on the two payloads that did arrive is confirmed offline and reproducibly, independent of this branch's own state.

## Question (1): `model: fable` on a Pro account

**On this (non-Pro) account: confirmed by direct observation.** `E1a`'s first spawn (`cf12spike:fablecheck`, `model: fable`) produced a `SubagentStop` payload whose `last_assistant_message` reads "I am running on Fable 5.1 (model ID: claude-fable-5-1)", and the captured transcript's `message.model` field is literally `"claude-fable-5-1"` for every assistant turn - not an inference, the field itself. `E1b` (the `allowlist` project, with a project-scope `availableModels` excluding `fable`) produced the identical outcome: `fablecheck` ran on Fable 5.1 again, confirming the free evidence's prediction that a project-scope `availableModels` setting is silently ignored (the docs say managed-settings-only, and this account's project-scope setting had no effect whatsoever - not even a warning line in the log).

`E1a`'s second spawn (`cf12spike:badmodel`, `model: claude-fable-0-0`, a model ID that does not exist) **failed the spawn outright**, with an `is_error` tool_result: "Agent terminated early due to an API error: There's an issue with the selected model (claude-fable-0-0). It may not exist or you may not have access to it. Run --model to pick a different model. (error type model_not_found, HTTP 404, request id ..., model sent to the API: claude-fable-0-0)". This is the plan's predicted "fails the spawn" outcome for a genuinely nonexistent model, distinct from a Pro-tier restriction on a real model.

**No Pro account is available** (plan status line), so E1p was not run and Pro behaviour rests on the ranked substitutes below, from highest to lowest confidence:

1. Docs and support article (high confidence): Pro plans bill Fable "with usage credits" and, under `-p`, bill silently without a consent prompt. So the most likely behaviour on Pro is: a Fable subagent runs, and is billed to usage credits without asking - not a spawn failure and not a silent fallback to another model, absent an `availableModels` allowlist (which is managed-only anyway, so a Pro *project* cannot itself impose that fallback).
2. `E1b` as a Pro proxy (low, now that it has run): it shows a project-scope allowlist has no effect on this account, which tells us nothing new about Pro specifically - it only confirms the allowlist mechanism itself is managed-only, consistent with the docs.
3. `E1a`'s `badmodel` run (medium-low, unchanged from the findings skeleton's original ranking - an earlier draft of this section bumped it to "medium" without saying why, which review round 1 caught; reverted here): shows the clean "model does not exist" failure path (`model_not_found`, HTTP 404, `is_error` tool_result) on this account. That is a different code path from a Pro-tier restriction on a real, existing model (`fable`) - a nonexistent model ID is rejected before the request reaches any plan-tier check at all, so this run bears on "what does an unrecognised model do" more than on "what does Pro do with a real model it restricts", and the ranking reflects that distance rather than the strength of the observation itself.
4. The init event on this account (low): carries no `subscriptionType` or `unavailable_models` field at all (see below) - so even the free "read it off the init event" plan does not work on this account's CLI/session shape, which is itself worth recording rather than assuming the field simply wasn't looked at hard enough.
5. Binary strings (low, interpretive): as above.

**Recommendation, regardless of what a future E1p run would show:** `/init`'s Fable wording for `spec-editor-fable` and `tech-editor-fable` should say plainly that on Pro, a Fable editor either bills usage credits without asking, fails the spawn outright, or runs on another model. Model *fallback* is not actually unreported - `E1a` shows exactly that: a genuine model swap is visible in the subagent's own `message.model` field and self-report, which a project author could check by asking the editor what model it is running on. What stays unreported is specifically the **usage-credit billing** case: nothing in a run's own output distinguishes "ran on Fable, billed normally" from "ran on Fable, billed to usage credits without asking", because both look identical from inside the run - the billing decision happens server-side and is never surfaced to the transcript. The wording has to cover that one gap, not model fallback in general, which a check of `message.model` already answers.

## Question (2): `maxTurns` and the handoff

**No, not reliably - and the hook was not observed to fire at all in any of the five capped runs across two rounds.**

- **`E2a`** (control: `turncap`, asked to read only `f1.txt`, well under the 3-turn cap; run once in round 1, once more in review round 1 - two independent runs): finished normally both times with a valid four-heading handoff. `SubagentStop` fired and was captured both times, and `board-subagent-stop.sh` logged "cf12spike:turncap succeeded with no blockers; commenting 1 \"## Done\" item(s)" - hook exit 0, as expected for a clean run.
- **`E2b`** (`turncap`, asked to read all eight files one per turn, so the 3-turn cap bites mid-task; run once in round 1, twice more in review round 1 - **three independent runs**): all three ended the same way - read three files, then stopped mid-task with no valid handoff, and no `SubagentStop` capture. Two of the three runs (both review-round-1 reruns) were dispatched by the parent as a **background** task; the round-1 original was **not** backgrounded. Both delivery paths still hit the cap with no handoff and no hook capture - see "Exact evidence source" and "Confidence and alternative explanations" below for what that dispatch difference does and does not change.
- **`E2c`** (`turncap-early`, the same eight-file task, told explicitly "make your third turn your handoff", **on `opus`**; run once in round 1, once more in review round 1): finished with a **valid** four-heading handoff both times - it read `f1.txt` and `f2.txt`, then spent its third turn entirely on the handoff, correctly listing the unread files under "## Not done". `SubagentStop` fired and was captured both times, hook exit 0.
- **`E2d`** (added in review round 1 - `turncap-early-haiku`, the identical instruction and task as `E2c`, but **on `haiku`**, isolating the instruction from the model): the instruction did **not** work on haiku. The subagent read `f1.txt` and `f2.txt`, then on its third turn issued **eight** `Read` tool calls back to back (`f3.txt` through `f8.txt`, `tool_uses: 8` in the usage line) rather than stopping to write the handoff, and was cut off mid-batch by the cap - "NOTE: this agent stopped at its 3-turn limit before finishing... I've read f2.txt... I'll now read the remaining 6 files in this final turn to complete the task." is the final text, not a handoff. No `SubagentStop` capture for this run either.

**`E2c` was confounded, and `E2d` unconfounds it.** `E2c`'s success cannot be attributed to the instruction alone: `turncap-early` runs on `opus` while the plain `turncap` control (`E2a`/`E2b`) runs on `haiku`, so `E2c` varied two things at once - a stronger model *and* an explicit instruction. `E2d` holds the instruction fixed and swaps only the model back to `haiku`, and the instruction alone does not save it: haiku still tries to cram the whole remaining task into its last turn rather than treating "turn" as the unit the instruction meant. So the working combination observed is "the instruction, on a model capable of following a turn-budget instruction over a multi-step task" - not the instruction by itself.

### Exact evidence source for the quoted text

Two different, both real, delivery paths produced the quoted `E2b` text, and neither of them is `capture-stop.sh` or a `SubagentStop` payload - both fired *despite* the hook never firing, because the runtime hands a spawned subagent's outcome back to its parent through a separate channel regardless of whether the hook ran:

- **Round 1's `E2b`** (not backgrounded): the parent session's own transcript (`<scratch>/logs/E2b.jsonl`, captured by `run.sh`'s own stdout redirection - not by `capture-stop.sh`) contains a `tool_result` for the `Agent` tool_use itself, whose text is the runtime's "subagent hand-back" - "NOTE: this agent stopped at its 3-turn limit... Now reading the third file." This is the literal hand-back text the runtime gives the *parent*, not the subagent's own `last_assistant_message` field (which only a `SubagentStop` payload carries, and none arrived).
- **Review round 1's two `E2b` reruns** (both backgrounded - the parent's `Agent` tool_use in both had no `run_in_background` key at all, so the runtime chose to background it, not the prompt): the parent's transcript instead contains a `system`/`subtype: task_notification` event, whose `summary` field carries the same shape of text - "NOTE: this agent stopped at its 3-turn limit before finishing... Now reading f3.txt." This is a different code path (a background-task completion notification) delivering functionally the same content.

Neither path is the `~/.claude/projects/.../subagents/agent-<id>.jsonl` transcript file `capture-stop.sh` copies (that copy only happens when `SubagentStop` fires and names `agent_transcript_path`, which did not happen here) - both are the *parent* session's own event stream, which the runtime populates independent of the hook.

### Confidence and alternative explanations

Three independent `E2b` runs, two different dispatch modes, one outcome each time (cap hit mid-task, no valid handoff, no hook capture) - that is a real replication, not a single anecdote, and the summary table's confidence has moved from the original "High" to **medium-high**, not because the direction is in doubt but because every run shares one harness configuration (`--setting-sources project,local`, `--plugin-dir`, `--permission-mode dontAsk`, this CLI version, this account). No `stop-unknown-*` file (the name `capture-stop.sh` would use if `jq` could not read an `agent_id` out of a payload) appeared in any round - so the absence is not a naming or parsing failure in the capture script; nothing arrived to name.

Three alternative explanations for the missing hook capture, considered and not ruled out by this batch:

1. **A background-dispatched agent may outlive the parent `claude -p` process.** If a backgrounded subagent is a child process of the same top-level invocation, the parent process exiting once its own turn is satisfied could terminate the child before it reaches its own `SubagentStop` moment - or before that hook's own process gets to finish writing. Two of the three `E2b` runs were backgrounded; the round-1 original was not, and it still produced no capture, which argues against this being the *whole* explanation, but does not rule out background dispatch making the gap worse or more likely.
2. **The missing-`agent_id` capture name is not the cause.** Ruled out directly: no `stop-unknown-*` file exists anywhere in either round's logs, so this is not a case of the hook firing and `capture-stop.sh` failing to name the file - the hook itself did not run.
3. **The whole batch ran nested inside a sandboxed Claude Code session** (this agent, running under the harness's own session sandbox, spawning `claude -p` as a child process). Whether that sandboxing itself interferes with a background subagent's own hook lifecycle - independent of whether it also would from a plain terminal - is not something this batch can distinguish from the other two explanations, because every run in both rounds shares that same nested condition.

None of the three is confirmed or excluded by the evidence gathered; they are named here as open, not resolved. The one thing ruled out is explanation 2.

**Consequence for CF-12.3-CF-12.5:** `maxTurns: 15` on `spec-editor`/`tech-editor` needs the same early-handoff instruction as a body invariant ("you have at most N turns; make your last turn your handoff"), not just the frontmatter number, **and** it needs a model capable of actually following that instruction over a multi-step task - `E2d` shows the instruction alone does not save a weaker model. `turncap`'s bare `maxTurns: 3` with no such instruction produced a silently un-gated, non-handoff stop on live evidence, replicated three times, and there is no hook safety net behind it in that exact circumstance. A `Propose item:` for CF-12's plan: whether `board-subagent-stop.sh` should be changed to also treat "no `SubagentStop` event arrived within the run's own lifetime" as a detectable condition is out of this spike's scope (it needs a different signal than the hook itself, since the hook is what is missing) - noting it here rather than proposing a fix.

## Question (3): `permissions.deny` and plugin-namespaced agents

**Yes, confirmed by direct observation, on both the throwaway plugin and the real `coder-fleet` plugin.**

- **`E3b`** (`deny-fable` project, `permissions.deny: ["Agent(cf12spike:probe-fable)"]`): spawning `cf12spike:probe-fable` returned an `is_error` tool_result: `"Agent type 'cf12spike:probe-fable' has been denied by permission rule 'Agent(cf12spike:probe-fable)' from projectSettings."` - blocked outright, with the exact rule named back. Spawning the **bare** name `probe-fable` (no prefix) returned a *different* `is_error`: `"Agent type 'probe-fable' not found. Available agents: cf12spike:badmodel, cf12spike:fablecheck, cf12spike:probe, cf12spike:sub:nested, cf12spike:turncap, cf12spike:turncap-early, claude, Explore, gene[ral-purpose, ...]"` - not a leak around the deny rule, but simple non-resolution: a plugin-loaded agent is not addressable by its bare name at all in this session shape, so there is nothing for the deny rule to fail to catch. Spawning `cf12spike:probe` (the prefix-sharing sibling, not denied) succeeded normally (dispatched as a background agent, no error).
- **`E3c`** (`deny-plain` project, `permissions.deny: ["Agent(cf12spike:probe)"]`, the mirror case): `cf12spike:probe` denied outright with the same message shape; bare `probe` "not found", listing `cf12spike:probe-fable` among the available agents; `cf12spike:probe-fable` (not denied) succeeded normally. Confirms the unsuffixed rule does not catch the `-fable` sibling, in either direction.
- **`E3d`** (`deny-real` project, `--plugin-dir` pointed at this checkout's real `claude/coder-fleet`, `permissions.deny: ["Agent(coder-fleet:scout)"]`): `coder-fleet:scout` denied outright: `"Agent type 'coder-fleet:scout' has been denied by permission rule 'Agent(coder-fleet:scout)' from projectSettings."` Bare `scout` "not found", with the available-agents list showing the real roster under its `coder-fleet:` prefix (`coder-fleet:coder`, `coder-fleet:fleet-steward`, `coder-fleet:lead`, `coder-fleet:refuter`, `coder-fleet:researcher`, `coder-fleet:reviewer`, `coder-fleet:scripter`, `coder-fleet:spec-writer`, `coder-fleet:tech-writer`, `coder-fleet:ui-designer`, and `claude`/`Explore`/`general-purpose`/`Plan`/`statusline-setup`). Same shape, same outcome, on the production plugin rather than the throwaway one.
- **`E3a`** (`deny-none`, control): both `cf12spike:probe` and `cf12spike:probe-fable` ran without any denial, confirming the deny rules in `E3b`-`E3d` are doing the blocking, not some other constraint (e.g. a missing agent definition).

**Consequence for CF-12.3-CF-12.5:** spec AC 17's hard stop exists as designed - `Agent(coder-fleet:<name>)` in `permissions.deny` does block the plugin-namespaced spawn, and the unsuffixed/`-fable` pair does not collide either direction. On this evidence, a `subagent_type` parameter-rule fallback (`Agent(subagent_type:*spec-editor-fable)`) is not needed: there is no leaking bare-name path to guard against, because a bare name does not resolve to a plugin agent in the first place in this session shape. That "not found" result is itself worth a one-line note in CF-12's error-handling text, since a project author denying a definition should read a "not found" result for the bare name as expected, not as a sign the deny rule failed.

**Scope of this verdict, stated plainly:**

- Observed only under `--plugin-dir`, `--permission-mode dontAsk`, and `--setting-sources project,local`. Whether the same "not found" (rather than "denied" or a successful spawn) result holds under a different permission mode, a different `--setting-sources` combination, or a plugin installed the normal way (via the marketplace, not `--plugin-dir`) was not tested.
- The bare-name spawn was tried in `E3b`-`E3d`, where it was expected to be denied or to leak. It was **not** tried in `E3a`, the control - so there is no direct evidence that a bare-name spawn of `probe` or `probe-fable` succeeds in a project with **no** deny rules at all. The `E3b`/`E3c`/`E3d` "not found" result shows a bare name never resolves regardless of whether a deny rule exists for the prefixed form, which is what the verdict above rests on - but the control run itself did not exercise the bare-name path, and it should have.
- A same-named agent placed under a **project's own** `.claude/agents/` directory (rather than loaded via a plugin) was not tested at all. If a project could define its own `spec-editor` agent alongside the plugin's `coder-fleet:spec-editor`, a deny rule scoped to `Agent(coder-fleet:spec-editor)` would have no reason to catch it - that is a different, untested spawn path, not a leak in the rule this spike checked, and CF-12's plan should not read this finding as covering it.
