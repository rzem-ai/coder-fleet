## Free evidence gathered in step 1

- **`code.claude.com/docs/en/sub-agents`** (fetched 2026-09-27). On the `availableModels` allowlist blocking a subagent's model: a family alias (e.g. `opus`) falls back "to the newest version of that family the allowlist permits"; anything else falls back "on the inherited model instead", with `CLAUDE_CODE_SUBAGENT_MODEL` tried first if set. The warning naming both models is shown "In interactive sessions" only, implying `-p` mode is silent. On `maxTurns`: "When the subagent reaches the limit, Claude Code returns its output marked as partial, and Claude can resume it to continue. The partial marking requires Claude Code v2.1.246 or later." Installed CLI is 2.1.283, so the partial marker should be present in any capped run.
- **`code.claude.com/docs/en/model-config`** (fetched 2026-09-27). `availableModels` (and `deniedModels`, `availableModelsMatch`) are read from **managed settings only**: "If you set either one in user, project, or local settings or with `--settings`, Claude Code ignores it with a warning." This directly answers the `allowlist` project's premise: a project-scope `availableModels` setting is expected to be ignored, so **E1b is dropped as originally conceived** - the run is kept in `run.sh` only because the plan's ten-core-command verify step depends on its exact command shape, but its result is predicted to be identical to E1a's first spawn (Fable runs, since the project-scope setting is a no-op), not a genuine allowlist test. For the subagent/teammate override: "Claude Code runs the subagent or teammate on a fallback model rather than failing the request." On Fable billing: "In non-interactive mode with the `-p` flag and through the Agent SDK, Claude Code never shows the consent prompt. When a Fable request there would bill to usage credits, Claude Code bills it without asking."
- **`code.claude.com/docs/en/permissions`** (fetched 2026-09-27). `Agent(AgentName)` rules: `Agent(Explore)`, `Agent(Plan)`, `Agent(my-custom-agent)` are the documented forms; add to `permissions.deny` or pass via `--disallowedTools`. ## Question (1): `model: fable` on a Pro account

Not yet answered live. **No Pro account is available** (plan status line), so E1p is not run and this question rests on the ranked substitutes below, from highest to lowest confidence:

1. Docs and support article (high confidence): Pro plans do bill Fable "with usage credits" and, under `-p`, bill silently without a consent prompt. So the most likely behaviour on Pro is: a Fable subagent runs, and is billed to usage credits without asking - not a spawn failure and not a silent fallback to another model, absent an `availableModels` allowlist.
2. E1b as a Pro proxy (medium-low): dropped as a genuine allowlist test per the free evidence above (project-scope `availableModels` is ignored), so it adds nothing beyond E1a's evidence.
3. E1a's `badmodel` run (medium-low): the server-refusal path for an unknown model ID, not the same code path as a Pro-tier restriction, but the binary evidence above suggests both may route through the same `model_not_found`/fallback machinery - worth checking once E1a's live evidence exists.
4. `unavailable_models` on this (non-Pro) account (low): informative about what this account's init event reports, not about Pro.
5. Binary strings (low, interpretive): as above.

Whatever a future E1p run shows, the recommendation stands regardless: `/init`'s Fable wording for `spec-editor-fable` and `tech-editor-fable` should say plainly that on Pro, a Fable editor either bills usage credits without asking or runs on another model, and nothing in a run reports which happened.
