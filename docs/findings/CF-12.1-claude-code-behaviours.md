## A harness bug the live batch itself caught

The first attempt at the paid batch (all ten core runs, exit 0 on every one) captured **zero** `SubagentStop` payloads across every run, in every project, including `model` and `deny-none` where the hook should fire unconditionally. The cause: `setup.sh` built each project's `.claude/settings.json` by splicing the hook command's own shell-quoted string directly into the file's JSON text (`content.replace(PLACEHOLDER, cmd)`), and that command text contains literal double quotes around each absolute path. Those quotes were never JSON-escaped, so every project's `settings.json` was invalid JSON - Claude Code could not parse the `hooks` key out of it, and no hook ever ran, on a **live paid run**, silently. `run.sh` itself did not notice, because nothing about a missing hook call changes a `claude -p` process's own exit code.

Fixed by routing the substitution through `json.load` / a value replacement on the parsed structure / `json.dump`, so Python does the escaping rather than this script's text (`setup.sh`, the `for settings in ... do python3 ...` block). A regression check was added to `selftest.sh` (built a scratch area, then `json.load`s every project's `settings.json`) so this class of bug fails loudly before any future paid run rather than after one. The whole batch was then re-run from a fresh scratch directory with the fix in place, and every capture below comes from that second, corrected run.

This is reported here because it is exactly the shape of finding this spike exists to catch: a harness that reports "exit 0" on every run while quietly gathering none of the evidence it was built for.

### Review round 1: two more harness bugs, and confirming the hook replay against `origin/main`

Review round 1 found two further bugs in the harness itself, both now fixed with failing-test-first `selftest.sh` cases: `resolve_scratch_dir` ran `mkdir -p` on its argument before any of its refusal checks, so a path that was going to be refused anyway (for example one under this repository's own main checkout root) got created on disk regardless - confirmed live during the fix, which created and then had to clean up a real directory under the main checkout; and `replay.sh` never called `require_scratch_shape` before writing into `<scratch>/replay-state`, so it would act on any resolvable path, not only one this harness's own `setup.sh` had built. Neither bug affected any evidence already gathered - both are about what the harness would do to an *unrelated* directory, not about what it reported from a real scratch area - but both are fixed and covered by `selftest.sh` checks 9 and 10.

Per the plan's step 3, `replay.sh` was re-run against the hook at `origin/main` over the newly captured `E2a`/`E2c` payloads from review round 1 (confirmed `diff`-identical to this branch's copy of `board-subagent-stop.sh` beforehand): both replayed to exit 0, matching their live results exactly - the hook's behaviour on the two payloads that did arrive is confirmed offline and reproducibly, independent of this branch's own state.

### Review round 2: a dot-component path escape in the round-1 fix itself

Review round 2 found that round 1's own fix (walking up to the nearest existing ancestor before resolving) was itself escapable: the walk reattaches its "remainder" from `basename`/`dirname` on the raw input, which does not collapse `..` - so a path containing `../..` could walk up to an existing ancestor, then have those literal `..` segments reattached as a plain string, and every refusal check afterwards (including the main-checkout-root prefix match) compared against that un-collapsed string rather than where the path would actually resolve once created. Fixed by refusing any `.` or `..` path component outright, before the ancestor-walk runs at all (`selftest.sh` check 11, built against a throwaway "fake root" under a temp directory so the test itself cannot create anything inside the real repository even if the guard fails - confirmed red against the pre-fix code, which created an empty throwaway sibling directory rather than anything in the repo, then green after the fix). This does not affect any evidence already gathered - the same reasoning as round 1's two bugs applies: it is about what the harness would do to an unrelated, adversarially-shaped path, not about anything a real scratch area reported.

That is a different code path from a Pro-tier restriction on a real, existing model (`fable`) - a nonexistent model ID is rejected before the request reaches any plan-tier check at all, so this run bears on "what does an unrecognised model do" more than on "what does Pro do with a real model it restricts", and the ranking reflects that distance rather than the strength of the observation itself.

**Recommendation, regardless of what a future E1p run would show:** `/init`'s Fable wording for `spec-editor-fable` and `tech-editor-fable` should say plainly that on Pro, a Fable editor either bills usage credits without asking, fails the spawn outright, or runs on another model. ## Question (2): `maxTurns` and the handoff

**No, not reliably - and, split into its two parts: a run cut off by the cap mid-task never ends with a valid handoff (4 of 4), and `SubagentStop` never fires when that happens (0 of 4), against 4 of 4 firing when a run finishes on its own.** Eight capped-eligible runs in total across both rounds (`E2a` x2, `E2b` x3, `E2c` x2, `E2d` x1), not five - the "five" in an earlier draft of this file undercounted the review-round-1 reruns.

- **`E2b`** (`turncap`, asked to read all eight files one per turn, so the 3-turn cap bites mid-task; run once in round 1, twice more in review round 1 - **three independent runs**): all three ended the same way - read three files, then stopped mid-task with no valid handoff, and no `SubagentStop` capture. ### Exact evidence source for the quoted text

Two different, both real, delivery paths produced the quoted `E2b` text, and neither of them is `capture-stop.sh` or a `SubagentStop` payload - both fired *despite* the hook never firing, because the runtime hands a spawned subagent's outcome back to its parent through a separate channel regardless of whether the hook ran:

- **Round 1's `E2b`** (not backgrounded): the parent session's own transcript (`<scratch>/logs/E2b.jsonl`, captured by `run.sh`'s own stdout redirection - not by `capture-stop.sh`) contains a `tool_result` for the `Agent` tool_use itself, whose text is the runtime's "subagent hand-back" - "NOTE: this agent stopped at its 3-turn limit... Now reading the third file." This is the literal hand-back text the runtime gives the *parent*, not the subagent's own `last_assistant_message` field (which only a `SubagentStop` payload carries, and none arrived).
- **Review round 1's two `E2b` reruns** (both backgrounded - the parent's `Agent` tool_use in both had no `run_in_background` key at all, so the runtime chose to background it, not the prompt): the parent's transcript instead contains a `system`/`subtype: task_notification` event, whose `summary` field carries the same shape of text - "NOTE: this agent stopped at its 3-turn limit before finishing... Now reading f3.txt." This is a different code path (a background-task completion notification) delivering functionally the same content.

Neither path is the `~/.claude/projects/.../subagents/agent-<id>.jsonl` transcript file `capture-stop.sh` copies (that copy only happens when `SubagentStop` fires and names `agent_transcript_path`, which did not happen here) - both are the *parent* session's own event stream, which the runtime populates independent of the hook.

### Confidence and alternative explanations

Two separate claims here carry different confidence, per the split summary-table rows:

- **(2a) A cap-cut-off run never ends with a valid handoff: medium-high.** Four independent runs (`E2b` x3, `E2d` x1), two different dispatch modes, one outcome every time (cap hit mid-task, plain prose, never a handoff) - a real replication, not a single anecdote. Held back from "High" because every run shares one harness configuration (`--setting-sources project,local`, `--plugin-dir`, `--permission-mode dontAsk`, this CLI version, this account).
- **(2b) `SubagentStop` does not fire when the cap cuts a run off: medium at most.** Zero of four cap-cut-off runs produced a capture, against four of four captures when a run finished on its own (`E2a` x2, `E2c` x2) - so the hook firing correctly under the very same nested sandbox and settings rules out sandboxing alone as a sufficient explanation, and narrows the field, but does not settle which of the remaining two explanations (or both together) is the actual cause. No `stop-unknown-*` file (the name `capture-stop.sh` would use if `jq` could not read an `agent_id` out of a payload) appeared in any round - so the absence is not a naming or parsing failure in the capture script; nothing arrived to name.

Three alternative explanations were named for the missing hook capture. One is ruled out; the other two both remain live, and only their combination with the cap - not either alone - is left standing:

1. **A background-dispatched agent may outlive the parent `claude -p` process.** If a backgrounded subagent is a child process of the same top-level invocation, the parent process exiting once its own turn is satisfied could terminate the child before it reaches its own `SubagentStop` moment - or before that hook's own process gets to finish writing. Two of the four cap-cut-off runs were backgrounded (`E2b`'s two review-round-1 reruns); the other two (`E2b`'s round-1 original, and `E2d`) were not, and both still produced no capture - so background dispatch is not necessary for the gap to appear, though it may still make it worse or more likely when it does apply.
2. **The missing-`agent_id` capture name is not the cause.** Ruled out directly: no `stop-unknown-*` file exists anywhere in either round's logs, so this is not a case of the hook firing and `capture-stop.sh` failing to name the file - the hook itself did not run.
3. **Nested sandboxing, alone, is not the cause - but nested-sandbox-plus-cap has not been excluded.** The whole batch ran nested inside a sandboxed Claude Code session (this agent, running under the harness's own session sandbox, spawning `claude -p` as a child process). `E2a` and `E2c` ran under that identical nested condition and the hook fired every time (4 of 4) - so sandboxing by itself cannot be the whole story, since it did not stop those captures. What is not ruled out is sandboxing *combined with* the cap specifically (as opposed to a plain, uncapped completion) - that combination is exactly what a plain-terminal `E2b` repeat, outside this sandbox, would test.

So two explanations remain open after this round: background dispatch (explanation 1, though shown not to be necessary on its own), and the nested-sandbox-plus-cap combination (the surviving part of explanation 3). Neither is confirmed or excluded by the evidence gathered.

**Consequence for CF-12.3/CF-12.4, stated as a recommendation:** the early-handoff instruction worked on opus (2 of 2, `E2c`) and failed on haiku (1 of 1, `E2d`) - and it is **untested on Fable**, which is exactly what `spec-editor-fable` and `tech-editor-fable` actually run. That gap matters more than it might for the unsuffixed editors: the Fable pair is the one this evidence has said nothing about at all, on either side. Three consequences follow:

1. **Keep the instruction, but as best-effort, not a guarantee.** It is cheap, it worked on the one strong model tried, and there is no evidence it hurts - but `E2d` shows a model can still ignore the turn-budget framing the instruction relies on, so nothing downstream should assume it always succeeds.
2. **Set `maxTurns` as a backstop, not a working budget.** For `spec-editor`/`tech-editor`'s actual input shape - one document plus the sources its brief names, never a codebase, never a loop - `maxTurns: 15` should be set high enough that it does not bind in normal use at all, the way a timeout is set to catch a hang rather than to shape how long an ordinary call takes. `turncap`'s `maxTurns: 3` against an eight-file task was deliberately tight to force the cap in this spike; CF-12's real editors should not run that close to their own cap as routine behaviour.
3. **Detecting a missing `SubagentStop` is needed, not optional.** `turncap`'s bare `maxTurns: 3` with no early-handoff instruction produced a silently un-gated, non-handoff stop on live evidence, replicated four times, with no hook safety net in that exact circumstance (see (2b) above). Given that a backstop cap can still bind in an unusual case, and the hook is not observed to fire when it does, CF-12's plan needs its own way to notice a subagent that stopped without a handoff and without a `SubagentStop` event at all - not a "would be nice" for a later phase. A `Propose item:` for CF-12's plan: whether `board-subagent-stop.sh` itself should be the place that detects this, or a separate check reading the board or the session state, is out of this spike's scope to decide - noting the need here rather than proposing the mechanism.

## Question (3): `permissions.deny` and plugin-namespaced agents

**Yes, confirmed by direct observation, on both the throwaway plugin and the real `coder-fleet` plugin.**

- **`E3b`** (`deny-fable` project, `permissions.deny: ["Agent(cf12spike:probe-fable)"]`): spawning `cf12spike:probe-fable` returned an `is_error` tool_result: `"Agent type 'cf12spike:probe-fable' has been denied by permission rule 'Agent(cf12spike:probe-fable)' from projectSettings."` - blocked outright, with the exact rule named back. Spawning the **bare** name `probe-fable` (no prefix) returned a *different* `is_error`: `"Agent type 'probe-fable' not found. Available agents: cf12spike:badmodel, cf12spike:fablecheck, cf12spike:probe, cf12spike:sub:nested, cf12spike:turncap, cf12spike:turncap-early, claude, Explore, gene[ral-purpose, ...]"` - not a leak around the deny rule, but simple non-resolution: a plugin-loaded agent is not addressable by its bare name at all in this session shape, so there is nothing for the deny rule to fail to catch. Spawning `cf12spike:probe` (the prefix-sharing sibling, not denied) succeeded normally (dispatched as a background agent, no error).
- **`E3c`** (`deny-plain` project, `permissions.deny: ["Agent(cf12spike:probe)"]`, the mirror case): `cf12spike:probe` denied outright with the same message shape; bare `probe` "not found", listing `cf12spike:probe-fable` among the available agents; `cf12spike:probe-fable` (not denied) succeeded normally. Confirms the unsuffixed rule does not catch the `-fable` sibling, in either direction.
- **`E3d`** (`deny-real` project, `--plugin-dir` pointed at this checkout's real `claude/coder-fleet`, `permissions.deny: ["Agent(coder-fleet:scout)"]`): `coder-fleet:scout` denied outright: `"Agent type 'coder-fleet:scout' has been denied by permission rule 'Agent(coder-fleet:scout)' from projectSettings."` Bare `scout` "not found", with the available-agents list showing the real roster under its `coder-fleet:` prefix (`coder-fleet:coder`, `coder-fleet:fleet-steward`, `coder-fleet:lead`, `coder-fleet:refuter`, `coder-fleet:researcher`, `coder-fleet:reviewer`, `coder-fleet:scripter`, `coder-fleet:spec-writer`, `coder-fleet:tech-writer`, `coder-fleet:ui-designer`, and `claude`/`Explore`/`general-purpose`/`Plan`/`statusline-setup`). Same shape, same outcome, on the production plugin rather than the throwaway one.
- **`E3a`** (`deny-none`, control): both `cf12spike:probe` and `cf12spike:probe-fable` ran without any denial, confirming the deny rules in `E3b`-`E3d` are doing the blocking, not some other constraint (e.g. a missing agent definition).

**Consequence for CF-12.3-CF-12.5:** spec AC 17's hard stop exists as designed - `Agent(coder-fleet:<name>)` in `permissions.deny` does block the plugin-namespaced spawn, and the unsuffixed/`-fable` pair does not collide either direction. On this evidence, a `subagent_type` parameter-rule fallback (`Agent(subagent_type:*spec-editor-fable)`) is not needed: there is no leaking bare-name path to guard against, because a bare name does not resolve to a plugin agent in the first place in this session shape. That "not found" result is itself worth a one-line note in CF-12's error-handling text, since a project author denying a definition should read a "not found" result for the bare name as expected, not as a sign the deny rule failed.

**Scope of this verdict, stated plainly:**

- Observed only under `--plugin-dir`, `--permission-mode dontAsk`, and `--setting-sources project,local`. Whether the same "not found" (rather than "denied" or a successful spawn) result holds under a different permission mode, a different `--setting-sources` combination, or a plugin installed the normal way (via the marketplace, not `--plugin-dir`) was not tested.
- The bare-name spawn was tried in `E3b`-`E3d`, where it was expected to be denied or to leak. It was **not** tried in `E3a`, the control - so there is no direct evidence that a bare-name spawn of `probe` or `probe-fable` succeeds in a project with **no** deny rules at all. The `E3b`/`E3c`/`E3d` "not found" result shows a bare name never resolves regardless of whether a deny rule exists for the prefixed form, which is what the verdict above rests on - but the control run itself did not exercise the bare-name path, and it should have.
- A same-named agent placed under a **project's own** `.claude/agents/` directory (rather than loaded via a plugin) was not tested at all. If a project could define its own `spec-editor` agent alongside the plugin's `coder-fleet:spec-editor`, a deny rule scoped to `Agent(coder-fleet:spec-editor)` would have no reason to catch it - that is a different, untested spawn path, not a leak in the rule this spike checked, and CF-12's plan should not read this finding as covering it.
