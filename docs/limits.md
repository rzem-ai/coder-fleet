# Known limits

What the fleet deliberately does not enforce or cover. Each item is a gap that was looked at and left, with the reason, so a deliberate gap is not mistaken for an oversight. Anything here that becomes a rule, a hook or a test leaves this file the same day.

## The board hooks

**The route to Done depends on a Claude Code gate the fleet does not own.** `TaskCompleted` fires only when a task is completed with `TaskUpdate`, and Claude Code 2.1.283 offers the task tools to current models only when `CLAUDE_CODE_ENABLE_TODO_TOOLS` is set. The fleet sets it in each project's settings through `/init`, but a later CLI can rename the variable or change the default. `/kickoff` checks that the lead has `TaskUpdate`, which turns such a change into a named failure rather than a board where nothing reaches Done again.

**The card gate sees only a `[board:<id>]` task completed with `TaskUpdate`.** `TaskCompleted` refuses Done while a card has no acceptance criteria or any unticked criterion or Definition of Done item, but it runs only when a task whose subject carries the marker is completed with `TaskUpdate`, which needs `CLAUDE_CODE_ENABLE_TODO_TOOLS` (above). A card reaching Done any other way is not checked, and in particular the gate cannot see the human moving a card to Done in the web UI, because no hook fires on a web UI edit. Left because a move the human makes is the human's decision, and refusing it would take a check inside the board binary on every status edit, which nothing asks for.

**Failure and cancellation never reach Blocked.** `SubagentStop` carries no `status` field, so `board-subagent-stop.sh` cannot detect a failed or cancelled run. The hook reads no status. A `Blocker:` line in the handoff routes to Blocked by human, and `TaskCompleted` is the only writer of Blocked. `agent_transcript_path` is present on every `SubagentStop` event and the hook already walks it to tell a schema spawn from a silent run, so what is missing is narrower than a new reader: teaching the existing one to recognise a failed or cancelled run.

**A turn-capped run never sends SubagentStop, and only a foreground one is caught.** `SubagentStop` does not fire when `maxTurns` cuts a run off (`docs/decisions/claude-code-behaviours.md`). So a capped run gets no handoff check and no comment from the stop hook. `board-agent-return.sh` covers foreground spawns only, on the Agent tool's `PostToolUse`: a completed run earns one comment on its card when it carries the runtime's cap note, or when it has no stopped marker, and never a column move. A background spawn's `PostToolUse` fires at launch with status `async_launched`, so background spawns rely on the lead to say on the card that the run came back without a handoff. That includes a spawn the runtime backgrounded on its own, with no `run_in_background` asked for (`docs/decisions/claude-code-behaviours.md`). A capped run resumed with SendMessage and cut off again is not an Agent call, so it is not caught either.

**A first start is bound per checkout, not per agent.** The hooks read the checkout's `.boards/.focus` at an agent's first start, so every fresh spawn in a focused checkout belongs to that item. A resume is the exception: it keeps the record its first start wrote, so refocusing between a spawn and its resume does not move it. A workflow run is the other exception: its comments and Blockers go to the item its earliest-started agent bound, decided at `SubagentStop` from the run id in `agent_transcript_path`. Its starts still read the focus, since `SubagentStart` names no run, so a lane that starts after a refocus moves the newly focused card to In Progress; that move is accepted. Per-agent binding at the first start needs a supported correlation between the Agent tool's invocation and the subagent identity in the event, and it must not be done with a shared "latest prompt" file: two agents spawned together would race for the same line. `SubagentStart` does carry `agent_id`, `cwd` and `prompt_id`, which is more to work with than the hooks currently use.

**The transcript reader fails open.** `board-subagent-stop.sh` consults `agent_transcript_path` to tell a schema-spawned run from one that produced nothing, and a transcript it cannot read - missing, unreadable, oversized, unparseable - passes with a log line rather than blocking. Deliberate: deadlocking a subagent is worse than a rare silent pass.

## The scope hook

**It is not a containment boundary.** `enforce-agent-scope.sh` reads shell text, and a shell does not. A program run through Bash writes wherever the process can, and no shell-level check sees inside it. The sandbox in `claude/home/settings.json` is a credential boundary, not a role boundary - its `denyWrite` covers `~/.ssh` and friends, not other repositories. Unattended steward runs need filesystem permissions before they are safe, and the steward is the agent this matters most for. Every entry below is one consequence of that; finding one hole is not evidence there are no others.

**`strip_quoted` pairs quotes naively in the general segmenter.** `echo "say \"x" ; git commit -m x ; echo "the end"` is allowed for `scout`, even though a real shell runs the commit as its own command: the escaped quote inside the first span shifts the parity, and the later quoted `"the end"` gives the naive pairing something to close against, erasing everything between, including the commit. The escape-aware stripper only reaches the interpreter-payload regex; the general command-segmentation path that every `enforce_*` function walks still uses the naive one.

**The 8192-byte scan bound truncates.** `echo <9000 bytes> ; git commit -m x` is allowed, with a log line naming how far over the bound the command was. Without the bound a long enough command blew the hook's 10-second timeout, which renders no decision at all and takes every role's guard down silently with no log. A narrow logged bypass is the trade for an absolute silent one.

**The 16-segment bound truncates the same way, and it is the tighter of the two.** `echo a ; ` sixteen times in front of `git commit -m x` is allowed for a break-mode `reviewer`, with a log line saying how many segments were dropped. Sixteen is generous against real work - the coder-fleet repo's own scope-hook corpus tops out at four segments - and the bound exists because bytes were never the cost: 200 chained `git log` steps is 2000 bytes, a quarter of the byte bound, and measures well past the 10-second timeout without it.

**Per-segment word count is unbounded.** `A=1 ` five hundred times in front of `git log` is 2007 bytes and one segment, and measures about 17 seconds against a 10-second timeout. `command_words` spawns two processes per leading assignment or wrapper word and nothing caps how many it walks. The fix is either a third bound or the single-pass rewrite that replaces all three.

**Variable expansion, `eval`, heredocs and other languages' inline-code flags are unreachable.** Any parser reading unexpanded text cannot see them. `python3 -c "import os; os.system('git commit -m x')"`, `node -e` and `perl -e` are all allowed; they are `eval` wearing a different name. The hook recovers payloads from `bash -c` and its four sibling shells only, and its own comment says so.

**Command substitution is unchecked for three roles.** `$(git commit -m x)` and the backtick form are allowed for a break or use-mode `reviewer`, `coder` and `ui-designer`, because only `fleet-steward`, `scout` and a review-mode `reviewer` check for substitution. The leading-token strip that closes `{ git commit -m x; }`, `( git commit -m x )`, `! git commit -m x`, `>/tmp/out git commit -m x`, `timeout 5 git commit -m x` and the body of an `if`, `for` or `while` cannot reach a substitution, because the word has no leading token to remove. `script -q /dev/null git commit -m x` stays open on purpose: `script` puts its typescript file between itself and the command, so listing it as a wrapper would close nothing, and `script cat` would then read as `cat` while actually creating a file called `cat` - the same asymmetry that keeps `sudo` off the wrapper list.

**A break or use-mode reviewer's "Never write inside the project" is not enforced against Bash.** `lib/check-write-scope.py` only ever sees `Write`, `Edit`, `MultiEdit` and `NotebookEdit`, so `echo mutated > claude/coder-fleet/agents/coder.md`, `cp /tmp/x claude/coder-fleet/workflows/review-round.js` and `rm -rf claude/coder-fleet` are every one of them allowed. `enforce_fleet_steward` resolves and checks redirection targets for an equivalent rule, so the pattern exists in the same file, and applying it here would still only reach redirections rather than `cp` or `rm` - which is why it is a design question rather than a missing line.

**An `agentType`-less lane is governed by nothing.** The `SubagentStop` matcher skips it and every branch of `enforce-agent-scope.sh` keys on an agent name, so "read-only git only" in a lane prompt is an instruction to a model, not a boundary. `review-round`'s two mechanical lanes, lint and smells, are in that position, and its git lanes are in it too, including the fix worktree lane, which writes: its `git worktree add` is bounded by its prompt and by the script refusing any worktree the lane does not report exactly. Widening `scout`'s or `reviewer`'s allowlist instead would weaken a role boundary for every run rather than for the one workflow that needs `worktree`, `merge-base` and `rev-parse`. A probe spawn that falls back to a non-fleet agent type can run `git commit --allow-empty` in the main checkout and it lands with no refusal.

**A reviewer's gate runs the diff's own code, and the hook bounds only the command line.** The gate rule decides which command the reviewer may type - a declared gate, from the top of a linked worktree, with no package manager but a bun project's `bun --no-install test`, no install but the one frozen, scripts-off install its lockfile names, and no snapshot update, fix or write mode, watch mode, in-repo build output or network tool - and nothing about what that command then executes. A test file in the diff under review runs under `node --test` or `vitest` with the reviewer's permissions and can write, fetch or delete anything the process can, so "nothing the reviewer runs changes the diff" holds for the reviewer's flags, not for the code it is reviewing; the sandbox is what contains that code. The same goes for a script or task runner declared as a gate - `make check`, `just test`, `bash scripts/check.sh` - whose recipe is a file the diff can rewrite, so declaring one hands the diff the choice of what the reviewer runs.

**An honest gate can still write, because tools write by default.** Outside CI, jest and vitest write a snapshot that does not exist yet: vitest 3.2.4 resolves `updateSnapshot` to `'none'` only when `isCI` (`resolveConfig.ts`) and to `'new'` otherwise, vitest 4 does the same through its `update` default (vitest.dev/config/update), and jest stores a new snapshot unless `ci` is on, which defaults to `isCI` (jest 29.7.0 `Defaults.ts`, jestjs.io/docs/cli). So a plain `vitest run` against a diff that adds a snapshot assertion creates a file in the worktree under review. A gate can start with `CI=true`, the one assignment the hook allows and only as a gate's first word, which the template's example does; the hook cannot require it, since a runner's config can override it. vitest's `--update=none` is not a way round this and is refused: vitest 4.x reads the value (checked in 4.1.10, not in 4.0), but vitest 3.x takes `--update` with no value, reads `none` as a file filter and rewrites every snapshot, and the hook cannot tell which version a worktree has. `tsBuildInfoFile` is worse: set in a `tsconfig.json` with `incremental` or `composite`, it makes even `tsc --noEmit` write a build-info file, and the path it names can be anywhere the process can write - inside the tree, tracked or not, or outside it. A runner's config can equally switch on a refused mode the command never names, such as a `vitest.config.ts` with `update: true`. Closing any of these would mean parsing tool configs, so the reviewer instead runs `git status --porcelain --ignored` after the gates and reports anything the run created or changed as a finding. That sees only the review worktree: new, changed and ignored files there, such as a snapshot, a `.tsbuildinfo` or a coverage directory. It does not see a write outside the worktree - a `tsBuildInfoFile` pointed elsewhere, a cache under the home directory - nor a file the run changed and then restored.

**The gate list is the main checkout's working tree, not a commit.** The hook reads `AGENTS.md` from the main checkout's directory, so an uncommitted edit there widens the list for every review until it is reverted, and a main checkout with another branch out gives that branch's list. Reading from the checkout rather than the worktree under review is what stops a diff widening its own reviewer's allowlist; reading a committed ref instead would need the hook to know which ref is the base, which it is never told. A layout whose checkout is not the common git dir's parent - `--separate-git-dir`, or a bare repository with worktrees - has no list at all and fails closed.

**A reviewer's lockfile install trusts the lockfile and the main checkout's config.** A review worktree is cut fresh with no node_modules, so the reviewer may run one install at its top, chosen by the one kind of lockfile there, frozen and with install scripts off (CF-199). Frozen means `npm ci`, the `--frozen-lockfile` of bun, pnpm and yarn 1, and berry's `--immutable` exit non-zero rather than rewrite a lockfile that disagrees with `package.json`; scripts off means no package's lifecycle script runs, pnpm's `--ignore-pnpmfile` runs no pnpmfile hook, and bun's `--no-env-file` loads no `.env`. An install also obeys its config, and a berry `yarnPath` or plugin is code. A list of known config files misses the next one, so the hook checks two allowlists against the merge base of the main checkout's HEAD and the review worktree's HEAD - a commit on main's own history, as the gates block is read from the main checkout, and the point the diff started from, so any later commit on main changes nothing; with no merge base, a merge base off the first-parent chain of main's HEAD (a side branch's commit main merged), or a worktree HEAD that is not a commit, the install is refused: every top-level dotfile or dot directory, and `bunfig.toml` and `pnpm-workspace.yaml` in any case, since macOS reads `BunFig.toml` as `bunfig.toml`, must hold on disk the content main's HEAD has, or be absent from both, unless it is spelled exactly as one of `.gitignore`, `.gitattributes`, `.editorconfig`, `.github`, `.vscode` and the prettier and eslint files; and every `package.json` field must equal main's, unless it is one a diff changes in ordinary work - name, version, the dependency maps, scripts and their kin. Contents are hashed rather than read from `git diff` or `git status`, which trust an index entry marked skip-worktree or assume-unchanged, and any such entry refuses too; a symlink, or anything but a regular file or directory, among or inside those entries, a lockfile or `package.json` refuses. What that config names is not followed: unchanged config can name a file the diff changes - a `yarnPath` outside `.yarn/`, a plugin, a bunfig `preload`, a pnpmfile path - and the install then runs the diff's code. That is the boundary a gate already has, since the gates run the diff's own code one command later in the same sandbox, and the coder ran the same install on the same code before the review began. Finding those paths means reading YAML and TOML in bash; nine security review passes each found a form the reader missed (flow mappings, quoted and escaped keys, anchors, plain string plugin items, multi-line scalars), so the reader was removed rather than left as a check that looks complete and is not. A real YAML and TOML parser in the hook, or running the install somewhere the diff's files are absent, would close it, and each is its own item. `.tool-versions`, `.nvmrc` and `.node-version` are config here, since asdf, mise and nodenv shims read them to pick the binary. What is left is trust in what that merge base already holds and in the lockfile itself: a lockfile the diff edits can name any tarball URL, a non-default registry included, and only its integrity hashes, which the same diff writes, check what arrives; config already on main, a registry or a `yarnPath` the human committed, is used as it is, and the file it names is run as the diff has it; main's HEAD is whatever branch the main checkout has out, and a branch based on an old main commit installs with that commit's config, so config main has since changed or removed is still used on such a branch; and config below the top level, such as a workspace package's own `.npmrc`, is not compared. The reviewer's `git status --porcelain --ignored` after the gates reports what the install wrote in the worktree, a berry PnP install's `.pnp.cjs` included. Lockfile names outside the six the hook reads are not scanned, which fails closed: pnpm's per-branch `pnpm-lock.<branch>.yaml` and a berry `lockfileFilename` are set in config that must match main, and without one of the six present the install is refused as having no lockfile. When a red declared gate leaves `review-round` to tell missing dependencies from a real failure, it reads one listing of the worktree's top and nothing the reviewer says: a `package.json` that declares a dependency with no `node_modules` and no `.pnp.cjs` is a gate that did not run, which is never an approval and starts no fix round. An install that failed part-way and left a `node_modules` reads as installed, so its red still starts a fix round.

**Go, Rust, Deno and uv projects cannot declare gates.** `go`, `cargo`, `deno`, `uv` and `uvx` are refused as package managers whatever the list says, because each may fetch or install before it runs a test, and those projects have no `node_modules/.bin` to call instead. Their reviewers run nothing and list the gates under Unverified. Allowing them would take a per-tool offline mode passed as a flag (`cargo --offline`, `deno --cached-only`), since a gate command may assign no variable, and each is its own item.

**A named, non-isolated spawn escapes the fleet entirely, and it is the likeliest shape of a trample.** Spawning a fleet agent with a `name` and no `isolation` puts it on the teammate path, where the hook events carry the name as `agent_type`: `enforce-agent-scope.sh` then allows everything, because no agent type it knows means the main session; the `SubagentStop` matcher never matches; no worktree is cut. A named `coder` commits straight to main with no refusal anywhere. A named read-only agent loses its whole output instead: idle notifications arrive in place of a result, the stop gate's exit 2 has nowhere to deliver, and the run looks like a success with a formatting hiccup. So a named spawn loses whichever half of the contract the role depends on, and neither failure is loud. A named reviewer loses the time cap and its mode-dependent scope as well, because `agent-clock.sh` and the scope hook key on the same agent type. The refusal branch of the worktree guard may be unreachable from a real typed spawn - a typed `coder` always gets a worktree, and only the ungoverned path ends up in the main checkout - which makes the teammate path the whole risk. Until the hook can key on something a teammate cannot rename, the rule is operational: never name a fleet spawn, and treat a teammate running a fleet body as ungoverned. The lead's body says so.

## The break-mode reviewer's time cap and modes

**The cap stops tools, not the model.** Past 25 minutes `agent-clock.sh` denies every tool call, but a turn that writes only text needs no tool, so text-only turns after the cap - including the re-emits `SubagentStop` asks for when a handoff is malformed - are bounded by the model alone.

**The in-flight Bash trim depends on undocumented behaviour.** Sending `updatedInput` with no permission decision is honoured by the 2.1.283 bundle and contradicted by the documentation (hooks README, item 20). If a later CLI follows the docs, the trim silently stops and the gap reopens to 25 minutes plus one command, up to the runtime's Bash ceiling, 10 minutes by default. The deny still holds.

**`run_in_background` is outside any timeout.** A backgrounded command can outlive the run. The run itself should not be held open, since `SubagentStop` carries `background_tasks`, but that is unobserved live.

**Missing state starts the clock late, and a corrupt file uncaps the run.** Both allow the call with a log line. A break-mode reviewer that deletes its own clock file restarts its clock at the next tool call: a speed bump, not a boundary.

**A same-user agent can still forge its own mode.** The mode is read from the reviewer's own transcript and recorded once, 0600, under the state directory (hooks README, "The reviewer's modes"), and every reviewer mode is refused write tools under the state and transcript directories, and Bash commands that name either in any case. That is a text match, and a break-mode reviewer's Bash is otherwise open: a path the text does not show - a `cd` and a relative path, a variable, a script it writes and runs, `python3` building the string, `find -exec` - reaches the record or the transcript unseen. A garbled record or one deleted gains it nothing, since garbage caps the run and a missing record is read again from the brief, but a well-formed overwrite to plain `review`, or a rewrite of the transcript's first line, lifts the cap and narrows nothing else. A same-user hook cannot close that; only a sandbox that keeps the agent out of those directories would. The refuter's clock file always had the same exposure.

**A malformed or unreadable brief is capped as break mode.** Fail closed, by the security review's call: a review-only run whose brief never lands on disk, or whose `Modes:` line is malformed, is denied at 25 minutes like a break-mode run, and its scope is review's. The log names it once.

**The reviewer's state directory is refused by name only.** `enforce-agent-scope.sh` refuses a reviewer's Bash command when it names the state or transcript directory, or a fixed tail of either such as `coder-fleet/modes`, and nothing else. A wider rule that refused any `cd`, glob, `$` or `~` beside a fragment such as `state` or `coder-fleet` refused ordinary mutation runs (`useState`, an OAuth state test, the session scratchpad) and was beaten by any script, so CF-192 dropped it. A same-user agent can still reach the state directory through a script or a path built at run time; the entry above says what that costs.

**Nothing counts mutants.** At most eight mutants a round is an instruction in the reviewer's body, the `looping` skill, the lead's brief and `review-round`'s break-lane prompt, and no hook or workflow counts them. A break-mode reviewer that runs a ninth is stopped only by the 20-minute round and the 25-minute deny, which bind first on any suite slower than about 100 seconds run one after another. Counting would mean parsing mutations out of Bash calls, and the time cap already bounds the spend.

**A reviewer run as the main agent is uncapped.** With `--agent reviewer` the events carry no `agent_id`, and the hook exits before it reads anything.

**Wall-clock includes machine sleep.** A break-mode reviewer on a laptop that slept is denied when it wakes. That is intended: the rule is wall-clock.

## Never run against a live Claude

**The reviewer's break and use modes.** Their permissions are pinned by the scope hook suite, but no stubbed suite can show whether a reviewer briefed for break actually refutes rather than reviews, or one briefed for use drives the product rather than reading the code. The refuter's and evaluator's evals went with them in CF-192 and the reviewer's eval has no break or use prompt yet, so until one runs, both modes are a design rather than a capability.

**`fix: true` in `review-round`.** Every branch is covered by deterministic tests that stub the model out, which is exactly the coverage that can hide a gate bug for a fortnight. What those cannot prove: that the git lanes report `isMain` correctly off `git worktree list --porcelain`, that the fix worktree lane runs exactly the `git worktree add` it is given and reports git's answer rather than its own, that `coder` works only through `git -C` and absolute paths into the worktree it was handed, and that `parallel()` returns lanes in a shape the tests-lane lookup finds. The lookup is by name rather than by position for that reason.

**`refute: true` and the refutation stage.** Same coverage, same gap. What the stubs cannot prove: that a break-mode reviewer asked to attack a change copies out of the project rather than mutating the tree under test, and that `survivorsOf` on a real refutation finds the `survived:` Done bullets the way the fixtures say it will.

**Worktree isolation for a workflow-spawned `coder`.** Workflow-spawned agents get no harness isolation. An Agent-tool `coder` spawned with the fleet type gets a locked linked worktree, because the harness honours the definition's `isolation: worktree`, but a workflow `agent()` call with the same `agentType` does not: in the live run `wf_1297e8b7-cb8` the fix-lane coder started in the main checkout, and only `enforce_coder` (`claude/coder-fleet/hooks/README.md` item 18) kept it off main. `review-round` compensates itself. Before a fix round spawns its coder, a git lane runs `git worktree add` under the main checkout's `.claude/worktrees/review-round-<issue>-r<n>`, on a new branch `review-round/<issue>-r<n>` at the pinned head, and reports what git says about it. The script stops the run with `fix worktree not created`, and spawns no coder, unless the lane vouches for exactly that path, branch and head as a linked worktree. An existing branch is a stop, never a reason to pick another name. The coder's prompt names the worktree and tells it to work only there, and the fix gate refuses a commit that git does not find on that worktree's branch. The worktrees are left in place and listed in the result's `fixWorktrees` for the lead to adopt or prune. With `worktree.baseRef` `"head"`, which the project settings template ships, a type-isolated Agent-tool `coder` is cut at the local HEAD rather than at `origin`, and the fix lane cuts its worktree itself at the pinned head, whatever the setting says. Not yet run live: the fix lane's cut in a real `review-round`, and a coder working through `git -C` from a main-checkout `cwd`; the entry stays for those two.

**Where `review-round` reads the tree.** The script names one tree after the pin: the coder's worktree when the pin lists it clean at the pinned head, said not to be the main checkout and neither the state worktree nor a `review-round-` tree of another run, or else a detached worktree it cuts at `.claude/worktrees/review-round-<issue>-at-<sha>` under the main checkout and removes in a `finally` with `git worktree remove`, never forced. Each lane that grades the tree - the two mechanical lanes, the verdict and the refutation - is told to check `rev-parse --show-toplevel` and `rev-parse HEAD` first and to run nothing when they are not that tree at that head, and the script drops any report that does not say so. That last part is what the script can enforce: a lane that runs a command somewhere else before reporting is stopped by nothing, the same position as any `agentType`-less lane, and a coder's worktree read in place can still move under a lane that already checked it if the coder is still working. The removal is refused when a lane left untracked or modified files there, and the run then reports the path rather than forcing it. `workflow-logic.mjs` drives a round against real git from a main checkout on `main` and shows its HEAD, branch and status unchanged and two mid-round board writes on `coder-fleet/state`, with stub lanes that run exactly the commands the script gives them. Not yet run live: a real round's lanes honouring the tree check.

**The break-mode time cap, end to end.** The contract pins what `agent-clock.sh` outputs, not what the runtime does with it: that a live break-mode reviewer is denied at 25 minutes, that its brief is on disk where the lib looks by its first tool call, writes its handoff after the deny, and has a long Bash call ended at the trimmed timeout. The post-merge probe in hooks README item 20 covers it until it runs.

**The disabled-agents hook against a live spawn.** `disabled-agents-contract.sh` pins what `enforce-disabled-agents.sh` prints for a given event, not what the runtime does with it: that a live Agent call is refused on the deny, that the invalid-config `systemMessage` reaches the human, and whether a workflow's `agent()` spawn reaches the hook at all. `review-round` reads `.claude/coder-fleet.json` itself so its phase never depends on the last one, but whether a live pin lane reads the main checkout's copy and reports it verbatim is unproven too. The script honours a found file only when the lane reports the path it read and that path is the main worktree's file; a found file with an empty or missing path, or any other path, is treated as unread and the phase is harden. It checks what the lane says, not what the lane did: a lane that read a linked worktree's copy and reported the main worktree's path, or read the right file and misreported its text, is believed.

**`review-round`'s origin pin.** For each end given as a branch name - a base, a head, a target, or the default branch a target is reviewed against - the script pins origin's commit when the local branch is behind it, keeps the local commit when it is ahead, and stops naming both commits when they have diverged. A base that is the default branch is `origin/<default>` whenever that ref exists, whatever the ancestry. A single-ref range's base is the parent of the pinned head, so moving the head to origin's tip does not widen the review. The script cannot run git, so all of that rests on what the pin lane reports: the default branch, `refs/remotes/origin/<name>`, the two `git merge-base --is-ancestor` answers and, for a single-ref range, origin's parent commit. `workflow-logic.mjs` pins the decision over that report, not that a live lane runs those commands and reports them truly; a lane that misreports ancestry is believed. A missing or contradictory ancestry answer stops the run rather than picking, and a lane that leaves the origin report out altogether pins the local commit and logs that origin was not checked. The workflow never fetches: origin is read as the checkout last fetched it, so fetching before the run is the lead's job, and a run after no fetch can still pin a stale origin.

## Disabled agents

**No workflow honours the list.** `review-round` spawns `scout` for its scope pass, and `spec-to-card` and `deep-research` spawn their own agents, none of which consults `.claude/coder-fleet.json`. A project that disables `scout` gets a denied scope pass, if the hook sees workflow spawns, and a `scope pass returned nothing` stop rather than a fallback. `review-round` honoured it for the refuter until CF-192 made that a reviewer mode; making each workflow fall back or stop by name for a disabled agent is separate work.

**A name that is no agent's is accepted.** `disabledAgents: ["researchr"]`, or a `refuter` or `evaluator` left from before CF-192, is valid and disables nothing, so the spawn hook allows every call as before. `enforce-disabled-agents.sh --check` prints a warning naming each such entry and still exits 0, against the roster `fleet_roster` builds from the plugin's agents directory; nothing warns at spawn time.

**The live main file trusts every writer of the main checkout.** The hook, `--check`, `/coder-fleet:agents` and `review-round` all read `.claude/coder-fleet.json` from the main checkout as it is on disk, uncommitted edits included, so toggles need no commit. Anything that can write there can disable an agent or set the phase to build, and that includes a fleet agent: `enforce_coder` does not confine a coder's `Write` or `Edit` to its own worktree, so a coder can write the main checkout's file by absolute path, and every later spawn and review reads it. `review-round`'s guard only sees a change that is in the reviewed range, which an uncommitted write to the main checkout never is. The defence today is that the human reads the file before trusting a skipped refutation, and that every skip says the build phase skipped it.

**A forged worktree is defended only through `CLAUDE_PROJECT_DIR`.** A repository made for the purpose that registers a worktree itself passes the check that the main checkout lists the starting worktree, because the check asks that repository. The spawn hook starts from `CLAUDE_PROJECT_DIR`, which a `cd` cannot move, so a lead whose `cwd` is in such a worktree still reads the real main's file. With the variable unset or not a directory the event's `cwd` decides, and so do `--check [dir]` and `/coder-fleet:agents`, which start from the directory they are given or run in.

**Outside a git repository, no config is read.** When the project is not a git repository, or its main checkout is bare, no `.claude/coder-fleet.json` is read and nothing is disabled, whatever a file in the current directory says.

## Refutation checks that do not exist

**Nothing checks that a refutation contains mutation evidence.** `review-round` stops on a `survived:` Done bullet, on a `Blocker:` line and on an empty refutation, and treats everything else as unbroken. The survivor transport is itself unproven: no live break-mode reviewer has yet been seen to write a `survived:` bullet, and the reader fails closed: any Done bullet that mentions surviving, a bare `survived:` key included, stops the round unless the whole bullet is one of a small set of strict nothing-survived forms. What it cannot see, and so fails open on, is a survivor described without the stem ("lived", "not killed", "not noticed"), look-alike or invisible characters inside the word, list markers other than `- `, and a clean-looking `survived: none` followed by a separate bullet that names a survivor. It never looks at whether the Done section says anything was mutated. A refutation whose only Done bullet is "I read the diff and it looks fine to me" returns `stopped: "clean"` and `approved: true`, which is the exact failure the role exists to prevent, arriving through the gate rather than around it. The check is deferred on purpose: it would have to pin a workflow decision to a new obligation on the break mode's Done-bullet wording, and a format obligation invented and depended on in one commit is how format obligations decay. The `survived:` bullet is not that case: survivors were already a parsed obligation, moved from Decisions needed to Done rather than invented, and the bullet rides the keyed Done bullets `fixHints` already depends on. The evidence check gets built once there is a real refutation handoff to parse, which needs the live runs above. The time cap widens the gap: a refutation stopped at 25 minutes, with its unfinished mutations under Not done, carries no `Blocker:` line and is read as clean too.

**The sensitive override covers authentication and secrets only.** Under `fix: true`, `review-round` spawns a break lane despite `refute: false` when a round's changed files match `SENSITIVE`, and that pattern names authentication, authorisation, session, crypto and secret paths but nothing for data writes, so a fix round that adds a migration under `refute: false` gets no break lane.

**A project with no `gates` block is never approved without a break lane.** With `refute: false`, `review-round` approves a clean verdict only when the reviewer's gate lines put a run on record with nothing under `gatesMissing` or `gatesFailed`: a reviewer that reports no gate line, a line it could not read, a gate it could not run or none for a gate the main checkout's `gates` block declares leaves something missing, and a line with a non-zero exit is a failed gate and a blocking finding. A project whose main checkout's `AGENTS.md` declares no `gates` block gives the reviewer nothing to run, so it gets `approved: false` from every review without a break lane, however often the lead runs the gates itself afterwards. There is no way yet to declare a gate absent for a project; the lead reads `gatesMissing` and the next step, which say so, and records its own gate run in its handoff.

## The deterministic suite

**Permission cases skip under root.** `board-hook-contract.sh`, `scope-hook-contract.sh` and `challenge-gate-contract.sh` each prove a fail-closed or fail-open branch by making a file or directory unwritable or unreadable with `chmod`, and `board-commit-log.test.ts` does the same for a `git add` that cannot read a card. A process running as root, or holding `CAP_DAC_OVERRIDE`, is not bound by those bits, so the case cannot show what it claims. Each script probes once (`perms_bind`: a scratch file at mode 000 that is still readable means permissions do not bind) and prints a `SKIP` line for the case, counted as neither pass nor fail; the bun test uses `it.skipIf` on uid 0. Asked for by the human on 18 October 2026, after a cloud session that runs as root reported the six sections red on a change that touched none of them. CI runs as an ordinary user and still proves every case; a run that shows `SKIP` lines has proved less than a run that shows none, and says so.

## The challenge gate

**A closed marker typed by hand passes.** `scripts/challenge-gate.py` decides from the spec and the project's `disabledAgents` alone, never from git history, so a `## Challenges (spec-editor): closed in <sha>` line passes whether or not the close made it, and whether or not the commit it names exists. Left by the human's decision (`docs/decisions/challenge-notation.md`): the gate guards against skipping the challenges by accident, not against a deliberate override, and reading no history is what lets it pass in a shallow clone or a cloud session.

**The close commits on whatever branch the checkout holds.** `run` commits the spec alone, twice at most, in the checkout it is run from, which for the lead and `spec-to-card` is usually the main checkout's local default branch. It never pushes. Left because the spec lives where the human edits it and the close has to land before anything is filed or built from it; getting the commit onto the remote is the lead's ordinary landing work.

**The scope hook holds a spec editor to `docs/specs/`, not to the one spec its brief names.** `enforce-agent-scope.sh` denies a spec editor every command and any write outside the project's `docs/specs/`, and nothing narrows it further: the brief's spec reaches the editor as prose, and the hook has no per-spawn input it could read it from, the same gap `CODER_FLEET_OUTPUT_FILES` leaves for `tech-writer`. Editing a second spec is held by the body's invariant alone. Left because the editor holds `Edit` but not `Write`, so it can change only a spec that exists, and the eval's `checks.sh` fails a run that changes anything but the named draft.

**The scope hook holds a tech editor to `tech-writer`'s scope, not to the documents its brief names.** `enforce-agent-scope.sh` denies a tech editor every command and any write outside `tech-writer`'s scope, documentation under `docs/` and a Markdown file at the project root, narrowed only where the launching environment sets `tech-writer`'s entry in `CODER_FLEET_OUTPUT_FILES`. The brief's documents reach the editor as prose, so editing a second document is held by the body's invariant alone, the same gap the spec editors have. Left because the editor holds `Edit` but not `Write`, so it can change only a document that exists, and the eval's `checks.sh` fails a run that changes anything but the named document.

**No gate where `spec-editor` is disabled, and no sight of a permission rule.** A project that disables `spec-editor` through `/coder-fleet:agents` gets no editor and no gate, so its specs build with no gate. `spec-to-card` still refuses to file a criterion that carries a `[challenge Cn]` marker there, since nothing closed it. The gate reads `disabledAgents` only: an `Agent(coder-fleet:spec-editor)` deny rule, which an earlier `/init` wrote for a project that answered neither, stops the editor but not the gate, which then refuses every spec for want of a challenges section. `/kickoff` offers to remove that rule as a leftover; a project that keeps it disables the editor through `/coder-fleet:agents` as well. Left by the human's decision on 13 November 2026: the gate reads `disabledAgents` alone, and old editor settings are removed, not honoured.
