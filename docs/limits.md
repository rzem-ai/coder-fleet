# Known limits

What the fleet deliberately does not enforce or cover. Each item is a gap that was looked at and left, with the reason, so a deliberate gap is not mistaken for an oversight. Anything here that becomes a rule, a hook or a test leaves this file the same day.

## The board hooks

**The route to Done depends on a Claude Code gate the fleet does not own.** `TaskCompleted` fires only when a task is completed with `TaskUpdate`, and Claude Code 2.1.283 offers the task tools to current models only when `CLAUDE_CODE_ENABLE_TODO_TOOLS` is set. The fleet sets it at project and user scope, but a later CLI can rename the variable or change the default. `/kickoff` checks that the lead has `TaskUpdate`, which turns such a change into a named failure rather than a board where nothing reaches Done again.

**The card gate sees only a `[board:<id>]` task completed with `TaskUpdate`.** `TaskCompleted` refuses Done while a card has no acceptance criteria or any unticked criterion or Definition of Done item (CF-24.4), but it runs only when a task whose subject carries the marker is completed with `TaskUpdate`, which needs `CLAUDE_CODE_ENABLE_TODO_TOOLS` (CF-20, above). A card reaching Done any other way is not checked, and in particular the gate cannot see the human moving a card to Done in the web UI, because no hook fires on a web UI edit. Left because a move the human makes is the human's decision, and refusing it would take a check inside the board binary on every status edit, which CF-24 did not ask for.

**Failure and cancellation never reach Blocked.** `SubagentStop` carries no `status` field, so `board-subagent-stop.sh` cannot detect a failed or cancelled run. The hook reads no status; the dormant branch was removed in v0.25.1. A `Blocker:` line in the handoff routes to Blocked by human, and `TaskCompleted` is the only writer of Blocked. `agent_transcript_path` is present on every `SubagentStop` event and the hook already walks it to tell a schema spawn from a silent run, so what is missing is narrower than a new reader: teaching the existing one to recognise a failed or cancelled run.

**A turn-capped run never sends SubagentStop, and only a foreground one is caught.** `SubagentStop` does not fire when `maxTurns` cuts a run off: measured on Claude Code 2.1.284 outside the sandbox on 2026-09-29, 0 of 3 cap cut-offs fired it and 2 of 2 normal finishes did. So a capped run gets no handoff check and no comment from the stop hook. `board-agent-return.sh` covers foreground spawns only, on the Agent tool's `PostToolUse`: a completed run earns one comment on its card when it carries the runtime's cap note, or when it has no stopped marker, and never a column move. A background spawn's `PostToolUse` fires at launch with status `async_launched`, so background spawns rely on the lead to say on the card that the run came back without a handoff. A capped run resumed with SendMessage and cut off again is not an Agent call, so it is not caught either.

**A first start is bound per checkout, not per agent.** The hooks read the checkout's `.boards/.focus` at an agent's first start, so every fresh spawn in a focused checkout belongs to that item. A resume is the exception: it keeps the record its first start wrote, so refocusing between a spawn and its resume no longer moves it. A workflow run is the other exception: its comments and Blockers go to the item its earliest-started agent bound, decided at `SubagentStop` from the run id in `agent_transcript_path` (CF-80). Its starts still read the focus, since `SubagentStart` names no run, so a lane that starts after a refocus moves the newly focused card to In Progress; that move is accepted. Per-agent binding at the first start needs a supported correlation between the Agent tool's invocation and the subagent identity in the event, and it must not be done with a shared "latest prompt" file: two agents spawned together would race for the same line. `SubagentStart` does carry `agent_id`, `cwd` and `prompt_id`, which is more to work with than the hooks currently use.

**The transcript reader fails open.** `board-subagent-stop.sh` consults `agent_transcript_path` to tell a schema-spawned run from one that produced nothing, and a transcript it cannot read - missing, unreadable, oversized, unparseable - passes with a log line rather than blocking. Deliberate: deadlocking a subagent is worse than a rare silent pass.

**The binary knows the human queue only as "Blocked by human".** The Actions for Human settle, which clears the section when a card leaves the human queue, matches the constant `Blocked by human` in the board binary, ignoring case and spaces, and never reads `board.env`. A `BOARD_COL_BLOCKED_HUMAN` override renames the column the hooks write and the one `SubagentStart`'s hold rule reads, but not the one the binary clears on leaving, so on a board whose queue is spelled otherwise, a card leaving it keeps its actions until it enters Done. Every template and this repository use the default name, and a config key would be a second place to keep in step with `board.env`; an item gets filed if an override is ever used. The human clears the section only by moving the card.

## The scope hook

**It is not a containment boundary.** `enforce-agent-scope.sh` reads shell text, and a shell does not. A program run through Bash writes wherever the process can, and no shell-level check sees inside it. The sandbox in `claude/home/settings.json` is a credential boundary, not a role boundary - its `denyWrite` covers `~/.ssh` and friends, not other repositories. Unattended steward runs need filesystem permissions before they are safe, and the steward is the agent this matters most for. Every entry below is one consequence of that; finding one hole is not evidence there are no others.

**`strip_quoted` pairs quotes naively in the general segmenter.** `echo "say \"x" ; git commit -m x ; echo "the end"` is allowed for `scout`, even though a real shell runs the commit as its own command: the escaped quote inside the first span shifts the parity, and the later quoted `"the end"` gives the naive pairing something to close against, erasing everything between, including the commit. The escape-aware stripper only reaches the interpreter-payload regex; the general command-segmentation path that every `enforce_*` function walks still uses the naive one.

**The 8192-byte scan bound truncates.** `echo <9000 bytes> ; git commit -m x` is allowed, with a log line naming how far over the bound the command was. Without the bound a long enough command blew the hook's 10-second timeout, which renders no decision at all and takes every role's guard down silently with no log. A narrow logged bypass is the trade for an absolute silent one.

**The 16-segment bound truncates the same way, and it is the tighter of the two.** `echo a ; ` sixteen times in front of `git commit -m x` is allowed for `refuter`, with a log line saying how many segments were dropped. Sixteen is generous against real work - the coder-fleet repo's own scope-hook corpus tops out at four segments - and the bound exists because bytes were never the cost: 200 chained `git log` steps is 2000 bytes, a quarter of the byte bound, and measures well past the 10-second timeout without it.

**Per-segment word count is unbounded.** `A=1 ` five hundred times in front of `git log` is 2007 bytes and one segment, and measures about 17 seconds against a 10-second timeout. `command_words` spawns two processes per leading assignment or wrapper word and nothing caps how many it walks. The fix is either a third bound or the single-pass rewrite that replaces all three.

**Variable expansion, `eval`, heredocs and other languages' inline-code flags are unreachable.** Any parser reading unexpanded text cannot see them. `python3 -c "import os; os.system('git commit -m x')"`, `node -e` and `perl -e` are all allowed; they are `eval` wearing a different name. The hook recovers payloads from `bash -c` and its four sibling shells only, and its own comment says so.

**Command substitution is unchecked for three roles.** `$(git commit -m x)` and the backtick form are allowed for `refuter`, `coder` and `ui-designer`, because only `fleet-steward`, `scout` and `reviewer` check for substitution. The leading-token strip that closes `{ git commit -m x; }`, `( git commit -m x )`, `! git commit -m x`, `>/tmp/out git commit -m x`, `timeout 5 git commit -m x` and the body of an `if`, `for` or `while` cannot reach a substitution, because the word has no leading token to remove. `script -q /dev/null git commit -m x` stays open on purpose: `script` puts its typescript file between itself and the command, so listing it as a wrapper would close nothing, and `script cat` would then read as `cat` while actually creating a file called `cat` - the same asymmetry that keeps `sudo` off the wrapper list.

**The refuter's "Never write inside the project" is not enforced against Bash.** `lib/check-write-scope.py` only ever sees `Write`, `Edit`, `MultiEdit` and `NotebookEdit`, so `echo mutated > claude/coder-fleet/agents/coder.md`, `cp /tmp/x claude/coder-fleet/workflows/review-round.js` and `rm -rf claude/coder-fleet` are every one of them allowed. `enforce_fleet_steward` resolves and checks redirection targets for an equivalent rule, so the pattern exists in the same file, and applying it here would still only reach redirections rather than `cp` or `rm` - which is why it is a design question rather than a missing line.

**An `agentType`-less lane is governed by nothing.** The `SubagentStop` matcher skips it and every branch of `enforce-agent-scope.sh` keys on an agent name, so "read-only git only" in a lane prompt is an instruction to a model, not a boundary. The four mechanical lanes in the workflows have always been in that position - they run the project's test suite - and `review-round`'s git lanes are in it too, including the fix worktree lane, which writes: its `git worktree add` is bounded by its prompt and by the script refusing any worktree the lane does not report exactly. Widening `scout`'s or `reviewer`'s allowlist instead would weaken a role boundary for every run rather than for the one workflow that needs `worktree`, `merge-base` and `rev-parse`. A probe spawn that falls back to a non-fleet agent type can run `git commit --allow-empty` in the main checkout and it lands with no refusal.

**A reviewer's gate runs the diff's own code, and the hook bounds only the command line (CF-90).** The gate rule decides which command the reviewer may type - a declared gate, from the top of a linked worktree, with no package manager, install, snapshot update, fix or write mode, watch mode, in-repo build output or network tool - and nothing about what that command then executes. A test file in the diff under review runs under `node --test` or `vitest` with the reviewer's permissions and can write, fetch or delete anything the process can, so "nothing the reviewer runs changes the diff" holds for the reviewer's flags, not for the code it is reviewing; the sandbox is what contains that code. The same goes for a script or task runner declared as a gate - `make check`, `just test`, `bash scripts/check.sh` - whose recipe is a file the diff can rewrite, so declaring one hands the diff the choice of what the reviewer runs.

**An honest gate can still write, because tools write by default (CF-90).** Outside CI, jest and vitest write a snapshot that does not exist yet: vitest 3.2.4 resolves `updateSnapshot` to `'none'` only when `isCI` (`resolveConfig.ts`) and to `'new'` otherwise, vitest 4 does the same through its `update` default (vitest.dev/config/update), and jest stores a new snapshot unless `ci` is on, which defaults to `isCI` (jest 29.7.0 `Defaults.ts`, jestjs.io/docs/cli). So a plain `vitest run` against a diff that adds a snapshot assertion creates a file in the worktree under review. A gate can start with `CI=true`, the one assignment the hook allows and only as a gate's first word, which the template's example does; the hook cannot require it, since a runner's config can override it. vitest's `--update=none` is not a way round this and is refused: vitest 4.x reads the value (checked in 4.1.10, not in 4.0), but vitest 3.x takes `--update` with no value, reads `none` as a file filter and rewrites every snapshot, and the hook cannot tell which version a worktree has. `tsBuildInfoFile` is worse: set in a `tsconfig.json` with `incremental` or `composite`, it makes even `tsc --noEmit` write a build-info file, and the path it names can be anywhere the process can write - inside the tree, tracked or not, or outside it. A runner's config can equally switch on a refused mode the command never names, such as a `vitest.config.ts` with `update: true`. Closing any of these would mean parsing tool configs, so the reviewer instead runs `git status --porcelain --ignored` after the gates and reports anything the run created or changed as a finding. That sees only the review worktree: new, changed and ignored files there, such as a snapshot, a `.tsbuildinfo` or a coverage directory. It does not see a write outside the worktree - a `tsBuildInfoFile` pointed elsewhere, a cache under the home directory - nor a file the run changed and then restored.

**The gate list is the main checkout's working tree, not a commit (CF-90).** The hook reads `AGENTS.md` from the main checkout's directory, so an uncommitted edit there widens the list for every review until it is reverted, and a main checkout with another branch out gives that branch's list. Reading from the checkout rather than the worktree under review is what stops a diff widening its own reviewer's allowlist; reading a committed ref instead would need the hook to know which ref is the base, which it is never told. A layout whose checkout is not the common git dir's parent - `--separate-git-dir`, or a bare repository with worktrees - has no list at all and fails closed.

**Go, Rust, Deno, bun and uv projects cannot declare gates (CF-90).** `go`, `cargo`, `deno`, `bun`, `bunx`, `uv` and `uvx` are refused as package managers whatever the list says, because each may fetch or install before it runs a test, and those projects have no `node_modules/.bin` to call instead. Their reviewers run nothing and list the gates under Unverified. Allowing them would take a per-tool offline mode passed as a flag (`cargo --offline`, `deno --cached-only`), since a gate command may assign no variable, and each is its own item.

**A named, non-isolated spawn escapes the fleet entirely, and it is the likeliest shape of a trample.** Spawning a fleet agent with a `name` and no `isolation` puts it on the teammate path, where the hook events carry the name as `agent_type`: `enforce-agent-scope.sh` then allows everything, because no agent type it knows means the main session; the `SubagentStop` matcher never matches; no worktree is cut. A named `coder` commits straight to main with no refusal anywhere. A named read-only agent loses its whole output instead: idle notifications arrive in place of a result, the stop gate's exit 2 has nowhere to deliver, and the run looks like a success with a formatting hiccup. So a named spawn loses whichever half of the contract the role depends on, and neither failure is loud. A named refuter loses the time cap as well, because `agent-clock.sh` keys on the same agent type. The refusal branch of the worktree guard may be unreachable from a real typed spawn - a typed `coder` always gets a worktree, and only the ungoverned path ends up in the main checkout - which makes the teammate path the whole risk. Until the hook can key on something a teammate cannot rename, the rule is operational: never name a fleet spawn, and treat a teammate running a fleet body as ungoverned. The lead's body says so.

## The refuter's time cap

**The cap stops tools, not the model.** Past 25 minutes `agent-clock.sh` denies every tool call, but a turn that writes only text needs no tool, so text-only turns after the cap - including the re-emits `SubagentStop` asks for when a handoff is malformed - are bounded by the model alone.

**The in-flight Bash trim depends on undocumented behaviour.** Sending `updatedInput` with no permission decision is honoured by the 2.1.283 bundle and contradicted by the documentation (hooks README, item 20). If a later CLI follows the docs, the trim silently stops and the gap reopens to 25 minutes plus one command, up to the runtime's Bash ceiling, 10 minutes by default. The deny still holds.

**`run_in_background` is outside any timeout.** A backgrounded command can outlive the run. The run itself should not be held open, since `SubagentStop` carries `background_tasks`, but that is unobserved live.

**Missing state starts the clock late, and a corrupt file uncaps the run.** Both allow the call with a log line. A refuter that deletes its own clock file restarts its clock at the next tool call: a speed bump, not a boundary.

**Nothing counts mutants.** At most eight mutants a round is an instruction in the refuter's body, the `looping` skill, the lead's brief and `review-round`'s refuter prompt, and no hook or workflow counts them. A refuter that runs a ninth is stopped only by the 20-minute round and the 25-minute deny, which bind first on any suite slower than about 100 seconds run one after another. Counting would mean parsing mutations out of Bash calls, and the time cap already bounds the spend.

**A refuter run as the main agent is uncapped.** With `--agent refuter` the events carry no `agent_id`, and the hook exits before it reads anything.

**Wall-clock includes machine sleep.** A refuter on a laptop that slept is denied when it wakes. That is intended: the rule is wall-clock.

## Never run against a live Claude

**The refuter.** Its permissions are pinned by 85 deterministic checks in the scope hook suite and its evals exist, but no stubbed suite can show whether an agent given that body actually refutes rather than reviews. `claude/evals/refuter/` probes both directions - a change with a genuinely vacuous test, and a change with nothing wrong where inventing a finding is the failure - and until it runs, the role is a design rather than a capability.

**`fix: true` in `review-round`.** Every branch is covered by deterministic tests that stub the model out, which is exactly the coverage that can hide a gate bug for a fortnight. What those cannot prove: that the git lanes report `isMain` correctly off `git worktree list --porcelain`, that the fix worktree lane runs exactly the `git worktree add` it is given and reports git's answer rather than its own, that `coder` works only through `git -C` and absolute paths into the worktree it was handed, and that `parallel()` returns lanes in a shape the tests-lane lookup finds. The lookup is by name rather than by position for that reason.

**`refute: true` and the refutation stage.** Same coverage, same gap. What the stubs cannot prove: that a refuter asked to attack a change copies out of the project rather than mutating the tree under test, and that `survivorsOf` on a real refutation finds the `survived:` Done bullets the way the fixtures say it will.

**Worktree isolation for a workflow-spawned `coder`.** Workflow-spawned agents get no harness isolation. An Agent-tool `coder` spawned with the fleet type gets a locked linked worktree, because the harness honours the definition's `isolation: worktree`, but a workflow `agent()` call with the same `agentType` does not: in the live run `wf_1297e8b7-cb8` the fix-lane coder started in the main checkout, and only `enforce_coder` (`claude/coder-fleet/hooks/README.md` item 18) kept it off main. `review-round` compensates itself (CF-127). Before a fix round spawns its coder, a git lane runs `git worktree add` under the main checkout's `.claude/worktrees/review-round-<issue>-r<n>`, on a new branch `review-round/<issue>-r<n>` at the pinned head, and reports what git says about it. The script stops the run with `fix worktree not created`, and spawns no coder, unless the lane vouches for exactly that path, branch and head as a linked worktree. An existing branch is a stop, never a reason to pick another name. The coder's prompt names the worktree and tells it to work only there, and the fix gate refuses a commit that git does not find on that worktree's branch. The worktrees are left in place and listed in the result's `fixWorktrees` for the lead to adopt or prune. The base is recorded: with `worktree.baseRef` `"head"`, which the project settings template ships (CF-52), a type-isolated Agent-tool `coder` was cut at the local HEAD `fc1b90e` while local main was ten commits ahead of `origin` (2026-10-01, CF-52 comment #11), and the fix lane cuts its worktree itself at the pinned head, whatever the setting says (CF-127, PR #58). Not yet run live: the fix lane's cut in a real `review-round`, and a coder working through `git -C` from a main-checkout `cwd`; the entry stays for those two. Cutting from the local HEAD has a cost: in the main checkout the local HEAD carries the board's auto-commits, so a pull request branch cut from it must not carry `.boards/` commits, which is why the CF-147 coder branched from `origin/main`.

**The refuter's time cap, end to end.** The contract pins what `agent-clock.sh` outputs, not what the runtime does with it: that a live refuter is denied at 25 minutes, writes its handoff after the deny, and has a long Bash call ended at the trimmed timeout. The post-merge probe in hooks README item 20 covers it until it runs.

**The disabled-agents hook against a live spawn.** `disabled-agents-contract.sh` pins what `enforce-disabled-agents.sh` prints for a given event, not what the runtime does with it: that a live Agent call is refused on the deny, that the invalid-config `systemMessage` reaches the human, and whether a workflow's `agent()` spawn reaches the hook at all. `review-round` reads `.claude/coder-fleet.json` itself so its refuter never depends on the last one, but whether a live pin lane reads the main checkout's copy and reports it verbatim is unproven too. The script honours a found file only when the lane reports the path it read and that path is the main worktree's file; a found file with an empty or missing path, or any other path, is treated as unread and the refuter stays on. It checks what the lane says, not what the lane did: a lane that read a linked worktree's copy and reported the main worktree's path, or read the right file and misreported its text, is believed.

**`review-round`'s origin pin (CF-126, CF-66).** For each end given as a branch name - a base, a head, a target, or the default branch a target is reviewed against - the script pins origin's commit when the local branch is behind it, keeps the local commit when it is ahead, and stops naming both commits when they have diverged. A base that is the default branch is `origin/<default>` whenever that ref exists, whatever the ancestry, because in a board repo local main always carries unpushed board commits and has diverged from origin after any fetch. A single-ref range's base is the parent of the pinned head, so moving the head to origin's tip does not widen the review. The script cannot run git, so all of that rests on what the pin lane reports: the default branch, `refs/remotes/origin/<name>`, the two `git merge-base --is-ancestor` answers and, for a single-ref range, origin's parent commit. `workflow-logic.mjs` pins the decision over that report, not that a live lane runs those commands and reports them truly; a lane that misreports ancestry is believed. A missing or contradictory ancestry answer stops the run rather than picking, and a lane that leaves the origin report out altogether pins the local commit and logs that origin was not checked, which is the behaviour from before. The workflow never fetches: origin is read as the checkout last fetched it, so fetching before the run is the lead's job, and a run after no fetch can still pin a stale origin.

## Disabled agents

**Only `review-round` honours the list among the workflows, and only for the refuter.** `review-round` spawns `scout` for its scope pass, and `spec-to-card` and `deep-research` spawn their own agents, none of which consults `.claude/coder-fleet.json`. A project that disables `scout` gets a denied scope pass, if the hook sees workflow spawns, and a `scope pass returned nothing` stop rather than a fallback. CF-111 proved the mechanism on the refuter; making each workflow fall back or stop by name for every other agent is separate work.

**A name that is no agent's is accepted.** `disabledAgents: ["refutor"]` is valid and disables nothing, so the spawn hook allows every call as before. `enforce-disabled-agents.sh --check` prints a warning naming each such entry and still exits 0, against the roster `fleet_roster` builds from the plugin's agents directory (CF-113); nothing warns at spawn time.

**The live main file trusts every writer of the main checkout.** The hook, `--check`, `/coder-fleet:agents` and `review-round` all read `.claude/coder-fleet.json` from the main checkout as it is on disk, uncommitted edits included, so toggles need no commit. Anything that can write there can disable the refuter, and that includes a fleet agent: `enforce_coder` does not confine a coder's `Write` or `Edit` to its own worktree, so a coder can write the main checkout's file by absolute path, and every later spawn and review reads it. `review-round`'s guard only sees a change that is in the reviewed range, which an uncommitted write to the main checkout never is. The defence today is that the human reads the file before trusting a skipped refutation, and that every skip says it was skipped by config.

**A forged worktree is defended only through `CLAUDE_PROJECT_DIR`.** A repository made for the purpose that registers a worktree itself passes the check that the main checkout lists the starting worktree, because the check asks that repository. The spawn hook starts from `CLAUDE_PROJECT_DIR`, which a `cd` cannot move, so a lead whose `cwd` is in such a worktree still reads the real main's file. With the variable unset or not a directory the event's `cwd` decides, and so do `--check [dir]` and `/coder-fleet:agents`, which start from the directory they are given or run in.

**Outside a git repository, no config is read.** When the project is not a git repository, or its main checkout is bare, no `.claude/coder-fleet.json` is read and nothing is disabled, whatever a file in the current directory says.

## Refutation checks that do not exist

**Nothing checks that a refutation contains mutation evidence.** `review-round` stops on a `survived:` Done bullet, on a `Blocker:` line and on an empty refutation, and treats everything else as unbroken. The survivor transport is itself unproven: no live refuter has yet been seen to write a `survived:` bullet, and the reader fails closed: any Done bullet that mentions surviving, a bare `survived:` key included, stops the round unless the whole bullet is one of a small set of strict nothing-survived forms. What it cannot see, and so fails open on, is a survivor described without the stem ("lived", "not killed", "not noticed"), look-alike or invisible characters inside the word, list markers other than `- `, and a clean-looking `survived: none` followed by a separate bullet that names a survivor. It never looks at whether the Done section says anything was mutated. A refutation whose only Done bullet is "I read the diff and it looks fine to me" returns `stopped: "clean"` and `approved: true`, which is the exact failure the role exists to prevent, arriving through the gate rather than around it. The check is deferred on purpose: it would have to pin a workflow decision to a new obligation on the refuter's Done-bullet wording, and a format obligation invented and depended on in one commit is how format obligations decay. The `survived:` bullet is not that case: survivors were already a parsed obligation, moved from Decisions needed to Done rather than invented, and the bullet rides the keyed Done bullets `fixHints` already depends on. The evidence check gets built once there is a real refutation handoff to parse, which needs the live runs above. The time cap widens the gap: a refutation stopped at 25 minutes, with its unfinished mutations under Not done, carries no `Blocker:` line and is read as clean too.

**The sensitive override covers authentication and secrets only.** Under `fix: true`, `review-round` spawns a refuter despite `refute: false` when a round's changed files match `SENSITIVE`, and that pattern names authentication, authorisation, session, crypto and secret paths but nothing for data writes, so a fix round that adds a migration under `refute: false` gets no refuter.

**A project with no test or build command is never approved without a refuter.** With `refute: false`, `review-round` approves a clean verdict only when both gate lanes ran something, and a lane that honestly reports `ran: []` is missing. A repository with no build step, or no test runner, therefore gets `approved: false` from every lanes-only review, however often the lead runs the gates itself afterwards. There is no way yet to declare a gate absent for a project; the lead reads `gatesMissing` and the next step, which say so, and records its own gate run in its handoff.

## The challenge gate

**A closed marker typed by hand passes.** `scripts/challenge-gate.py` decides from the spec and the `Spec editor:` line alone, never from git history, so a `## Challenges (spec-editor): closed in <sha>` line passes whether or not the close made it, and whether or not the commit it names exists. Left by the human's decision (CF-12 spec, Q19): the gate guards against skipping the challenges by accident, not against a deliberate override, and reading no history is what lets it pass in a shallow clone or a cloud session.

**The close commits on whatever branch the checkout holds.** `run` commits the spec alone, twice at most, in the checkout it is run from, which for the lead and `spec-to-card` is usually the main checkout's local default branch, beside the board's own auto-commits. It never pushes. Left because the spec lives where the human edits it and the close has to land before anything is filed or built from it; getting the commit onto the remote is the lead's ordinary landing work.

**The scope hook holds a spec editor to `docs/specs/`, not to the one spec its brief names.** `enforce-agent-scope.sh` denies a spec editor every command and any write outside the project's `docs/specs/`, and nothing narrows it further: the brief's spec reaches the editor as prose, and the hook has no per-spawn input it could read it from, the same gap `CODER_FLEET_OUTPUT_FILES` leaves for `tech-writer` (CF-12 spec, open questions). Editing a second spec is held by the body's invariant alone. Left because the editor holds `Edit` but not `Write`, so it can change only a spec that exists, and the eval's `checks.sh` fails a run that changes anything but the named draft.

**The scope hook holds a tech editor to `tech-writer`'s scope, not to the documents its brief names.** `enforce-agent-scope.sh` denies a tech editor every command and any write outside `tech-writer`'s scope, documentation under `docs/` and a Markdown file at the project root, narrowed only where the launching environment sets `tech-writer`'s entry in `CODER_FLEET_OUTPUT_FILES`. The brief's documents reach the editor as prose, so editing a second document is held by the body's invariant alone, the same gap the spec editors have. Left because the editor holds `Edit` but not `Write`, so it can change only a document that exists, and the eval's `checks.sh` fails a run that changes anything but the named document.

**No gate where `AGENTS.md` records no spec editor.** A project with no `Spec editor:` line gets no editor and no gate, and the gate says to run `/kickoff` (Q21), so specs written before the editor existed build as they always did. `spec-to-card` still refuses to file a criterion that carries a `[challenge Cn]` marker there, since nothing closed it.
