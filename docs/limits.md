# Known limits

What the fleet deliberately does not enforce or cover. Each item is a gap that was looked at and left, with the reason, so a deliberate gap is not mistaken for an oversight. Anything here that becomes a rule, a hook or a test leaves this file the same day.

## The board hooks

**The route to Done depends on a Claude Code gate the fleet does not own.** `TaskCompleted` fires only when a task is completed with `TaskUpdate`, and Claude Code 2.1.283 offers the task tools to current models only when `CLAUDE_CODE_ENABLE_TODO_TOOLS` is set. The fleet sets it in each project's settings through `/init`, but a later CLI can rename the variable or change the default. `/kickoff` checks that the lead has `TaskUpdate`, which turns such a change into a named failure rather than a board where no lead-closed card reaches Done again.

**The card gate runs on two triggers only.** It moves a card to Done on the stop of the `coder` or `scripter` bound to it, and on the completion of a task whose subject carries the `[board:<id>]` marker, which needs `CLAUDE_CODE_ENABLE_TODO_TOOLS` (above). A card fully ticked by the lead after its builder stopped waits for a marked task or `/triage`. The human's move into Done in the web UI overrides the gate and is recorded in the trail as bypassing it. Left because a move the human makes is the human's decision.

**Failure and cancellation never reach Blocked.** `SubagentStop` carries no `status` field, so the board's SubagentStop hook cannot detect a failed or cancelled run. A `Blocker:` line in the handoff routes to Blocked by Human, and the test gate's failed release run is the only writer of Blocked. `agent_transcript_path` is present on every `SubagentStop` event, so what is missing is a reader that recognises a failed or cancelled run from it.

**A turn-capped run never sends SubagentStop.** `SubagentStop` does not fire when `maxTurns` cuts a run off (`docs/decisions/claude-code-behaviours.md`). So a capped run gets no handoff check, its `Blocker:` lines reach no card, and its card stays where it is. Nothing catches it: the lead says on the card that the run came back without a handoff. That includes a spawn the runtime backgrounded on its own, and a capped run resumed with SendMessage and cut off again.

**A workflow lane binds to the focus, not to its own call.** A spawn is bound when it is sent, by its `Board-Item:` line or the checkout's focus at that moment, and found again at its first stop through the `toolUseId` Claude Code writes beside its transcript. A workflow lane is sent by no Agent call and its `.meta.json` names none, so it binds to the focus as it was when its start was noted; a lane that starts after a refocus belongs to the newly focused card. Accepted, because a workflow runs for one card and the lead focuses that card before launching it.

**The transcript reader fails open.** The board's SubagentStop hook consults `agent_transcript_path` to tell a schema-spawned run from one that produced nothing, and a transcript it cannot read - missing, unreadable, oversized, unparseable - passes rather than blocking. Deliberate: deadlocking a subagent is worse than a rare silent pass.

**A plugin update removes the boards binary a session on an older version still needs.** The session-start fetch of a newer version deletes every older `boards-<version>` from the plugin's shared data directory before it fetches its own (`prune_old` in `claude/coder-fleet/hooks/boards-binary.sh`), whether or not a session is still running on that older installed version. That session's board hooks then do nothing and its disabled-agents shim refuses every spawn until it restarts onto the current version. The hook compares version numbers only; it does not look at which versions Claude Code's plugin cache still holds.

## The lines under the prompt

**Only a terminal session gets them.** The two lines coder-fleet draws under the prompt are a `ui.render` hook on `PromptHint` that answers only the terminal surface; the desktop app and VS Code get no lines and no status row, only the binary's state told to the session at SessionStart. `CODER_FLEET_STATUS_LINES=off` turns them off in the terminal too. Left because the design is a terminal design and the human chose to draw nothing elsewhere.

**Line 2 follows only the agents this session saw spawned.** The module learns of a fleet agent from `agent.spawn` while it is loaded, so an agent started before a reload of the module, or in another session, is not on the line. Its card is read the way the board binds a spawn, its `Board-Item:` line else the checkout's focus, but by the module itself as the spawn is sent, so a focus changed in the same instant can name a different card from the board's binding. Left because the line is a view, never a writer, and the board's own binding is what moves cards.

**"Downloading" and "another session is fetching" are told apart by timing.** The fetch lock carries no owner, so while this session's SessionStart hooks run a held lock reads as this session's download, and once they finish as another session's. A session that starts while another holds the fetch shows `downloading` until its own hooks finish, a few seconds at most. Left because naming the owner in the lock would change the fetch for a word on one line.

## The board's web UI

**On `listen: 0.0.0.0` the web UI has no access control.** A board whose `config.yml` sets `listen: 0.0.0.0` serves its web UI on every IPv4 address of the machine, and anyone who can reach the port can read every card and make every write the human can: fill and order Next, move any card past both gates and delete cards. There is no token, password or read-only mode. The human chose this knowingly when ordering CF-10, to reach the board from another machine on a trusted network; the default stays `127.0.0.1`, and setting `0.0.0.0` is a per-board choice made by hand. What stays is the guard against other sites' pages: the `Host` must be an IP literal or `localhost` on the server's port, so DNS rebinding is refused, and a write's `Origin` must be the request's own `http://` address, so a page elsewhere cannot post to it. A client that is not a browser sets both headers as it likes, so neither is access control.

## Agent scoping and the push and release settings

**No hook scopes an agent's tool calls.** CF-21 removed the per-agent scope hook and the break-mode reviewer's clock. What each agent may write, which commands it may run, which gates a reviewer runs and that a coder writes only in its own worktree are instructions in its body, and its `tools` list is the only hard edge. Host-level `permissions.deny` and the sandbox still hold, for every agent alike; a per-agent boundary they cannot express is a line the model follows, not one a hook checks.

**The push and release settings are followed, not enforced.** `push` and `release` in `.claude/coder-fleet.json`, set with `/coder-fleet:agents`, are settings the lead reads and follows. No hook refuses a push, a tag or a `gh release create` that breaks them, from the lead, a subagent or the human, and nothing stops an agent other than the lead writing the settings file; a subagent's brief and invariants are what keep it from pushing.

**An `agentType`-less lane is outside the handoff gate.** The `SubagentStop` matcher skips it, and "read-only git only" in a lane prompt is an instruction to a model, not a boundary. `review-round`'s two mechanical lanes, lint and smells, are in that position, and its git lanes are in it too, including the fix worktree lane, which writes: its `git worktree add` is bounded by its prompt and by the script refusing any worktree the lane does not report exactly. A probe spawn that falls back to a non-fleet agent type can run `git commit --allow-empty` in the main checkout.

**A reviewer's gate runs the diff's own code, and the gate rule bounds only the command line.** The gate rule in the reviewer's body says which command it may type - a declared gate, from the top of a linked worktree, with no package manager but a bun project's `bun --no-install test`, no install but the one frozen, scripts-off install its lockfile names, and no snapshot update, fix or write mode, watch mode, in-repo build output or network tool - and nothing about what that command then executes. A test file in the diff under review runs under `node --test` or `vitest` with the reviewer's permissions and can write, fetch or delete anything the process can, so "nothing the reviewer runs changes the diff" holds for the reviewer's flags, not for the code it is reviewing; the sandbox is what contains that code. The same goes for a script or task runner declared as a gate - `make check`, `just test`, `bash scripts/check.sh` - whose recipe is a file the diff can rewrite, so declaring one hands the diff the choice of what the reviewer runs.

**An honest gate can still write, because tools write by default.** Outside CI, jest and vitest write a snapshot that does not exist yet: vitest 3.2.4 resolves `updateSnapshot` to `'none'` only when `isCI` (`resolveConfig.ts`) and to `'new'` otherwise, vitest 4 does the same through its `update` default (vitest.dev/config/update), and jest stores a new snapshot unless `ci` is on, which defaults to `isCI` (jest 29.7.0 `Defaults.ts`, jestjs.io/docs/cli). So a plain `vitest run` against a diff that adds a snapshot assertion creates a file in the worktree under review. A gate can start with `CI=true`, the one assignment the gate rule allows and only as a gate's first word, which the template's example does; nothing makes a project write it, and a runner's config can override it. vitest's `--update=none` is not a way round this, and the template tells projects not to use it: vitest 4.x reads the value (checked in 4.1.10, not in 4.0), but vitest 3.x takes `--update` with no value, reads `none` as a file filter and rewrites every snapshot, and a gate line cannot say which version a worktree has. `tsBuildInfoFile` is worse: set in a `tsconfig.json` with `incremental` or `composite`, it makes even `tsc --noEmit` write a build-info file, and the path it names can be anywhere the process can write - inside the tree, tracked or not, or outside it. A runner's config can equally switch on a mode the gate rule rules out and the command never names, such as a `vitest.config.ts` with `update: true`. Closing any of these would mean parsing tool configs, so the reviewer instead runs `git status --porcelain --ignored` after the gates and reports anything the run created or changed as a finding. That sees only the review worktree: new, changed and ignored files there, such as a snapshot, a `.tsbuildinfo` or a coverage directory. It does not see a write outside the worktree - a `tsBuildInfoFile` pointed elsewhere, a cache under the home directory - nor a file the run changed and then restored.

**The gate list is the main checkout's working tree, not a commit.** The reviewer reads `AGENTS.md` from the main checkout's directory, so an uncommitted edit there widens the list for every review until it is reverted, and a main checkout with another branch out gives that branch's list. Reading from the checkout rather than the worktree under review is what stops a diff widening its own reviewer's gate list; reading a committed ref instead would need the reviewer to know which ref is the base, which it is never told. A layout whose checkout is not the common git dir's parent - `--separate-git-dir`, or a bare repository with worktrees - has no list at all.

**A reviewer's lockfile install trusts the lockfile and the main checkout's config.** A review worktree is cut fresh with no node_modules, so the reviewer runs one install at its top, chosen by the one kind of lockfile there, frozen and with install scripts off (CF-199), and skips it when the diff changes top-level config or a `package.json` field beyond the ordinary ones, as its body says. Nothing checks that it did. An install also obeys its config: a berry `yarnPath` or plugin is code, and a lockfile the diff edits can name any tarball URL, a non-default registry included, with only its integrity hashes, which the same diff writes, checking what arrives. The reviewer's `git status --porcelain --ignored` after the gates reports what the install wrote in the worktree.

**Go, Rust, Deno and uv projects cannot declare gates.** `go`, `cargo`, `deno`, `uv` and `uvx` are package managers, which the reviewer never runs whatever the list says, because each may fetch or install before it runs a test, and those projects have no `node_modules/.bin` to call instead. Their reviewers run nothing and list the gates under Unverified. Allowing them would take a per-tool offline mode passed as a flag (`cargo --offline`, `deno --cached-only`), since a gate command may assign no variable, and each is its own item.

**A named, non-isolated spawn escapes the fleet entirely, and it is the likeliest shape of a trample.** Spawning a fleet agent with a `name` and no `isolation` puts it on the teammate path, where the hook events carry the name as `agent_type`: the `SubagentStop` matcher never matches and no worktree is cut. A named `coder` commits straight to main. A named read-only agent loses its whole output instead: idle notifications arrive in place of a result, the stop gate's exit 2 has nowhere to deliver, and the run looks like a success with a formatting hiccup. So a named spawn loses whichever half of the contract the role depends on, and neither failure is loud. The rule is operational: never name a fleet spawn, and treat a teammate running a fleet body as ungoverned. The lead's body says so.

## The break-mode reviewer's budget

**Nothing caps the clock.** A break-mode round is 20 minutes of wall-clock from the spawn, an instruction in the reviewer's body and the lead's brief. Since CF-21 no hook denies a run past it, so a reviewer that ignores it runs until it stops or its turns run out.

**Nothing counts mutants.** At most eight mutants a round is an instruction in the reviewer's body, the `looping` skill, the lead's brief and `review-round`'s break-lane prompt, and no hook or workflow counts them. A break-mode reviewer that runs a ninth is stopped only by its own 20-minute round.

## Never run against a live Claude

**The reviewer's break and use modes.** No stubbed suite can show whether a reviewer briefed for break actually refutes rather than reviews, or one briefed for use drives the product rather than reading the code. The refuter's and evaluator's evals went with them in CF-192 and the reviewer's eval has no break or use prompt yet, so until one runs, both modes are a design rather than a capability.

**`fix: true` in `review-round`.** Every branch is covered by deterministic tests that stub the model out, which is exactly the coverage that can hide a gate bug for a fortnight. What those cannot prove: that the git lanes report `isMain` correctly off `git worktree list --porcelain`, that the fix worktree lane runs exactly the `git worktree add` it is given and reports git's answer rather than its own, that `coder` works only through `git -C` and absolute paths into the worktree it was handed, and that `parallel()` returns lanes in a shape the tests-lane lookup finds. The lookup is by name rather than by position for that reason.

**`refute: true` and the refutation stage.** Same coverage, same gap. What the stubs cannot prove: that a break-mode reviewer asked to attack a change copies out of the project rather than mutating the tree under test, and that `survivorsOf` on a real refutation finds the `survived:` Done bullets the way the fixtures say it will.

**Worktree isolation for a workflow-spawned `coder`.** Workflow-spawned agents get no harness isolation. An Agent-tool `coder` spawned with the fleet type gets a locked linked worktree, because the harness honours the definition's `isolation: worktree`, but a workflow `agent()` call with the same `agentType` does not: in the live run `wf_1297e8b7-cb8` the fix-lane coder started in the main checkout, and only the scope hook (`claude/coder-fleet/hooks/README.md` item 18, retired in CF-21) kept it off main. Nothing but the coder's body, which tells it to confirm its worktree before it writes, does now. `review-round` compensates itself. Before a fix round spawns its coder, a git lane runs `git worktree add` under the main checkout's `.claude/worktrees/review-round-<issue>-r<n>`, on a new branch `review-round/<issue>-r<n>` at the pinned head, and reports what git says about it. The script stops the run with `fix worktree not created`, and spawns no coder, unless the lane vouches for exactly that path, branch and head as a linked worktree. An existing branch is a stop, never a reason to pick another name. The coder's prompt names the worktree and tells it to work only there, and the fix gate refuses a commit that git does not find on that worktree's branch. The worktrees are left in place and listed in the result's `fixWorktrees` for the lead to adopt or prune. With `worktree.baseRef` `"head"`, which the project settings template ships, a type-isolated Agent-tool `coder` is cut at the local HEAD rather than at `origin`, and the fix lane cuts its worktree itself at the pinned head, whatever the setting says. Not yet run live: the fix lane's cut in a real `review-round`, and a coder working through `git -C` from a main-checkout `cwd`; the entry stays for those two.

**Where `review-round` reads the tree.** The script names one tree after the pin: the coder's worktree when the pin lists it clean at the pinned head, said not to be the main checkout and not a `review-round-` tree of another run, or else a detached worktree it cuts at `.claude/worktrees/review-round-<issue>-at-<sha>` under the main checkout and removes in a `finally` with `git worktree remove`, never forced. Each lane that grades the tree - the two mechanical lanes, the verdict and the refutation - is told to check `rev-parse --show-toplevel` and `rev-parse HEAD` first and to run nothing when they are not that tree at that head, and the script drops any report that does not say so. That last part is what the script can enforce: a lane that runs a command somewhere else before reporting is stopped by nothing, the same position as any `agentType`-less lane, and a coder's worktree read in place can still move under a lane that already checked it if the coder is still working. The removal is refused when a lane left untracked or modified files there, and the run then reports the path rather than forcing it. `workflow-logic.mjs` drives a round against real git from a main checkout on `main` and shows its HEAD, branch and status unchanged, with stub lanes that run exactly the commands the script gives them. Not yet run live: a real round's lanes honouring the tree check.

**The board's Stop hook under `/goal`.** CF-4's Stop hook (`claude/boards/src/hooks/stop.ts`) sends the lead back once per stop, and `/goal` is itself a session-scoped prompt-based Stop hook, so both fire after every turn of a `/drain`. What the Claude Code docs say, read 2026-11-15 (`hooks.md`, Stop, and `goal.md`): `stop_hook_active` is true "when Claude Code is already continuing as a result of a stop hook"; stop hooks are cut off after eight consecutive continuations, a count that resets whenever Claude calls a tool; and the goal's evaluator is skipped for a turn that ends with a subagent or background shell still running. They do not say in which order the goal's evaluator and a settings Stop hook run, nor whether a continuation the goal starts sets `stop_hook_active` on the next stop. Neither is verified live: no paid session was run. What the build does prove, in `test/stop-hook.test.ts`, is that a drain's final state, with the focus cleared after its last card or that card parked on an Action for Human, gets nothing from the hook, and that a focus left on an unfinished card costs one extra turn and then lets the stop through. If a goal continuation does set `stop_hook_active`, the hook stays silent on every goal turn after the first and sends the lead back less often than its criteria allow, never more.

**The disabled-agents hook against a live spawn.** `disabled-agents-contract.sh` pins what `enforce-disabled-agents.sh` prints for a given event, not what the runtime does with it: that a live Agent call is refused on the deny, that the invalid-config `systemMessage` reaches the human, and whether a workflow's `agent()` spawn reaches the hook at all. `review-round` reads `.claude/coder-fleet.json` itself so its phase never depends on the last one, but whether a live pin lane reads the main checkout's copy and reports it verbatim is unproven too. The script honours a found file only when the lane reports the path it read and that path is the main worktree's file; a found file with an empty or missing path, or any other path, is treated as unread and the phase is harden. It checks what the lane says, not what the lane did: a lane that read a linked worktree's copy and reported the main worktree's path, or read the right file and misreported its text, is believed.

**`review-round`'s origin pin.** For each end given as a branch name - a base, a head, a target, or the default branch a target is reviewed against - the script pins origin's commit when the local branch is behind it, keeps the local commit when it is ahead, and stops naming both commits when they have diverged. A base that is the default branch is `origin/<default>` whenever that ref exists, whatever the ancestry. A single-ref range's base is the parent of the pinned head, so moving the head to origin's tip does not widen the review. The script cannot run git, so all of that rests on what the pin lane reports: the default branch, `refs/remotes/origin/<name>`, the two `git merge-base --is-ancestor` answers and, for a single-ref range, origin's parent commit. `workflow-logic.mjs` pins the decision over that report, not that a live lane runs those commands and reports them truly; a lane that misreports ancestry is believed. A missing or contradictory ancestry answer stops the run rather than picking, and a lane that leaves the origin report out altogether pins the local commit and logs that origin was not checked. The workflow never fetches: origin is read as the checkout last fetched it, so fetching before the run is the lead's job, and a run after no fetch can still pin a stale origin.

## Disabled agents

**No workflow honours the list.** `review-round` spawns `scout` for its scope pass, and `spec-to-card` and `deep-research` spawn their own agents, none of which consults `.claude/coder-fleet.json`. A project that disables `scout` gets a denied scope pass, if the hook sees workflow spawns, and a `scope pass returned nothing` stop rather than a fallback. `review-round` honoured it for the refuter until CF-192 made that a reviewer mode; making each workflow fall back or stop by name for a disabled agent is separate work.

**A name that is no agent's is accepted.** `disabledAgents: ["researchr"]`, or a `refuter` or `evaluator` left from before CF-192, is valid and disables nothing, so the spawn hook allows every call as before. `enforce-disabled-agents.sh --check` prints a warning naming each such entry and still exits 0, against the roster `fleet_roster` builds from the plugin's agents directory; nothing warns at spawn time.

**The live main file trusts every writer of the main checkout.** The hook, `--check`, `/coder-fleet:agents` and `review-round` all read `.claude/coder-fleet.json` from the main checkout as it is on disk, uncommitted edits included, so toggles need no commit. Anything that can write there can disable an agent or set the phase to build, and that includes a fleet agent: no hook confines a coder's `Write` or `Edit` to its own worktree, so a coder can write the main checkout's file by absolute path, and every later spawn and review reads it. `review-round`'s guard only sees a change that is in the reviewed range, which an uncommitted write to the main checkout never is. The defence today is that the human reads the file before trusting a skipped refutation, and that every skip says the build phase skipped it.

**A forged worktree is defended only through `CLAUDE_PROJECT_DIR`.** A repository made for the purpose that registers a worktree itself passes the check that the main checkout lists the starting worktree, because the check asks that repository. The spawn hook starts from `CLAUDE_PROJECT_DIR`, which a `cd` cannot move, so a lead whose `cwd` is in such a worktree still reads the real main's file. With the variable unset or not a directory the event's `cwd` decides, and so do `--check [dir]` and `/coder-fleet:agents`, which start from the directory they are given or run in.

**Outside a git repository, no config is read.** When the project is not a git repository, or its main checkout is bare, no `.claude/coder-fleet.json` is read and nothing is disabled, whatever a file in the current directory says.

## Refutation checks that do not exist

**Nothing checks that a refutation contains mutation evidence.** `review-round` stops on a `survived:` Done bullet, on a `Blocker:` line and on an empty refutation, and treats everything else as unbroken. The survivor transport is itself unproven: no live break-mode reviewer has yet been seen to write a `survived:` bullet, and the reader fails closed: any Done bullet that mentions surviving, a bare `survived:` key included, stops the round unless the whole bullet is one of a small set of strict nothing-survived forms. What it cannot see, and so fails open on, is a survivor described without the stem ("lived", "not killed", "not noticed"), look-alike or invisible characters inside the word, list markers other than `- `, and a clean-looking `survived: none` followed by a separate bullet that names a survivor. It never looks at whether the Done section says anything was mutated. A refutation whose only Done bullet is "I read the diff and it looks fine to me" returns `stopped: "clean"` and `approved: true`, which is the exact failure the role exists to prevent, arriving through the gate rather than around it. The check is deferred on purpose: it would have to pin a workflow decision to a new obligation on the break mode's Done-bullet wording, and a format obligation invented and depended on in one commit is how format obligations decay. The `survived:` bullet is not that case: survivors were already a parsed obligation, moved from Decisions needed to Done rather than invented, and the bullet rides the keyed Done bullets `fixHints` already depends on. The evidence check gets built once there is a real refutation handoff to parse, which needs the live runs above.

**The sensitive override covers authentication and secrets only.** Under `fix: true`, `review-round` spawns a break lane despite `refute: false` when a round's changed files match `SENSITIVE`, and that pattern names authentication, authorisation, session, crypto and secret paths but nothing for data writes, so a fix round that adds a migration under `refute: false` gets no break lane.

**A project with no `gates` block is never approved without a break lane.** With `refute: false`, `review-round` approves a clean verdict only when the reviewer's gate lines put a run on record with nothing under `gatesMissing` or `gatesFailed`: a reviewer that reports no gate line, a line it could not read, a gate it could not run or none for a gate the main checkout's `gates` block declares leaves something missing, and a line with a non-zero exit is a failed gate and a blocking finding. A project whose main checkout's `AGENTS.md` declares no `gates` block gives the reviewer nothing to run, so it gets `approved: false` from every review without a break lane, however often the lead runs the gates itself afterwards. There is no way yet to declare a gate absent for a project; the lead reads `gatesMissing` and the next step, which say so, and records its own gate run in its handoff.

## The deterministic suite

**Permission cases skip under root.** `challenge-gate-contract.sh` proves a fail-closed or fail-open branch by making a file or directory unwritable or unreadable with `chmod`, and the board's own tests do the same for a state directory or a focus that cannot be written. A process running as root, or holding `CAP_DAC_OVERRIDE`, is not bound by those bits, so the case cannot show what it claims. The script probes once (`perms_bind`: a scratch file at mode 000 that is still readable means permissions do not bind) and prints a `SKIP` line for the case, counted as neither pass nor fail; the bun test uses `it.skipIf` on uid 0. Asked for by the human on 18 October 2026, after a cloud session that runs as root reported the six sections red on a change that touched none of them. CI runs as an ordinary user and still proves every case; a run that shows `SKIP` lines has proved less than a run that shows none, and says so.

## The challenge gate

**A closed marker typed by hand passes.** `scripts/challenge-gate.py` decides from the spec and the project's `disabledAgents` alone, never from git history, so a `## Challenges (spec-editor): closed in <sha>` line passes whether or not the close made it, and whether or not the commit it names exists. Left by the human's decision (`docs/decisions/challenge-notation.md`): the gate guards against skipping the challenges by accident, not against a deliberate override, and reading no history is what lets it pass in a shallow clone or a cloud session.

**The close commits on whatever branch the checkout holds.** `run` commits the spec alone, twice at most, in the checkout it is run from, which for the lead and `spec-to-card` is usually the main checkout's local default branch. It never pushes. Left because the spec lives where the human edits it and the close has to land before anything is filed or built from it; getting the commit onto the remote is the lead's ordinary landing work.

**No gate where `spec-editor` is disabled, and no sight of a permission rule.** A project that disables `spec-editor` through `/coder-fleet:agents` gets no editor and no gate, so its specs build with no gate. `spec-to-card` still refuses to file a criterion that carries a `[challenge Cn]` marker there, since nothing closed it. The gate reads `disabledAgents` only: an `Agent(coder-fleet:spec-editor)` deny rule, which an earlier `/init` wrote for a project that answered neither, stops the editor but not the gate, which then refuses every spec for want of a challenges section. `/kickoff` offers to remove that rule as a leftover; a project that keeps it disables the editor through `/coder-fleet:agents` as well. Left by the human's decision on 13 November 2026: the gate reads `disabledAgents` alone, and old editor settings are removed, not honoured.
