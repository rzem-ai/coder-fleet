# Divergence register

One row per artefact in `claude/coder-fleet/`. The register is what makes this a port rather than a rewrite: a reader goes from any fleet artefact to either its counterpart here or the reason for its absence, without reading a diff.

Four dispositions, and the last two are not the same thing.

- **Ported** - carried across with no change to meaning. Frontmatter keys may be renamed to suit OpenCode's schema.
- **Re-expressed** - the behaviour survives, the mechanism changed. The row says which mechanism replaced which.
- **Deferred** - in scope for the fleet, out of scope for v1, and intended. Something here is expected to grow back into it, and the row says what would have to be true first.
- **Dropped** - not coming back. Either the target cannot express it or it has no referent here. Nothing later depends on it.

The target is OpenCode 2.x, pinned to 2.0.32 by `opencode/test/run.sh live` and CI. Where 2.x differs from 1.x is in the spec under "OpenCode 2.x". File and line references to OpenCode source in the rows below are to the 1.18.30 tree; where one describes a mechanism 2.x replaced, a row under "OpenCode 2.x" below says so.

"Spec decision N" is decision N in `docs/specs/opencode-agents-port.md`. That file is the other half of the port's core documentation: what the port decided and what OpenCode turned out to do, where this one is what happened to each fleet artefact.

## Open

No skill collides with the vendored names across the four discovery roots, so `OPENCODE_DISABLE_CLAUDE_CODE_SKILLS` is not set. It would not be enough on its own anyway: it suppresses `~/.claude` only, and the two OpenCode-native roots survive every flag (`docs/specs/opencode-agents-port.md`, Skills). A personal skill installed later under a vendored name would win or lose by race, with a log line as the only sign.

Three consequences of OpenCode's schema that every ported body meets, recorded here once.

**An unknown frontmatter key is sent to the model.** `normalize` at `packages/core/src/v1/config/agent.ts:62-66` sweeps every key outside its known set into `options`, `migrateAgent` turns `options` into `request.body`, and that is merged into the provider request. So a leftover `effort: low` or `skills:` does not fail, warn, or get ignored - it is posted to LM Studio as a chat-completion parameter. Delete stray keys rather than leaving them.

**A bad value loses the whole agent silently.** The `color` row above is one instance of a general rule: decoding is all-or-nothing and failure yields `Option.none`, which `decode` returns as `undefined`, which is filtered out. The agent simply does not appear in `opencode agent`. Check `GET /agent` on a live server after editing any body.

**`mode: subagent` cannot be run directly.** `opencode run --agent scout` silently runs `build` instead, because `defaultInfo` rejects a subagent and there is no error path back to the flag. Every observation of a ported subagent has to go through a primary session calling `task`, which is how the fleet uses them anyway, but it makes ad-hoc testing of one agent more awkward than it looks.

## Where rule order is load-bearing, and the shape that is safe

`Permission.disabled` and `Permission.evaluate` both use `findLast` (`packages/opencode/src/permission/index.ts:29`, `:210`), and YAML key order survives into the ruleset - the V1 permission schema is parsed with `propertyOrder: "original"` for exactly this reason, and `Permission.fromConfig` walks `Object.entries` in that order. "Denies last" is half of it.

The rule is **broadest first, narrowest last**. A broad allow after a narrow deny reopens it; a broad deny after a narrow allow closes it. Writing `"git log *": allow` and then `"git *": deny` further down, which is what "denies last" literally asks for, denies `git log` - the wildcard matches it and comes later. The safe shape is a wildcard deny first and an explicit allowlist after it, which is also the shape that expresses the fleet's `tools:` allowlist.

Within a `bash:` block the same rule applies and has one extra consequence. If `"*": deny` were written last rather than first, the last rule matching `bash` would have `pattern === "*"` and `action === "deny"`, and `Permission.disabled` would strip the `bash` tool from the payload entirely instead of scoping it.

## Known holes in `scout`'s bash allowlist

`scout`'s ruleset denies by default and allows fourteen read verbs, and each command node in the shell AST is matched separately - `ls -la x || echo $?` is denied, because `echo` matches no allow and every pattern must evaluate to allow. But the pattern is the raw source text of the command node (`packages/opencode/src/tool/shell.ts:408`), redirections included, so `cat a > b` matches `cat *` and writes a file. `echo hello > f` is denied only because `echo` is not on the list, not because the redirection was noticed. Interpreter payloads - `bash -c`, `sh -c`, `env`, `xargs`, `eval` - are the residue spec decision 6 assigns to the plugin, and so is redirection out of an allowed read verb, which the plugin's redirection gate holds (below).

The allowlist is knowingly too tight to be comfortable, and that is a decision rather than an oversight. `rg foo | sort -u` is refused, `ls -la x || echo missing` is refused, and `sort`, `uniq`, `cut`, `awk`, `git status`, `git rev-parse` and `git grep` are all denied and all wanted. Widening rests on the plugin's central redirection gate, without which every allowed verb becomes a write primitive the moment `>` is appended, applied to every agent against one gate rather than in nine hand-written allowlists each wrong in its own way.

## Two rules in `scout`'s ruleset, and the general lesson in the first one

Both are in `.opencode/agent/scout.md`. The first guards against a trap every ruleset can fall into.

| Fleet artefact | Disposition | What happened | Mechanism or reason |
|---|---|---|---|
| `scout`'s read scope | Re-expressed | `read: { "*": allow, "*.env": deny, "*.env.*": deny, "*.env.example": allow }` rather than `read: allow` | OpenCode's own defaults at `agent.ts:128-133` ship `read: { "*": allow, "*.env": ask, "*.env.*": ask, "*.env.example": allow }`. A custom agent is built as `merge(defaults, user)` with the body's block appended last (`agent.ts:262-293`), so a bare `read: allow` would be the last rule matching every path, `.env` included, since `Wildcard.match("/x/.env", "*.env")` is true: `scout` could read credential files that stock OpenCode cannot. The body restates the guard as `deny` rather than the upstream `ask`, because an "ask" auto-rejects in a non-interactive run - for a subagent it is a deny with a worse failure mode |
| `find` in `scout`'s bash allowlist | Dropped | No `"find *": allow` in the ruleset and no `find` in the verb list in the body's invariants, with a line telling the agent to use `glob` | `find . -exec sh -c '...' \;` and `find . -delete` both match `find *`, because an `-exec` payload is an argument and is never parsed into a command node of its own. It is an arbitrary-execution primitive and it cannot be closed declaratively, since `find` has no read-only mode to glob for. Maintaining a flag denylist forever costs more than the capability is worth when `glob` already covers what `scout` needs, and `scout`'s own workflow step 2 sends it to `glob` first anyway |

**The general lesson, which is a property of the platform rather than of `scout`: the block you write is always the last block.** Every rule in an agent body is appended after `defaults` and after the project's `permission` block, so every rule in it is a potential reopen of something upstream that was closed on purpose. A ruleset that is internally correct - narrowest last, no self-contradiction, every deny reachable - can still be wrong, because correctness here is a property of the merged list and not of the file. Reading a body in isolation cannot tell you what it does. The check that catches this is mechanical: pull the merged ruleset from a live server, and for every permission the body names, evaluate the paths and patterns the upstream defaults treat specially and confirm the body did not flatten them. `test/invariants/rulesets.test.ts` does this for every ported body (The remaining agents, above).

`scout`'s `external_directory: { "*": ask }` is the same class and is left as it is, with a comment. It narrows rather than reopens - OpenCode's defaults allow the tmp, skill and reference directories outright and this rule downgrades all three to "ask" - so the failure is a refusal rather than a leak, and truncation still works because `agent.ts:295-310` appends a `Truncate.GLOB` allow after everything a body writes. It stops being harmless for an agent that needs a skill's own `references/` files, which is why `tech-writer` reopens humanize's.

### What the enforcement can and cannot see, stated once

The plugin exists for exactly what OpenCode's shell AST does not parse into, and it is two shapes.

An interpreter payload. `bash -c "git push --force"` is ONE command node whose inner string is never parsed, so every declarative rule matches `bash` and nothing matches `git push`. Same for `sh`, `zsh`, `dash`, `ksh` and `eval`.

A wrapper. `env git push --force` is one node whose arity prefix is `env`, because `permission/arity.ts` lists `env: 1`, so a `git push *` deny never matches it. `commandWords` walks off the leading assignments and the wrappers the way a shell does.

**Deliberately uncovered, and the same list the fleet's hook carries:** a payload built from a variable (`bash -c "$VAR"`), a heredoc, any expansion at all, and a nesting that would need unescaping to reach - `sh -c "bash -c \"git push --force\""` is allowed today, while `zsh -c "sh -c \"bash -c 'git push --force'\""` is denied, because the innermost payload there is single-quoted and survives as real quote characters for the next pass. Both are asserted in the test file, the gap included, so closing it is a visible change rather than a surprise.

**Bypasses held, each with a test that fails with the rule removed.** A redirect target is normalised before the `/dev/` allowance is applied, so `cat a > /dev/../<path>` is judged as a write to `<path>`; only `/dev/null`, `/dev/stdout`, `/dev/stderr`, `/dev/tty` and `/dev/fd/N` pass. `decide` scans every segment of a command and refuses a call of more than 256 outright rather than checking part of it. `argvWrite` denies `rg --pre`, `sort -o` and an awk print redirect, each of which writes or runs a program through a read verb on `READ_ONLY_SHELL`. Every denial assertion in `scope.test.ts` names the denial it expects, and `expectDenied` rejects an empty fragment ([`docs/decisions/denial-tests-name-the-denial.md`](../../docs/decisions/denial-tests-name-the-denial.md)).

**This is a role reminder, not a containment boundary.** The fleet said the same of its hook and had a sandbox underneath it. The port has no sandbox. That is the single largest thing this register has to say about enforcement, and `coder`'s body says so too.

| What | Consequence | Where it is recorded |

### The redirection gate and the allowlists

`scout`'s allowlist is tight because an allowed verb becomes a write primitive the moment `>` is appended. The central redirection gate covers every agent whose rule is an allowlist: `redirectTargets` runs over every segment and every recovered payload, so `cat a > b` is refused on the redirection rather than on the verb.

### One thing not settled

`.opencode/command/init.md` takes the name `init`, and OpenCode ships a built-in command of that name - "guided AGENTS.md setup", at `packages/opencode/src/command/index.ts:70-76`. Config commands are written into the same record after the built-ins (`:90-102`), so ours wins by overwrite, silently. The fleet's own names are plugin-namespaced - `/coder-fleet:init` and `/coder-fleet:kickoff` - and OpenCode namespaces by subdirectory, so `command/fleet/init.md` would give `fleet/init` and leave the built-in reachable. That is arguably the closer port. The port keeps the two plain names, because shadowing a built-in is a smaller surprise than renaming a command the lead asked for. `kickoff` has no collision either way.
