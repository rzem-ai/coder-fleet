# Divergence register

One row per artefact in `claude/coder-fleet/`. The register is what makes this a port rather than a rewrite: a reader goes from any fleet artefact to either its counterpart here or the reason for its absence, without reading a diff.

Four dispositions, and the last two are not the same thing.

- **Ported** - carried across with no change to meaning. Frontmatter keys may be renamed to suit OpenCode's schema.
- **Re-expressed** - the behaviour survives, the mechanism changed. The row says which mechanism replaced which.
- **Deferred** - in scope for the fleet, out of scope for v1, and intended. Something here is expected to grow back into it, and the row says what would have to be true first.
- **Dropped** - not coming back. Either the target cannot express it or it has no referent here. Nothing later depends on it.

Rows are added by the phase that makes the change. Phases 0 to 8 are in `docs/plans/opencode-agents-port.md`.

Three consequences of OpenCode's schema that Phase 5 will meet ten times each, recorded here once.

**An unknown frontmatter key is sent to the model.** `normalize` at `packages/core/src/v1/config/agent.ts:62-66` sweeps every key outside its known set into `options`, `migrateAgent` turns `options` into `request.body`, and that is merged into the provider request. So a leftover `effort: low` or `skills:` does not fail, warn, or get ignored - it is posted to LM Studio as a chat-completion parameter. Delete stray keys rather than leaving them.

**A bad value loses the whole agent silently.** The `color` row above is one instance of a general rule: decoding is all-or-nothing and failure yields `Option.none`, which `decode` returns as `undefined`, which is filtered out. The agent simply does not appear in `opencode agent`. Check `GET /agent` on a live server after editing any body.

**`mode: subagent` cannot be run directly.** `opencode run --agent scout` silently runs `build` instead, because `defaultInfo` rejects a subagent and there is no error path back to the flag. Every observation of a ported subagent has to go through a primary session calling `task`, which is how the fleet uses them anyway, but it makes ad-hoc testing of one agent more awkward than it looks.

## Where rule order is load-bearing, and the shape that is safe

`Permission.disabled` and `Permission.evaluate` both use `findLast` (`packages/opencode/src/permission/index.ts:29`, `:210`), and YAML key order survives into the ruleset - the V1 permission schema is parsed with `propertyOrder: "original"` for exactly this reason, and `Permission.fromConfig` walks `Object.entries` in that order. The brief for Phase 3 put it as "denies last". That is half of it, and the half that is missing bit once while writing `scout`.

The rule is **broadest first, narrowest last**. A broad allow after a narrow deny reopens it; a broad deny after a narrow allow closes it. Writing `rzem-memory_memory_kv_get: allow` and then `rzem-memory_memory_kv_*: deny` further down, which is what "denies last" literally asks for, denies `kv_get` - the wildcard matches it and comes later. The safe shape is a wildcard deny first and an explicit allowlist after it, which is also the shape that expresses the fleet's `tools:` allowlist.

Within a `bash:` block the same rule applies and has one extra consequence. If `"*": deny` were written last rather than first, the last rule matching `bash` would have `pattern === "*"` and `action === "deny"`, and `Permission.disabled` would strip the `bash` tool from the payload entirely instead of scoping it.

## Known holes in `scout`'s bash allowlist

Recorded now rather than discovered in Phase 4.

`scout`'s ruleset denies by default and allows fourteen read verbs, and each command node in the shell AST is matched separately - `ls -la x || echo $?` is denied, because `echo` matches no allow and every pattern must evaluate to allow. But the pattern is the raw source text of the command node (`packages/opencode/src/tool/shell.ts:408`), redirections included, so `cat a > b` matches `cat *` and writes a file. `echo hello > f` is denied only because `echo` is not on the list, not because the redirection was noticed. Interpreter payloads - `bash -c`, `sh -c`, `env`, `xargs`, `eval` - are the residue plan decision 6 already assigns to the plugin; redirection out of an allowed read verb belongs on the same list and was not on it.

The allowlist is knowingly too tight to be comfortable, and that is a decision rather than an oversight. `rg foo | sort -u` is refused, `ls -la x || echo missing` is refused, and `sort`, `uniq`, `cut`, `awk`, `git status`, `git rev-parse` and `git grep` are all denied and all wanted. Widening waits for Phase 4's central redirection gate, because until that exists every allowed verb becomes a write primitive the moment `>` is appended. The widening then belongs to Phase 5, applied to all ten agents against one gate, rather than nine hand-written allowlists each wrong in its own way.

## Two defects the review found in `scout`, and the general lesson in the first one

Both fixed in `.opencode/agent/scout.md`. Recorded here because Phase 5 writes nine more rulesets and the first defect is reachable from every one of them.

| Fleet artefact | Disposition | What happened | Mechanism or reason |
|---|---|---|---|
| `scout`'s read scope | Re-expressed, corrected | `read: allow` became `read: { "*": allow, "*.env": deny, "*.env.*": deny, "*.env.example": allow }` | OpenCode's own defaults at `agent.ts:128-133` ship `read: { "*": allow, "*.env": ask, "*.env.*": ask, "*.env.example": allow }`. A custom agent is built as `merge(defaults, user)` with the body's block appended last (`agent.ts:262-293`), so `read: allow` was the last rule matching every path, `.env` included, and `Wildcard.match("/x/.env", "*.env")` is true. `scout` could read credential files, and stock OpenCode could not. The replacement restores the guard as `deny` rather than the upstream `ask`, because an "ask" auto-rejects in a non-interactive run - for a subagent it is a deny with a worse failure mode |
| `find` in `scout`'s bash allowlist | Dropped | `"find *": allow` removed from the ruleset and `find` struck from the verb list in the body's invariants, with a line telling the agent to use `glob` | `find . -exec sh -c '...' \;` and `find . -delete` both match `find *`, because an `-exec` payload is an argument and is never parsed into a command node of its own. It is an arbitrary-execution primitive and it cannot be closed declaratively, since `find` has no read-only mode to glob for. Maintaining a flag denylist forever costs more than the capability is worth when `glob` already covers what `scout` needs, and `scout`'s own workflow step 2 sends it to `glob` first anyway |

**The general lesson, which is a property of the platform rather than of `scout`: the block you write is always the last block.** Every rule in an agent body is appended after `defaults` and after the project's `permission` block, so every rule in it is a potential reopen of something upstream that was closed on purpose. A ruleset that is internally correct - narrowest last, no self-contradiction, every deny reachable - can still be wrong, because correctness here is a property of the merged list and not of the file. Reading a body in isolation cannot tell you what it does. The check that catches this is mechanical and should be run on all nine remaining bodies: pull the merged ruleset from `GET /agent` on a live server, and for every permission the body names, evaluate the paths and patterns the upstream defaults treat specially and confirm the body did not flatten them.

`scout`'s `external_directory: { "*": ask }` is the same class and is left as it is, with a comment. It narrows rather than reopens - OpenCode's defaults allow the tmp, skill and reference directories outright and this rule downgrades all three to "ask" - so the failure is a refusal rather than a leak, and truncation still works because `agent.ts:295-310` appends a `Truncate.GLOB` allow after everything a body writes. It stops being harmless the first time a Phase 5 agent needs a skill's own `references/` files.

## The invariant register

Added by Phase 4. One row per invariant the fleet's bodies declare, with the mechanism that holds it here and the test that observes it. `test/invariants/scope.test.ts` exercises `decide` directly, one test per row; `test/invariants/live.test.ts` proves one denial end to end through a running OpenCode process against a mock endpoint. Run both with `bun test test/invariants`.

An invariant that cannot be enforced is **Unenforced** here rather than absent, because a body claiming a lock that is not there is worse than a body with no lock at all - that is the central argument of `docs/findings/claude-agents-2026-09-12.md`, and the point of writing this table is not to become another instance of it.

The declarative `permission` rulesets Phase 5 writes are a second lock over the top, not the only one.

### What the enforcement can and cannot see, stated once

The plugin exists for exactly what OpenCode's shell AST does not parse into, and it is two shapes.

An interpreter payload. `bash -c "git push --force"` is ONE command node whose inner string is never parsed, so every declarative rule matches `bash` and nothing matches `git push`. Same for `sh`, `zsh`, `dash`, `ksh` and `eval`.

A wrapper. `env git push --force` is one node whose arity prefix is `env`, because `permission/arity.ts` lists `env: 1`, so a `git push *` deny never matches it. `commandWords` walks off the leading assignments and the wrappers the way a shell does.

**Deliberately uncovered, and the same list the fleet's hook carries:** a payload built from a variable (`bash -c "$VAR"`), a heredoc, any expansion at all, and a nesting that would need unescaping to reach - `sh -c "bash -c \"git push --force\""` is allowed today, while `zsh -c "sh -c \"bash -c 'git push --force'\""` is denied, because the innermost payload there is single-quoted and survives as real quote characters for the next pass. Both are asserted in the test file, the gap included, so closing it is a visible change rather than a surprise.

**This is a role reminder, not a containment boundary.** The fleet said the same of its hook and had a sandbox underneath it. The port has no sandbox. That is the single largest thing this register has to say about enforcement, and it belongs in `coder`'s and `refuter`'s bodies in Phase 5 rather than only here.

### Three properties of OpenCode this phase had to find out the hard way

| What | Consequence | Where it is recorded |
|---|---|---|
| Every export of an auto-discovered plugin module must be a function | `getLegacyPlugins` (`packages/opencode/src/plugin/index.ts:99-111`) walks `Object.values(mod)` and throws on the first non-function, and the throw fails the WHOLE module. Exporting a rule table beside the plugin stopped the plugin loading at all - taking the preload transform down with the enforcement - logged once at ERROR and visible only under `--print-logs`. Hence `.opencode/lib/scope.ts`: discovery globs `{plugin,plugins}/*.{ts,js}` (`config/plugin.ts:21`), so a sibling directory is not scanned | The header of `.opencode/lib/scope.ts`, and an assertion in the live test that the phrase `failed to load plugin` does not appear |
| The agent is looked up on every call, with no cache | Phase 0 reproduced a cache keyed on `sessionID` returning `build` for a session that had become `spike-alt`. In this plugin that is one agent's rules applied to another agent's command, silently, with enforcement reporting success. The lookup is 0.65ms at p50, so there is no performance case for the optimisation that produces it | The comment on `agentFor` in `.opencode/plugin/fleet.ts` |
| The lookup fails open | If the session cannot be resolved the call is allowed, loudly, on `console.error`. The fleet's hook fails open too and states the cost; the cost is larger here because there is no sandwich of other locks underneath | The same comment |

### What this closes from the previous phase

Phase 3 recorded that `scout`'s allowlist was knowingly too tight because "until [a central redirection gate] exists every allowed verb becomes a write primitive the moment `>` is appended". That gate now exists for every agent whose rule is an allowlist: `redirectTargets` runs over every segment and every recovered payload, so `cat a > b` is refused on the redirection rather than on the verb. Widening the frontmatter allowlists against it is Phase 5's, as that row said.

### One thing Phase 6 did not settle

`.opencode/command/init.md` takes the name `init`, and OpenCode ships a built-in command of that name - "guided AGENTS.md setup", at `packages/opencode/src/command/index.ts:70-76`. Config commands are written into the same record after the built-ins (`:90-102`), so ours wins by overwrite, silently. The fleet's own names were plugin-namespaced - `/claude-agents:init` and `/claude-agents:kickoff` - and OpenCode namespaces by subdirectory, so `command/fleet/init.md` would give `fleet/init` and leave the built-in reachable. That is arguably the closer port. It was not done, because the phase brief named the two paths explicitly and shadowing a built-in is a smaller surprise than renaming a command the lead asked for. `kickoff` has no collision either way.
