# Port the claude-agents fleet to OpenCode

Status: draft, pre-interview. This is a strawman for the human to edit, not an interviewed spec. Every line marked *(supplied)* is the author's recommendation rather than something the human said, and every question the interview would have asked stands in Open questions rather than being quietly answered here.

## Problem

The fleet at `/Users/alex/Dev/Work/ai/claude-agents` is a working set of ten role agents, eight skills, two commands, four hooks and three workflows that together impose a particular discipline on agent work: a spec before a plan, a plan approved by a human before code, a fixed four-heading handoff out of every subagent, a Notion board whose columns only hooks may write, and a "blocked by human" queue that is the one thing the human watches. It runs only inside Claude Code.

Alex wants the same fleet available in OpenCode. The naive reading - copy ten markdown files into an `agent/` directory and change the frontmatter keys - produces something that boots and does not work, because two of the mechanisms the fleet's discipline rests on have no counterpart in the target:

The board integration is four shell hooks bound to `SubagentStart`, `SubagentStop` and `TaskCompleted`. OpenCode has no subagent lifecycle events. Without them there is nothing to move a card to Doing, nothing to parse a handoff and reject a malformed one, nothing to post a blocker into the human queue, and nothing to run the test gate before an item closes. The handoff format stops being a machine contract and becomes a request.

The three workflows are JavaScript that calls a `phase()` and `agent()` runtime that only Claude Code provides. OpenCode has no deterministic multi-agent orchestration at all - composition is one `task` tool call spawning one subagent, `subagent_depth` defaults to 1, and children are force-denied the `task` and `todowrite` tools unless their own ruleset re-grants them. The fleet's flagship pipelines have nowhere to land as written.

The third gap is the safety rail. `enforce-agent-scope.sh` is roughly 1200 lines of bash plus a Python helper, bound to `PreToolUse`, that parses bash command lines per agent and denies writes outside an agent's territory - it is what actually stops `spec-writer` writing source and `coder` touching `main`, since the frontmatter cannot express either. OpenCode has no OS-command hook shape at all: no `hooks.json`, no `hooks:` config key, no subprocess hook comparable to `PreToolUse`. The nearest host is a TypeScript plugin on `tool.execute.before`. So this is not a port of a script, it is a rewrite of the fleet's only real enforcement mechanism in a different language against a different interface, and the thing that has to survive is the set of invariants, not the file.

Two smaller mismatches compound it. `effort`, which the lead's entire escalation policy is expressed in, has no equivalent; the nearest thing is `variant`, a free-form provider-specific string, and `disallowedTools`, which every non-lead agent carries as a second lock on a stated invariant, has none either - restriction is per-tool `permission` rules instead, which is a better mechanism but a different one. And `skills:` preloading does not exist - OpenCode loads skills on demand through a `skill` tool, so `glossary` and `handoff` being in every agent's context at startup, which is what makes the handoff contract enforceable rather than optional, has to be achieved some other way. Per-agent skill *restriction* does have a native analogue, so the fleet's `skills:` list splits into two problems with different answers.

So the question this spec has to settle before anything is built is what "a complete port" means when the target lacks the mechanisms that make the original work, and which of the fleet's properties are the ones actually worth carrying across.

## The target runtime

Inference is local. Alex has confirmed that constraint applies to inference only - Notion and other hosted services may stay, so the board is not ruled out by this.

**Every frightening assumption in this port has now been tested, and each came back better than the argument predicted.** That is worth stating before the detail, because it changes how much defensive machinery the port has to justify. The model was assumed to be poor at sustained format discipline: twenty runs produced zero semantic failures, with every failure in whitespace or a trailing sign-off. Model swapping was assumed to cost enough to rule out per-role models: it costs thirteen seconds. Tool-calling was not assumed either way and is the one that would have been fatal: six of six, the correct tool selected every time with valid JSON in the `tool_calls` field, no plain-text tool calls, no refusals, no malformed arguments. The fleet's core loop is an agent picking a tool and reporting in a fixed format, and both halves are now measured rather than feared. The spec's remaining caution should be proportionate to what is still unmeasured, not to what was frightening before anyone checked.

*(The tool-calling result also implies the install postdates the Qwen3-Coder chat-template bug that broke tool-calling, patched upstream on 22 July 2026. Worth recording, because an older install would have failed this test for a reason that has nothing to do with the model's ability.)*

Serving is LM Studio on `trillian` at `http://10.0.0.3:1234/v1`, OpenAI-compatible, with one large model resident at a time. `qwen3-coder-next` is the model everything below was measured against, but it is not fixed: Alex has opened model choice beyond what is currently on the box, and a researcher is investigating other families. So the port targets the *shape* of this runtime - a local OpenAI-compatible endpoint, one large model resident, a context window in the tens of thousands rather than hundreds - and the specific model id is an open question. Nothing in the port should hard-code it.

Whatever the model, its id must be pinned explicitly in the OpenCode `provider` block. `trillian` is LM-Link federated to `marvin` and `eddie`, and `/v1/models` lists 39 ids across the federation, so a request naming a model that is not the loaded local one may silently execute on another machine. A configuration that relies on a default, an alias or a picked-from-the-list id is a configuration that will sometimes run somewhere else. *(Two stale facts in the homelab documentation set were found in one session, which is itself worth treating as a caution about relying on it. It states LM Studio on trillian is not serving, when it is. And an older project memory records the memory server's unit as `memory.service` at `/srv/sprites/mcp/memory`, when the live-verified reference is `agent-memory-mcp.service` at `/srv/agent-memory/current`. Take the newer one, and verify rather than cite when that set is the only source.)*

**The escalation policy becomes four levers, and the tier language goes.** Decided. The fleet's `opus` / `sonnet` / Fable tiering is deleted from the lead's body rather than translated, because there is nothing to translate it into and a body that still reads as though it can escalate by model is lying to whoever reads it next. What replaces it, in order of reach: another review round; a bigger or tighter brief; the lead doing the work itself rather than delegating; and, as the escape hatch for genuinely hard work, a deliberate manual model swap.

The swap is affordable but deliberate. Measured on trillian: unload 3.0s, cold load at 64768 9.2s, first request 0.4s, total outage 13.4s. *(Caveat: trillian had 114GB in page cache, so the model file was almost certainly warm; a genuinely cold first swap after a reboot is slower and unmeasured.)* Thirteen seconds makes a swap an ordinary operation rather than a catastrophe, which is why it can be a lever at all. But it is explicitly a deliberate act, not something the fleet does automatically on an agent's say-so, because the binding constraint is swap *frequency* rather than swap *cost*, and an automatic swap is exactly how frequency gets out of hand.

**The fleet is genuinely tiered across two or three models, and the mechanism is declare and batch.** Both decided. This is a larger commitment than "one model with `ui-designer` as an exception", which is what the runtime constraint first appeared to force, and it makes the scheduling machinery load-bearing rather than a nicety.

Agents declare the model they need in frontmatter. The lead orders work so that same-model jobs run together. A per-session swap ceiling is recorded, so thrashing surfaces as a number rather than as a slow afternoon nobody attributes to anything. No agent swaps the resident model on its own initiative, which matters more under a tiered design rather than less: the dangerous failure is a design task routed to `ui-designer` silently evicting the model another agent is mid-run against.

Tiers are expressed as role requirements rather than model ids, because selection is still open. There is a coding and tool-calling tier, which is most of the fleet. There is a vision tier, which is `ui-designer`. There may be a cheap tier for high-frequency shallow work, `scout` being the candidate. The ids drop into those slots once the trials land; nothing in the port names a model outside its configuration.

**This is the port's one genuine invention, and the divergence register has to say exactly that.** Everything else in this repo traces back to a counterpart in `claude-agents`. Declare-and-batch does not, because the fleet never had to schedule a shared resource: there, `model: opus` on a body routes the work and nothing waits on anything. Here an agent's model is a claim on a single resident slot, and honouring it costs an outage everyone else sits through. There is no fleet behaviour to trace this back to, and the register should record it as invented rather than ported, with the reason, so a later reader does not go looking for the original.

So the lead's escalation section becomes a batching policy. It names the lead as the one who orders work, since nothing else has the whole queue in view. It says what happens when two queued jobs want different models - they are grouped, not interleaved, and the lead finishes one group before starting the other. And it carries the swap ceiling, so a session that exceeds it is a signal that the ordering is wrong rather than that the hardware is slow.

**Co-residency is capped at roughly 3GB alongside the main model.** Measured: a 6.55GB 9B failed to load beside `qwen3-coder-next` with an llama-server SIGABRT; a 2.84GB 4B loaded fine, leaving 3.5GB spare (29058 of 32607 MiB). So a permanently resident small model for cheap roles is possible but tightly bounded, and one specific trap is recorded: `nvidia/nemotron-3-nano-4b` returned HTTP 200 with completely empty content, having spent its entire 120-token budget on reasoning. A reasoning model in a cheap tool-calling slot is worse than having no cheap tier at all, because it fails silently and successfully.

**The context window is a setting, and measuring it is an early task rather than an assumption.** 64768 was the loaded value when this was measured, against a model ceiling of 262144. Alex has confirmed that measuring the real per-agent requirement before fixing the window is in scope. So the spec does not treat 64k as a requirement; it treats the measurement as the input to choosing one. What holds regardless of the number: a window in this range makes the fleet's scout-first discipline structurally mandatory rather than merely good hygiene, and it prices the preloading answer, since anything put into every agent's system prompt is a fixed tax on every turn.

**Four concurrent requests.** LM Studio on trillian is configured PARALLEL 4. Fanning more than four agents out at once buys nothing; the fifth queues.

## The handoff contract: an external dependency

Handoff conformance on a local model is being solved in separate work, not here. This section records what is known, states what the port depends on, and stops. It deliberately proposes no mechanism - no normaliser, no retry loop, no structured output - because that design belongs to the other session and two designs would be worse than one.

An earlier draft of this spec called this the biggest risk in the port, reasoning that the contract loses both its supports at once - Opus's reliability, and the `SubagentStop` hook that exits 2 on a malformed handoff. The second half stands: there is no `SubagentStop` equivalent in OpenCode, so nothing validates a handoff unless something is built to. The first half has been measured and is wrong in an important way.

Twenty runs of `qwen3-coder-next` across five realistic agent tasks - scout, coder, reviewer, researcher, refuter - with the full contract in the system prompt at temperature 0.3, ten runs per condition:

- Strict parsing, contract exactly as written: 4/10 conforming.
- Trailing whitespace normalised before parsing: 6/10 on a fresh sample.

Those numbers look alarming and are not, because of what the failures were. Across all twenty runs there was **not one semantic failure**. No omitted section. No mis-typed `Blocker:` line. No typed line under the wrong heading. No invented fourth prefix. No missing `- None`. Every failure was cosmetic and of exactly two kinds: two trailing spaces after a heading, `## Done  ` instead of `## Done`, breaking the `^## Done$` anchor, which is a markdown hard-break habit; and a stray sign-off line after the final item, literally `Handoff.` or `handoff`, violating "nothing follows the last item of Decisions needed".

The model therefore has excellent content discipline and sloppy whitespace discipline, and the failures are all in the cheap-to-fix class. Part of what was measured here was the parser's strictness rather than the model's reliability, and that half has since been fixed upstream: `claude-agents` v0.11.1, commit `e132516`, right-trims every line before any anchor sees it, so two trailing spaces after a heading can no longer fail it. The measurement above predates that commit by hours. What remains a live concern for this port is the other failure mode in the same sample, a stray sign-off line after the final item, which is a genuine violation of "nothing follows the last item" and which the upstream validator already rejected before the fix.

What the port depends on is simply that this is handled - that by the time a ported agent's handoff reaches whatever consumes it, conformance has been dealt with by the mechanism that work lands. The port's own acceptance criteria reference conformance being handled and do not specify how. If that work changes the contract's wording or the parser's strictness, the port follows it rather than diverging.

One consequence stands regardless of which mechanism lands, and it is why this matters to the port at all: a handoff does not degrade gracefully. A missing heading or a dropped typed line is indistinguishable from an agent with nothing to report, so a format failure becomes a lost blocker silently, and nobody finds out. That is what makes the acceptable conformance rate a real question rather than a tuning detail, and it stays open here even though the mechanism does not.

## What the port is for

*(supplied)* The success condition is that Alex can open OpenCode on a project, describe an idea, and get the same sequence of events he gets in Claude Code: an interview, a spec on disk, a plan he approves, a coder that works one phase, a reviewer that reads the diff, and handoffs he can trust the shape of. Whether that is delivered by the same file inventory is not the point; whether the discipline survives is.

The stated principle in `CLAUDE.md` already constrains the answer: this repo ports, it does not invent, and every agent, skill or command traces back to its counterpart in the fleet with a note wherever it deliberately diverges. So the port is allowed to drop things and allowed to re-express things, but not allowed to drop them silently. One thing has now been admitted as invented rather than ported - declare-and-batch scheduling, which has no fleet counterpart because the fleet never shared a resource between agents. That is the exception the principle anticipates, handled the way it asks: recorded, reasoned, and not pretended to be a port.

What this looks like on local inference is worth saying plainly, because it is different from what the same sentence would have meant against Claude Code. The fleet stops being a set of agents that differ by how much you are willing to spend on them, and becomes a set of agents that differ by what they are allowed to touch, what they carry in context, and which of two or three models they need. The discipline the port is preserving - a spec before a plan, a human gate before code, a fixed handoff, work that gets scoped to one agent's territory - never depended on model tiering in the first place. It depended on the roles being distinct and the contracts between them being machine-checkable, and both of those survive the move intact.

## Non-goals

Improving the fleet. A behaviour that is wrong in `claude-agents` is ported wrong, and fixed upstream in a separate issue. This has been tested rather than assumed, and the test completed: the port found a genuine defect in the handoff parser, the decision was to normalise around it here and raise the fix separately, and the fix shipped upstream the same day as v0.11.1. The non-goal stands and the loop it prescribes demonstrably works.

Solving handoff conformance on a local model. Separate work owns that, and the port consumes whatever it lands. No normaliser design, no retry loop, no structured output proposal belongs in this issue.

Writing to `/Users/alex/Dev/Work/ai/claude-agents`. It is read-only reference material for this project.

Contributing anything upstream to OpenCode. If the port needs an event that does not exist, the answer within this issue is a workaround or a documented gap, not a pull request to `/Users/alex/Dev/Work/desktop/opencode`. *(supplied - see Open questions, Alex may want exactly the opposite.)*

Choosing the models. The port is built against role requirements - a coding and tool-calling tier, a vision tier, a possible cheap tier - and the ids drop in once the trials land. Naming a model in this issue would hard-code a choice that is still being researched.

Keeping the two fleets in sync automatically. There is no shared source of truth, no generator that emits both, no CI check that the ported bodies match the originals. Divergence after the port is handled by hand or by a later issue. *(supplied)*

Optimising the runtime. Quantisation policy, MoE against dense throughput, and whether a small model sits co-resident are all real questions with no published answers, and all of them are cheaper to settle by trial after the fleet runs than by argument before it does.

Sprites. The glossary already puts them out of scope and nothing here changes that.

Running the ported fleet anywhere but on Alex's own machines. No packaging for public distribution, no npm publish, no docs written for a stranger.

## Acceptance criteria

Criteria marked *(contingent)* have their exact form determined by an answer in Open questions, and are written here as the shape the criterion will take rather than its final wording.

**Runtime**

The fleet runs against a local OpenAI-compatible endpoint with the model id pinned explicitly, and every agent resolves to the intended model with no path by which a request reaches a federated peer. Demonstrated by a run plus the served model id in the response. The port carries no hard-coded model id outside its configuration, so changing model is a config edit rather than a sweep through ten agent bodies.

Each agent's fixed context overhead - system prompt, preloaded text, tool definitions - is measured and recorded before the context window is set, and the window is then chosen against those measurements with a stated working margin. The criterion is that the number is derived rather than inherited.

Every ported agent completes a representative task within the chosen window.

Whatever model the fleet settles on has the two measurements the core loop depends on taken against it before the port commits: tool selection with valid JSON arguments in the `tool_calls` field, and handoff format discipline. The `qwen3-coder-next` figures - 6/6 tool-calling, zero semantic handoff failures in twenty runs - are the reference point, and they do not transfer to another model by assumption. A model that fails the tool-calling check is disqualified whatever else it scores; the conformance threshold is not set here, being owned by the separate conformance work.

The divergence register carries a model dimension: for every agent, the tier it declares and why.

Declare-and-batch is recorded in the register as invented rather than ported, with the reason - the fleet never scheduled a shared resource - so a later reader does not go hunting for a counterpart that does not exist.

`ui-designer` runs on a vision model rather than shipping blind. Demonstrated by a `ui-designer` run that reads back an image of its own output, since having a vision model and being able to see your own work are not the same claim.

A session records its model swap count, and exceeding the ceiling is visible rather than silent. Demonstrated by a session that deliberately interleaves two tiers: the count is reported in the session's own output, and a run over the ceiling is legible as a number afterwards rather than as an unexplained slow afternoon.

No agent swaps the resident model on its own initiative. A swap is a deliberate act, and the port has no path by which routing a task silently evicts the model another agent is mid-run against.

The lead's body contains no `opus`, `sonnet` or Fable tier language, and its escalation section names the four levers that exist: another round, a tighter brief, the lead doing the work itself, and a deliberate manual swap.

The fleet's own pipelines run end to end on the chosen model: a spec produced, a plan produced, a phase coded, a diff reviewed. Not well, necessarily - the criterion is that the sequence completes without a stage failing for a reason attributable to the model rather than the work.

**Inventory and traceability**

Every one of the ten fleet agents has a counterpart in this repo, or a written entry in a divergence register saying it was dropped and why. The register is a single file, and a reader can go from any fleet artefact to either its port or its reason for absence without reading a diff.

The same holds for each of the eight shipped skills, the two commands, the four hooks and the three workflows: ported, re-expressed, or registered as dropped with a reason.

**Agent behaviour parity**

Each ported agent's frontmatter is valid against OpenCode's agent schema - it loads without error and `opencode agent` lists it with the description the fleet gave it.

Every fleet invariant that was enforced by `tools`, `disallowedTools` or the `enforce-agent-scope.sh` hook is either enforced by an OpenCode `permission` ruleset, enforced by a plugin hook on `tool.execute.before`, or listed in the divergence register as unenforced. The criterion is about the invariants, not the script: nothing here asks for a line-for-line translation of 1200 lines of bash, and an invariant that OpenCode's `permission` rules can express declaratively should be expressed that way rather than reimplemented in a hook.

The invariants are enumerated in the divergence register, one row each, with its enforcement mechanism and its test. At minimum and checkably: `fleet-steward` cannot merge, `reviewer`, `refuter`, `scout` and `researcher` cannot edit, `spec-writer` cannot write outside `docs/specs/`, and `coder` cannot force-push, rewrite published history or read a credential file. Each is demonstrated by a test that attempts the forbidden action and observes it denied. An invariant that the port cannot enforce is registered as unenforced rather than quietly dropped, since an unenforced invariant that still reads as enforced is worse than an absent one.

Each ported agent's skill access is scoped, using OpenCode's per-agent `permission.skill` rules, to the set its fleet counterpart preloaded, so an agent cannot reach a skill that was never meant for it.

Every MCP tool name in a ported body is checked against the identifiers OpenCode actually produces at runtime, not against an assumed pattern. Demonstrated by an agent that calls a memory tool successfully. This is the only check that catches either of the two silent-failure classes the findings record - a name that grants nothing, and a name collided with another server's tool - and an agent suffering either would look completely healthy.

The corpus write lock is expressed as `permission` rules on the full prefixed tool identifiers, denying the capture, forget and kv-write tools on the eight agents that must not write to the shared corpus and allowing them on `researcher` and the lead. Demonstrated by a read-only agent attempting a corpus write and observing it denied, and this row sits in the enumerated invariant register with the others.

No credential, and no reference to one, appears in any committed file. The memory server's `mcp` entry lives in the user's global OpenCode config rather than in the repository, and within that entry the token is a `{file:...}` reference to a mode 600 file rendered by the existing `scripts/install-home.sh` pattern rather than a literal. The port introduces no second mechanism for secrets. Demonstrated twice: a working session resolving the token from the rendered location, and a clean checkout with no token present failing loudly at startup rather than authenticating as nobody.

`coder` runs against an isolated working copy, or the divergence register records that it does not and says what the consequence is. *(contingent - depends on whether the experimental workspace adapter is in play.)*

**The handoff contract**

Whatever is needed to produce a conforming handoff is in context for every ported agent at the point it produces its final message, without the agent having chosen to load it. The demonstration is an agent run from a cold session that emits a correctly shaped handoff having never called the `skill` tool. Whether that means the whole of `handoff` and `glossary` or a compressed subset is an open question, since the context budget prices it.

Handoff conformance is handled by the separate work named above, and the port consumes it rather than reimplementing it. The criterion is that every ported agent's handoff passes through whatever that work lands, that a violation - a missing heading, a nested bullet, an untyped line under Decisions needed, a typed line under the wrong heading - is detected rather than silently accepted, and that no part of the port carries its own competing correction logic. How conformance is achieved is explicitly out of scope here. The existing `evals/fixtures/handoff-cases` are the test corpus, so the port's side of this is checkable against cases the fleet already wrote.

Conformance is measured on the model actually chosen rather than inherited from the `qwen3-coder-next` sample, and the recorded rate meets whatever threshold that work and Alex settle on. The figures to beat are 40% strict and 60% whitespace-normalised.

Semantic conformance is reported separately from cosmetic conformance wherever the port reports a rate at all, because the measured sample shows they fail independently and only one of them carries meaning. A suite reporting a single pass rate would have scored this model at 40% and hidden that its content discipline was perfect.

No stage of the pipeline treats an absent `Blocker:` line as evidence that nothing is blocked, unless the handoff it came from was verified as conforming. This is the criterion that stops a format failure from turning silently into a lost blocker.

**The pipeline**

Running the port's equivalent of `spec-to-plan` on a brain dump produces `docs/specs/<issue>.md` and stops for the human, then on a second run produces `docs/plans/<issue>.md` and stops for approval. The two human gates are observable stops, not statements in prose that the agent then continues past. This is the criterion most exposed to the model change, since a gate is only a gate if the agent actually stops at it, so it is demonstrated on the chosen model rather than reasoned about.

Running the port's equivalent of `review-round` on a diff produces a reviewer verdict with ranked findings, and the fix loop, if ported, verifies a commit against git rather than against what the coder claimed. *(contingent on the workflow answer.)*

`init` and `kickoff` exist as OpenCode commands and do what their fleet counterparts do to a fresh project. Behaviour they gain from the richer target - positional arguments, subdirectory namespacing, per-command model, inline shell in the template - is used only where the fleet command already wanted it and could not have it, and each such use is a registered divergence. Gaining capability is not a licence to redesign the commands.

**The board**

*(contingent, entirely - see Open questions. The criterion is one of: board columns move on session events that stand in for the five the fleet uses, with the register naming every transition whose semantics differ or cannot be reproduced, since OpenCode has no subagent lifecycle events to reproduce them exactly; or board state is reconciled by an explicitly invoked step and the gap between board and reality is bounded and documented; or the board is out of the port and the divergence register says so and names what the human now has to do by hand.)*

**Installation**

There is one documented command that installs the fleet into a project or a home directory, and running it twice is safe. *(contingent on the packaging answer.)*

After installation, a session started in a ported project uses the ported lead as its primary agent and can spawn every ported subagent.

**Evals**

Each ported agent has an eval suite that runs without Claude Code, scoring against the same rubric as its fleet counterpart, or the divergence register records that the rubric changed and why.

The suite runs and produces a baseline rather than matching one. The first run against the chosen model is the baselining run, and the suite is a regression gate from the second run onward. The divergence register records that the fleet's recorded Opus baselines do not carry across a model change and why, so a later reader does not treat the fleet's numbers as a target this port failed to hit.

The handoff format checks in `evals/lib/` are ported, since they test a contract that survives the platform change. *(supplied - this is the one part of the eval suite that is clearly portable as-is.)*

**Conventions**

Every file in the repo follows `CLAUDE.md`: Australian English, standard hyphens, no emojis, no hard-wrapped prose. Any deliberate divergence from the fleet carries a note saying why.

## Things found during drafting that the human should know

These are facts about the target, established by reading the OpenCode source, that change what is possible. They are recorded here because each one either closes an option or opens one, and a plan written without them would be wrong.

`experimental.chat.system.transform` exists in the plugin interface and is triggered when an agent's system prompt is assembled. This is a real route to preloading `glossary` and `handoff` into every agent, so the handoff contract can stay a contract rather than becoming a convention. It is marked experimental and undocumented, which is a risk to carry rather than a reason to discount it.

`experimental_workspace.register` exists, with a shipped example adapter, gated behind an environment flag that is off by default. This is the only route to `coder`'s worktree isolation, and taking it means the port depends on an experimental flag being on.

`opencode run --agent <name>` refuses to run an agent whose mode is `subagent` - it warns and falls back to the default agent. So an eval harness that drives one agent per invocation either needs every ported agent set to `mode: all`, which also exposes them all as primary agents in the picker, or it needs to drive the server API and spawn through the `task` tool instead. This is the single biggest constraint on what the eval port looks like, and it was not obvious.

`subagent_depth` defaults to 1 and `deriveSubagentSessionPermission` force-denies `task` and `todowrite` to children. The platform default is a strictly flat fleet: the lead spawns, subagents do not. Any fleet behaviour that assumed a subagent could delegate has to be re-expressed or dropped.

Skills are permission-gated per agent by name. `available()` filters the skill list through `Permission.evaluate("skill", skill.name, agent.permission)`, name or glob, the same mechanism as tool permissions. So the fleet's per-agent `skills:` list splits cleanly: the *restriction* half has a native and better analogue, and only the *preloading* half needs the system-prompt transform.

OpenCode reads skills from `~/.claude/skills/**/SKILL.md` and from project-local `.claude/skills` searched upward to the worktree root, with an opt-out, plus the same under `.agents/`, plus native `{skill,skills}/**/SKILL.md` across every configured directory, plus extra paths and remote URLs from `opencode.json`. Two consequences matter. Discovery is wide enough that the port can be shadowed by skills already on Alex's machine, and on a duplicate name the later discovery wins with only a logged warning. And frontmatter validation is loose - a skill whose `name` is not a string is silently skipped rather than erroring, which is the same class of silent no-op the fleet's own contract doc warns about for MCP server names.

Skill frontmatter is narrower than Claude Code's - only `name` and `description`. `disable-model-invocation: true`, which `handoff` carries, has no counterpart, so `handoff` cannot be hidden from the model's own discovery the way it is today. Denying it through `permission.skill` is the closest equivalent, and only works if `handoff` is preloaded by other means.

Commands are richer than the fleet's, not poorer. Subdirectory namespacing gives `command/git/commit.md` the name `git/commit`. Templates resolve `$ARGUMENTS` for the raw string, `$1` and `$2` positionals with quote-aware tokenising where the highest placeholder absorbs the remainder, and append the arguments when a template carries no placeholder at all. Inline backtick shell execution in a template is substituted before the prompt is sent. A per-command `model` beats the agent's model, which beats the caller's current model - which is a lever the fleet's static-frontmatter rule never had, and one that could carry part of what `effort` used to do.

The memory server comes across unchanged, verified live rather than reasoned from the config schema. rzem-memory is a standard HTTP MCP server that gates itself - nothing about it is claude.ai-specific. `agent-memory-mcp.service` on slarti binds 127.0.0.1:3002 and is public at `memory-mcp.rzem.ai` through the Cloudflare tunnel and nginx, with no oauth2-proxy in front because it validates its own credentials. Probed without credentials: `/health` returns 200, `/mcp` returns 401, and `/.well-known/oauth-protected-resource` returns 200 naming authorization server `https://id.rzem.ai/realms/rzem` with scopes `memory:read`, `memory:write` and `memory:admin`. Auth is static bearer tokens checked first, then Keycloak JWT, and the namespace comes from the credential rather than from an argument - there is no `agent_id` parameter on any tool. So an OpenCode remote entry works with zero server-side changes, and the recall step in six agent bodies survives.

The tool identifiers change, and getting them wrong fails silently. Server-side the tools are the bare nine: `memory_search`, `memory_capture`, `memory_forget`, `memory_read_document`, `memory_tree`, `memory_kv_get`, `memory_kv_set`, `memory_kv_delete`, `memory_kv_list`. The `mcp__claude_ai_Memory__` prefix the fleet's bodies use is purely claude.ai's connector-naming convention and does not exist here. OpenCode's own rule is now verified rather than assumed: `toolName = sanitize(clientName) + "_" + sanitize(name)`, where `sanitize` replaces every character outside `[a-zA-Z0-9_-]` with an underscore. Registering the server as `rzem-memory` therefore yields `rzem-memory_memory_search`, and the identifier follows whatever name the config uses. This is the same silent-failure class the fleet's own contract doc warns about - a `tools` line naming a server that does not exist grants nothing, raises no error and prints no warning - and six bodies name these tools explicitly. An agent that quietly lost its recall tools would look completely healthy.

The corpus write lock has a real mechanism, not just an assertion that one exists. Permission matching runs against the full prefixed identifier and supports globs, so the fleet's invariant is expressible as config rather than as an intention. `visibleTools` filters on `Object.keys(tools)`, which are the prefixed names, and `disabled` matches each against a ruleset via `Wildcard.match`, which supports `*` and `?`, anchors the whole string, and is case-sensitive everywhere but Windows. So "only `researcher` and the lead write to the shared corpus" becomes: deny `<server>_memory_capture`, `<server>_memory_forget` and `<server>_memory_kv_*` on the eight agents that must not write, and allow them on the two that must.

Two details of that mechanism matter when the rules are written. There are two evaluation points, not one: `disabled` hides a tool outright, and only when the matched rule has `pattern === "*"` and `action === "deny"`, while conditional per-argument rules are evaluated separately at call time through `Permission.evaluate`, keyed on the same tool-name string. And matching uses `findLast`, so the last matching rule in a ruleset wins rather than the first - a broad allow written after a narrow deny silently reopens what the deny closed.

There is no collision detection on tool names, and this one is the platform's problem rather than the port's. Tools are registered by plain object assignment: `result[McpCatalog.toolName(clientName, def.name)] = {...}`, with no dedup anywhere in the MCP catalogue or index. If two server-and-tool pairs sanitise to the same string, the later client silently overwrites the earlier one, with no error and no warning. A server `memory` with a tool `kv_get` and a server `memory_kv` with a tool `get` both produce `memory_kv_get`, and one simply wins. The config key itself is unconstrained - a plain string record, with no length cap, charset restriction or reserved words - so sanitisation does all the work. This argues for a distinctive server key rather than a short generic one, which the double-prefixing makes cheap: registering as `memory` yields `memory_memory_search`, while `rzem-memory` yields `rzem-memory_memory_search` and is far less likely to collide with anything added later.

A bearer token in config is a credential the repo must never hold. An OpenCode remote MCP entry carries `headers: {Authorization: "Bearer ..."}`, and this project's `CLAUDE.md` forbids editing any file holding a credential, so a committed `opencode.json` with a live token in it is exactly the wrong outcome.

OpenCode substitutes variables in config, and it does so on the config text before the JSONC parse, which means it applies everywhere including inside `headers`. There are two forms and they fail differently, which is what decides the choice. `{env:VAR}` resolves an unset variable to an empty string, silently - no error, no warning - so a missing variable sends `Authorization: Bearer ` with nothing after it, and the failure presents as a server-side auth problem rather than as a config problem. `{file:path}` reads the file's contents and, with the default `missing: "error"`, throws `bad file reference` on a missing or unreadable file. It expands a leading `~/`, resolves a relative path against the config directory, skips tokens on commented lines, and both trims the content and JSON-escapes it before insertion - so a trailing newline in a rendered token file does not end up in the header.

The recommendation has two layers, and they defend different things.

The primary control is that the `mcp` entry for the memory server does not live in the repository at all. OpenCode merges three files from the global config directory - `config.json`, `opencode.json` and `opencode.jsonc` under `Global.Path.config`, which is the XDG config directory and overridable by `OPENCODE_CONFIG_DIR` - into whatever the project supplies. So the whole server entry, headers included, can sit in `~/.config/opencode/opencode.json` at mode 600, and the committed project config need never mention the server. This is the stronger control because it removes the credential-bearing configuration from the repository rather than pointing at a secret from inside it: a tree that does not contain the configuration cannot leak it, whatever anyone does to the tree later.

The secondary control is that the token itself is a `{file:~/.config/claude-agents/memory-token}` reference rather than a literal, and `{file:}` rather than `{env:}`. This protects the global config, which is an ordinary file on disk that gets backed up, synced and copied around like any other. The form matters for the reason above: an unset environment variable silently becomes an empty string and the agent authenticates as nobody, presenting as a server-side auth failure that sends whoever debugs it to the wrong end of the problem, while a missing file throws at config load and names itself. It also maps onto the fleet's existing pattern, where `scripts/install-home.sh` renders secrets from 1Password into `~/.config/claude-agents/` at mode 600, so the port follows an established mechanism rather than inventing a second one, which is what `CLAUDE.md` asks for.

Together they mean a clean checkout carries neither a credential nor a reference to one, and the machine-local config carries a path rather than a secret.

The silent-empty behaviour of `{env:}` is worth knowing as a general trap rather than a credential one. It applies to every use of the form anywhere in the config, so anything substituting an unset variable gets an empty string and carries on as though it were configured.

Reaching LM Studio is a `provider` block in `opencode.json` pointing an OpenAI-compatible adapter, `@ai-sdk/openai-compatible`, at `http://10.0.0.3:1234/v1` with the model id declared explicitly. The shape is standard and the spec does not design it; what the spec requires is that the id is pinned rather than defaulted or picked from the list, for the federation reason above. *(Unverified: the adapter package name and whether OpenCode bundles it or expects it installed.)*

The 64k context is a load-time setting, not a ceiling. LM Studio reports `qwen3-coder-next` with `max_context_length` 262144 and `loaded_context_length` 64768. So the budget is a choice Alex has already made, presumably against VRAM on a 38.43 GB model, and it can be revisited at a cost. That matters because it turns "the fleet does not fit in 64k" from a dead end into a trade-off.

`reasoning_effort` is accepted by the endpoint and appears inert on this model. A probe sending `reasoning_effort: "high"` returned normally with an empty `reasoning_content` and `reasoning_tokens: 0`. That is one trivial prompt rather than proof, but combined with the absence of any reasoning capability in LM Studio's own model metadata it is enough to plan on: there is no reasoning tier to map `effort` onto, so effort tiers are dropped rather than translated. Note the metadata is weak evidence on its own - LM Studio's capability vocabulary in this build reports only `tool_use` across all 39 models, so it cannot distinguish "no reasoning" from "not described".

Two better-fitting model candidates exist and neither has been tested. Model research has landed, and its headline is that `qwen3-coder-next` is not the best fit for this hardware - it is simply the one that was already loaded. Both candidates below fit with no RAM offload at all, which means they would be faster than the current setup and would leave room for a co-resident second model.

`Devstral Small 2` (Mistral, 24B dense, Apache 2.0, 256K context) is the best-evidenced purpose-built agentic coder for this hardware. The vendor's 72.2% SWE-bench Verified figure belongs to the 123B sibling rather than to Small 2, and the Q4-Q5 size of roughly 14-17GB is extrapolated rather than vendor-stated - both worth holding loosely. `Seed-OSS-36B` (ByteDance, 36B dense, Apache 2.0, 131K context) is the only large model in the survey that fits 32GB VRAM alone at Q4; its hardware fit is clean but no independent tool-use benchmark was found, so its agentic standing is unverified.

Two families are ruled out on grounds that matter to this port specifically. DeepSeek has documented open issues of tool calls emitted as plain text instead of in the `tool_calls` field, rejection of `tool_choice: required`, and non-JSON output breaking OpenCode integration by name - which is a direct contradiction of the one capability the fleet cannot do without, regardless of how the model scores elsewhere. Llama 4 has weak agentic scores and reports of tool use degrading mid-execution. Separately, GLM-4.6, DeepSeek-V3.2, Kimi-K2 and MiniMax-M2 do not fit any box in this stack including the 128GB Mac; GLM-4.5-Air does fit with RAM offload.

Two things are commonly believed here and are not established. The claim that Q4 is fine for chat but degrades tool-calling and structured output has no published benchmark behind it as of September 2026 - no source compares tool-calling across quant levels for any model - so this spec writes no quantisation policy and makes it an open question answerable in-house. And the mechanism by which `qwen3-coder-next` tolerates RAM spill is MoE sparsity, only a fraction of experts activating per token, which llama.cpp's `--n-cpu-moe` flag confirms as a real mechanism and which is consistent with the swap measurement. But no published head-to-head throughput benchmark of MoE against dense exists on this class of hardware, so it is a design consideration rather than a benchmarked certainty. It matters because both candidates above are dense.

`ui-designer` swaps to a vision model. Decided: it does not ship blind. `qwen3-coder-next` is typed `llm` by LM Studio and has no vision, which for an agent whose job is screens and HTML prototypes means producing output it cannot look at. The resident candidates, all at 262144 max context, are `qwen3.8-27b` (20.7GB), `qwen/qwen3.5-35b-a3b` (22.0GB), `qwen3-vl-32b-instruct` (21.0GB) and `google/gemma-4-31b` (19.9GB). All four fit VRAM more comfortably than `qwen3-coder-next` does, so the vision run is if anything the lighter load. Which one to use waits on the model research now running.

This is the clearest illustration of why the swap measurement mattered. Before it, a vision-less model looked like an unresolvable exception that forced `ui-designer` to ship blind or not ship. After it, `ui-designer` loads a vlm, works, and the box swaps back - thirteen seconds, once per design session.

There is no OS-command hook shape anywhere: no `hooks.json`, no `hooks:` config key, no subprocess hook. The generic `event` hook is a firehose over the internal bus rather than a named per-lifecycle enum. `enforce-agent-scope.sh` and `check-write-scope.py` therefore have no host, and the same is true of the three board scripts.

The fleet's hooks were built against field schemas reverse-engineered from the Claude Code binary, per `claude-agents/hooks/README.md`. They are not a specification anyone owes compatibility to, which is an argument for re-deriving the board integration from what OpenCode actually emits rather than trying to port the hook logic shape-for-shape.

## Proposed work this spec does not resolve

Three items came out of the model research as things to do rather than things to decide. They are recorded here so they are not mistaken for open questions awaiting an answer from Alex - each is answerable by trial, and none blocks the spec.

Trial `Devstral Small 2` and `Seed-OSS-36B` directly on trillian, against the tool-calling and handoff measurements rather than against published benchmarks.

Run a small in-house eval across two or three quantisation levels, since no published source answers it and the fleet has the instrument already.

Resolve the light-tier question by direct trial - FunctionGemma, and `nemotron-3-nano-4b` retried with reasoning properly disabled - rather than by more research, since the BFCL leaderboard was not fetchable.

## Open questions

The recommendations here are the author's and exist to be argued with, not to stand in for an answer. Most of these questions are genuinely undecided, but three are not, and they are marked where they appear rather than removed: question 4's mechanism is settled and owned elsewhere, leaving only the threshold; question 5's policy is decided, leaving only the mechanics; and question 7 is answered outright and retained as a stub so the numbering holds.

**1. What does "complete" mean - behaviour or inventory?** Recommendation *(supplied)*: behaviour. The port is judged agent by agent against the fleet's stated invariants, and the file inventory is allowed to differ wherever the platform demands it, with every difference in the divergence register. The alternative - insisting every fleet file has a same-named counterpart - produces stub workflows and dead hooks that look like parity and are not. This answer sets the shape of every other one.

**2. What happens to the board?** Alex has confirmed the local-only constraint covers inference, not services, so Notion stays reachable and the board is not ruled out on those grounds - this question is live rather than settled by the runtime. Three positions, and the author has no confident recommendation. (a) Reimplement on OpenCode's generic `event` hook and `session.*` events, accepting that the semantics will not be identical and that some transitions may be missed. (b) Drop the event-driven model and reconcile: a command or a periodic script that reads session state and writes Notion, so the board is eventually right rather than continuously right. (c) Drop the board from the port entirely; the fleet's discipline survives in the agent bodies and the handoff, and Alex moves cards himself. The thing worth deciding first is not which mechanism but which property matters: is the board's value the automation, or the "blocked by human" queue being the one place he looks? If it is the queue, (b) may be enough and is far cheaper than (a).

**3. What happens to the three workflows?** Recommendation *(supplied)*: `spec-to-plan` and `review-round` become commands plus stronger agent bodies, because their value is the sequence of human gates and that sequence can be carried by a command's template. `deep-research` becomes a command that spawns `researcher` once. An external Bun script driving the OpenCode server API would preserve the determinism, but it would be a second runtime to maintain for two pipelines, and it is the kind of thing that gets written once and never run. Counter-argument worth weighing: `review-round.js` is 57KB of logic, and "collapse it into an agent body" may be a polite way of dropping it.

**4. What conformance rate is acceptable?** The mechanism is out of this spec's scope, but the threshold is still a real question and the port needs the answer to know when it is done. Framed concretely: if one handoff in twenty drops a `Blocker:` line, a blocker never reaches the human queue and nobody finds out. The answer may come from the separate conformance work rather than from Alex directly, but it has to come from somewhere, because "conformance is handled" is not a criterion anyone can check without a number.

**4a. Does the port depend on the contract's current wording?** If the conformance work changes the format - different anchors, a tolerant parser, different headings - the port follows rather than diverging, which is the stated position above. What needs confirming is that this is understood as a dependency in that direction: the port does not get a vote on the contract, and its agent bodies and eval fixtures will need updating if the contract moves. Worth knowing whether that work considers the wording settled or in play.

**5. Who performs a deliberate swap, and how does an agent ask for one?** The policy is decided - agents declare, the lead batches, a swap ceiling is recorded - but the mechanics underneath it are not. If `ui-designer` needs a vlm, does Alex load it before the session and the lead simply refuses to route design work when the wrong model is resident? Does the lead prompt him to swap and wait? Does a command do it, making the deliberate act "running the command" rather than "touching LM Studio"? Recommendation *(supplied)*: the port records each agent's required model declaratively, the lead checks what is resident before routing, and a mismatch is surfaced to Alex as a request rather than performed silently - which keeps the act deliberate while not making him remember which agent needs what. Worth confirming, because it decides whether the port needs to read LM Studio's state at all.

**5a. Is there a light tier at all?** Whether one is worth it depends on whether any fleet role is cheap enough to want one, `scout` being the candidate. The co-residency question that used to be attached to this one has dissolved: tiering happens by swap, so the roughly 3GB cap measured against `qwen3-coder-next` no longer decides anything, and a light tier would simply be a third batched group like the others.

A correction belongs here, because an earlier draft of this spec got it wrong. `nemotron-3-nano-4b` returning HTTP 200 with empty content is a documented bug with a documented fix, not evidence the model is unsuitable: reasoning is on by default via `LLM_ENABLE_THINKING`, and `LLM_REASONING_BUDGET=0` alone does not disable it. So the correct statement is not "avoid small reasoning models" but "reasoning must be explicitly disabled for a tool-calling slot", which is a configuration requirement rather than a model-selection constraint. The general lesson survives the correction and is worth keeping: a model that spends its budget reasoning fails silently and successfully, returning a 200 with nothing in it, which is the worst failure shape available.

Recommendation *(supplied)*: resolve it by direct trial rather than more research, since the BFCL leaderboard was not fetchable - try FunctionGemma, and retry `nemotron-3-nano-4b` with reasoning properly disabled. Defer the decision until the coding and vision tiers are proven.

**5b. Which model does the fleet default to?** Still open, but the shape has changed: the research found two candidates that fit better than the incumbent, and the incumbent is the only one with measurements behind it. So the real question is whether to trial `Devstral Small 2` and `Seed-OSS-36B` on trillian before the port commits, or to build against `qwen3-coder-next` - measured, adequate, and demonstrably not the best fit - and revisit later. Recommendation *(supplied)*: trial both before committing. The measurements that make this spec confident are all `qwen3-coder-next` measurements, and they do not transfer; a candidate that fits without RAM offload changes the runtime's economics enough to be worth a day. But note what the trial has to cover, because SWE-bench standing is not the question - the fleet needs tool-calling in the `tool_calls` field and format discipline in a final message, and Devstral's evidence is agentic-coding evidence while Seed-OSS has no independent tool-use benchmark at all.

**5c. Does any agent besides `ui-designer` warrant its own model?** Open. Note this now sits inside an accepted tiering design rather than arguing against one - the question is how many tiers, not whether. `refuter` and `reviewer` are the plausible candidates, on the grounds that adversarial reading is the work most sensitive to model quality. Recommendation *(supplied)*: the coding tier plus the vision tier, and no third until an agent demonstrably underperforms, because every additional tier is another group the lead has to batch around and another swap in someone's day.

**5d. What quantisation, and who decides?** The widely-repeated claim that Q4 is fine for chat but degrades tool-calling and structured output has no published evidence behind it. This spec therefore writes no quant policy. Since the industry has no answer, a short in-house eval across two or three quant levels would produce one - and the fleet already has the instrument, because the tool-calling probe and the handoff conformance sample are exactly the two measurements that would show the degradation if it exists. Recommendation *(supplied)*: run it, because the answer is cheap here and unavailable anywhere else.

**5e. What has to be resident, and is the answer measured or decided?** Preloading `glossary` and `handoff` into every agent is a fixed per-turn tax. Options: preload both in full; preload a compressed handoff-format card and leave the glossary on demand; preload nothing and rely on the `skill` tool, accepting the contract becomes advisory. Recommendation *(supplied)*: preload a compressed handoff card into every agent and leave `glossary` on demand for the agents whose bodies actually turn on its vocabulary, because the handoff is a machine contract and the glossary is a dictionary. This contradicts the fleet's "every agent preloads glossary" rule and is a registered divergence. But note that since measuring the context requirement is now an in-scope early task, this may resolve itself: if the full contract fits comfortably, the compression is unnecessary complexity. The conformance sample was run with the full contract in the system prompt and the content discipline was perfect, which is weak evidence for preloading it whole rather than compressing it.

**6. What happens to the twelve skills the fleet references but does not ship?** `using-memory`, `review-checklist`, `brainstorming`, `docwright`, `design-studio`, `cyber-identity-docs`, `tdd`, `electron`, `react`, `drizzle`, `fastify`, `tailwind`. Recommendation *(supplied)*: drop the ones that resolve nowhere today, since a name in a `permission.skill` allowlist that matches no skill grants nothing and warns about nothing. The exception is `using-memory`, which the lead's body depends on for corpus-write labelling - vendor it, or fold its rule into the lead's invariants. Worth confirming: is `using-memory` still the live source for that convention, and where does it actually live? Note that several of these - `brainstorming`, `tdd`, and the stack suite - may already exist on Alex's machine under `~/.claude/skills`, which OpenCode discovers natively, in which case the port inherits them for free and the question is only whether to depend on that.

**6a. Does the port rely on OpenCode discovering `~/.claude/skills`, or ship its own copies?** Relying on discovery means the fleet's skills and Alex's personal skills share one namespace where the later discovery silently wins a name collision, so a personal `handoff` would shadow the fleet's and the only sign would be a log line. Shipping copies under the port's own directory avoids that and creates a second source of truth for eight skills that already exist. Recommendation *(supplied)*: ship copies, and register the duplication, because a silently shadowed `handoff` breaks the contract the whole fleet rests on.

**7. Does the memory server come across?** Answered, not open - see the findings section, which records the live verification, the tool-renaming consequence and the credential requirement. Retained here only so the numbering stays stable. Nothing is outstanding on it. The corpus write lock that used to lean on `disallowedTools` is an acceptance criterion with a named mechanism, and the credential question - whether `headers` can read an environment variable - is answered in the findings: it can, and the port should not, because `{env:}` resolves an unset variable to an empty string silently while `{file:}` throws.

**8. Plugin package, `.opencode/` directory, or both?** Recommendation *(supplied)*: both, with the plugin as the unit of truth and an install script that materialises it into a project, mirroring `scripts/install-home.sh`. The plugin is also the only place the system-prompt transform and any board hooks can live, so it is not really optional. The open part is whether Alex wants it installable from a path, a git URL or a published package.

**9. What do the evals become?** Recommendation *(supplied)*: port the contract checks in `evals/lib/` first, since they test the handoff format rather than the platform, and drive the agent runs through `opencode run --format json` against agents set to `mode: all`. The cost of `mode: all` is that all ten appear in the primary agent picker, which is clutter and arguably a footgun. The alternative is driving the server API, which is more work and more faithful. The baselines question now has an answer: recorded Opus baselines are meaningless against any local model, so the first run against whichever model is chosen is a baselining run, and the suite becomes a regression gate only from the second run on. Two consequences worth confirming - the judge in `evals/lib/judge-prompt.md` also needs a model, and running it on the same local model means the fleet grades its own homework; and eval runs are bounded by PARALLEL 4, so a ten-agent suite is four at a time, which makes it a slow job rather than a quick check.

**10. Does `coder` get isolation?** Turning on `OPENCODE_EXPERIMENTAL_WORKSPACES` and writing a git-worktree adapter is the only route. Without it, parallel coders share a working tree and several of `coder`'s invariants stop being true. Recommendation *(supplied)*: take the experimental route, because the alternative changes what `coder` is. But it is a dependency on an unstable flag and Alex may prefer to run one coder at a time instead.

**11. Is the flat fleet acceptable?** `subagent_depth: 1` and the force-denied `task` tool mean the lead spawns and nobody else does. Recommendation *(supplied)*: accept it, since the fleet's own delegation policy already routes everything through the lead. But confirm: is there any fleet behaviour today that depends on a subagent spawning another, and if `review-round`'s fix loop is one of them, that changes question 3's answer.

**12. How much of the scope enforcement gets rewritten?** `enforce-agent-scope.sh` is 1200 lines of bash with a Python helper, and it has no host on OpenCode - it becomes TypeScript in a plugin on `tool.execute.before`, or it does not exist. Three positions. (a) Rewrite it faithfully, including the per-agent bash command-line parsing, which is the expensive option and the one most likely to be subtly wrong in a new language. (b) Express what `permission` rules can express declaratively - which is most of the path and tool scoping - and write a much smaller plugin hook for the residue, chiefly the bash command parsing that stops `coder` force-pushing. (c) Drop it, rely on `permission` alone, and register every invariant it enforced that now goes unenforced. Recommendation *(supplied)*: (b). It is the only one that treats the target's own mechanism as the first choice, and the fleet's own contract doc admits the bash script exists precisely because Claude Code's frontmatter could not express path or command scope - OpenCode's largely can. The open part is whether Alex accepts a smaller enforcement surface, because (b) will not catch everything 1200 lines of bash catches.

**13. Does the port use the commands' extra capability, or hold the line?** OpenCode commands have positional arguments, namespacing, inline shell and a per-command model override. `CLAUDE.md` says this repo ports and does not invent, which argues for holding the line. Recommendation *(supplied)*: hold the line by default, use the extra capability only where a fleet command visibly wanted it, register each use. The per-command model override is the one piece with a clear argument for use: agents already declare their model in frontmatter under the tiering decision, so a command declaring the model its work needs is participating in that design rather than reaching for a lever the fleet withheld. The open part is whether a command should be able to declare a tier the agent it invokes did not, and what happens when the two disagree.

**14. Does the fleet still want ten agents?** Worth asking deliberately rather than inheriting. The fleet's roster was shaped partly by per-token pricing - a cheap `scout` existed partly because it was cheap - and local inference removes that. What remains justifying a separate agent is context isolation, permission scope, and now the model it needs, since an agent's model is a scheduling input. Recommendation *(supplied)*: port all ten. Context isolation alone justifies them under a window in the tens of thousands, and revisit only if a specific agent turns out to have no distinct scope, no distinct model and no isolation benefit.

**15. Is contributing upstream to OpenCode in or out?** Listed as a non-goal above on the author's judgement. If Alex would rather land `SubagentStop` equivalents in OpenCode than work around their absence, that inverts the whole shape of this work and needs to be said now rather than after the workarounds are built.
