Spike for board item GPTA-1.1, plan `docs/plans/GPTA-1.1.md`, spec `docs/specs/GPTA-1.md` questions 8, 11, 16 and 21, run against codex-cli 0.156.1 on 25 September 2026. Harness: `scripts/spike/codex-hooks/`.

## Summary (questions 1, 2, 3 - file edits)

Go. All three fired, once the human trusted the three hooks in `gpta-1.1-r2/codex-home` via `/hooks` and round 3 ran plain `codex exec` (no bypass flag) against that trusted `CODEX_HOME`. SubagentStart fired with `agent_type` in the payload. SubagentStop fired, carried `last_assistant_message`, and a `decision: "block"` response measurably sent the subagent back - it acknowledged the block reason in its next message. Rounds 1 and 2's "unverified" stood on the hook-trust wall; round 3 shows trust alone was enough to unblock everything once granted, but does not isolate trust as the sole prior cause, since round 2 also changed the hook command paths and output shapes and never ran Codex in between - see "Why hooks never fired in rounds 1 and 2" below for what is and is not established.

Question 6 (worktree) and the re-confirmation of question 7 remain unverified this round, not because of hooks, but because the ChatGPT account backing this `CODEX_HOME`'s auth hit its usage cap partway through round 3 ("You've hit your usage limit... try again at Sep 29th, 2026 8:48 PM"). Questions 1, 2 and 5 were answered by a clean run before the cap; question 3's apply_patch and MCP evidence was captured by the same run that later hit the cap - that run ended on the usage-limit error with no final parent message, but the hook payloads and the subagent's own report were already written to the logs and the rollout before it did. See the question sections and "Why hooks never fired" below.

**Yes.** `run-subagent-lifecycle.sh` against `gpta-1.1-r2` (human-trusted hooks, plain `codex exec`, no bypass flag) produced this in `$SPIKE_LOG_DIR/SubagentStart.log`:


`agent_type` is `"spike-worker"`, the custom agent's `name` from its TOML. The payload also carries `session_id`, `turn_id`, `transcript_path`, `cwd`, `model` and `permission_mode` - none of that was guessed in earlier rounds.

## 2. Does SubagentStop fire, carry last_assistant_message, and does decision: "block" send the subagent back?

**Yes**, all three parts. `$SPIKE_LOG_DIR/SubagentStop.log` shows two calls for the same `agent_id` in the same run. First call, `stop_hook_active` false, `subagent-stop-block-once.sh` returned the block:

```json
{"...","stop_hook_active":false,"agent_id":"01a0d815-564e-7bc3-8e37-b3a89d0e11c7","agent_type":"spike-worker","last_assistant_message":"Success: wrote `hello-from-spike-worker` to `spike-output.txt`. SPIKE_MARKER_9f3a"}
```

Second call, `stop_hook_active` true - Codex re-invoked the subagent and re-ran SubagentStop after it acted on the block reason:

```json
{"...","stop_hook_active":true,"agent_id":"01a0d815-564e-7bc3-8e37-b3a89d0e11c7","agent_type":"spike-worker","last_assistant_message":"Success: `spike-output.txt` contains `hello-from-spike-worker`. Received the one-time SubagentStop block. SPIKE_MARKER_9f3a"}
```

The subagent's own words - "Received the one-time SubagentStop block" - are the plainest possible confirmation that `decision: "block"` sent it back to work with the reason, not just that a second hook call happened.

## 3. Does PreToolUse fire for a file edit (apply_patch), a shell command, and an MCP tool call, with what tool name and agent_type, and does decision: "block" stop each?

**Yes for all three tool kinds firing; yes, confirmed, for apply_patch actually being stopped.** Evidence from two runs against `gpta-1.1-r2` (`run-subagent-lifecycle.sh`, then a targeted follow-up prompt asking `spike-worker` to use `apply_patch` on `README.md` and then call a stub MCP tool), both logged into the same `$SPIKE_LOG_DIR/PreToolUse.log`:

- **Shell command**, from inside the subagent (`agent_type` present): `{"...","agent_id":"01a0d815-564e-...","agent_type":"spike-worker",...,"hook_event_name":"PreToolUse",...,"tool_name":"Bash","tool_input":{"command":"printf '%s' 'hello-from-spike-worker' > spike-output.txt"},...}`.
- **apply_patch**, from inside a second subagent instance: `{"...","agent_id":"01a0d816-9cfa-...","agent_type":"spike-worker",...,"tool_name":"apply_patch","tool_input":{"command":"*** Begin Patch\n*** Update File: README.md\n@@\n scratch repo for the GPTA-1.1 codex hooks spike\n+apply-patch-question-3\n*** End Patch"},...}`. `pretooluse-log.sh` returned the primary `hookSpecificOutput.permissionDecision: "deny"` shape on this call, and it worked: the parent's own run log shows `ERROR codex_core::tools::router: error=Command blocked by PreToolUse hook: spike: refusing this apply_patch call once...`, `README.md` in the scratch repo is unchanged (still just its original one line), and the subagent's own `SubagentStop` report quotes the refusal back verbatim: `"apply_patch was blocked; README.md was not changed. Exact result: ... Command blocked by PreToolUse hook: spike: refusing this apply_patch call once..."`.
- **MCP tool call**, from the same subagent instance, immediately after: `{"...","agent_id":"01a0d816-9cfa-...","agent_type":"spike-worker",...,"tool_name":"mcp__spike_stub__spike_echo","tool_input":{"text":"mcp-question-3-test"},...}`. Confirms the tool-name prefix Codex gives an MCP tool: `mcp__<server-name>__<tool-name>`, and that `agent_type` is carried on an MCP call the same as on a shell or apply_patch call. `pretooluse-log.sh` does not deny MCP calls (it only matches `apply_patch`), so this call was not tested for a deny - it did fail, but for an unrelated reason: Codex's own MCP client returned `{"content":[{"type":"text","text":"MCP tool call requires approval, but approval policy is never"}],"isError":true}` before the tool's own logic ever ran. That looks like a genuine Codex-side quirk worth a note for the eventual port - `approval_policy = "never"` did not exempt this particular MCP tool call from needing approval - but it is a fact about Codex's own approval handling, not about `PreToolUse`, and it is not one of this round's questions to chase further.

`tool_name` for the parent's own `spawn_agent` call (which precedes all of the above and is also logged) carries no `agent_type` at all, since it is the parent session's own call, not a subagent's: `{"...","hook_event_name":"PreToolUse",...,"tool_name":"collaborationspawn_agent","tool_input":{"task_name":"spike-worker","agent_type":"spike-worker",...}}` - note `agent_type` there is a field *inside* `tool_input` (the target agent being spawned), not the top-level `agent_type` the hook payload itself carries for a call made from within a subagent.

Ancillary finding, not one of the seven questions but relevant to the port: the first `spawn_agent` attempt with `task_name: "spike-worker"` (a hyphen) failed with `error=agent_name must use only lowercase letters, digits, and underscores`; the model retried with `task_name: "spike_worker"` (underscore) and it succeeded. `task_name` needs snake_case; the custom agent's own `name` field (`spike-worker`, with a hyphen, used as `agent_type`) was unaffected. Worth carrying into the port's own agent-naming convention.

## 5. Does SubagentStart accept additionalContext, and does that text reach the subagent?

**Yes.** `subagent-start-context.sh` returns `{"hookSpecificOutput":{"hookEventName":"SubagentStart","additionalContext":"SPIKE_MARKER_9f3a: ... Mention the literal token SPIKE_MARKER_9f3a somewhere in your final message."}}`. The direct evidence is in both subagent rollouts, not just their final messages: each subagent's own session JSONL carries a `"role":"developer"` input item whose text is exactly the `additionalContext` string, verbatim, including the marker - `grep`ing `.../sessions/2026/09/25/rollout-2026-09-25T20-21-12-01a0d815-564e-....jsonl` and the apply_patch/MCP run's subagent rollout both return `"role":"developer","content":[{"type":"input_text","text":"SPIKE_MARKER_9f3a: if you can see this sentence, additionalContext from SubagentStart reached you. ..."}]`. That is Codex injecting the hook's `additionalContext` into the subagent's own input as a developer-role message - the mechanism itself, not an inference from behaviour. Corroborating but secondary: all five calls logged in `$SPIKE_LOG_DIR/SubagentStop.log` this round carry the literal token `SPIKE_MARKER_9f3a` in `last_assistant_message`, across two separate subagent instances (not four - see the next paragraph for why there are five, not four, entries).

`SubagentStop.log` has five entries this round, not four, and the count matters for question 2 as much as question 5. The first two are the lifecycle run's subagent (`agent_id` ending `564e...`): `stop_hook_active` false, then true, as already described. The next two are the apply_patch/MCP run's subagent (`agent_id` ending `9cfa...`), same pattern: false then true, for the same `turn_id`. The fifth entry is a *third* call for that same `9cfa...` agent_id, but with a new `turn_id` - it follows a `collaborationfollowup_task` call visible in `PreToolUse.log`, and its `stop_hook_active` is false again. This is not the block re-firing: `subagent-stop-block-once.sh`'s marker file is keyed by `agent_id` alone, and that marker already existed from the agent's first stop, so the hook allowed this stop through without a decision. `stop_hook_active` is not a per-agent latch either - it reports whether *this specific turn* was itself a resumption forced by a SubagentStop block, and a turn started by the parent's own `followup_task` is not one, so it reads false again even though the block already fired once earlier in the same agent's life. The practical implication for the port: a "was this subagent already blocked once" state needs to be keyed on `agent_id`, matching what this harness's marker file already does, not on `stop_hook_active`, which resets per turn.

## Why hooks never fired in rounds 1 and 2, and what round 3 actually establishes

Rounds 1 and 2 could only infer the hook-trust wall from the docs plus the harness's own empty logs - no run in either round ever produced a Codex-emitted trust-refusal message of any kind, in any log or transcript. Round 3 confirms the trust wall is sufficient to explain the silence: once the human trusted the three hooks by hand via `/hooks` against `gpta-1.1-r2/codex-home`, plain `codex exec` produced full payloads on the very first run. What round 3 does not establish is that the trust wall was the *only* thing wrong in round 1: round 2 changed the hook `command` paths (from `$CODEX_HOME`-relative to absolute) and the SubagentStart/PreToolUse output shapes (from guessed flat forms to the docs-confirmed `hookSpecificOutput` forms) before any trust step ever happened, and round 2 itself never ran Codex against either version to isolate the two changes. So round 3 shows trust plus round 2's fixes together are sufficient; it does not show trust alone would have been.

`learn.chatgpt.com/docs/hooks` (fetched 25 September 2026): "Before a non-managed hook can run, Codex requires you to review and trust the exact hook definition... Codex records trust against the hook's current hash, so new or changed hooks are marked for review and skipped until trusted." Round 3 also found exactly where that trust is recorded, which the docs themselves never named: in `config.toml` itself, one `[hooks.state."<absolute-path-to-hooks.json>:<event_snake_case>:0:0"]` table per trusted hook, each holding `trusted_hash = "sha256:..."`. This is why the rules for this round forbade editing `hooks.json` or the scripts under `hooks/` - any change there is expected to produce a new hash that no longer matches the `trusted_hash` the human just recorded, reverting the hook to untrusted, though which of the two files' contents the hash actually covers is unverified - see the next section.

Consistent with the previous paragraph: round 3 shows the fixed scripts (absolute command paths, docs-confirmed output shapes) work once trust is granted - it does not show the two confounds round 2 fixed were never actually live, since whether the *original*, round-1 scripts (relative on `$CODEX_HOME`, guessed flat output shapes) would also have worked once trusted was never tested. Round 2 replaced them before any trust step happened, so that narrower question - were the confounds ever really a problem, or was the trust wall doing all the work even in round 1 - stays open. It no longer matters for the port either way: the shapes now in `scripts/spike/codex-hooks/` are docs-confirmed and working, whether or not the earlier ones would have been too.

## What trusted_hash actually covers

Unverified, checked without running Codex. The three `trusted_hash` values in `gpta-1.1-r2/codex-home/config.toml` are:

```
pre_tool_use:0:0    sha256:f3f2a7f087d40c54db634445f571bc50ed83f1ee935c0fc11a5bbc0237310ee7
subagent_start:0:0  sha256:95ca82f66e985e61b3654c34a08ec6b3c3a32a60403a8436bb69a77b77a8aff2
subagent_stop:0:0   sha256:066401dd7e224f35cb1b6035bf30db3722ec31f2af60d916ba33cda8dc4c85b4
```

The last two colon-separated fields in each key are `:0:0` in every one of these, and in every key this spike has ever seen, since this harness's `hooks.json` only ever defines one matcher group per event with one hook in it. Reading them as "matcher-group index, then hook-within-group index" is a plausible guess from the schema's shape, not something confirmed by seeing any other value - there is no evidence here about what a second group or a second hook would produce.

For each, computed `shasum -a 256` of the hook script's own file bytes and the raw `hooks.json` file bytes exactly as written on disk, and, for the corresponding handler entry in `hooks.json`, sha256 over roughly thirty plausible canonical forms across three scripts: the handler object alone and its enclosing matcher-group object, each as compact JSON (`separators=(",", ":")`), as sort-keyed compact JSON, and as Python's default `json.dumps` spacing; the bare `command` string; the whole `hooks.json` file, re-serialised compact and sort-keyed; just the event's own array within it; the script bytes concatenated with the command string; a handful of `<key>:<command>`-shaped strings echoing the `[hooks.state...]` table key format itself; and the handler object with plausible default fields filled in (`matcher`, `timeout`, `statusMessage`, `async`, `additionalContextLimit`) in several combinations. None of the roughly thirty candidates tried, across all three hooks, matched any of the three `trusted_hash` values. Full candidate list and code, re-runnable against any trusted `codex-home`: `scripts/spike/codex-hooks/trust-hash-investigation/` (`hash-test.py`, `hash-test2.py`, `hash-test3.py`, with a README naming exactly what each tries).

This is genuinely unverified, not a near-miss - reasonable guesses at "hash the script", "hash the JSON definition" in several forms, and "hash the JSON definition with defaults filled in" were all tried and none matched, so the mechanism computing `trusted_hash` is not one of the forms tried here. Families not tried at all, because trying them properly means reimplementing Codex's own Rust JSON serialisation rather than guessing at it in Python: the full cross product of every optional `hooks.json` field in every plausible default and field order (only a handful of combinations were tried, not all of them); hashing via a canonical-JSON crate that may order keys, escape strings or format numbers differently from Python's `json` module; and anything that is not JSON at all, which nothing in the docs suggests but which this investigation cannot rule out either. The test that would settle it does need Codex: put a byte-identical copy of a trusted hook script under a *different*, untrusted `hooks.json` entry (or vice versa - keep the script identical, reword an unrelated field in `hooks.json`) in a fresh `CODEX_HOME`, and see whether `/hooks` lists it as already trusted or as pending review. If trust follows the script's own bytes regardless of where `hooks.json` points at it, changing `hooks.json`'s formatting or unrelated hooks doesn't retrigger review for hooks whose scripts are unchanged; if trust follows some hash over the `hooks.json` definition instead, any edit to that file re-triggers review for every hook it defines, not just the one whose script changed. That test needs Codex and a fresh trust cycle, so it belongs in GPTA-1.2, not this spike.

## Hook output shapes, confirmed from the docs

Re-fetched `learn.chatgpt.com/docs/hooks` on this round, 25 September 2026, specifically for the schema and output shapes rather than a paraphrase of the whole page. Quoted results:

- **Schema.** "The full hooks.json schema organizes under a top-level `hooks` object containing event names (like `SessionStart`, `PreToolUse`) as keys, each mapping to an array of matcher groups. Each matcher group contains a `matcher` field and a `hooks` array of handlers." This harness's `hooks.json` omits `matcher` on each group, which the docs separately confirm is valid: "matcher" is optional for many events... "Use \"*\", \"\", or omit matcher entirely to match every occurrence" of supported lifecycle events.
- **Command execution.** "Commands run with the session cwd as their working directory," and the worked example includes a `command` value containing shell substitution syntax, `"$(git rev-parse --show-toplevel)"`. That is consistent with shell execution but the docs never say "runs through a shell" in so many words - see the first confound above.
- **SubagentStart additionalContext:** `{"hookSpecificOutput": {"hookEventName": "SubagentStart", "additionalContext": "..."}}`.
- **SubagentStop block:** `{"decision": "block", "reason": "..."}`, or exit code 2 with the reason on stderr. No `hookSpecificOutput` form is documented for this event.
- **PreToolUse block:** primary form `{"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "deny", "permissionDecisionReason": "..."}}`; "legacy form" `{"decision": "block", "reason": "..."}`; or exit code 2.

The config-reference page (`learn.chatgpt.com/docs/config-file/config-reference`, re-fetched this round) was asked the same question about shell-vs-argv execution and had nothing further to add - "The documentation does not provide explicit details about how hook 'command' strings are executed (shell vs argv)... suggesting the full schema is documented in a separate Hooks guide" - i.e. it points back at the hooks guide above rather than adding independent confirmation.

## What this means for the gate

Spec criterion 0 and question 21 require the plan to see SubagentStart, SubagentStop with `decision: "block"`, and PreToolUse on a file edit, actually fire, before GPTA-1 is planned. All three now have a Yes, with exact payloads, from round 3. The mechanism that made this take three rounds is itself the finding the plan needs to carry forward: hooks fire only after a one-time review, and that review's outcome is a plain table in `config.toml` - `[hooks.state."<absolute hooks.json path>:<event>:<field>:<field>"]` (the last two fields' meaning itself unverified - see above), holding `trusted_hash = "sha256:..."`. That table is a config-file mechanism, not a black box: an installer that could reproduce the hash could in principle write the table directly and skip the interactive step, the same way this harness pre-seeds `config.toml`'s `[projects...]` trust entries today. Whether an installer actually can do that depends entirely on what the hash is computed over, and that is unverified (see "What trusted_hash actually covers" above) - GPTA-1.2 needs to settle it before the plan can decide between an installer that writes trust directly and one that still asks the human to run `/hooks` once. That an installer writing `trusted_hash` directly is even possible in principle does not make it the obviously right choice: it means the installer's author, not each human reviewing `/hooks` on their own machine, decides that a given hook definition is safe to run - a security decision the port's plan should make deliberately, not adopt as a convenience because it happens to be technically available.

Relocating the port's `hooks.json` to a new path after installation, even with byte-identical content, is expected to break trust and need a fresh review, since the key includes the absolute path to the file - but this is an inference from the key's format, not something observed: no run in this spike ever moved a trusted `hooks.json` and watched trust actually break. The real `~/.codex/hooks.json` the eventual port installs will need its own trust step the first time a human runs it on each machine - trusting `gpta-1.1-r2`'s scratch hooks did nothing for that. GPTA-1's plan should treat that trust step (interactive, or written directly if GPTA-1.2 confirms the hash can be reproduced, and decides that is the right trade-off) as a named, one-time piece of the install procedure (per Open question 2/3's install script), not an implementation detail to discover later.

Two things questions 6 and 7 leave open, both closeable once quota resets rather than by more design work: whether user-level hooks also fire from inside a git worktree (question 6, trusted and ready to re-run), and a stricter re-confirmation of question 7's already-No verdict with a prompt that rules out the parent doing the write (question 7, also trusted and ready).
