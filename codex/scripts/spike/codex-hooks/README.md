# GPTA-1.1 codex-hooks spike harness

Re-runnable harness behind `codex/docs/findings/GPTA-1.1-codex-hooks.md`. Built and run against codex-cli 0.156.1 on 25 September 2026. Re-run it on a later Codex release to see whether the answers changed.

Everything here runs entirely in a scratch area outside this repository, and no script here ever deletes anything except named files and directories it can name in advance - see "How setup.sh and teardown.sh keep this safe" below for exactly what that means and does not mean. Nothing here writes to `~/.codex` directly - see the note on the auth symlink further down, which is a narrower claim than "never touches it".

Status as of round 3's evidence: questions 1, 2, 3, 4 and 5 are answered Yes/No with payloads; question 7 is No on round 1's evidence, not re-confirmed under round 3's stricter prompt; question 6 (worktree) was never reached at all. See the findings file for all seven, and its "What trusted_hash actually covers" section for an open question this README used to overclaim.

## What is in this directory

- `lib/guard.sh` - shared safety functions every other script here sources. `resolve_scratch_dir` turns a script's `<scratch-dir>` argument into a checked, physically-resolved (`pwd -P`, not the logical `pwd` a symlink could spoof) absolute path, refusing an empty argument, `/`, `$HOME`, a `codex-home` under the argument that resolves to the real `~/.codex` (checked by resolving `$SP/codex-home` itself with `pwd -P` too, so a `codex-home` that is a symlink to `~/.codex` is caught, not just a literal string match), and this harness's own repo toplevel. It does not decide whether a directory is safe to write into or safe to delete from - `setup_or_refuse_dir` and `require_scratch_shape` do that, and neither of them trusts `resolve_scratch_dir`'s identity checks alone to mean "safe".
- `codex-home/` - a template scratch `CODEX_HOME`: `config.toml`, `hooks.json`, and `hooks/*.sh`. It has no `auth.json` - you add that yourself (see below). `config.toml` has no project trust entries and `hooks.json` has no real hook command paths - both name absolute scratch paths that only exist on the machine you run this on, so `setup.sh` fills them in from the `SCRATCH_REPO_PATH` / `SCRATCH_WORKTREE_PATH` / `HOOKS_DIR_PATH` placeholders.
- `agents/` - the two custom agent TOMLs used by the spike (`spike-worker.toml`, ordinary; `spike-readonly.toml`, `sandbox_mode = "read-only"`).
- `mcp-stub/server.py` - a minimal stdio MCP server for question 3's MCP tool call case. Speaks newline-delimited JSON-RPC 2.0, exposes exactly one tool, `spike_echo`, which echoes its `text` argument back.
- `trust-hash-investigation/` - `hash-test.py`, `hash-test2.py`, `hash-test3.py`, the scripts behind the findings file's "What trusted_hash actually covers" section. One-off analysis, not part of the re-run harness proper, kept for anyone who wants to add more candidates rather than start from nothing.
- `setup.sh` - creates a throwaway git repo plus a worktree of it in a scratch directory you name, and a scratch `CODEX_HOME` at `<scratch-dir>/codex-home`. Refuses to run against a directory that is not empty and does not already carry the marker file this script itself writes - see below.
- `register-mcp-stub.sh` - registers `mcp-stub/server.py` against a scratch `CODEX_HOME` via `codex mcp add`. Safe to re-run.
- `teardown.sh` - removes everything `setup.sh` is known to create under one scratch directory, by name, one thing at a time - never the directory itself with `rm -rf`. See below.
- `run-subagent-lifecycle.sh` - spawns `spike-worker` and asks it to write a file, to test SubagentStart/SubagentStop firing and the block-once SubagentStop decision.
- `run-applypatch-mcp.sh` - spawns `spike-worker` and asks it to use `apply_patch` on `README.md`, then call the stub MCP tool, to test PreToolUse on both a file edit and an MCP tool call. Appends to the same logs `run-subagent-lifecycle.sh` writes, rather than clearing them, so a run of both in sequence leaves one combined trail covering shell, apply_patch and MCP tool calls. Does clear its own `state/blocked-apply_patch` marker on every run, so a re-run exercises the apply_patch deny again instead of silently skipping it because a previous run already tripped it.
- `run-readonly-sandbox.sh` - spawns `spike-readonly` and asks it to write a file, to test whether `sandbox_mode = "read-only"` on a custom agent refuses the write.
- `features-list.sh` - runs `codex features list` against the scratch `CODEX_HOME` to check the current name and default state of the hooks feature flag, independent of whether hooks actually fire.

Every `run-*.sh` script and `features-list.sh` calls `resolve_scratch_dir` and then `require_scratch_shape` before doing anything else - before any `rm`, before `codex mcp add`, before `codex features list | tee`. `register-mcp-stub.sh` does too, even though it is not a `run-*.sh` script, since it also writes into `config.toml`.

Note on provenance: `register-mcp-stub.sh` and `run-applypatch-mcp.sh` as committed are a guarded rewrite of the scratch-copy versions that actually produced round 3's question 3 evidence (the MCP stub, the hooks these scripts drive, and the prompt text are byte-identical; only the argument-handling around them has changed since). Their first run as committed, and the first run of anything under the current `setup.sh`/`teardown.sh`/`lib/guard.sh`, is unverified and belongs to GPTA-1.2, not any round of this spike - this round's own testing (see "How setup.sh and teardown.sh keep this safe") used throwaway scratch directories, never `gpta-1.1-r2`.

## How setup.sh and teardown.sh keep this safe

An earlier version of this harness let `setup.sh` be pointed at any directory - including `~`, a repo checkout, or an unrelated directory full of someone else's files - and, once that directory happened to contain a `scratch-repo/.git` and a `codex-home/hooks.json` (which `setup.sh` itself would create there), `teardown.sh` would then `rm -rf` the whole thing, taking everything else in it down too. Fixing that needed a structural change, not another identity check on the path, because the problem was never really about which path was named - it was that "this directory has the shape setup.sh builds" and "this directory is safe to recursively delete" were being treated as the same fact when they are not: `setup.sh` can build that shape inside a directory that had other things in it first.

The fix: `setup.sh` refuses to run against a directory that is not empty, unless that directory already carries a marker file, `.gpta-spike-scratch`, that `setup.sh` itself writes the first time it successfully sets up (or adopts) a directory. A directory this script has never touched can never get the marker, so `setup.sh` can never be pointed at `~`, a repo checkout, or any directory with pre-existing content and have it treated as an empty canvas. `teardown.sh` requires that same marker before doing anything (`require_scratch_shape`, the same check every `run-*.sh` script and `features-list.sh` also make), and never runs `rm -rf` on the scratch directory as a whole. It removes only the specific things `setup.sh` is known to create - the worktree (via `git worktree remove`, then a fallback `rm -rf` of the directory itself), `scratch-repo`, `codex-home` (including the `auth.json` symlink, reported separately, never the file it points at), `logs`, `state`, a legacy `mcp-stub/` some earlier scratch areas held, the run output logs, `features-list.txt`, and the marker itself - then, only if the directory is now empty, removes the directory itself with `rmdir`, which fails loudly rather than deleting anything if something unexpected is still in it. Anything `teardown.sh` does not recognise is reported, never guessed at and never deleted.

Tested against a throwaway directory under the scratchpad holding a canary file, never against `~`, a repo checkout or `gpta-1.1-r2`: `setup.sh` against the non-empty canary directory refused outright, and the canary file was confirmed untouched afterwards. `setup.sh` then `teardown.sh` against a second, empty throwaway directory removed everything `setup.sh` had created; with an extra unexpected file dropped into that directory before running `teardown.sh`, the known children were still all removed but the directory itself was correctly left in place (not `rmdir`-able while non-empty) and the unexpected file was reported rather than swept up. A `codex-home` symlinked to the real `~/.codex` was also confirmed refused by `resolve_scratch_dir` directly, independent of `setup.sh`/`teardown.sh`.

## How to run it

1. Pick a scratch directory outside this repo, for example your own session scratchpad, that is either empty or one this harness has already set up. Everything below assumes `$SCRATCH` points at it.
2. `bash setup.sh "$SCRATCH"`. Refuses if `$SCRATCH` is non-empty and has no `.gpta-spike-scratch` marker. Otherwise creates `$SCRATCH/scratch-repo` (with a worktree at `$SCRATCH/scratch-worktree`, for the worktree-hooks question) and `$SCRATCH/codex-home`, unless `$SCRATCH/codex-home` already exists, in which case it is left untouched.
3. Symlink your own Codex auth into the scratch home, read-only, by reference: `ln -s ~/.codex/auth.json "$SCRATCH/codex-home/auth.json"`. Never copy the file, never `cat` it, and never let its contents reach a log, this repo, or a commit. `setup.sh` deliberately does not do this step for you. Note that this is a symlink, not a one-way read: if Codex refreshes the ChatGPT auth token during a run, it writes back through the symlink to the real `~/.codex/auth.json`, the same file every other Codex session on the machine uses. That is expected and is why the file is symlinked rather than copied - but it means this step does touch `~/.codex`, just not by adding or changing any file this harness owns.
4. `bash register-mcp-stub.sh "$SCRATCH"` to wire up the MCP case ahead of time.
5. Trust the hooks once: run `codex` interactively (`CODEX_HOME="$SCRATCH/codex-home" codex`, from `$SCRATCH/scratch-repo`), use `/hooks`, and trust all three pending hooks (`SubagentStart`, `SubagentStop`, `PreToolUse`). This writes `[hooks.state...]` tables with `trusted_hash` values into `$SCRATCH/codex-home/config.toml` - see "Where hook trust actually lives" below, including what is and is not confirmed about what the hash covers. Do not edit `hooks.json` or anything under `hooks/` after this step; either is expected to invalidate the trust just granted, though that expectation itself is unverified - see the findings file.
6. `bash run-subagent-lifecycle.sh "$SCRATCH"`, then `bash run-applypatch-mcp.sh "$SCRATCH"`, then `bash run-readonly-sandbox.sh "$SCRATCH"`, then `bash features-list.sh "$SCRATCH"`. Each writes its own log under `$SCRATCH/logs` and prints where; the first two append to the same `SubagentStart.log` / `SubagentStop.log` / `PreToolUse.log`.
7. To check question 6 (worktree hooks) - never actually reached in this spike - repeat step 6's `run-subagent-lifecycle.sh` but `cd "$SCRATCH/scratch-worktree"` first instead of `scratch-repo`. The worktree is already marked trusted in `config.toml` by `setup.sh`, and the hooks trusted in step 5 are the same `hooks.json`, so no new trust step should be needed for the user-level half of this question. The project-level half of issue #27133 is a separate trust scope and needs its own trust step, not covered by this harness as committed.
8. Before treating any of it as evidence, grep the logs and your own terminal history for anything token-shaped (`sk-`, a long base64 blob, `Bearer `) and stop if you find one.
9. When you are done, `bash teardown.sh "$SCRATCH"`. Refuses unless `$SCRATCH` has the `.gpta-spike-scratch` marker. Removes the auth symlink and everything else `setup.sh` is known to have made, by name, then removes `$SCRATCH` itself only if that leaves it empty - see "How setup.sh and teardown.sh keep this safe" above. Do not run this against evidence you still want to keep - `codex/docs/findings/GPTA-1.1-codex-hooks.md` cites `gpta-1.1-r2` directly and that scratch area was deliberately left in place rather than torn down.

## Where hook trust actually lives, and what is still unverified about it

Confirmed by direct inspection of a trusted scratch `CODEX_HOME`'s `config.toml`, not just the docs: Codex records hook trust as a table per hook, directly in `config.toml`:

```toml
[hooks.state."/abs/path/to/codex-home/hooks.json:pre_tool_use:0:0"]
trusted_hash = "sha256:f3f2a7f087d40c54db634445f571bc50ed83f1ee935c0fc11a5bbc0237310ee7"
```

Confirmed: one table per event, keyed by the absolute path to the `hooks.json` that defines it, the event name in snake_case, and two more colon-separated fields. Unverified: what those last two fields actually index. This harness's `hooks.json` only ever defines one matcher group per event with one hook in it, so every key observed anywhere in this spike ends `:0:0` - there is no evidence from this spike about what a second matcher group or a second hook in a group would produce, so reading them as "matcher-group index, then hook-within-group index" is a plausible guess from the schema shape, not something confirmed by seeing a different value. Also unverified: what `trusted_hash` is actually a hash *of*. `codex/docs/findings/GPTA-1.1-codex-hooks.md`'s "What trusted_hash actually covers" section and `trust-hash-investigation/` tried roughly thirty plausible candidates - the hook script's own bytes, the raw `hooks.json` file bytes, the handler's JSON entry in several canonical forms and with several plausible default fields filled in - against the three real `trusted_hash` values in `gpta-1.1-r2/codex-home/config.toml`, and none matched. So the operating assumption this harness's rules run on - that editing `hooks.json` or a hook script un-trusts it - is a reasonable inference from the docs' own wording ("records trust against the hook's current hash") and from the key format including the `hooks.json` path, not something this spike confirmed by computation or by observing a value change. The test that would confirm it needs Codex and a fresh trust cycle and is GPTA-1.2's, not this round's.

## The hook-trust wall, and what got past it

On codex-cli 0.156.1, a non-managed hook (anything in a user or project `hooks.json`, which is everything this harness defines) requires interactive review and trust before it runs. `codex exec` is non-interactive and has no prompt for this, so a hook defined in `codex-home/hooks.json` is silently skipped - no error, no log line, exit 0 - until it has been trusted once, either through the `/hooks` command in the interactive TUI or via `codex exec --dangerously-bypass-hook-trust`.

Rounds 1 and 2 of this spike could not clear that wall automatically - the `--dangerously-bypass-hook-trust` flag exists (confirmed in `codex exec --help`), but the agent session building the harness had it refused by its own host tooling as a named "Safety Bypass Flag", before it ever reached Codex. That refusal was a property of that harness-building session's environment, not a Codex limitation. Round 3 cleared the wall the other documented way: a human ran `/hooks` interactively against the scratch `CODEX_HOME` and trusted all three hooks by hand, and plain `codex exec` (no bypass flag) produced full hook payloads immediately afterwards, on the first run. That confirms trust plus round 2's fixes (absolute command paths, docs-confirmed output shapes) together are enough - it does not by itself confirm trust alone would have been, since round 2 never ran Codex against the original, round-1 hook definitions to isolate the two changes. See `codex/docs/findings/GPTA-1.1-codex-hooks.md` for the payloads and the fuller reasoning.
