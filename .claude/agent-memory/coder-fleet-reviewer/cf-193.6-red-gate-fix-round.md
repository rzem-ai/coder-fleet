Settled on CF-193.6 (human's decision on the card, 2026-11-12): under fix: true a gate line with a non-zero exit is a blocking finding and starts a fix round, superseding CF-193.4's "red gate stops clean with a Not an approval prefix" (see [[cf-193.4-gate-run-settled]]). The pin lane now reads the main checkout's AGENTS.md gates block (`declaredGates`), every declared gate no line reports goes under gatesMissing, and a gate finding carries only the declared command, never the reviewer's line text. A red line matching no declared gate stops as `failing gate not declared` - a deliberate injection guard, not a defect.

**Why:** the human chose the fix-round outcome; the undeclared-red stop is the coder's guard against a diff steering the reviewer's text into a coder's command.

**How to apply:** don't relitigate either. Do check line-to-declared matching against real reviewer lines: board cards show reviewers writing `gate: bash x.sh (rerun) - exit 0` and the reviewer brief says rerun a failing test with a file or name appended, so exact-match matching sends a genuine failure's rerun line to the undeclared stop (round 1 at be8edc3, raised as must fix). Round 2 (a62fff6) settled the matcher: strip one leading `cd <dir> &&`, then exact or prefix-plus-space, longest declared command wins, one finding per declared gate; an undeclared red line beside a declared red one rides under gatesUnactionable while the declared fix goes ahead. Don't relitigate that. CF-193.7 (d8d708c) closed the follow-up: gatesOf now uses `gateReported` (exact command or name after the cd strip, one trailing ` (note)` allowed), while red classing keeps the prefix matcher. Don't relitigate the split. `prevFix.testResults.verifiedBy` never reaches a coder brief (`commissionFixes` serialises only blocking, low and follow-up findings); it surfaces only in the result's `unverified`. It still sets `verified = true` from any green lines, narrowed or undeclared, which gatesMissing now backstops.
