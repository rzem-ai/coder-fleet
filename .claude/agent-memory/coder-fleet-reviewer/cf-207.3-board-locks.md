CF-207.3 adds `boards/src/lock.ts` (withLock: wx lock file with pid/time/actor JSON, 5 s wait, 30 s or dead-pid stale, a `.break` guard file so two breakers never remove a fresh lock; writeAtomic: tmp in same dir then rename, or link for exclusive create). cards.ts wraps allocateId in `locks/ids.lock`, updateCard/writeCard/deleteCard in `locks/<ID>.lock`; updateCard writes the card then appends the event (criterion 16). Re-key criterion #7 was dropped when the human cut the re-key (2026-11-14).

Round 1 (9cf8d09a, 2026-11-14): approved with follow-ups. Suite green, boards section 49 tests across 8 files (the re-key tests were cut after CF-207.2 round 3, so the count looks unchanged though concurrency.test.ts adds 6). Lows raised: the stale branch in withLock `continue`s without sleep or deadline check (busy-spin up to 30 s behind a dead breaker's guard); `writeCard(board, file)` takes a snapshot read outside the lock, so read-then-writeCard callers lose updates despite criterion 2.

**Why:** later groups (moves, MCP, web) will call these; the writeCard snapshot shape is the trap to watch for in their reviews.

**How to apply:** in a later CF-207 group review, check that new card writers go through updateCard's change callback, not readCard + writeCard. See [[cf-207.2-new-board-storage]].
