CF-207.10 (group J, spec criteria 67 and 68) added one list each in the new board's package `claude/coder-fleet/boards/`: `COMMANDS` (cli.ts, guard before the switch, which has no default), `WEB_OPERATIONS` (web.ts), `CARD_FIELDS` (cards.ts, `checkFields` in createCard and updateCard). The lead settled that the spec's "replace the old board" wording is the human's framing and isn't a migration path.

Round 1 (2026-11-14) findings worth rechecking later: createCard passes `spec.fields` as the kept set, so it can never refuse a field (only tests pass `fields`, so no user path yet); the MCP check is `skipIf(!existsSync(src/mcp.ts))`, so group G has to export `MCP_TOOLS` from that exact path or the check stays skipped without saying so; the unknown-CLI-command and unknown-web-op guards aren't pinned by any test, and without the CLI guard an unknown word exits 0.

**Why:** group G (MCP, binary) is where these gaps would bite.

**How to apply:** when reviewing group G, check that src/mcp.ts exports MCP_TOOLS and that the MCP tools don't pass caller-supplied fields to createCard.
